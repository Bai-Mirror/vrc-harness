# 工程与素材统一导入

GUI/TUI 的统一入口接受文件夹、`.zip`、`.7z`、`.rar`、`.tar`、`.gz` 和 `.unitypackage`。确定性层只处理路径穿越、符号链接、特殊文件、体积上限与安全解包；目录不符合预设、没有 Unity 根或存在多个根时，不据此否定用户的“这是工程”声明，而是把原结构放入隔离恢复工作区交给 AI。

AI 分析必须输出 `classification`（`project`、`asset_bundle`、`mixed` 或 `unknown`）、置信度、工程根、Avatar 根、依赖缺口、素材候选、风险和两种接手方案。素材/混合输入可复用现有素材库登记和项目关联；低置信度结果不自动搬运文件。分析报告只能写 `_Harness/Recovery/`，通过独立 JSON/文件检查后，才允许建立改造任务。

分析还要写 `_Harness/Recovery/facts.json`（`harness-takeover-facts/1`）：把能落到文件上的发现写成结构化候选，每条带依据所在的工程内相对路径与说明；缺少的依赖写成 `dependency:<名称>` 的 `present=false`；无法从文件证明的历史进度、批准和验证不能写成候选，只能写进 `questions`。Task 的固定内部检查在通过前核对三份输出、工程内真实定位与前序依赖；失败依据进入下一次受管运行，新建分析任务最多自动修复一次，暂停或取消不会追加运行。耗尽后恢复记录置为 `failed`，保留具体原因，不写入候选事实。通过后入库仍执行同一检查，候选仅作为**待确认推断**记录，恢复记录置为 `ready`。`ready` 只表示分析输出结构齐全，不表示工程可交付，也不表示历史已恢复；GUI 的应用改造和采用素材按钮仅在该状态启用，Runtime 同样核对状态。格式与校验规则见 `project-archive.md` 第 5.2 节。

导入、临时任务和正式制作通过实际目录复用同一工程身份；历史相对路径和绝对路径都按所属工作区解析，执行器、观察器与确认产物读取绝对位置，保留原项目记录和历史。若已有多个登记身份指向同一目录，操作会拒绝并要求修复登记歧义，不自动合并历史或重绑事实。此修复防止继续新增重复身份，不会自动修补旧版本已经分裂的记录。

- 浅接手保留原工程的菜单、参数、组件与目录做法，仅在 `_Harness/Recovery/` 和 `Assets/_Harness/Patches/` 做最小变更。
- 深度改造在导入时先生成隔离副本，之后才允许全工程重构，并要求保留来源、映射和回退记录。
- 可选蒸馏只产生本地候选，不直接采用。项目的「记忆与 SOP · 本地修复」（TUI 项目对话按 `l`）可生成、验证、明确采用及回到正式版本；采用绑定基线、内容和独立评测，仅用于后继新制作，不热换 Run，也不等于修复已有工程。结构检查仅支持本项目验证使用，设置本机默认还需相关隔离对照；基线变化先重新验证。无需上传即可本地采用，官方跨用户发行仍须权利复核、独立验证与签名。

VPM 管理调用官方 CLI。操作前备份 `Packages/manifest.json` 与 `Packages/vpm-manifest.json`，失败则恢复。上传交接只在工程中放入一次性 Editor 启动器并启动配置的 Unity，由脚本打开官方 VRChat SDK Panel；Harness 不存储 VRChat 登录态、不切换账号，也不点击上传。
