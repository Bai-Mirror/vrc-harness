# 捏脸：数值存在哪里，决定它会被谁覆盖

## 捏脸值的四种存放方式与各自会被谁覆盖

- **适用范围**：只调形态键、不自由编辑顶点的捏脸（历史工程与客户工程都是这种做法）；Unity 2022.3、VRChat SDK 3、面捕框架（Triturbo、Fermata）。
- **结论**：同样是「把某个脸部键调到某个值」，存放位置不同，后果完全不同：
  1. **渲染器上的默认权重**（`m_BlendShapeWeights`）：多个历史工程的捏脸都是这种，未烤入顶点。任何动画一写同一个键（表情、口型、面捕），这个值就被盖掉；例如某素体有 45 个表情动画在写 `eye_pupil_OFF`，场景里设的静态值会被表情层覆盖。
  2. **FX 里常驻播放的片段**写死捏脸值：一个 Kipfel 工程在 FX 第 0 层（Write Defaults 开）和一个优先级最高的 MA Merge Animator 里常驻播放默认表情片段，捏脸值压过面捕与手势层——闭眼时面捕的清零键与捏脸键叠加，眼部破面。
  3. **Shape Changer 写脸部键**：一个历史工程这样做；挂载物体停用时自动回退。
  4. **烘焙进 FBX**：一个 Kaguya 工程与一个 Milfy 工程把捏脸烘进了素体 FBX（Milfy 工程把覆盖前的原版另存为还原点；Kaguya 工程里在用的 FBX 与捏脸目录下的烘焙文件逐字节相同）。烘焙后文件哈希改变；面捕插件的生成网格若按 FBX 哈希认版本，就可能认不出（该 Kaguya 工程的 FBX 哈希不在面捕插件的版本表里，是否由烘焙导致未证实）。
- **判据**：接手工程先查清捏脸值在哪一层、谁还在写同一批键（动画、面捕清零片段、手势、口型）；在 Play（形态键钳制开）下渲睁眼、半闭、全闭与常用表情，确认捏脸在这些状态下保持且不破面；超出 0–100 的值在客户端会被钳掉。面捕根的脸部网格是插件生成的，键名与索引要直接读生成网格资产，Blender 键序与 Unity 槽位的对应关系只在渲染器直接用 FBX 网格时成立。
- **修法**：需要随眨眼保持的捏脸值，放进由眼睑参数驱动的混合树，只在接近全闭、开始破面的那一段淡出；需要永久生效的键（如关瞳孔）批量改写所有写它的动画，并列出会连带失效的表情。
- **证据等级**：多工程验证——历史工程（默认权重、Shape Changer）、一个 Kipfel 工程（常驻片段）、一个 Kaguya 与一个 Milfy 工程（烘焙 FBX）各自核实。
- **失效条件**：自由编辑顶点的捏脸（直接改网格）不在本条范围内。
