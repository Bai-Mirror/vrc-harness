# 环境与工具链：质量记忆

Unity、Blender、编辑器桥与命令行环境里验证过的事实与坑。多数只在一台 Linux 主机上验证过，已逐节标明标定环境。每节独立成立，按「适用范围、结论、判据、证据等级、失效条件」写。

## 编辑器渲图可信度：图形 API、GPU 与首次读数

- **适用范围**：在 Linux 上的 Unity 2022.3.22f1 编辑器里渲图（验收渲图、送视觉评审的图），材质为 lilToon 及其衍生着色器。
- **结论**：编辑器渲图的材质观感受图形 API 与 GPU 环境影响，与上传包无关（上传包按 Windows 目标构建）。全程只用一种图形 API，不混着比对；成文时的约定是 `-force-vulkan`。
- **判据**：OpenGL（`-force-glcore`）下部分 pass 超过 32 个纹理参数上限：`ltspass_cutout` 33、`lilToonRefraction` 33、`LilBugShader/Refraction` 56、`LilBugShader/ltspass_opaque` 52；症状是控制台每秒上百条 `State comes from an incompatible keyword space`（3 分钟 4.9 万条、日志 197 MB）。在只挂核显的远程桌面会话里，OpenGL 走核显：不透明 lilToon（皮肤材质 `Body_base`、脸、指甲）在编辑器里 0 像素，`lilToonOutline` 的缎带出洋红，透明描边的衣服照常；核显自带显存只有 512 MB，又从系统内存借了约 2.87 GB（读 `/sys/class/drm/card*/device/mem_info_gtt_used`），并不省内存；Scene 视图每画一帧报一条上述日志（一个会话的 `Editor-prev.log` 涨到 18.6 GB），不需要看场景时切到 Game 标签或关掉 Scene 视图。没有 GPU 的沙箱（如 `bwrap --dev /dev` 只给最小设备集，没有 `/dev/nvidia*` 与 `/dev/dri`）里，Unity 落到软件 Vulkan，lilToon 出洋红。渲图自检：大片 `(255,0,255)`、日志里有 `failed to load driver`、`incompatible keyword space` 成片出现，渲图都不可信。测渲染的第一次读数不可信（同一段代码第一次测出 1600 像素，之后稳定为 0）：关异步编译（`ShaderUtil.allowAsyncCompilation=false`）并至少测两遍。批处理渲图不要加 `-nographics`，会渲出空白图。向人描述时如实说「皮肤、脸、指甲在编辑器里看不见，上传的模型不受影响」，不要弱化成「发灰」。
- **证据等级**：单一案例（候选）——只在一台 Linux 主机（远程桌面图形会话，核显加独显）上验证过。
- **失效条件**：换图形 API、显示环境、驱动或 lilToon 版本后需复测；让 OpenGL 走独显（PRIME offload：`__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia`）的办法成文时未实测。

## VRChat SDK 构建与 Play 会改写的工程文件

- **适用范围**：在源工程（而不是隔离构建副本）里做 SDK 构建、上传或进出 Play 之后看 `git status`；SDK 3.10.4、lilToon 2.3.4 时期。
- **结论**：这些改动是工具的副作用，不是谁的设置，要从本阶段的改动里分出来；否则交付 diff 看不清，也无法证明交付的设置就是调过的那套。
- **判据**：同一工程两次实测：数百个厂商贴图 `.meta` 的 `mipMapMode` 从 0 同向翻成 1（mip 滤波 Box → Kaiser，一次 285 个），另有 253 个被塞进显式的 `platformSettings` 默认块；`GraphicsSettings.asset` 的 `m_FogStripping: 0 → 1`（SDK 的 `EnvConfig.SetFogSettings`，不会自己还原）；`ProjectSettings/lilToonSetting.json` 被 lilToon 的 `VRChatModule`（预处理顺序 100）改写，剥掉头像材质没用到的 shader 功能（一次关 48 项、留 56 项），要对照头像材质的 `_UseXxx` 开关核有无影响（例：剥掉了 `EMISSION_2ND`，而两个眼睛材质都是 `_UseEmission2nd: 0`，无影响）。触发源是 SDK 构建本身（时间戳与点上传的那几分钟吻合）；最初「崩溃后全量重导」的归因是错的。进 Play 时 Avatar Optimizer 或 SDK 把 `legacyClampBlendShapeWeights` 置 1、正常退出置回 0；Unity 还会翻 iOS 图形 API 的 `m_Automatic`；提交前先看 `git diff ProjectSettings/`，会话结束后按基线提交还原 `ProjectSettings.asset`，或只提交要提交的路径。推断、未证实：Play 中被强杀（`EnteredEditMode` 没跑到）时 1 可能留在盘上；进 Play 前先 `grep -n legacyClampBlendShapeWeights` 读一遍，见到 1 就还原，不据此断言外推一定被钳。切换图形 API 时，lilToon 按 `CurrentRP.txt` 重写 `lilToonSetting.json` 并按头像材质重编译 `.shader`（一次 30 个 `LIL_FEATURE_*` 由 false 变 true，都是无材质引用的功能），不进上传包——上传走 `IVRCSDKBuildRequestedCallback`，按实际材质重算。识别：同一次操作把几百个厂商文件在同一字段上同向改写，就是归一化；对照 `git grep -h "<字段>:" HEAD -- <Assets 路径>` 看原来的分布（一例为 0 的 949 个、为 1 的只有 2 个）。处置：贴图 `.meta` 批量副作用逐个还原，再跑一次普通 `AssetDatabase.Refresh()`（不带 `ForceUpdate`）复验不会被改回；两个 ProjectSettings 可按现状保留，但 `m_FogStripping` 在最后一次构建后改回 0 再打包；还原前先看清里面有没有真成果，例如上传成功写回的 `blueprintId`（形如 `avtr_…`）。
- **证据等级**：单一案例（候选）
- **失效条件**：SDK 或 lilToon 版本变化后需复测；构建放在隔离副本里进行时，源工程不会出现这些改动。

## 预制体覆盖的两个坑：不显式记录会丢，缩短数组留残项

- **适用范围**：用脚本或编辑器桥修改场景里预制体实例的组件属性（Unity 2022.3）。
- **结论**：①改预制体实例上的组件属性，要显式调用 `PrefabUtility.RecordPrefabInstancePropertyModifications()`，否则覆盖会丢；有的编辑器桥封装的组件接口漏了这一步。②缩短数组类属性时，超出新长度的元素覆盖不会被自动清掉。
- **判据**：成文时的实例：把 `sharedMaterials` 从 4 个改成 3 个后，`m_Materials.Array.size` 的覆盖变成 3，但 `m_Materials.Array.data[3]` 那条覆盖还在，仍指着本该删掉的材质；Inspector 里看不出来，`grep <旧 guid>` 场景文件才现形。它会让「这个资产还有没有人引用」的判断出错，也可能在数组以后变长时把旧值复活。改完数组长度，`grep -c <旧引用的 guid>` 场景文件应为 0。修法：`PrefabUtility.GetPropertyModifications(root)` 取全部覆盖（一例 389 条），滤掉 `propertyPath` 以 `m_Materials.Array.data[` 开头且指向目标资产的条目，再 `SetPropertyModifications` 写回。同类风险：`m_BlendShapeWeights.Array.data[i]`。
- **证据等级**：单一案例（候选）
- **失效条件**：Unity 版本变化后需复测。

## Linux 命令行管进程：按名精确匹配，等产物不等进程

- **适用范围**：在 Linux shell 里查找、结束、等待 Unity、Blender 或脚本进程。
- **结论**：按命令行匹配（`-f`）会匹配到发出命令的 shell 自己；等进程结束最稳的方式是等产物或完成通知。
- **判据**：①`pkill -f <串>` 与这个串出现在同一条命令里时，会杀掉自己的 shell（退出码 144、没有输出，随后的 `cd` 像没执行过）；改用 `pgrep -f` 列出 PID、排除自身 `$$` 后逐个结束，Unity 用 `pgrep -x Unity`。②`until ! pgrep -f <串>` 会匹配到等待循环自己，永远等不完（一次被等的进程 512 秒就结束了，却一直判「还在跑」）。③`pgrep` 的模式是 ERE，`\|` 是字面竖线而不是「或」，整条匹配为空，会误判「进程没在跑」——一次因此删了锁文件、在同一工程上起了第二个编辑器；多模式写 `pgrep -f 'A|B'`。④`read -t N < /dev/zero` 不会等待（`/dev/zero` 永远立刻有数据），写成轮询就是空转。做法：等产物（`until [ -f 出参文件 ]`），或让被等的命令在后台运行、完成时通知；非要睡眠，用 `python3 -c "import time;time.sleep(1)"` 这类确定会等的写法。看门狗一类按命令行匹配的脚本，模式要锚定可执行文件的完整路径，并把脚本写成文件再运行（否则父 shell 的命令行里就带着匹配串，一次把启动它的 shell 当目标杀掉）。规则记得住，栽的往往是触发时刻：写复合命令前问「这条命令里有没有 `pkill -f`，后面的串是不是也出现在命令的别处」。
- **证据等级**：多工程验证
- **失效条件**：无（均为 shell 与 procps 的确定行为）。

## 脚本不报错却行为不对：几个常见的坑

- **适用范围**：编写 bash 与 Python 脚本（打包、导入队列、预演、写记录、解析 git 输出）。
- **结论**：这些坑都不报错、日志一片通过，但行为与预期不同。
- **判据**：①`set -e` 下写 `[ 条件 ] && 动作`，条件为假时整条返回 1，脚本直接退出；用 `if … then … fi`。②`set -o pipefail` 下，命令替换里的 `grep` 无命中会拖垮整个脚本；提取「可能没有」的东西（菜单项、首个标题行、版本号）一律加 `|| true`。③列压缩包成员不要用 `7z l -ba | awk '{print $NF}'`，路径含空格时只取到最后一个词；用 `7z l -slt a.zip | awk '/^Path = /{sub(/^Path = /,""); print}'`。④预演（dry-run）里的建目录与写文件也要受开关保护，判据是跑完 `git status` 与跑之前一模一样。⑤命令输出可能被本地化：中文区域设置下 `free -g` 的表头是「内存：」而不是 `Mem:`，`awk '/^Mem:/'` 取不到值；脚本开头 `export LC_ALL=C`，或用 `free -g | awk 'NR==2 {print $NF}'`，最稳是直接读 `/proc/meminfo` 的 `MemAvailable`。⑥不带引号的 heredoc（`<<EOF`）里，正文的反引号会被当命令执行、文字被吞掉；一律用 `<<'EOF'`，写完回读。⑦正文带 `%` 时不要用 `%` 格式化（会 `TypeError: not enough arguments`），改用占位符替换（`body.replace("@TS@", ts)`）或 f-string（其中的 `{}` 同样要当心）；写入与提交之间用 `&&` 串起来，并先回读确认落盘——一次写入失败而提交照跑，提交信息描述了盘上不存在的内容。⑧脚本解析 git 输出（`log --name-only`、`diff --name-only`）一律带 `-c core.quotepath=false`，否则中文路径被转成 `\346\...` 这类转义，在干净克隆里匹配不上。⑨`json.dump(obj, open(p, "w"))` 不持有文件句柄，遇到不可序列化的值会写一半就断；用 `with open(...)` 并给 `default=float`。⑩非 ASCII 路径不要手打字面量：从 ASCII 祖先目录按商品号通配定位——有的目录名是 NFD 形式，手打的 NFC 字符串匹配不上。⑪含反斜杠的 Python 写成文件再执行，不塞进不带引号的 heredoc。⑫长文本，或含反引号、引号、`$`、`!` 的参数写成文件再传，不内联进 shell 命令：内容会被 shell 吃掉，而接收方照样交回一份像样的结果（一次对照：内联 4/6 正确，走文件 6/6）；Windows 上经 `cmd.exe` 转一道时，非 ASCII 参数还会被代码页打坏，要直接调用可执行入口、不经 shell。
- **证据等级**：多工程验证
- **失效条件**：无（均为确定的语言与工具语义）。

## Blender 5.2 几何脚本：骨骼 API、量纲与精度

- **适用范围**：用 Blender 5.2（无头或经 MCP）写测量、导出、贴合类几何脚本。
- **结论**：几处 API 与数值细节会让判据静默地自证成立或差出三个数量级。
- **判据**：①`bpy.types.Bone` 已没有 `roll`：在编辑模式读 `EditBone.roll`，或由 `bone.matrix_local` 反算。②`Bone.x_axis/y_axis/z_axis` 实测是父骨空间（同一世界朝向，根骨与子骨读数不同）；核「骨的局部轴朝世界某轴」一律用 `bone.matrix_local.col[i]`。③`mathutils.Vector` 是 float32，在 Blender 外用 numpy float64 重写同一算法，逐点会差约 1e-6；要逐点一致就回 Blender 用 mathutils 跑，或按对方存盘精度（如保留 8 位小数）比。④`BVHTree.find_nearest`/`ray_cast` 返回场景单位（多为米），写报告前换算，否则「0.0039 mm」其实是 3.9 mm。⑤在从大网格里抠出来的开口子网格上，用法线符号判「穿进去没有」会假负（边附近符号为负、实际分离 1.5 mm）；穿透一律用 `BVHTree.overlap` 判，带符号距离只作深度诊断。⑥只转根骨加平移一根子骨的姿态族里，同一骨刚性驱动的两块几何相对距离恒定；扫掠读数不随参数变化时先查这条，不是脚本坏了。⑦单个三角面的法线在窄化或剪切下会给出假转角（一例 8.27°，邻域面积加权为 0.47°）；曲面法线判据用邻域面积加权。⑧跨工具的资产在源工具里往返核对不算验收：一件网格在 Blender 里差 0.000 mm，进 Unity 蒙皮后偏 71 mm；以目标工具里的结果（Unity 中 `BakeMesh` 后的世界坐标）为准，能在 Unity 里直接做的就别绕 Blender。
- **证据等级**：单一案例（候选）——均来自同一类饰品几何任务。
- **失效条件**：Blender 版本变化后，①②需复测；其余为数值与几何的一般性质。

## 无头 Blender：驱动告警不等于不能渲，实例要串行

- **适用范围**：`blender --background` 渲图或测量；Blender 5.2。
- **结论**：无头 EEVEE 打出的 `amdgpu_device_initialize failed`、`failed to load driver: radeonsi` 告警不代表不能渲；每个无头实例都要完整加载 .blend，内存开销是 GB 级。
- **判据**：小物体在大画幅里时，整帧均值看着像全是背景，容易误判「EEVEE 不可用」；判据用非背景像素计数（或遮罩渲量物体的像素宽）。一份 135 MB 的场景，一个无头实例就是 GB 级，一轮连开 6 次曾把内存与交换区打满。能在已经开着的 Blender 会话里只读测量的，就别另起无头实例；无头实例串行、跑完即退，不挂在后台并发。Blender 的 MCP 插件（`bl_ext.user_default.mcp`）健康检查可调 `get_objects_summary`；无头启动它用 `blender --background --command blender_mcp`，不加 `--factory-startup`（会跳过用户扩展、报 `Unrecognized command`）；用完要关，否则占着监听端口（成文时 9876），图形界面版的 MCP 起不来。插件要求偏好里开启「在线访问」。
- **证据等级**：单一案例（候选）
- **失效条件**：Blender 版本、GPU 驱动或 MCP 插件变化后需复测。

## 离线编译编辑器脚本：复用工程自己的 .rsp

- **适用范围**：改完 `Assets/Editor/*.cs` 后、让 Unity 刷新之前预编译（Unity 2022.3）。
- **结论**：用工程自己的 `.rsp` 调 Unity 自带的编译器，几秒出结果，不触发域重载，也不会在交互编辑器里弹出 Safe Mode 模态框；不要手搓引用列表。
- **判据**：Unity 每次编译都把完整引用集写在 `Library/Bee/artifacts/*.dag/<程序集>.rsp`；复制它、只换掉 `-out:`，交给 Unity 自带的 `Editor/Data/NetCoreRuntime/dotnet` 加 `Editor/Data/DotNetSdkRoslyn/csc.dll`（带 `-nostdlib -noconfig`），退出码 0 为通过。手搓引用必踩：`CS0433 类型"MenuItem"同时存在于 UnityEditor 和 UnityEditor.CoreModule`（单体 `Managed/UnityEditor.dll` 与模块化 `UnityEditor.CoreModule.dll` 同时引用）；`CS0518 预定义类型"System.Object"未定义` 或 `CS0433 StringBuilder 同时存在于 mscorlib 和 netstandard`（`mscorlib`、`netstandard` 少给、给重或版本不对）。前提：工程至少被 Unity 成功编译过一次（全新工程或清过 `Library/` 时找不到 rsp，只能先让 Unity 编一次）；rsp 里的源文件清单是上次编译时的，新增文件第一次要么先让 Unity 编一次，要么手动追加到临时 rsp。拼接 rsp 时每段后补换行（`printf '\n'`），否则下一条 `-out:` 会和上一行的 `-additionalfile:` 粘成一行被当成文件名，dll 与 pdb 落进工程根——跑完 `git status` 看工程根有没有多出 `*.dll`、`*.pdb`。已经弹出 Safe Mode 时，`grep -nE "error CS[0-9]+" Editor.log` 定位最快。成文时的一例：一个编辑器脚本少了 `using System.Collections.Generic;`，编辑器被 Safe Mode 对话框挡住，工作中断。
- **证据等级**：单一案例（候选）
- **失效条件**：Unity 版本或其内置编译器的目录结构变化时需复测。

## 编辑器桥的环境细节：配置被改写、失败关闭与死实例路由

- **适用范围**：MCP for Unity（成文时 10.1.2，stdio）在 Linux 上接入代理客户端。
- **结论**：编辑器桥只在图形界面模式下启动，批处理模式不起；它的几种故障都「看起来像桥坏了」，其实是配置被改写、依赖缺失或路由到了死实例。
- **判据**：编辑器桥在图形界面模式下监听（成文时 6400 端口）；选 stdio 后的设置写在 Unity 偏好里（`MCPForUnity.UseHttpTransport=0`），冷启动自动连。Unity 每次启动都会改写各客户端的配置（有的被加上 `--offline`，有的被加上工程级条目）；有的桌面客户端运行时会用内存里的旧配置写回，要改它的配置得先完全退出。服务端不要加 `--offline`：本地包缓存缺依赖时它失败关闭、刷屏 `Failed to download`，工具静默消失。被强杀的 Unity 会在 `~/.unity-mcp/` 留下 `unity-mcp-status-<哈希>.json`，之后别的工程进 Play（域重载、心跳暂断）时，请求会被路由到这个死实例（报 instance not found，available 里列着旧工程）；删掉哈希与当前工程不符、时间是被杀那刻的那份（`ls -t ~/.unity-mcp/` 看）。多开实例时用 `set_active_instance <工程名>@<哈希>` 路由，哈希见状态文件。
- **证据等级**：单一案例（候选）
- **失效条件**：MCP for Unity 或客户端版本变化后需复测。

## 资源预算：Unity、无头 Blender 与并发的内存量级

- **适用范围**：在一台机器上同时跑交互编辑器、批处理 Unity、无头 Blender 与多个执行会话。
- **结论**：并发上限按内存定，不按 CPU 定；Unity 是内存大户。内存耗尽时，同一进程组里的进程会被一起杀掉（编辑器、批处理、执行会话一起死），代价是未提交的产出与中断的队列。
- **判据**（成文时在一台 30 GB 内存的主机上标定）：一台交互 Unity 约 3–5 GB（跑完整预处理时再涨 2–3 GB，一例达 7.8 GB）；批处理导入 2–4 GB；一个执行会话连同其工具子进程约 0.3–0.8 GB；无头 Blender 按场景大小，GB 级。可用内存低于 8 GB 不再起新的批处理或执行会话；起交互 Unity 要求 ≥8 GB、批处理 ≥6 GB；每个 Unity 进程放进带内存上限的单元（如 `systemd-run --user` 单元的 `MemoryMax`：交互 14 GB、批处理 10 GB），超限只死它自己；两台交互编辑器都开着时不跑批处理导入，批处理导入与交互 Unity 合计 ≤2 个；交互编辑器在跑完整预处理时不起批处理（「≥8 GB」只看起点）；看门狗在可用内存 < 3 GB 时先结束批处理 Unity（最不要紧、可重跑），保交互编辑器。交换区用掉一半以上先清场再干活；别人正在用的编辑器不由执行方关闭，把可关的列给人决定。7-Zip 的 LZMA2 每线程约 500 MB，内存紧时线程数不超过 `-mmt=6`。
- **证据等级**：单一案例（候选）
- **失效条件**：主机内存、工程规模或编辑器版本不同时重新标定；这些数属于调度阈值，由 Runtime 维护方决定是否采用。

## 构建期取证与非破坏式生成的插件接口（成文时）

- **适用范围**：写 NDMF 插件或构建期审查工具；成文时的版本为 Modular Avatar 1.18.1、NDMF 1.14.3、Avatar Optimizer 1.9.16、VRChat SDK 3.10.4。
- **结论**：几条接口事实决定了构建期工具能不能编译、能不能拿到构建后的真实状态。
- **判据**：①Avatar Optimizer 的运行时程序集没开 Auto Referenced，脚本里直接 `using` 编不过；要挂 Trace And Optimize 或读它的私有序列化设置，用反射。②构建前名字到构建后名字的映射，可借 Avatar Optimizer 的公开接口 `ComponentInformation<T>.ApplySpecialMapping` 取得；要在 Avatar Optimizer 之后截获，NDMF 插件在 Optimizing 阶段声明 `AfterPlugin("com.anatawa12.avatar-optimizer")`；Modular Avatar 反应式组件的分析结果，可用 Harmony Postfix 钩住 `ReactiveObjectAnalyzer.Analyze` 取得。③非破坏式生成：在头像根上挂一个实现 `IEditorOnly` 的安装组件，NDMF 插件在 Transforming 阶段、Modular Avatar 之后把生成物做进构建克隆，再删掉安装组件；生成失败一律走 NDMF 的错误报告（标题、详情、怎么修），不静默跳过；供人看位置的预览用「不保存」的临时物体。④用 VRChat SDK 的 `AvatarPerformance` 接口出性能报告时，报告要同时写文件——Console 会截断多行日志。⑤单例型的 NDMF 组件在头像上挂了两个，会让插件抛异常、中止构建；Modular Avatar MergeAnimator 的空引用同样会中止构建。⑥工具不要写死头像名（成文时一批工具写死了 `const string AvatarName = "Kipfel"`，换工程就报「找不到」）：取当前选中的物体，或场景里激活的 `VRCAvatarDescriptor`。
- **证据等级**：单一案例（候选）
- **失效条件**：插件版本变化后逐条复核；这些是成文时版本的接口事实。

## 工具里固化的三条测量判据（成文时）

- **适用范围**：编写部件盘点、捏脸复核类的测量脚本。
- **结论**：以下判据已在审查工具中固化复用，可直接沿用，但各有适用前提。
- **判据**：①「哪块网格是身体」：**先按 Harness 已知身份**——方案 `body_prefab` 里名字归一到身体词根的那些渲染器（贴合探针由请求 `body_prefab` 带入，素体可为多块网格并集）；Harness 装配层 `_Outfit` 之下（含优化器压平名 `_Outfit$…`）的渲染器在任何一层都不作身体候选。没有身份时才退「名字候选过蒙皮权重关 → 几何兜底（同样要过权重关）」，全落空就报错/留空，不拿顶点最多者顶替。部件盘点、T-10 poke、贴合探针三处共用 `AuditBodyPick`。②捏脸烘焙后的形态键全量检查：动画里某键的峰值加上已烘焙进网格的量超过 100，即判为双重应用、会破形。③眼尾相对眼头是抬还是垂：先按 x 把顶点分成左右眼，再比较每只眼最外 10% 与最内 10% 顶点簇的 Δz；眼周高度带的阈值要按素体调。
- **证据等级**：单一案例（候选）
- **失效条件**：①没有 `body_prefab` 身份、且素体被拆成多块或脚部无权重时，权重判据选不出素体（贴合探针把这类衣物的逐件穿模数标成 no_data、不并入旧口径原始计数；但按「没量到的不当没问题」，它的命中仍算「看得见的穿出」并单独记在 `fit_pierced_no_data_vertices`，新口径见 `context/regression/装配类失败定位.md`）；②只适用于「已烘焙且动画仍驱动同一个键」的情形；③换素体要重新标定眼周高度带。

## Linux 上启动编辑器与工具的细节（成文时）

- **适用范围**：在 Linux 桌面（远程桌面图形会话）上启动 Unity Hub、Unity 编辑器与 Blender。
- **结论**：几项启动参数与偏好不设会直接崩溃或静默失效。
- **判据**：Unity Hub 命令行要加 `--ozone-platform=headless` 并去掉 `DISPLAY`，否则被 GTK 全局菜单模块弄崩（另设 `UBUNTU_MENUPROXY=0`）。编辑器语言写在 EditorPrefs 的 `Editor.kEditorLocale`。编辑器窗口矩形存在 `~/.local/share/unity3d/prefs` 的 `RestoredMainWindowSizeX/Y/W/H`；在远程桌面换过分辨率后，若它恰好等于某个旧屏宽，启动时会与窗口管理器协商不收敛而崩溃，而且每次重开都崩在同一处；备份后把矩形改成明显不贴边的值、关掉最大化即可。Blender 的 MCP 插件要在偏好里开启「在线访问」才会自启监听。
- **证据等级**：单一案例（候选）
- **失效条件**：换桌面环境、Hub 或 Blender 版本后需复测。

## Unity 工程进版本库的范围：文本资产入库，5 MB 线与主场景例外

- **适用范围**：用 git 管理 Unity 头像工程；以版本库文件为依据做产物指纹或回退时。
- **结论**：文本资产入库，可再生的大文件与二进制不入库；阈值按实测体积定，主场景单独放宽。
- **判据**：入库：`Assets/`、`ProjectSettings/` 下的文本资产（`.unity`、`.prefab`、`.anim`、`.controller`、`.mat`、`.asset`、`.meta`、`.cs`）、`Packages/*.json`、工程根的说明文件。不入库：`Library/`、`Temp/`、`Logs/`、`obj/`、`UserSettings/`、`*.csproj`、`*.sln`、VPM 包目录、生成目录（如 `ZZZ_GeneratedAssets/`、`Triturbo/*/Generated/`）、`_backup/`；二进制（FBX、贴图、PSD、blend、音频、dll、压缩包）与单个 > 5 MB 的文件。5 MB 线是量出来的：四个工程的文本资产共 2.5 GB，其中 63 个 > 5 MB 的文件占 1.27 GB，几乎全是面捕生成网格、BlendShare 数据和厂商 AFK 动画，都能从包重新生成，剩下约 1 GB 的 YAML 入库；调高会让仓库膨胀、`git status` 变慢，调低会漏掉大场景。主场景是例外：一个工程拆出两个头像后主场景 6.28 MB，被排除规则从版本库移出（`git rm --cached`）；主场景单独放宽（成文时上限 32 MB），并检查提交输出里主场景有没有出现在「排除的大文件」里。VPM 包不入库，版本冻结在 `vpm-manifest.json`，`vrc-get resolve` 能还原；代价是对 VPM 包的本地改动（如 lilToon asmdef 的 `autoReferenced`）不受版本管理，要写进记录。FBX、贴图不在库里，靠各工程自己的还原点目录。回退：`git log --oneline -- <工程>/` 找到提交，`git checkout <提交> -- <路径>`；回退场景、预制体、动画前先关掉 Unity 或确认没人在编辑，回退后在 Unity 里刷新。修过依赖（去掉 `file:`、git 依赖）之后，旧的存档包要重打，否则存档里仍是坏依赖。
- **证据等级**：多工程验证
- **失效条件**：工程构成不同（如大量大体积 YAML 场景）时重新量线；产物指纹若只取版本库文件，被排除的大文件不在指纹里，需要另行登记。
