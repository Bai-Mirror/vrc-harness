# 骨骼与动骨（装配相关）

跨工程的质量记忆。每节固定写适用范围、结论、判据、证据等级、失效条件；先列多工程验证的，后列候选。

## 服装兼容性按骨骼名集合判断：文件名在两个方向上都会判错

- **适用范围**：任何素体与通用服装包，日系共用素体企划尤其常见；与插件版本无关。
- **结论**：「文件名或目录名里有没有素体名」既会漏判——共用素体企划的服装按企划名发布适配，角色名不出现；也会误判——包里叫本素体名的文件夹可能属于另一个同名素体。能判断兼容的只有服装 FBX 的骨骼名集合与素体人形主干的比对。误判的服装在编辑期看起来「装上了」，要到动骨或换姿势才暴露。
- **判据**：人形主干 19 项（Hips、Spine、Chest、Neck、Head，以及左右 Shoulder、UpperArm、LowerArm、Hand、UpperLeg、LowerLeg、Foot）零缺失。服装多出来的骨（带包前缀，或 `.001`～`.00N` 链）是自带动骨链，不算缺失。同源 FBX 连骨名的拼写错误都一致，可作指纹。
- **证据等级**：多工程验证（一个工程里按文件名排除了一整批其实适配的服装；另一个工程里同名文件夹的服装比对下来缺 5 项主干：Head、双小腿、双脚）。
- **失效条件**：服装不走人形骨合并（例如纯 BoneProxy 挂点的头饰），或素体骨架不是人形时，主干比对不适用。

## 名字只当线索：部件、骨骼与开关名都会误导

- **适用范围**：所有厂商服装、素体自带件与开关参数，跨素体。
- **结论**：物体名、材质名、开关名与实际部件经常不符；按名字归类、并组或挂收缩键会出错，而且错误常常只在「全关」那格或用户实测时才暴露。包围盒同样会误导。
- **判据**（已核实的例子）：

| 名字 | 以为 | 实际 |
|---|---|---|
| ANEMONE `skirt` | 裙 | 背心裙外层，应归外套 |
| MMN `Ring` | 戒指 | 头顶光环 |
| Violet Nocturne `Straps`（材质 `Anklet`） | 上衣件 | 脚踝绑带 |
| KemoHandMB `Toggle-Foot` | 腿饰 | 兽爪鞋套（鞋袜全关那格才暴露） |
| PixelBoot | 靴 | 发饰（审查工具因此出现大量假命中） |
| 「厚底」运动鞋 | 能盖脚踝 | 低帮 |
| いたずらメイド `mimi_Im` | `true`＝显示 | `true`＝隐藏 |
| Shinano 默认服装的 `Sweater`、`Dress` 等五件 | 五件独立衣服 | 默认服装的 `*_OFF` 叠穿开关 |
| Rurune 的 `leg fixed` | 腿部件 | 移动系统（Paryi Loco）的「足固定」 |
| The Velour `T07_Nubra`（材质 `bra`、`bra plastic`） | 文胸 | 乳贴 |
| The Velour `T07_Corset`（带 `Waist_thin_____腰_細く` 键） | 身体改形键 | 束身衣，是衣物 |

  另外：整套共用图集的材质槽名不能说明两件有关系（The Velour 的 `T07_Choker` 材质槽为 `corset`／`briefs`／`silver metal`／`pearl`，`T07_Briefs` 为 `corset`／`briefs`／`corset line`）；GRF 的装饰耳 `Rose_Ears` 曾被「体积比 0.76＋中心距 1 cm」这类包围盒指标判成变体（定论要看逐顶点最近距离中位数：< 2 mm 为变体，> 5 mm 为装饰）。未核实的名字嫌疑：LUNALICE 的 `Underwear_Garter`（内裤还是吊袜带）、いたずらメイド 的 `U_Innmon`（厂商开关名为 `heart_off`）——建档时先看图核实。
- **证据等级**：多工程验证。
- **失效条件**：无——名字从来只是线索。分组与参数极性以厂商目录下的 clip 与菜单资产为准。

## 编辑期计算骨权重要按骨名比，不按 Transform 物件比

- **适用范围**：编辑模式下、MA MergeArmature 尚未执行（它在构建期才合并）时，计算衣物顶点蒙在哪些身体骨上。
- **结论**：编辑期服装骨与素体骨是不同的 Transform 物件，按物件比一件都命中不了，要按骨名比。
- **判据**：按骨名匹配的命中顶点数 > 0；按物件匹配为 0 时，说明口径错了，不是没有覆盖。
- **证据等级**：单一案例（候选）。
- **失效条件**：在合并后的克隆或构建产物上计算时，按物件比也成立。

## 服装自带的动骨链随 MergeArmature 并入，节点名常与网格名重叠

- **适用范围**：带自有物理骨链的厂商服装与发型。
- **结论**：服装 FBX 里多出来的骨（带包前缀，或 `.001`～`.00N` 链）是它自带的动骨链，MergeArmature 会一并带入。`Jacket`、`Tops` 这类名字常常既是网格名又是 PhysBone 节点名，任何按叶子名的比对、查找或差异导出都会串。
- **判据**：比对与查找一律用完整路径；为厂商变体新增的实例带来的骨链，计入骨骼与动骨预算（例：一个兜帽变体实例带来 24 根骨）。
- **证据等级**：单一案例（候选）。
- **失效条件**：属于命名习惯层面的风险，没有明确的失效条件；厂商改用唯一命名时风险降低。

## 多套服装头像的 PhysBone：停用的也计数，256 是构建期硬上限

- **适用范围**：VRChat SDK（上限来自 SDK 源码常量 `MAX_AVD_PHYSBONES_PER_AVATAR = 256`）；多套服装叠在同一个头像上。
- **结论**：PhysBone 组件超过 256 不只是评级变差：构建期会对**处理后**的头像再校验一次并抛 `ValidationException`，上传拿不到包。同处的其他上限：碰撞体 256、Contact 256、Constraint 2000、Raycast 80。性能评级把停用的组件也算进去，而 CPU 每帧只跑激活的；多套服装的头像停用组件常占一半以上，所以「评级数字」与「真实每帧开销」要分开报，并说清哪个对应帧数。SDK 面板的统计跑在构建前的场景对象上，构建期合并（如 AAO MergePhysBone）改变不了面板上的数字。
- **判据**：处理后头像的 PhysBone 组件数 ≤ 256；碰撞检查数＝Σ（每条链受影响的骨数 × 该链挂的碰撞体数），摘掉一个碰撞体的收益等于那条链的骨数，与碰撞体大小无关。
- **证据等级**：单一案例（候选）（一个多套服装、双头像根的工程从 520 个组件压到 236 个；上限值来自 SDK 源码）。
- **失效条件**：SDK 调整上限常量或统计口径时。

## 动骨组件的覆盖子链不能包含人形主干骨

- **适用范围**：VRCPhysBone，尤其是 `rootTransform` 指向父物体且 `multiChildType = Ignore` 的配置（场景内合并动骨时常见，厂商把动骨根设在身体骨上时也会出现）。
- **结论**：`rootTransform`＝父物体加上 `multiChildType = Ignore`，会把父物体下**所有**子链变成物理链，包括原本没有 PhysBone 的。出现过：`Hips` 上的组件覆盖了 `Spine` 与大腿，`Head` 上的覆盖了 `LeftEye`，`Chest` 上的覆盖了 `Neck`／`Shoulder`——整副骨架变软。
- **判据**：遍历所有 PhysBone，Spine、Neck、左右 Shoulder、左右 Upper_leg、Hips、Chest、Head、LeftEye、RightEye、左右 Hand 不得出现在任何组件的覆盖子链里（必须为 0）。合并类操作后，每个组件实际覆盖的一级子链数（父物体 childCount 减去落在 `ignoreTransforms` 里的）必须等于源链数，对不上就中止。安全做法：把父物体下不属于本组的子物体全部加进 `ignoreTransforms`——不动层级，也不打断按路径引用骨骼的动画。
- **证据等级**：单一案例（候选）。
- **失效条件**：SDK 改变 `multiChildType` 的语义时。

## 给发链挂身体碰撞体：静止在内的不挂、够不着的不挂、挂在常驻物体上

- **适用范围**：头发、尾巴等 PhysBone 链穿过身体；VRChat PhysBone 碰撞。
- **结论**：正解是给链挂一个躯干碰撞体，但不能全挂：每挂一条就多「骨数」次检查／帧，挂错了还会把造型顶变形。
- **判据**：
  1. 静止姿态下已经在碰撞体里面的链不挂——挂上瞬间会被弹出，站立造型直接变形（常见于贴颈侧、胸前垂下的短发）。
  2. 够不着的链不挂：链根到碰撞体表面的距离 < 链长（根到最远骨）＋余量才挂。不能看静止时离多近——10 cm 长的呆毛离胸口 24 cm，怎么甩都碰不到；40 cm 长的后发静止时不近，一低头就贴上去。
  3. 碰撞体上沿停在肩线以下；别直接复用厂商给尾巴用的躯干胶囊（上沿常盖到下巴，会把贴颈的发链顶出去）。
  4. 碰撞体挂在永远激活的物体上（主骨架的躯干骨），不挂在可开关的部件下——部件一关碰撞体就失效，穿模只在特定档位复现。
  5. 链的 `radius` 不能为 0：碰撞按「骨线＋radius」算，≈0 时骨线贴着皮肤，网格仍会穿进去；要抬到能覆盖网格厚度的量级。
- **证据等级**：单一案例（候选）。
- **失效条件**：改用别的碰撞方案，或 SDK 改变碰撞计算方式时。

## 调发型动骨参数前先确认现状：gravity、immobile 与 falloff 的顺序

- **适用范围**：调整厂商发型、服装上的 VRCPhysBone 参数。
- **结论**：厂商发型常见 `gravity = 0`＋`immobile = 0`＋无角度限制——完全不下垂，走路时整头被拖成一条线，不是「已经调好了」。`gravityFalloff = 0` 时重力是恒定作用的，必须先把 falloff 抬起来再加 gravity，否则站立造型会被永久压塌。
- **判据**：动骨观感编辑期不模拟，只能在 Play 里看；实测动作：静止、低头、侧头、走路、原地转身。
- **证据等级**：单一案例（候选）。
- **失效条件**：SDK 改变这些参数的语义时。

## 候选：PhysBone 超 256 时先测算三档再定方案

- **适用范围**：VRChat PhysBone 组件数超过 256 硬上限的头像，尤其是多套服装、多个交付根的工程；用 AAO MergePhysBone 语义在场景里合并。
- **结论**：先删纯空转组件、排除不能合并的组，再按三档算出能压到多少，然后才定方案；光靠「同父合并」常常到不了 256。
- **判据**：先清点：按头像根下的顶层子物体统计 PhysBone 数找下手点，并列出每条链的受影响骨数 × 碰撞体数；重复组件逐字段比对确认冗余后才删。纯空转：`rootTransform`（为空时取组件自身）名下没有任何子 transform，且 `endpointPosition` 为 0，什么都不模拟，删掉零损失；根下没有子骨但设了 `endpointPosition` 的有一个虚拟端点，不是空转（该例两个根各有 15 个，保留）。不能合并的组：任一成员被动画写（`m_Enabled` 或 `VRCPhysBone` 类型的曲线）；组内有 ≥2 个不同的非空 `parameter`（合并只能留一个，另一个的抓取、拉伸参数失效）；`allowGrabbing`/`allowPosing` 不一致（合了会改变能否抓取、摆姿，要合就明确对齐到组内多数派并记录）。三档：① 同父且设置完全相同才合（手感零变化）；② 同父就合、设置强行对齐；③ 再往上一层合。一例两个根各从 520 起：删纯空转 5 个到 515，同父合并 69 组到 257，再把每个发型的各部分合成一条（4 组）到 236；该例同父合并的纯数学上限是 259，必须叠加删空转或跨层合并。合并手段按精确度递增选：找可合并的兄弟组 → 点名合并 → 编辑期真合并（设多道闸门）→ 改组件的目标表；一次只落一个改动。
- **证据等级**：单一案例（候选）
- **失效条件**：VRChat 调整 PhysBone 上限，或 AAO 的合并语义改变时需复核；在只允许删除逐字段等价重复项的流程里，②③ 两档都属于要用户授权的方案。

## 候选：场景内合并 PhysBone 必须排除非源子链

- **适用范围**：用户已授权在场景里真合并 PhysBone（让 SDK 面板的构建前计数下降），合并语义照 AAO 的 `MergePhysBoneProcessor`（1.9 系列）。
- **结论**：留下的组件挂在父物体上，`rootTransform = 父`、`multiChildType = Ignore`，`ignoreTransforms` 与 `colliders` 取并集；这种写法会把父物体下所有子链都变成物理链，包括原本没有 PhysBone 的，必须把非源子链排除掉。
- **判据**：漏排的实测后果：Hips 上的组件覆盖了 Spine 与两条大腿，Head 上的覆盖了眼睛，Chest 上的覆盖了 Neck 与 Shoulder，整副骨架变软。AAO 自己的做法是把源链重新挂到新建空物体下隔离（只有父物体的子物体恰好全是源链、且父物体没被动画写时才直接复用父物体）；更省事的等价做法是把父物体下不属于本组源链的子物体全部加进 `ignoreTransforms`，不动层级、不打断按路径引用骨骼的动画。硬自检：合完立刻算该组件实际覆盖的一级子链数（父物体 childCount 减去落在 `ignoreTransforms` 里的），必须等于源链数，对不上就中止。整机判据：人形核心骨（Hips、Spine、Chest、Neck、Head、左右 Shoulder、左右 UpperLeg、左右 Hand、左右眼）出现在任何组件覆盖子链里的数量必须为 0；核心骨按 Animator 的人形映射取，不按骨骼名匹配（源案例的 `Upper_leg.L`、`Shoulder.L` 只是一个素体的命名）。合并后可能新出现 `This avatar contains VRCPhysBone or VRCPhysBoneCollider components which have cyclic dependencies`：SDK 说明后果是某个碰撞体晚一帧运行、有意为之可忽略，是 Warning 不拦上传；先剔除「碰撞体长在自己链上」的自环，剔不掉的记为已知项。
- **证据等级**：单一案例（候选）——合并语义取自 AAO 源码，失败后果与自检在一个工程实测。
- **失效条件**：AAO 合并实现改版，或 SDK 对循环依赖改为 Error 时需复核。

## 候选：发链挂躯干碰撞体前先过两条几何判据

- **适用范围**：给头发、尾巴等 PhysBone 链挂躯干碰撞体，防止甩动时穿过身体。
- **结论**：「头发穿过身体」的正解是给发链挂躯干碰撞体，但不能全挂：每挂一条就多「该链骨数」次检查/帧，挂错了还会把造型顶变形。
- **判据**：① 静止姿态下已经在碰撞体**里面**的链不能挂——挂上的瞬间会被弹出，站立造型直接变形（通常是贴着颈侧、胸前垂下的短发）。② 够不着的链不挂：判据不是「静止时离多近」，而是「链根到碰撞体表面的距离 < 链长（根到最远骨）＋ 余量」。例：呆毛静止时离胸口 24 cm、只有 10 cm 长，怎么甩都碰不到；后发静止时也不近，但有 40 cm 长，一低头就贴上去。
- **证据等级**：单一案例（候选）
- **失效条件**：PhysBone 碰撞算法或 VRChat 的开销计算方式改变时需复核；余量取多少尚无标定值。

## 候选：躯干碰撞体的尺寸、挂点与链半径

- **适用范围**：自建躯干碰撞体给发链、尾巴使用。
- **结论**：碰撞体自己定一根矮的，挂在永远激活的主骨架躯干骨上，并把链的 `radius` 抬到能覆盖网格厚度的量级。
- **判据**：直接复用厂商给尾巴用的躯干胶囊是常见错误：那种胶囊上沿常盖到下巴，等于把脖子也按躯干粗细算，会把贴颈的发链顶出去；上沿要停在肩线以下。现成的身体碰撞体常挂在可开关的部件下（尾巴、某套衣服的碰撞体组），部件一关碰撞体就失效，头发只在特定档位穿模。碰撞按「骨线 ＋ radius」算，radius ≈ 0 时骨线贴着皮肤，网格仍会穿进去。
- **证据等级**：单一案例（候选）
- **失效条件**：素体自带的碰撞体已挂在常驻骨上且尺寸合适时，可以直接复用。

## 候选：改动骨参数前先确认现状，先抬 falloff 再加 gravity

- **适用范围**：厂商发型、裙摆等 PhysBone 的参数调整。
- **结论**：厂商发型常见 `gravity = 0`、`immobile = 0`、无角度限制——那是「完全不下垂、走路时整头被拖成一条线」，不是「已经调好了」。
- **判据**：`gravityFalloff = 0` 时重力恒定作用，必须先把 falloff 抬起来再加 gravity，否则站立造型会被永久压塌。动骨观感只能在 Play 里看（编辑期不模拟），要实测的动作：静止、低头、侧头、走路、原地转身。
- **证据等级**：单一案例（候选）
- **失效条件**：PhysBone 版本变化导致参数语义改变时需复核。

## 蒙皮包围盒常年虚报：量身高用骨骼坐标，取景用色键反测

- **适用范围**：用渲染器包围盒量头像身高，或给整身出图自动取景。
- **结论**：`SkinnedMeshRenderer.bounds` 由资产里烘好的 localBounds 经根骨变换得到，与蒙皮后的真实几何常对不上。成文时它把 0.755 m 高的头像报成 2.24 m，把 1.15 m 的报成 2.38 m。按它取景，主体会缩在画面一角甚至出框。
- **判据**：量身高用 Head 与脚部骨骼的世界坐标之差；精确取景渲一张色键探针图反测：先对纯色背景渲一趟，找出非背景像素的包围框与背景占比，再据此调机位与正交尺寸渲第二趟。取景日志里要有探针那一行（包围框、背景占比、收敛后的尺寸）；没有探针行、尺寸异常大，图多半是空的。
- **证据等级**：多工程验证（两个身高不同的头像）
- **失效条件**：渲染器的 localBounds 已按蒙皮后的真实顶点重算过时，`bounds` 可用于粗取景；量身高仍以骨骼为准。

## 场景文本里挂在素体骨上的物体：stripped 父级要回溯源预制体

- **适用范围**：不开 Unity、直接解析 `.unity` 或 `.prefab` 的 YAML，判断某个物体挂在哪根骨上、是不是重复实例。
- **结论**：挂在素体骨骼上的物体，父级 fileID 指向的是 stripped Transform，必须顺着 `m_CorrespondingSourceObject` 回溯到源预制体，才知道真实挂载点。把 stripped 父级一律折叠到预制体根，会把「分别挂在左右手食指上的两个物体」误判成「同父、同坐标的重复实例」。素体骨骼来自 FBX 导入，其 fileID 由 Unity 哈希生成，不出现在任何文本里，无法从文本反解出骨骼名。
- **判据**：文本解析得出的挂载结论，要么回溯到源预制体，要么进 Unity 用 API 读 `transform.parent` 核对；从文本里解析不出骨骼名时，报「判不了」，不猜。
- **证据等级**：单一案例（候选）
- **失效条件**：无。

## 未实测：编辑期服装与素体骨架是分开的，看 bones[0] 往上落在哪

- **适用范围**：用 Modular Avatar Merge Armature 装衣服的工程，在编辑期观察衣服与身体的位置、形变是否一致（例如「袜子的脚跟与身体的脚对不上」）。
- **结论**（早期经验记录，现行规程未收）：Merge Armature 在构建期才把衣服的 `bones[]` 改指到素体真骨。编辑期衣服的蒙皮根是它自带的 `Armature` 副本，两套骨架各走各的，编辑期看到的衣服位置与形变都不可信。一例「袜子的脚跟与身体的脚对不上」，烘焙后再查，蒙皮根变成了素体的 `Armature/Hips`，位置就对了——不是缺陷。
- **判据**：从 `smr.bones[0]` 往上走：落在素体的 `Armature/...` 下，说明已经合并；落在衣服自带的骨架下（例如 `_Outfit/<某套>/Armature`），说明还没合并，关于位置与形变的结论一律改到烘焙后再下。
- **证据等级**：未实测
- **失效条件**：衣服直接蒙在素体骨上、不走 Merge Armature 时不适用。

## 未实测：一个物体挂多个 PhysBone 时，AAO 只重映射第一个的动画绑定

- **适用范围**：装了 Avatar Optimizer（AAO），且有动画曲线写 PhysBone 组件属性（启用开关或参数）的头像。
- **结论**（早期经验记录，现行规程未收）：同一物体上挂了多个 VRCPhysBone 时，AAO 只能重映射第一个组件的动画绑定，其余绑定被丢弃，控制台报「Animation targeting non-first component of the type VRCPhysBone … Skipping this binding」。被丢的绑定对应的开关在成品里不起作用，且不报错。
- **判据**：构建日志里搜这句警告。命中时，把被动画控制的 PhysBone 拆到各自的物体上，或确认被丢的绑定不影响功能，并回归对应的开关。
- **证据等级**：未实测
- **失效条件**：AAO 改变这一重映射行为时。

## PhysBone 合并与替代方案的施工纪律（调研结论，未逐条实测）

- **适用范围**：想通过合并或替换 PhysBone 降低性能开销的 VRChat 头像。
- **结论**（三路调研一致）：
  - 先清碰撞体列表再合并，顺序反了碰撞检查数会暴涨；合并时碰撞体不要用 Merge 选项；
  - 单个 PhysBone 组件不超过 128 根骨（官方多线程建议，256 是硬上限）；
  - AAO 1.9.16 的 EndBone 替换在骨位于原点时有问题，1.9.17 修复；
  - Magica Cloth 2、Dynamic Bone、Unity Cloth 都不可用（不在白名单、被强制转成 PhysBone，或顶点预算只有 50–200）；用 VRC Constraint 替代 PhysBone 最多吸收约 21%，而且受影响骨挂约束会关掉 AAO 的自动合并。
- **证据等级**：未实测（来自一个工程的文档调研，官方路线图等信息有时效）
- **失效条件**：VRChat 或 AAO 版本更新后要重新核对。
