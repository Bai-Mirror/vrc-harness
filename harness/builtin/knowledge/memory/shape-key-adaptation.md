# 形态键适配：跨工程的稳定结论

来自多个客户工程与历史工程的审查、修复和回放记录。每节写明适用范围与证据等级；只在一个工程成立的写成候选。

## Shape Changer 的 Delete 是删顶点，不是把键设成 100

- **适用范围**：Modular Avatar Shape Changer（在 MA 1.18.1 源码上核对；旧版本未逐一核）；所有用 Delete 给衣服让位的身体。
- **结论**：Delete 忽略 value，按「该形态键位移超过阈值的顶点」删掉或隐藏这些顶点，而不是把权重设成 100。常驻激活的 Delete 在构建期直接从网格物理删除顶点；随开关变化的 Delete 用 NaN 骨骼（LocalScale 动画为 NaN，图元被 GPU 裁掉）实现。BlendshapeSync 不传播 Delete——这是设计用法（删身体的胸，但保留匹配胸型的外衣）。
- **推论**：同一物体、同一键上同时登记 Set（如 60）和 Delete 时，Set 对已被删的顶点没有可见效果，面板数值不代表实际效果；「Delete 把脚烤成满高跟」「Delete 改形导致同步衣服错位」这类说法都不成立。
- **判据**：任何几何度量（穿模、贴合、包含率）都要单独报告被删顶点的数量——实测一个 Kaguya 工程袜子开时脚部 1189 个顶点被删，一个 Milfy 工程某状态下脚部 5109 个顶点里 1807 个（35.4%）不可用；不单列就会把「被删」当成「在衣服里」，或让连通区域被切碎。静态检查：同物体同键同时 Set 与 Delete 直接报出（两个历史工程各发现一例）。
- **证据等级**：多工程验证——顶点被删的现象在两个工程实测；语义细节来自 MA 1.18.1 源码判读。
- **失效条件**：MA 版本改变 Delete 实现时复核；Set/Delete 的选择本身会影响「脱掉后能否回退」，决定前写明。

## 多个 Shape Changer 写同一键：层级先序、后者覆盖

- **适用范围**：Modular Avatar Shape Changer 之间的冲突（MA 1.18.1 源码判读）；不含动画层直接写形态键的情况。
- **结论**：多个 Shape Changer 写同一个形态键时，按层级先序遍历，**后者覆盖**，不取最大值。Shape Changer 会自动恢复：构建时生成常驻的 `MA Shape Changer Defaults` 层记录网格原值，挂载物体停用即退出覆盖。所以「脱衣后身体不恢复」只会发生在厂商动画层或手写动画直接写形态键的地方。
- **判据**：枚举同一键的所有写者（跨服装、跨根），按层级先序预测胜者，再在构建产物或 Play 下渲图对账；动画层与 MA 反应层谁赢，静态读不出来，要在构建产物或运行态核对。开→关往返后比对权重，确认回退。
- **常见形态**：两双鞋都写脚型键且都能同时开（历史工程里同一脚型键在不同鞋上分别写 78 / 100、按套装写 70 / 80 / 100）；厂商滑块层与 Shape Changer 抢同一个键（脚型、胸型滑块非默认时换鞋）。
- **证据等级**：未实测——MA 1.18.1 源码判读；多写者现象本身在多个历史工程静态可见。
- **失效条件**：MA 版本变化；动画层参与时本条不能单独定胜负。

## 身体收缩键要挂在真正遮住那块身体的部件上

- **适用范围**：带多件可拆部件的整套服装；Milfy、Sio、Kipfel 工程中出现过；凡用收缩键（shrink / `*_OFF`）防穿模的素体。
- **结论**：收缩键的生效条件必须与「谁遮住这块身体」一致。挂在整套根上（只要选了这套就常驻 100）时，脱掉外套会腰腹缺块、光脚时脚部塌陷；挂在某件衣服上但它只负责一部分区域时，穿别的衣服也会误收（例：一件衬衫的肩部收缩键在穿其他衣服时仍生效，肩膀被收掉）。
- **判据**：对每个非零收缩键，列出「此刻可见、并覆盖该区域的部件」；没有覆盖件而键仍开着即缺陷。真序列测试：全穿 → 逐件脱 → 全脱，每一步读收缩键权重并近拍相应部位。实例：一套垂耳兔服装把 11 个收缩键（`Shoulder`、`Upper_arm`、`Elbow`、`Lower_arm`、`Chest_2`、`Spine_1`、`Spine_2`、`Ankle`、`Foot`、`Toe`、`Foot_heels`）挂在整套上，修后各键改由鞋、外套、上衣等覆盖件持有，全穿时读数与修前一致。
- **修法**：把整套级 Shape Changer 拆开，每条挂到覆盖该区域的件上；同一件有多个版本（如两版外套）时各自挂一份。
- **另一实例**：一个 Rurune 工程的一套服装把 8 个身体收缩键挂在根上，关袜时小腿塌成一条线；拆到覆盖件后修好。同一组件在交付用的面捕根上还曾被预制体覆盖删掉、导致失效——多根工程要逐根核对。
- **证据等级**：多工程验证——Milfy、Rurune 两个工程 Play 真序列修复并盲测，一个 Sio 历史工程静态发现同款服装常驻 11 个收缩键，一个 Kipfel 工程出现衬衫收缩键误收。
- **失效条件**：厂商已按部件挂好收缩键时无需改动；检测「衣服没了、收缩键还开着」的自动几何探针三次标定都没成功，目前只能靠上述枚举＋近拍。

## 平脚与高跟键要覆盖鞋袜的每一种可达组合

- **适用范围**：所有有脚型键的素体与会影响脚的服装（鞋、袜、靴、脚趾甲）。各素体的键语义不同，要分开查：Kaguya、Rurune 的默认脚是高跟姿态，写 `Foot_heel_OFF_____足_ヒールオフ` = 100 才放平；Milfy 默认是平脚，`Foot_heels` / `Foot_highheels` 负责抬跟；Shinano 系用 `Toe_heels` / `Toe_highheels`（两套命名出自不同厂商目录，同时开两双鞋会同时写 `Body_base`）。
- **结论**：厂商常把脚型键只挂在一件上（例：只挂在袜子上），菜单却能切出「穿鞋、脱袜」等组合；这时脚回到默认姿态，脚趾从包趾鞋头整段穿出。「厂商就是这么做的」只能说明谁在写，不能说明对不对。
- **判据**：按菜单枚举鞋 × 袜 × 其他影响脚的件的全部可达状态，每个状态读脚型键值并在 Play 下低机位、俯视近拍脚部；先按厂商展示图把鞋分成包趾、露趾、镂空。实例读数：一双包趾鞋修前脚趾 170 个顶点里 63 个穿出、包含率 2%，补键后 0 穿出、100% 在鞋内；一双厚底鞋没有任何平脚写者，补上后穿鞋 100、脱鞋 0；一双冬靴由靴上 Shape Changer 写 `Toe_heels` = 100。
- **修法**：给缺写者的鞋补同款 Shape Changer（可从同场景已正确的鞋上复制）；只穿丝袜时脚趾也可能穿出（一个工程把鞋上的 Shape Changer 复制到两件丝袜上才修好）；袜子 Delete 了脚部键时，要对照同穿的露趾或镂空鞋检查缺趾。
- **两个写者**：同一脚部键可能同时被鞋件 Shape Changer 和 FX 的脚型层写（一个 Milfy 工程就是这样，关鞋袜后脚仍收起）；先把写者列全，再决定由谁写。
- **证据等级**：多工程验证——Kaguya、Rurune、Milfy、Shinano 四个工程各自实测。
- **失效条件**：素体脚型键语义不同时逐素体复核；鞋底厚度与跟高不同，取值按鞋定。

## 衣物上的同名体型键必须跟随身体

- **适用范围**：会随胸型、体型滑块变化的服装件与贴身饰品（乳贴、衬衫、外套、领带、兜帽等）；在两个 Rurune 工程与一个 Kaguya 工程出现过。
- **结论**：厂商滑块驱动身体的胸型键，但服装件上带着同名键却无人同步（恒 0），胸型拉满时双乳整片穿出。另一种情况是件上干脆缺键（厂商乳贴只有 `Breast_Big(mizuki)`，没有 `Breast_small`、`Breast_big(limit)`），默认胸型下外浮 5.74 mm、拉满时错位 14.95 mm。
- **判据**：对每个可见服装件，列出身体被驱动的体型键；件上同名键必须与身体逐值相同；件上缺键时量「件 → 身体」的间隙 p50（修后应 ≤2 mm，实例修后 1.28 / 1.66 mm）。正面肤色像素可作辅助指标（实例 6822 → 837）。
- **修法**：件上有哪个键就同步哪个（MA BlendshapeSync，源为身体网格）；缺键时在 Unity 内按身体位移场给件烘焙新帧，再接 BlendshapeSync——一次在 Blender 离线副本上做的尝试偏了 71 mm，已弃用。件的某个键若应由装配方写（如内层衬衣在外套下的 `Parker_on`），要在生成器里显式登记，漏一行就会无人写。
- **证据等级**：多工程验证——两个 Rurune 工程与一个 Kaguya 工程各自修复并读回。
- **失效条件**：厂商已自带 BlendshapeSync 的件不要重复挂；自动「同名键跟随」检查只覆盖「件上有键但无人写」一种形态，查不出「件上缺键」和「键挂错件」。

## 按几何给身体形态键分类：姿态键与收缩键

- **适用范围**：在 Kaguya v1.06 与 Milfy 1.5.0 的 FBX 上离线标定（Blender 5.2）；其他素体要重标。
- **结论**：按键名字面规则分类不可靠（Kaguya 8 个键错 6 个）；要用刚体拟合：姿态键（脚尖下压的高跟脚型等）接近整块刚体旋转，残差小；收缩键是向内的非刚体位移，残差比接近 1。Milfy 的收缩键多数也带 13°–17° 旋转（`Toe` 为 4.6°），只看旋转角会误判，必须看残差比。
- **判据**：刚体拟合残差比 < 0.3 且旋转 > 5° → 姿态；残差比 ≥ 0.5 且归一内收 > 0.15 → 收缩；[0.30, 0.50) 为灰带，交人判。实测两簇都可分：Kaguya 姿态最大 0.199、收缩最小 0.982；Milfy 分别为 0.131 与 0.716。每具素体按「姿态簇最大与收缩簇最小的中点」可得本素体阈值（Kaguya 0.4418、Milfy 0.3067），操作上仍取保守带。
- **用途**：姿态键决定脚型与鞋的配合（按鞋定取值），收缩键只在对应部位被遮住时才该开。
- **证据等级**：多工程验证——两具素体、两个工程的 FBX 离线标定；分类结果与人工判断一致。
- **失效条件**：素体换版本或换素体时重标；灰带内的键不要自动归类。

## 形态键写者的六条静态检查（只出候选）

- **适用范围**：离线读场景与预制体（含预制体变体链与 `m_AddedComponents`）得到的「谁写哪个形态键」清单；在 14 个历史工程上跑过一遍。
- **结论**：静态检查能便宜地列出嫌疑，但**只出候选、不判对错**，对错要靠几何量距、构建期截获或人判。
- **判据（六条）**：
  - **K1 同键多写者**（只算配置型写者：Shape Changer、BlendshapeSync、ObjectToggle；动画片段里的写者跨状态本来就取不同值，全算进来会淹没候选）——14 个工程 312 条，其中值不同的 43 条才是冲突候选；
  - **K2 同一物体同键 Set 与 Delete 并存**（11 条）；
  - **K3 整套档位层与逐件部位层抢同一个键**（14 个历史工程为 0，但在一个 Milfy 工程与一个 Kaguya 工程里有真样本：厂商脚型层 4 档与服装 Shape Changer 抢键、整套片段与部位片段同键 32 例）；
  - **K4 收缩键挂在套装根上、目标是身体**（29 条；物件级宿主不一定是误报）；
  - **K5 脚型键归属**（写在袜上、鞋上还是判不了；取不到宿主真名时写「判不了」，不按文件类型猜）；
  - **K6 形态键目标值越界**（排除材质属性与非形态键路径，否则会把材质、拖尾、相机参数的合法值误报；14 个工程真越界为 0）。
- **做法**：扫描要沿预制体变体链递归到基础预制体（一次漏扫就是因为厂商服装的变体预制体没被解析）；Delete 写者在报告里排在前、不折叠。
- **证据等级**：多工程验证——14 个历史工程的扫描结果，K3 真样本来自两个客户工程。
- **失效条件**：胜负判定（谁最终生效）静态做不了，要看构建产物。
