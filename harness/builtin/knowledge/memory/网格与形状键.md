# 网格与形状键（装配相关）

跨工程的质量记忆。每节固定写适用范围、结论、判据、证据等级、失效条件；先列多工程验证的，后列候选。

## 脚部形态键分两类：姿态键守恒几何，删除类只给全包的鞋

- **适用范围**：带脚部形态键的素体（键名因素体而异）；给鞋、袜选脚型键，以及为每套服装写收缩键复核理由时。
- **结论**：姿态类（改变脚的角度，几何守恒）与删除／收缩类（删顶点或把体积缩到 0）代价完全不同。默认按鞋跟高度选一个姿态键，平底不上；删除类只在鞋**完全包住**那个部位时成立（长靴、高帮鞋），船鞋、乐福鞋、露趾凉鞋、任何露脚背的款式都不成立。收缩过头会把顶点折到一处，出现尖锥和细长拖丝；鞋不会跟着变，缩多了就是脚缩进鞋里「消失」。
- **判据**：选键前先问「这双鞋的跟有多高？对应的姿态档试过没有？」；施加键前后脚部包围盒长度变化 < 5%，体积或有效顶点数不减半；露趾、开口鞋上不出现删除类键。仍然穿模就改鞋（放大、加内衬），不回头删脚。
- **证据等级**：多工程验证（两种素体的工程上，收缩类被误用在露跟拖鞋、开口的船袜款鞋、高跟凉鞋上，改用姿态键后正确）。
- **失效条件**：鞋完全封闭（长靴、包头鞋）时缩脚是标准做法；素体没有姿态类键时，只能从鞋一侧处理。

## 收缩键挂错宿主的后果是单向的：盖它的件一关，身体还缩着

- **适用范围**：用 MA Shape Changer（反应式组件）实现的身体收缩；鞋、袜、袖套、衣身等能分别开关的部件。
- **结论**：Shape Changer 只在宿主物体激活时生效。收缩键挂在鞋上、整套根上或头像根级容器上，而真正盖住那一段的是另一件（例如袜子）时，关掉那件后身体仍然缩着：脚踝、小腿塌成细线，或塌成尖锥直插鞋口。关掉那件衣服的人正好在看那个位置，而只测「全穿」状态的检测一直报没问题。
- **判据**：收缩键影响的顶点，在每个开关组合下都要有可见衣物盖着；按覆盖表拆件后，「单关一件」渲图无塌陷；脚部要过全穿、只穿鞋、只穿袜、光脚四组合，光脚所有脚部键为 0。
- **证据等级**：多工程验证（两个工程、两种素体：一例厂商把 8 个收缩键挂在整套根上，一例全挂在低帮鞋上；拆到覆盖件后四组合读回正确）。
- **失效条件**：部件不能单独开关（只能整套一起开关）时，挂在整套根上不会出现这个后果。

## 用像素差或「画面整洁度」挑形态键，会系统性地选中删除类

- **适用范围**：用离屏渲图的整体统计量（像素方差、差分像素数、边缘数、整洁度）在多个形态键候选之间做选择，尤其是脚型键。
- **结论**：把脚缩掉就不可能穿出，所以删除类键在这类判据上分数总是最好；姿态键让脚相对鞋移动、改变的像素更多，分数反而更差。判据不是量错了，而是方向就是反的，会稳定地推荐最坏的选项。封闭鞋上缩脚是对的，判据也对；露趾鞋、绑带鞋、短袜上判据是反的。
- **判据**：自检问句「如果把被测物删掉，这个指标会不会变好？」会，就不能单独使用。数值只做初筛，每个候选都要看特写渲图判角度；配成对判据（没穿出＋没有白缩），并用光脚作对照组。
- **证据等级**：多工程验证（两种素体的工程：一例按方差选中的键把脚缩短 32%、体积近乎减半，而鞋是开口款；一例差分判据选中的组合渲出「有鞋没有脚」，正解的姿态键分数反而最差）。
- **失效条件**：判据量的是几何本身（包围盒长度、体积、最低点），或与「没有白缩」成对使用时，不受此影响。

## MA Shape Changer 的六条语义（按 MA 1.18.1 源码核对）

- **适用范围**：Modular Avatar 1.18.1 的 `ModularAvatarShapeChanger`；其他版本需复核。
- **结论与判据**：

| # | 语义 | 后果与可查问句 |
|---|---|---|
| C1 | `ChangeType` 只有 Delete=0、Set=1 | 序列化 JSON 里就是 0／1，别按面板文字猜 |
| C2 | Delete 删的是顶点，不是把键设成 100 | 同一物体同一键又有 Set（如 60）又有 Delete：两个字段各自合法，但 Set 作用的顶点已被删或隐藏，等于白设 |
| C3 | 多写者按层级先序（`GetComponentsInChildren` 的顺序），后注册者覆盖 | 两件压同一个键的衣服同开时，先按先序预测胜者，再渲图对账 |
| C4 | Set 随宿主物体停用自动恢复（反应式组件） | 「脱衣后身体不恢复」只可能出在动画层直接写形态键的那几处，不会出在 Set |
| C5 | 常驻 Delete 在构建期物理删顶点（`RemoveVertices`）；随开关变化的 Delete 在删除生效时把骨骼缩放设为 NaN 来隐藏 | 量删除区只能读编辑模式的原网格；可查问句：「量的这批顶点，在 Play 里还是原来那批吗？」 |
| C6 | 删除区按写者自己的 `m_threshold`（默认 0.01，网格局部单位）加图元级选择计算 | 不是世界坐标 0.1 mm，也不是「位移 > 0 就算」 |

- **证据等级**：单一案例（候选）（按源码核对，部分条目在工程中观察到）。
- **失效条件**：MA 版本变化时逐条复核。

## 形态键与贴合的几何量测：统一用 BakeMesh，真的量两端

- **适用范围**：编辑模式下量衣物到身体的距离、形态键施加前后的几何变化；Unity `SkinnedMeshRenderer.BakeMesh`。
- **结论**：
  - 几何来源统一：身体与衣物都用 `BakeMesh`（带当前形态键权重，读完还原），产出里写明几何来源（`geometry_source` 字段）；不要一边用 `sharedMesh` 原始顶点、一边用蒙皮后顶点——两种空间混用，距离没有意义。多帧形态键取满权重帧。
  - 之后要乘 `localToWorldMatrix` 时，必须 `BakeMesh(m, true)`（useScale），否则缩放 ≠ 1 的渲染器会被缩放两次。
  - 「键 0／100 两端」要真的把身体键设 0 烘一次、设 100 烘一次，再还原原值；不能拿「当前权重」和「当前＋100」冒充两端。
  - 衣物到身体的距离用最近距离的分位数（p50 等）表达。
- **判据**：量测记录写明几何来源、是否 useScale、两端的实际键值。
- **证据等级**：单一案例（候选）（来自一个工程的多轮验收）。
- **失效条件**：改用其他几何来源（如 GPU 蒙皮读回）时，要重新确认空间一致。

## 删除区与构建后网格：只能在编辑模式量，Play 里别换网格

- **适用范围**：用了 MA Shape Changer 的 Delete，或 NDMF／Avatar Optimizer 会在构建期改动网格的工程。
- **结论**：
  - 进 Play 或构建后，MA 已处理身体网格：常驻 Delete 物理删顶点，可开关的用 NaN 骨骼隐藏（MA 的 `ReactiveObjectPass`）；Play 里的 `BakeMesh` 量不到「本该删的区」。删除区按写者自己的 `m_threshold` 取，不自定阈值；写者挂在没有网格的容器上要报出来，不许静默跳过。
  - NDMF／AAO 构建后，渲染器的骨骼数组可能被重排，身体可能被合进 `$$AAO_AUTO_MERGE_SKINNED_MESH_n`。运行时把 `sharedMesh` 换成资产里的原网格，蒙皮就错了：量到的距离是 100 mm 量级的垃圾值，渲图甚至逐像素不变。
  - Play 里按名字找身体也可能失败（已被合并改名）。
- **判据**：比较「换网格前后」时，在编辑模式用场景里真实的骨骼做；只改形态键值的对照可以在 Play 里做。
- **证据等级**：单一案例（候选）。
- **失效条件**：工程既不用 AAO 的网格合并、也不用 MA Delete 时，Play 里的网格与编辑模式一致。

## Unity 形态键 API 的三个陷阱：索引不含 Basis、改帧只能整体重灌、按名字回填

- **适用范围**：Unity `Mesh` 的形态键 API（`AddBlendShapeFrame`、`ClearBlendShapes`、`SetBlendShapeWeight`），以及与 Blender 形态键之间的核对。
- **结论**：
  1. Unity 的形态键索引不含 Basis，比 Blender 的 shape_keys 索引小 1——跨工具核对按名字，不按索引。
  2. Unity `Mesh` 没有修改某个形态键已有帧的 API：只能 `ClearBlendShapes()` 后把**全部**键按原顺序（或新顺序）重新 `AddBlendShapeFrame`。
  3. 重灌后键的下标可能变，渲染器上的 `SetBlendShapeWeight` 与动画绑定都要按名字回填，不能按下标。
  另外，服装自带骨架导入后骨骼可能改名或合并，按骨骼名兜底匹配。
- **判据**：重灌前后逐键比对名字、帧数与帧权重；渲染器上的权重按名字读回一致。
- **证据等级**：单一案例（候选）。
- **失效条件**：Unity 提供修改单帧的 API 时，第 2 条不再成立。

## 面积阈值跨素体会失效：换算成顶点数，并报出被门槛丢掉的量

- **适用范围**：穿出检测、覆盖检测这类以面积、长度或顶点数为阈值的几何判据，跨工程或跨素体复用时。
- **结论**：阈值是在另一具身体上标定的；同一个 cm² 在不同的网格密度上不是同一回事。于是一个 0 可能表示「没有」，也可能表示「有，但没够到门槛」。
- **判据**：先问「这个阈值当初在哪具身体上标的？换到这具身体，它对应多少个顶点？」面积阈值换算成跨身体可比的量（例如「至少 N 个连通顶点才算一片」），或者至少把每顶点面积（`area_per_vert`）与「被面积门槛丢掉的分量数与总面积」一起输出——不让同一个 0 同时表示两种情况。判据里凡有「某类顶点直接跳过」的逻辑（`opening` 开口排除、删点排除），都要问：它会不会把一整片切成够不到门槛的碎块？
- **实例**：穿出面积门槛 `min_patch_area_cm2 = 0.5` 的初值按 Kaguya 标定（假设顶点间距 3–6 mm、脚趾出鞋 3–8 cm²）。换到 Milfy，脚趾区每个顶点只摊到约 0.0043 cm²，两只脚全部脚趾皮肤加起来才 11.34 cm²——「3–8 cm²」等于要求两脚 26%–71% 的脚趾皮肤同时以一块连通区域穿出，物理上不可能。于是脚趾实际穿出 14.86 mm 深、472 个顶点在鞋外，`patch_count` 照样是 0；据此撤掉了鞋的收缩键，脚趾在 Play 里戳出了鞋头。
- **证据等级**：单一案例（候选）（一次跨素体复用造成的真实漏报）
- **失效条件**：阈值已按目标素体重新标定，或判据本身以顶点数表达时。

## 遮挡射线判据：先剔除被测物自己的面，再验「该报」与「不该报」两侧

- **适用范围**：用射线遮挡量「闭眼时眼球露出多少」这类判据：沿视线方向对被测顶点打射线，统计被遮挡的比例。
- **结论**：被测物前面常有它自己的透明层（角膜、高光卡片），射线先撞上它，每个顶点都被判成「被遮挡」，判据恒为 0；而恒为 0 看起来永远像通过。
- **判据**：构建遮挡体（BVH）时剔除被测物自身的面（任一顶点属于被测簇就排除），只留眼睑与皮肤当遮挡体。判据成立的标准是它能分辨已知状态：成文时修正后睁眼露出 33.5%、`vrc.blink` 为 0.0%、单眼 wink 只闭一边（L = 0，R = 34.16）。只验「该报警」一侧会漏掉恒零判据。判完再问一句「这个零有没有余量」：再扫几档中间值（例如 blink = 0.6、0.7、0.8、0.9），厂商原网格与改后网格的曲线同步（0.9 档 4.31% 对 5.47%），才能下「闭眼没坏、不用补偿」的结论。
- **证据等级**：单一案例（候选）
- **失效条件**：被测物没有自身的透明覆盖层时第一步可省，其余照做。

## 未实测：跨网格比较遮挡率时，两边的遮挡体集合必须一致

- **适用范围**：在厂商原网格与改后网格（例如捏脸放大了眼睛）上分别计算露出率，再做比较。
- **结论**（早期经验记录，现行规程未收）：按「眼中心 32 mm 以内」取皮肤面作遮挡体时，厂商网格取到 1165 个面，改后网格只取到 926 个——眼睛变大，把皮肤挤出了选取半径——少了 239 个遮挡面，露出率被高估：一个闭眼键报 17.91%；半径放到 55 mm 后，真实值是 0.75%。判据坏了一次就说「没修好」，差点推翻了一个其实正确的修复。
- **判据**：比较之前核对两边遮挡体的面数，或按同一组面索引选取遮挡体；按半径选取时留足余量，并在报告里写出两边各取到多少个面。
- **证据等级**：未实测
- **失效条件**：遮挡体按固定面索引选取时不存在这个问题。

## 未实测：FBX 二进制自检要数带长度前缀的节点名，比例因子要读值

- **适用范围**：从 Blender 导出 FBX、覆盖素体之后，落盘进 Unity 之前的二进制自检。
- **结论**（早期经验记录；现行规程只写「计数与厂商原版比对」，没写怎么数）：FBX 二进制里的顶点与形态键数组是 zlib 压缩的，压缩数据里会随机出现任意字节序列，所以 `b.count(b"Lcl Scaling")` 这类裸字符串计数会被巧合命中污染，文件越大污染越多。一例原版 16.5 MB、新导出 27.4 MB：`Lcl Scaling` 的裸计数从 514 变成 550，看着像出了问题；按带长度前缀的数法，两边都是 0——全是巧合命中。
- **判据**：
  1. `UnitScaleFactor` 与 `OriginalUnitScaleFactor` 看**值**，应为 100.0：在字符串之后找 FBX double 属性的类型码 `D`，再用 `struct.unpack('<d', …)` 解出来。这一条最重要。
  2. 结构计数按「1 字节长度 + 名字」数，即数 `bytes([len(s)]) + s.encode()`：`Model`、`Geometry`、`Deformer`、`Pose` 与原版逐项相等（该例两边分别都是 291、681、4819、28）。
  3. `LayerElementSmoothing` 的裸计数应为 0（它本该一次都不出现，裸计数够用）；`BlendShapeChannel` 名字较长、不易巧合，裸计数一般够用，差异很小又拿不准时同样改用带前缀的数法。
  文件大小不是哨兵：正常导出可能比原版大 60% 以上。
- **证据等级**：未实测
- **失效条件**：改用完整的 FBX 解析库读结构时，按库给出的节点树计数即可。

## 未实测：顶点数有两个口径，Blender 拓扑顶点与 Unity 渲染顶点不能互比

- **适用范围**：比较同一网格在 Blender 与 Unity 两侧的顶点数，或比较工程里的件与新导入的对照件的顶点数。
- **结论**（早期经验记录，现行规程未收）：Blender 报的是拓扑顶点，Unity 报的是渲染顶点（在 UV 缝、法线断点处拆开），一例是 11548 对 12168，两者互比没有意义。同在 Unity 侧，对照件用的是新生成的默认 `.meta`、工程件用的是厂商调过的 `.meta`（`weldVertices: 1`、`normalSmoothAngle: 60`、`normalCalculationMode: 4`）时，差出的 1198 个顶点全是导入设置的差异；换成同一份 `.meta`，只差 2 个（0.016%）。
- **判据**：比较前先对齐口径：同一侧、同一套导入设置、同一种顶点定义；报告里写明比的是哪一种顶点。
- **证据等级**：未实测
- **失效条件**：无。

## 认身体网格：看蒙皮权重覆盖脚骨与躯干骨，不看名字与顶点数

- **适用范围**：工具要自动识别「哪个渲染器是身体」（同名键检查、穿出检测、身体被写键统计），而素体有多个名字像身体的网格时。
- **结论**：按名字（如 `Body`）或顶点数认身体会认错。成文时在两个同为 Kipfel 素体的工程上，工具把脸网格 `Body`（7539 个顶点，权重全在头与眼）认成了身体，真正的身体 `Body_Base`（5451 个顶点）被漏掉——统计出的「身体被写键」303/375 条全是表情键，结果全部作废。
- **判据**：候选网格（`Body_b`、`Body_base`、`Body` 等，大小写不敏感）里，蒙皮权重覆盖脚骨与躯干骨的才是身体；都不满足，再退回几何启发。可查问句：导出的身体路径是不是 `Body_base`、`Body_b` 这一类？被写到身体上的键是不是全是 eye、mouth 开头的表情键？是后者，就是认错了。
- **证据等级**：多工程验证（两个工程，但同为 Kipfel 素体；其他素体的命名方式未验证）
- **失效条件**：素体只有一个蒙皮网格，或工具已按骨权重识别身体时。

## 露趾还是闭趾：量脚部最前端与趾尖的前后差，并看有没有开口边界环

- **适用范围**：判断袜子或鞋在脚趾处是否开口，以决定脚甲要不要隐藏、脚趾收缩键挂不挂。
- **结论**：不要靠商品图或件名猜。成文时同一批几双袜子里只有一双是露趾的，名字与缩略图都看不出来。
- **判据**：量这件衣物脚部网格的最前端与素体趾尖的前后差（衣物前端落在趾尖之后，即露趾），同时检查衣物脚部网格有没有边界环（开口）。两项一致才下结论；不一致时渲一张强制显示脚甲的特写确认。
- **证据等级**：单一案例（候选）
- **失效条件**：无。

## 鞋靴默认不加脚型键：先测量现状，数据支持再改

- **适用范围**：Kipfel、Rurune 素体的换装头像；厂商没有要求平脚或抬跟的鞋靴。
- **结论**：没挂脚型键的鞋靴多数本来就贴合；给它们加平脚、下移或抬跟键，穿出往往反而变大。先测量，只有数据证明需要时才加。
- **判据**：
  - 量法：每双鞋全穿态的穿出斑块（三顶点都穿出的三角面，≥0.5 cm² 才计）＋真材质与红身体渲图；带正对照（把脚型键拉满应报警）。
  - 客户工程实测：Kipfel 的靴、靴加袜、乐福鞋、只穿袜均为 0，给靴或袜挂整脚下移键反而报 32.9 cm² 和 248 cm²；Rurune 的三套鞋靴均无斑块；另一 Rurune 工程里运动鞋现状 31.2 cm²、改平脚 50 时 32.9、100 时 81.6，现状最好，跟靴现状 0 斑块、压平更差。
  - 用户的一致决定：厂商没要求、也没穿模的鞋不改。
- **证据等级**：多工程验证（三个客户工程）
- **失效条件**：厂商说明书明确要求某个脚型键，或展示图显示平底鞋而素体默认为跟型时，按厂商要求做；只测了静态姿势，动态姿势未测。

## 形态键跟随「真正包住该部位」的那一件，而不是整套或任意一件

- **适用范围**：用 MA Shape Changer 或动画写身体收缩、脚型键的服装装配。
- **结论**：键挂在哪一件上，就只在那一件显示时生效。挂在整套根上会在部件单关后继续收缩身体；只挂在鞋上而丝袜也按该脚型建模，脱鞋后脚会从丝袜里穿出。
- **判据**：
  - 逐件问「它包住哪块身体、按什么形状建模」，键就挂在那一件上；多件共同覆盖时，按覆盖区域拆开（一例：袜子收膝、小腿、脚踝、脚背、脚趾；袖套收肘、前臂；连衣裙收肩；鞋只收脚趾）。
  - 验收：逐个部件单关，被它覆盖的身体区域应恢复，其他区域不受影响；鞋袜四种组合都读回脚型键。
- **证据等级**：多工程验证（Rurune 两处独立缺陷；Kipfel 的收缩键改挂到衬衫上后姿势扫描穿出消失）
- **失效条件**：厂商有意用整套收缩（例如整套一起穿脱、没有部件开关）时可以保留在根上，但要确认菜单里不存在能单关部件的开关。
