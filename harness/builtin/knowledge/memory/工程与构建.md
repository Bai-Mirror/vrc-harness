# 工程与构建：质量记忆（构建、测量与交付）

## 能编译不等于能用：交付缺陷集中在功能层

- **适用范围**：VRChat SDK3 头像改装工程的交付（Unity 2022.3 + VCC，Modular Avatar / NDMF / AAO），尤其是多套服装、带部位开关与轮盘的菜单。
- **结论**：交付后返工的缺陷几乎都在「能用」这一层（菜单点了没反应、形态键不跟随、轮盘档错位、包缺文件），不在编译层；只在编辑器里自查、由开发者自己验，会系统性漏掉这类缺陷。
- **判据**：一个多套服装工程的复盘里，15 个功能缺陷由客户在游戏里发现，编辑器里只主动查出 5 个。另有多个已交付工程同时待重交：一单 6 项缺陷；一单胸型不跟随与轮盘档错；一单厂商子菜单 9 个开关整体无效；一单总包缺 19 个文件。一次执行者自验 382 组全过，独立核查仍查出 5 个缺陷。对应的交付卡口依次是：冷解包编译 → 缺失项零命中 → 构建后菜单断言（期望由第二视角写）→ 上传后自测。
- **证据等级**：多工程验证
- **失效条件**：交付流程已在构建后产物上做全状态断言、且上传后自测的回传长期为零缺陷时，本条描述的漏检比例不再成立；卡口本身的有效性尚无多工程统计。

## 性能数字只认构建后克隆体上的文件快照

- **适用范围**：VRChat SDK3 头像的性能测量（SDK 面板、编辑期性能报告），使用 NDMF / MA / AAO 等构建期插件的工程。
- **结论**：SDK 面板与编辑期性能报告统计的是构建前的场景对象，决定上传结果的是构建后的头像。性能数字必须在构建后的克隆体上量，并能追溯到具体的报告文件。
- **判据**：同一头像 PhysBone 面板显示 520、构建后 497；一例构建后贴图内存 153.8 → 110.6 MB、贴图清单总量 313.4 → 242.5 MB，与编辑期读数不同。烘焙克隆可用 NDMF 的 `AvatarProcessor.ProcessAvatar(clone)`，不进 Play；它只跑 NDMF，不等于完整的 SDK 构建链。测量时在调用侧记录目标对象名；量完销毁克隆；日志里有多个 before 读数时引最后一次（一例 649.3 → 671.0 → 160.7 MB，真值 671.0）。
- **证据等级**：多工程验证
- **失效条件**：SDK 面板改为统计构建后的头像时，面板数可以直接采信；报告工具自带构建步骤并打印目标名时，调用侧记录可省。

## AAO Trace And Optimize 默认设置的实测收益

- **适用范围**：Avatar Optimizer 1.9 系列的 Trace And Optimize（默认设置），多套服装的 PC 头像。
- **结论**：默认设置对骨骼、形态键、蒙皮网格数有稳定的大幅收益；它不做网格简化，面数只在删除「永远关着」的渲染器时下降；贴图内存的大头来自 UV 重打包与单色贴图，不是压缩格式。
- **判据**：一例骨骼 758 → 588、形态键 536 → 157、蒙皮网格 64 → 51、面数 391,865 不变；一例蒙皮网格 105 → 82、骨骼 1526 → 1180、贴图内存 254.4 → 226.8 MB（再做三档分级到 116.4 MB，贴图项评级 VeryPoor → Poor）；一例面数 996,612 → 922,682（删掉 89,072 面永远关着的素体自带服装与发型）、贴图内存 671.0 → 160.7 MB。
- **证据等级**：多工程验证
- **失效条件**：AAO 大版本变化，或关掉 `optimizeTexture` 等默认项时收益结构会变（关掉后贴图收益明显减少是推论，未实测）。

## 超时的编辑器调用会被重发：动作必须幂等

- **适用范围**：通过编辑器桥（如 MCP 的 `execute_code`、`execute_menu_item`）远程调用 Unity 编辑器执行重活的自动化。
- **结论**：调用超时后会被重发，换成菜单入口同样会被重发；重发排在编辑器主线程当前任务之后执行。规避靠动作本身幂等，而不是换入口，也不是加一把「跑完就删」的锁。
- **判据**：一次依赖编译的 Apply 跑了 4 次；一次贴图分档菜单跑了 4 次，因代码有 `if (apply && plans.Count > 0)` 保护、第 2–4 次「改动 0 张」而没有损失。锁在 `finally` 里删除时，重发的请求在锁刚删掉那一刻整跑一轮（一个 14 分钟的任务连跑两轮，期间其它调用全部超时）。写法：`finally` 里**刷新**锁的时间戳而不是删除，冷却窗口从「跑完」起算；要有意重跑先手动删锁。可查问句：这个操作跑第二遍时，对已经做完的状态会怎么写？回滚用的日志与备份最容易被第二遍清空。
- **证据等级**：多工程验证
- **失效条件**：编辑器桥改为对请求去重、或重活全部改走批处理时，重发风险消失；幂等仍应保留。

## 重活不进单次编辑器调用：构建与预处理走批处理

- **适用范围**：Unity 2022.3 编辑器自动化，涉及完整构建、NDMF / VRCFury 预处理、耗时的测量或渲图。
- **结论**：任何单次可能超过约 20 秒的调用都算重活。完整构建与预处理一律走批处理（`-batchmode` 加本工程真实存在、可批处理的入口静态方法）、全机串行；只能在编辑器里做的测量或渲图挂 `EditorApplication.delayCall`，调用立即返回、结果写报告、开头查单飞锁、外部轮询完成标记。
- **判据**：在单次调用里同步跑 `AvatarProcessor.ProcessAvatar(克隆)` 时，NDMF 单个 pass 耗时 29–51 秒，请求超时被重发，日志里出现同一段源码重叠执行（报告文件被同名重写），随后在 `Baselib_ThreadLocalStorage` 断言 → FMOD `AudioManager::systemCallback` → `profiler_begin` 处 SIGSEGV。`delayCall` 只让调用尽快返回，不能消除构建期崩溃。可查问句：是不是完整构建或预处理？是就批处理；否则确认必须在编辑器里做且超过 20 秒，才挂 `delayCall`。
- **证据等级**：多工程验证
- **失效条件**：编辑器桥支持真正的异步任务与请求去重时，可改用其任务机制；批处理入口不存在时记阻断，不退回交互编辑器里补跑。

## 候选：客户交付总包用 store ZIP，存档件用 7z/LZMA2

- **适用范围**：Unity 头像工程的客户交付总包，以及交付后的工程存档。
- **结论**：两种产物用途不同，不能混用。交付总包是「工程 zip ＋ 素材 zip ＋ 追加素材 ＋ 说明」，内层已是 zip，总包用 store（`7z a -tzip -mx0`）；存档件用 7z/LZMA2，同一份源比 zip/deflate 多省约 8.5%（deflate 对 Unity 工程几乎无能为力）。交付总包放进存档目录，也不因路径就改成 7z。
- **判据**：总包大小 ≈ 三个成员之和 ＋ 几百字节头；交付目录里除总包外没有散件；`7z t` 退出码为 0（不要加 `-bso0`，它会吞掉判定行）；追加素材在总包层与素材 zip 内各留一份是刻意的重复。存档后删本地源之前，必须对存档位置里的那一份跑 `7z t`，不是验打包前的源。LZMA2 每线程约占 500 MB 内存，并发线程数 ≈ 可用内存 ÷ 0.5 GB，再往上加会换页、吞吐断崖式下降。
- **证据等级**：单一案例（候选）——压缩率与每线程内存各只测过一次。
- **失效条件**：工程内容构成变化很大（例如大量已压缩的媒体文件）时压缩率差异会变；7z 版本变化时每线程内存需重测。

## 候选：交付工程在 Windows 上的可用性判据

- **适用范围**：在 Linux 上制作、交给在 Windows 上用 VCC 打开的客户的 Unity 工程。
- **结论**：交付或归档前，按一组可机器检查的判据确认工程在 Windows 上能原样打开、还原依赖并编译。
- **判据**：非法文件名、只差大小写的重名、路径长度超过 259、符号链接、`file:` 与 git 依赖，全部为 0；解包后 batchmode 编译 0 错误。脚本里调用外部程序时，路径含日文等非 ASCII 字符就用参数列表传（如 Python `subprocess` 传 list），不经 shell，否则会被编码打散。
- **证据等级**：单一案例（候选）——这组判据在一个工程的归档中使用过。
- **失效条件**：Windows 启用长路径支持且客户环境确认开启时，路径长度一项可放宽。

## 未实测：Play 前要隔离全部预处理入口

- **适用范围**：需要在 Play 里测量已构建头像（菜单导出、状态扫描）的场景，工程装有 NDMF（以 1.14.3 为准）与 VRCFury。
- **结论**：进 Play 不是构建入口，它会触发 NDMF、VRCFury 等 Play 期预处理；CPU 高或能轻量调用都不能证明没有重触构建。Play 测量只在已加载持久化构建产物、且全部 Play 预处理入口都已隔离的会话里做；前提缺一项就记 `blocked` / 未测。
- **判据**：NDMF 保存并幂等设 `nadena.dev.ndmf.config.Config.ApplyOnPlay = false` 后读回；`ApplyOnBuild` 是独立开关，完整构建要启用；菜单 `Tools/NDM Framework/Apply on Play` 是翻转操作，不能盲目重发。VRCFury 经 `PlayModeTrigger` 调完整 SDK 链，开关读 `EditorPrefs.GetBool("com.vrcfury.playMode", true)`：先记下该键是否存在与旧值，再临时设 false 并读回；EditorPrefs 是同一用户共享的配置，会影响其它编辑器会话。Av3Emulator 与工程自定义的 Play 回调也要逐一核实。NDMF 默认 `Packages/nadena.dev.ndmf/__Generated` 在退出 Play 时清理，VRCFury 进 Play 前也清临时资产；`ManualProcessAvatar` 虽有持久目录，仍只跑 NDMF。`warmup_frames` 只是等帧。出现新的预处理日志就停止测量、记未测。会话结束按快照还原全部开关（原键不存在就恢复为不存在）与 `legacyClampBlendShapeWeights` 等设置，逐值读回。
- **证据等级**：未实测——来自源码核验，整套流程未实跑验收。
- **失效条件**：NDMF / VRCFury 的 Play 钩子或设置名变化；或已有经过验收的「批处理产物 → 免重构建 Play」通用流程。

## 候选：构建超时不等于构建失败

- **适用范围**：由外部进程或编辑器桥触发、设有超时的 Unity 头像完整构建与 NDMF 预处理。
- **结论**：超时后构建可能仍在运行并继续写出产物；超时先查日志与完成文件，不重发，也不在交互编辑器里补跑。
- **判据**：一次编辑器桥构建超时后仍在运行，最终生成约 445 MB 资产。做法：构建一律批处理、全机串行，把阶段、错误与最终判据写进文件；单独跑 `ProcessAvatar` 只跑 NDMF，不等于完整 SDK 链；临时克隆在测量与持久化完成后销毁；本次改动过的设置按会话前快照还原并读回；引用临时生成目录的克隆不能当作可跨会话复用的成品。
- **证据等级**：单一案例（候选）
- **失效条件**：构建器提供可靠的完成状态与「超时即取消」语义时，可按其状态判定。

## 候选：编辑器开着时不要从外部改写已打开的场景文件

- **适用范围**：Unity 2022.3 编辑器开着、装有 NDMF（带预览代理）的工程。
- **结论**：编辑器打开的 `.unity` 被外部改写（哪怕只改一行）时，Unity 会重导场景并连带重建 NDMF 预览代理，随后主线程可能不再响应。要改派生字段（如 `RenderSettings.m_IndirectSpecularColor`）就在编辑器里改完再存，或关掉编辑器后再改文本。
- **判据**：同一工程两次卡死：编辑器桥连续 `Command TCS timed out`，SIGTERM 无效，只能 SIGKILL。卡死判据：CPU ≈ 0、`Library/ArtifactDB-lock` 的时间戳不再变化、编辑器桥连续 3 次超时，满足即停手、报 `CRASHED`。兜底：SIGKILL → 删 `Temp/UnityLockfile` 与编辑器桥的状态文件（如 `~/.unity-mcp/unity-mcp-status-<哈希>.json`）→ 重开。退出 Unity 前先读 `scene.isDirty`，否则可能卡在保存对话框。
- **证据等级**：单一案例（候选）
- **失效条件**：Unity 或 NDMF 版本变化后重导行为不同时需复测。

## 候选：测量工具改过的渲染器状态要从磁盘重载复原

- **适用范围**：在编辑器里截图、测量的工具，它们会在内存中关闭渲染器或改动物体状态。
- **结论**：只比层级摘要（路径、`activeSelf`、位置）会漏掉没恢复的 `Renderer.enabled=false`，下一个存盘的任务就会把它写进场景。只读类任务收尾前用 `EditorSceneManager.OpenScene(路径)` 从磁盘重载；改场景的任务开工第一步也先重载，再动手。
- **判据**：一次漏恢复后，场景被写入 735 条 `m_Enabled=0`。恢复核对要含 `activeSelf`、`Renderer.enabled`、引用与设置差异；有用户未保存的改动时，不能直接重载或丢弃。
- **证据等级**：单一案例（候选）
- **失效条件**：测量改在隔离的构建副本上进行、不回写源场景时，风险降低，但同一副本上的后续测量仍受影响。

## 候选：构建中的原生崩溃按崩溃线程栈归因

- **适用范围**：Linux 上交互运行的 Unity 2022.3 编辑器；远程桌面的 X 只挂核显、Vulkan 走独显向核显窗口呈现的环境。
- **结论**：构建中崩溃，先看崩溃线程与调用栈，不按「第几轮必崩」凑规律；不同的栈是不同的原因。
- **判据**：在上述环境中，两次崩溃的线程是 `UnityGfxDeviceW`：`VKWindow::Reshape → GfxDeviceVK::AdjustPrimarySwapChain → … → libnvidia-glcore`，即窗口改尺寸时 Vulkan 重建交换链、在 NVIDIA 驱动里崩溃；第二次发生在重启后的第一轮，「第三轮必崩」的说法已被推翻。另一次崩溃的栈是 `Baselib_ThreadLocalStorage` 断言 → FMOD `AudioManager::systemCallback` → `profiler_begin`，发生在同一段代码因重发而重叠执行之后，是另一个原因。
- **证据等级**：单一案例（候选）——只在一种主机环境中观察到。
- **失效条件**：换图形 API、显示环境或驱动版本后需复测；批处理（无窗口）运行时第一种原因不适用。

## 候选：编辑器桥执行代码的两个编译与拦截坑

- **适用范围**：通过编辑器桥（如 MCP 的 `execute_code`）执行的 C# 片段。
- **结论**：两类错误与执行逻辑无关，却会让片段编译失败或被拦下。
- **判据**：`Object` 与 `System.Object` 有歧义，一律写 `UnityEngine.Object`；`File.Delete` 与 `FileUtil.DeleteFileOrDirectory` 会被桥的安全检查拦截，删锁文件这类操作要显式带 `safety_checks=false`。
- **证据等级**：单一案例（候选）
- **失效条件**：换用别的编辑器桥，或桥的安全检查规则改变。

## 候选：审查工具读回的数值口径与请求模板

- **适用范围**：AvatarAudit 类的状态扫描与菜单导出工具（请求文件驱动、结果写 JSON）。
- **结论**：读工具产出前先确认它的口径：数值精度、断言中止条件、驱动方式与输出位置，都可能让结果看起来对、实际错。
- **判据**：产出 JSON 的参数值按 6 位小数回显（`AuditIO.cs` 的 `0.######`），从产出反推请求要重算精确分数。回读断言遇到被钳位或被参数驱动器合法改写的参数，会让整批 aborted，读 `audit.log` 找是哪个参数。状态扫描会核 `Assets/AvatarAudit/VERSION` 里的审查源码哈希，与部署的源码不一致就拒跑；审查源码正在改动时，从版本库已提交的版本部署，否则半成品编译失败、编辑器桥起不来。复制旧请求当模板时，`sequence` 里每个步骤自带的 `out` 不会被顶层 `out` 覆盖，要逐步改写：一例只改了顶层 `out`，6 个步骤把旧产物原地覆盖，新目录里只剩 `audit.log` 与 `sequence_status.json`。宁可每次用脚本现生成请求。
- **证据等级**：单一案例（候选）
- **失效条件**：工具的输出精度、断言策略或请求格式改版。

## 未实测：审查工具在 Play 中的入口、请求字段与完成判据

- **适用范围**：AvatarAudit 的状态扫描（`AuditStateDriver`）与菜单导出（`AuditMenuDump`），两者都是 `RequiresPlayMode=true`。
- **结论**：这两个工具只能在 Play 中跑；入口不会替你隔离预处理，也不会替你判完成，工具报 `done` 不等于测到了东西。
- **判据**：入口是 `AvatarAudit.AuditRunner.RunRequestFromMenu()`（菜单 `Tools/AvatarAudit/Run Request`），读 `<工程>/Library/AvatarAudit/request.json`；`auto_play:true` 只调用 `EnterPlaymode()`、不隔离预处理，请求应明确写 `auto_play:false`；`sequence` 依赖编辑器帧泵。无界面的 `AvatarAudit.AuditBatch.ExportInventory`（界面入口 `Export Part Inventory`）只打开场景、做部件盘点、退出，跑不了状态扫描与菜单导出；把异步菜单方法直接塞进批处理入口，也不会自动获得「等 Play、取结果、失败退出」的流程；只测某个固定控制器一层的测试、只烘焙 NDMF 的测试，都不能代替完整预处理与状态扫描。请求字段：菜单导出 `"tool":"menu"`、`avatar`、`out`、`auto_play`、`warmup_frames`；状态扫描 `"tool":"state"`，另有 `ensure_gm`、`version_check`、`reset`、`states`。先跑菜单导出，状态扫描的参数名取自同一产物的菜单导出。触发后轮询各自的 `status.json`：状态扫描要 `state=done`、版本戳通过、`states.json.gm_controlled=true` / `driver=gesture_manager`，并核状态数、回读断言与警告；菜单导出要核菜单、描述器、参数存在、警告与未声明参数，不能只看 `done`（SDK 字段缺失时也可能写出空结果）。默认态请求只作入口冒烟。
- **证据等级**：未实测——入口与字段来自源码核验，「构建产物 → Play 测量」的整套衔接未实跑验收。
- **失效条件**：审查工具改版（入口、字段或 `RequiresPlayMode` 改变）。

## 构建被中止：先筛 Error 严重度，再按嫌疑顺序查

- **适用范围**：VRChat SDK 构建或进 Play 时弹出「Preprocess Callback Failed / BuildFrameworkOptimizeHook reported a failure」，SDK 不说是哪一条（NDMF 管线的工程）。
- **结论**：别从最显眼的那条警告开始猜。NDMF 的报告分 Information、NonFatal、Error 三级，只有 Error 会中止构建；NonFatal 的警告（例如 AvatarPoseSystem 报「PhysBone 超过 256」）根本不是阻塞源——一例为这条 NonFatal 折腾了很久，还写了硬合并工具想把数量压下去，全是无用功。
- **判据**（按顺序）：
  1. 日志里筛 `Error Reported` 那一行。
  2. 查单例型组件有没有挂重复。很多 NDMF 插件只允许挂一个，多了会在自己的 pass 里抛 `InvalidOperationException` 中止。症状极具迷惑性：该插件该生成的骨骼、菜单、参数全都没生成；后面 AAO 又抱怨「检测到未知的组件类型」（没人处理它，组件残留到了后面的 pass）；异常可能是日文、被 NDMF 吞进 `Error Reported`，控制台上并不显眼。一例就是场景里挂了两个 AvatarPoseSystem。
  3. 查本工程自己加的优化组件。AAO MergePhysBone 配错会报 Error 直接中止；校验要看每个目标 PhysBone「有效根」的父对象，不是组件所在物体的父对象——按后者判，坏配置会全部被判成正常。顺带扫 MA MergeAnimator 的空引用，以及空转、重复的 PhysBone。
  4. 查插件硬编码的 GUID 能不能解析：插件用 `AssetDatabase.GUIDToAssetPath("…")` 定位自己的目录，素材若是手工拷进 Assets、文件夹 `.meta` 的 GUID 被重新生成，就会解析不到，随后 `Instantiate(null)`。征兆是插件行为异常、Console 却不报缺资源，看起来像插件自己的缺陷。
  5. 编辑器调用全部超时：先确认是不是被模态弹窗挡住了，别以为编辑器桥挂了。
  6. 编译不过：这不是 NDMF 的问题，按编译判据查（程序集 dll 在不在、多新）。
- **证据等级**：多工程验证（各步骤分别来自不同工程的构建中止）
- **失效条件**：NDMF 改变严重度分级或报告格式时，第 1 步的筛法要跟着改。

## 编译错误会让不相干的插件一起静默失败：先清编译错误再查插件

- **适用范围**：构建时多个互不相关的插件同批抛 `NullReferenceException`（例如服装管理类插件与面捕量化插件一起炸）。
- **结论**：工程里只要有一个脚本编译不过，编辑器程序集就是坏的，`AnimatorState.AddStateMachineBehaviour<T>()` 会静默返回 null、不报错，于是所有往动画层里添加 Parameter Driver 的插件同时抛 `NullReferenceException`。
- **判据**：先清编译错误，再查插件。编译是否成功看程序集 dll 在不在、时间戳多新（厂商自带程序集的错误要点名查它自己的 dll），不数日志里 `error CS` 的行数。
- **早期记录（未实测）**：一个为切换场景临时写的小工具用了不存在的公开 API（`EditorSceneManager.ClearSceneDirtiness`，Unity 2022.3 不公开），编译错误恰好覆盖了有人点上传的那一刻：前两次上传都好，加了这个脚本之后那次就挂。由此两条做法：往别人正在用的工程里加临时脚本，加完立刻确认编译通过再离开；排查间歇性构建失败时，先按日志行号把「编译错误出现的时间」与「失败那次构建的时间」对齐。
- **证据等级**：单一案例（候选）
- **失效条件**：无。

## 进 Play 后编辑器调用全部超时：先看有没有模态对话框

- **适用范围**：进 Play 之后，通过编辑器桥（如 MCP for Unity）发出的调用连续超时，Unity 日志里是 `MCP-FOR-UNITY: Command TCS timed out (N consecutive)`，CPU 掉到 0。
- **结论**：多半是一个模态对话框在等人点，编辑器主线程被挡住，不是桥挂了。一例：VRCFury 在测试构建时发现参数超限（342/256，压缩后仍有 291），弹出「would have failed to upload」的单按钮警告（成文时的版本在 `ExceptionService.cs` 里无条件调用 `DisplayDialog`），主线程被挡；只要参数没砍到 256 以下，每次进 Play 都会弹。
- **判据**：截屏，或枚举 Unity 进程的可见窗口，确认有没有对话框。处理：场景已存盘、且没有人在用这个编辑器时，按 PID 结束该 Unity 进程（不要用带路径的 `pkill -f` 模式，它可能匹配到发起命令的 shell 自己），并还原被 Play 改写的 `ProjectSettings.asset`；否则交回人。根治是把参数砍到 256 以内；自动化会话可以用一个只拦截单按钮对话框的开关启动。
- **环境**：成文时在 Linux 宿主上，没有可用的界面自动点击工具，点不掉对话框；有这类工具的环境可以另行处理。
- **证据等级**：单一案例（候选）
- **失效条件**：编辑器桥能自己检测并报告模态对话框时，直接读它的报告。

## 旧存档能不能删：按路径、大小、CRC 三元组分三类判

- **适用范围**：清理旧的 Unity 工程存档（7z 包），判断某个旧包能不能删。
- **结论**：只比文件数不算数。`7z l -slt` 会列出每个文件的 CRC32，不解压就能比较 `(路径, 大小, CRC)` 三元组。
- **判据**：分三类：
  1. 完全重合（0 缺失、0 不同）→ 可删；
  2. 差异只在可再生物（`Library/`、`Assets/*__Generated/`、`Packages/*.temp/Builds/`、插件升级后被删掉的旧版源码）→ 可删；
  3. 有独有的非再生内容 → 先弄清那是什么。一例「副本」里有 7 个材质比新包更新，看着像丢了活；比对出来是这 7 个材质被批量换成 `VRChat/Mobile/Toon Standard`（着色器 GUID `e765db0afa7ecfc44ade2e4e2491f65a`）、渲染队列钉成 2000——那是一次失败的移动端转换，不是要保的内容。
  存档落到目标位置后，对目标位置的那一份跑 `7z t`；删源之前必须验它，而不是验打包前的源。
- **证据等级**：单一案例（候选）
- **失效条件**：存档不是 7z 格式时，换用该格式能列出逐文件校验和的命令。删存档属于不可逆操作，仍需人确认。

## 同版本 lilToon 的着色器文件两边不同：是它按渲染管线自改写

- **适用范围**：比较两个工程里同一版本的 lilToon（迁移依赖、合并存档、判断包有没有被改过）时。
- **结论**：同为 lilToon 2.3.2 的两份拷贝，有 5 个着色器文件内容不同，而且两边互有新旧——那是 lilToon 自己按渲染管线改写 `#pragma skip_variants`（`Editor/CurrentRP.txt` 是它的记号），导入时会自动重写。拷哪一份都行，不要当成「包被污染」去追。
- **判据**：差异只落在着色器文件的 `skip_variants` 相关行、且包内有 `CurrentRP.txt` 时，按自改写处理；差异落在别处，才当作真改动去查。
- **证据等级**：单一案例（候选）
- **失效条件**：lilToon 改变这套自改写机制时。

## 未实测：幂等重跑的三个盲区——去重守卫、残值与检查的位置

- **适用范围**：会被反复重跑的装配、生成与写值脚本（挂配饰、写捏脸值、改菜单档位、换材质套）。
- **结论**（早期经验记录，现行规程未收）：
  1. **去重守卫要查物件的最终父节点**。「先在临时父节点下 `Find` 旧件并删除 → 实例化 → 之后改父到手指骨」这种写法，下次运行时旧件已不在临时父节点下，`Find` 返回 null，于是每跑一次多留一个副本。一例一只手的无名指上叠了 4 枚一模一样的戒指、另一只手 2 枚；同一脚本里不改父的件没有重复。
  2. **回读要查「没写的是不是 0」**。写值脚本只管写清单里的项；清单删掉一条后，上一轮写进去的值原地留着，而回读只对着当前清单查，条条都对。一例清单 14 条、回读 14 条全对，渲图时顺手打出「非零形态键 18 条」才露馅，多出的项里恰好有委托方明确要求去掉的那一条。回读要遍历整个目标对象（全部形态键、参数、材质槽），断言「非零项集合 = 清单 ∪ 厂商出厂非零值」；厂商出厂值单列白名单复位，不一律清零（例如 Milfy 出厂的 `mouth_Λ=70`、`mouth_narrow=45` 是设计好的静息口型）。
  3. **只在第一次运行上通过的自检证明不了幂等**。一例生成脚本「先删再建」材质，再按槽里现有材质的名字重新挂载，挂载时还跳过 null 槽（`if (ms[i] == null) continue;`）。第一次运行时资产还不存在，自带的「空材质槽」检查报 0；第二次运行删掉了场景正引用着的那一份，GUID 变了，槽里的名字也已改过、匹配不上，一处都没挂回去，整脸整身洋红才暴露。挂载按「物体名 + 槽序号」显式指定，不按槽里现有材质的名字匹配；资产已存在就原地改，不删了重建。
- **判据**：脚本连跑两次，物件数量与非零项集合都不变，才算幂等。可查问句：第二次跑的时候，第一次的产物在哪、谁在引用它？上一次留下的东西，这一次会不会被清掉？
- **证据等级**：未实测
- **失效条件**：无。

## 未实测：预处理中止时量到的数不作数；收到头像包先扫缺失脚本

- **适用范围**：依赖构建产物的读数（性能统计、参数审计）；接收别人发来的头像工程或 `.unitypackage`。
- **结论**（早期经验记录，现行规程未收）：进 Play 时若弹出「Preprocess Callback Failed / BuildFrameworkOptimizeHook reported a failure」，说明 SDK 预处理中止了，此时量到的性能与参数数字都不作数。常见根因是丢失的脚本引用（控制台成排的 `The referenced script on this Behaviour is missing`），而它往往来自「`.unitypackage` 装不下 VPM 包」：包里只有 `Assets/`，VRCFury、AAO、MA 这些插件住在 `Packages/`。
- **判据**：先确认这一轮构建没有中止，再量。收到包先扫缺失脚本：拿工程内全部 `.meta` 的 GUID 建集合，再扫预制体与场景里的 `m_Script: {fileID: …, guid: …}` 求差集；认不出是哪个插件时按序列化字段名认，出现 `vrcfuryVersion`、`somethingIsBroken`、`config`、`content` 的就是 VRCFury。反过来，自己交付时把依赖包清单单独写进说明。
- **证据等级**：未实测
- **失效条件**：无。

## 每次跑完 Unity 都要核对的副作用清单

- **适用范围**：Unity 2022.3 + VRChat SDK3 + lilToon 的头像工程，批处理或带界面编辑器会话之后。
- **结论**：打开、导入、进出 Play、批处理保存场景都会改动与本次任务无关的文件；提交或交付前必须逐项核对并还原，让差异只包含本次改动。
- **判据**（客户工程里反复出现的项）：
  - `ProjectSettings/lilToonSetting.json`：首次打开时 lilToon 启动钩子把 `LIL_FEATURE_*` 改成 true（设计行为，不影响上传包）；
  - `ProjectSettings` 的 `legacyClampBlendShapeWeights` 0→1（VRChat SDK 初始化时改写，会截断超过 100 的权重）与 iOS `m_Automatic` 0→1；
  - 场景文件的 `m_IndirectSpecularColor`（批处理保存场景时重算）；
  - `Packages/packages-lock.json`（添加 git 依赖后被改写）；
  - 自动化工具的状态文件（例如构建状态 JSON 被 Unity 启动改写）。
  - 反过来也要查漏交：新建的脚本或资产必须连同 `.meta` 一起提交（一个工程出现过只提交 `.cs`、漏了 `.meta`）。
  - 自查方法：会话结束后看版本控制差异，除本次改动外只允许出现上面这些，并逐项还原。
- **在 Harness 流程里**：执行方不开 Unity、不提交；这份清单用于判读 Runtime 产物与交付副本的差异：清单内的改动归为已知副作用写进诊断，清单外的改动写明证据交人。
- **证据等级**：多工程验证（六个客户工程）
- **失效条件**：插件或 SDK 版本变化可能新增或去掉某项；出现清单外的改动时，先查来源再决定还原还是提交。

## 形态键实测前后记录 clamp 开关

- **适用范围**：读形态键权重、渲染形态键效果的实测。
- **结论**：`legacyClampBlendShapeWeights` 为 1 时权重被截断到 100，实测结论可能随之改变；这个开关会在会话中被 SDK 改写。
- **判据**：实测报告写明开关的前后值；实测中出现过大于 100 的权重时，必须在开关与工程提交值一致的条件下重测。工程提交值为 0。
- **在 Harness 流程里**：执行方读 Runtime 的实测报告时核对其中记录的 clamp 值，与工程提交值不一致的结论标为待复测。
- **证据等级**：多工程验证（两个客户工程出现过改写）
- **失效条件**：SDK 不再改写该开关后可以放宽，但仍建议记录。
