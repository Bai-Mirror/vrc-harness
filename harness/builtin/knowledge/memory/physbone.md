# PhysBone：硬规则、互动、预算与降数

官方文档整理（VRChat SDK 3.10.4 时期）加上两个工程的降数实践。官方条目在工程里没有逐条实测的，标「未实测」。

## PhysBone 硬规则：根、约束、动画与嵌套

- **适用范围**：VRChat SDK 3.x 的 VRCPhysBone（按官方文档整理，SDK 3.10.4 时期）。
- **结论**：
  - **根骨只能旋转、不能平移**；人形骨（Head、Neck 等）不能当 PB 根，要复制一根骨当根。需要「整段滑出」时，在前面加辅助根，用可拉伸的段实现。
  - **同一物体上不能同时挂约束和 PhysBone**，约束放到父物体上。
  - **PB 的属性不能被动画修改**；唯一办法是改完属性后把组件关掉再打开，官方不保证一直有效。所以「切换时临时调高 Immobile / Pull」这类做法不可行。
  - 链内任何骨（包括根）要吃动画，必须勾 **Is Animated**；单骨链或只有一层子骨的链必须设 **Endpoint Position**。
  - 单个组件最多管 256 个变换；SDK 3.8.0 起 PB 与碰撞体按层级决定执行顺序，最多嵌套 8 层；头像上最多 4 个全局碰撞体。
  - **Version 1.1** 新增 Max Squish、Stretch Motion 与 `_Squish` 参数；Gravity 改为「静止时朝上/朝下转动的比例」且需要 Pull 为正才生效，Stiffness 改为「保持上一帧朝向的比例」——从 1.0 升到 1.1 要重调 Gravity 与 Stiffness。Stretch Motion 为 0 时只有抓取和碰撞才会拉伸或压缩。Max Stretch 是原骨长的倍数。
  - **Limit 远比碰撞体省**（官方原话 far more performant）；Polar 有额外开销。Radius 同时用于碰撞与抓取判定。Immobile Type 为 World 时只抵消场景里的位移，动画和 IK 照常生效。
- **判据**：装配后逐条对照；需要动画驱动的锚点先确认它不是 PB 根本身。
- **证据等级**：未实测——官方文档整理，部分条目在一个饰品工程的设计中被引用。
- **失效条件**：SDK 版本更新时以官方文档为准复核。

## PhysBone 互动权限与参数同步

- **适用范围**：允许抓取、摆姿势、碰撞的 PB 饰品与头发（官方文档与社区资料，SDK 3.10.4 时期）。
- **结论**：
  - Allow Grabbing / Allow Posing / Allow Collision 都能分「自己 / 他人」。用户侧互动模式默认 **Friends**，**双方都必须允许**才能互动；陌生人要互动，佩戴者得改成 Everyone 或对个人单独允许。
  - `_IsGrabbed`、`_IsPosed`、`_Angle`、`_Stretch`、`_Squish` 在本地和远端都各自计算（两端都跑 PB），**不需要放进同步参数表**、不占同步位；抓取与摆姿势本身由 PB 组件联网同步（官方正文没写实现与延迟，属推断）。
  - `_Stretch` 在加载、传送、快速移动时会误报：用它驱动效果时要用 `_IsGrabbed || _IsPosed` 门控，并把 Stretch Motion 设 0。用 PB 参数驱动动画时，被驱动的动画不能反过来移动链根，否则形成反馈回路。
  - 旁观者把最低显示性能等级设得比头像评级高时，全部 PhysBone、PB 碰撞体与 Contact 会被移除；链子停在建模姿态——**静止造型本身必须好看**。PC 默认最低显示等级是 Very Poor（即默认全显示）。
  - 被别人摆住的 PB 会一直停在那个姿势；给互动饰品留逃生口（关掉物体配合 Reset When Disabled 归位，或加超时复位）。
- **判据**：交付说明写清「陌生人互动需把模式改为 Everyone」；互动饰品在两台客户端上实测抓取一致性（官方未写延迟）。
- **证据等级**：未实测——官方文档与社区资料整理，一个饰品工程据此设计，Play 实测未完成。
- **失效条件**：VRChat 客户端或 SDK 行为更新时复核。

## PhysBone 性能等级阈值与计数口径

- **适用范围**：VRChat 头像性能评级（官方 avatar-performance-ranking-system，SDK 3.10.4 时期）。
- **结论（PC，超过 Poor 即 Very Poor）**：

| 项 | Excellent | Good | Medium | Poor |
|---|---|---|---|---|
| PB 组件 | 4 | 8 | 16 | 32 |
| PB 受影响变换 | 16 | 64 | 128 | 256 |
| PB 碰撞体 | 4 | 8 | 16 | 32 |
| PB 碰撞检查 | 32 | 128 | 256 | 512 |
| Contacts | 8 | 16 | 24 | 32 |

- **计数口径**：停用的物体和组件也计入；碰撞检查 ＝ 每个碰撞体能影响的 PB 变换数之和。移动端 Very Poor 是硬上限（组件 8、变换 64、碰撞体 16、检查 64），超出就移除全部 PB、Contact 与约束。他人手指碰撞体的开销随同场人数增长、不进你的评级。
- **判据**：评级在构建后读；多套服装、多套发型的头像很容易远超 Poor（实例：一个工程组件 229、变换 1237、碰撞检查 791；另一工程 142 个组件），此时「降到 Poor」往往不现实，要和需求方确认目标等级与可接受的手感损失。
- **证据等级**：未实测——官方文档整理；超限读数来自两个工程。
- **失效条件**：官方阈值调整时更新。

## PhysBone 降数只合并逐字段相同的链

- **适用范围**：PB 组件数超出预算、需要合并时（Modular Avatar / AAO MergePhysBone）。
- **结论**：把参数不同的多条链合并到一个组件，会明显改变摆动手感——一个工程把多条头发链并到 `Hair_Root` 一个组件（`multiChildType=Ignore`、忽略 `Hair_Head`）后，需求方明确反馈效果变差并要求恢复。两个工程最终都只做「零手感合并」：仅合并所有序列化字段逐字段相同的链。
- **判据**：可合并组的条件——有效根同父或同链组；VRCPhysBone 全部序列化字段逐字段相等（`pullCurve`、`springCurve`、`stiffnessCurve`、`gravityCurve`、`radiusCurve`、各限位曲线等曲线字段按关键帧 time/value/inTangent/outTangent/inWeight/outWeight/weightedMode 与 pre/post WrapMode 比较）；碰撞体集合相同；grab / pose / parameter 为空或相同；没有动画在写。不满足就不合并，**不自行放宽**。
- **修法**：先出只读合并计划（每组成员、比较过的字段、排除原因）给人审，再执行；合并后在克隆上跑完整预处理、按 SDK 口径输出前后四项计数。已经合并坏了的，按合并前的版本逐字节恢复原参数。
- **逐字段相同还不够**：另一个工程按上述条件先列出 6 组可合并，逐组复审后全部否决——构建期 VRCFury 或 MA 会写成员的开关或 `m_Enabled`、链根有多个子链、成员有曲线参数、端点位置会被 AAO 默认清零、宿主上已有合并组件。零手感口径下可合并的是 0 组；该工程构建后 PB 142/256（旧记录写的 207 不准），整体 Very Poor 由 92 万面、147 个材质槽决定，合并也改变不了等级，最终不合并。
- **证据等级**：单一案例（候选）——「手感变差」只在一个工程由需求方确认；「只做零手感合并」在两个工程被需求方采纳，其中一个工程审查后可合并组为 0。
- **失效条件**：需求方接受手感变化以换取评级时，另行评估。

## PhysBone 计数要在完整预处理后的克隆上做

- **适用范围**：需要判断「是否超过组件上限」或给出构建后评级的时候（Unity 2022.3、VRChat SDK 3.10.4 批处理）。
- **结论**：编辑期组件数不代表构建后：合并、删除、插件搬移都会改变数量。要克隆头像，跑完整预处理（NDMF、VRCFury、AAO）后按 SDK 同口径统计组件、变换、碰撞体、碰撞检查。批处理里调用 SDK 的性能评级计算会抛空引用（两个工程都遇到）——只取统计：`new AvatarPerformanceStats(false)` 后调 `AvatarPerformance.CalculatePerformanceStats(name, go, stats, isMobile:false)`，或自己遍历构建后克隆上的 VRCPhysBone / VRCPhysBoneCollider 按 SDK 口径计数，拿不到就记「未测」。
- **判据**：每个要上传的根在完整预处理后按 SDK 口径的四项计数（组件、变换、碰撞体、碰撞检查），组件数 ≤ 上限（该工作流按 256 执行）；读不到就记「未测」，不用编辑期数量代替。
- **超限处置顺序（一个工程的实例）**：服装按两个头像根拆分，每根各自 ≤256；在根之间移动一件衣服（一件外套约贡献 50 个 PB）；停掉单个饰品的 PB（网格保留、不再摆动）；超限的旧根不上传、在场景里默认停用。每一种都先试算再给需求方选。
- **批处理试算的内存**：同一 Unity 进程里反复完整预处理，内存约 5 分钟涨到 10 GB 上限被系统杀掉（Linux 批处理实测）。做法：每项试算结果立即追加落盘、支持续跑；每项后销毁克隆、`Resources.UnloadUnusedAssets()`、`GC.Collect()`；每个进程只跑 N 项后正常退出。
- **证据等级**：多工程验证——构建后计数与评级接口空引用在两个工程出现；超限处置与内存问题各来自一个工程。
- **失效条件**：SDK 修复评级接口后可直接用评级。
