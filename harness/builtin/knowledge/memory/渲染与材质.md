# 渲染与材质：出图、观测与材质排查的质量记忆

## 出图后先验像素：纯色图、重复图与逐字节相同

- **适用范围**：用 `Camera.Render()` 或离屏相机批量出验收图、评审图、交付图（Unity 2022.3，编辑器或批处理）。
- **结论**：日志里的「wrote xxx.png 1500x1500」、形态键回读 PASS，只证明文件写出来了、参数写进去了，不证明画面对。送审或交付之前，必须对像素本身做检查。
- **判据**：
  1. 极值：`Image.open(p).convert("RGB").getextrema()` 三通道都是同一个值（例如 `(205,205)`）即纯色，什么都没渲上。近似判据：与同机位已知好图比字节数，空白图小一到两个数量级（成文时 17–31 KB 对 1019 KB）。
  2. 两两比较：同一批不同状态的图逐张算 MD5，或用 `ImageChops.difference(a, b).getbbox()`，任意两张完全相同（`None`）即状态没切到，这批图不可用。真实渲染有抗锯齿抖动，同一状态渲两次都未必逐字节相同，何况不同状态。
  3. 一次会话连拍多组（多个捏脸候选、多套配色、多个配饰组合）时，每组之间重新 `EditorSceneManager.OpenScene`；只改参数接着拍，会拍出与上一组逐字节相同的图——成文时三组候选里两组 MD5 一致，而参数回读是对的。
  4. 「不同输入渲出相同像素」的排查顺序：先怀疑取图管线（场景没重载、蒙皮没更新、路径没解析到），再怀疑输入没生效，最后才怀疑被测对象。
- **成文时纯色图的成因**：自动取景的探针没有运行，正交尺寸直接取了 4.946，把 1.18 m 的头像放进约十米的视野；正常那次收敛到 0.717。送一批空白图去评审，评审会认真评论背景色，「零条指认」会被误读成通过。
- **证据等级**：单一案例（候选）
- **失效条件**：出图工具自带像素自检与重复图报警时，只需核对它的输出。

## 出图的批处理命令不加 -nographics

- **适用范围**：用 Unity `-batchmode` 运行需要出图的脚本。
- **结论**：出图的命令去掉 `-nographics`，只留 `-batchmode`。编译、导入资源、读控制台这类不出图的命令，加着无妨，还更快。
- **判据**：命令里有 `-nographics` 而脚本要出图，就是错的。一次实测报告：加了它之后，直接采样相机的 RenderTexture，得到与场景内容无关的恒定色。
- **证据等级**：单一案例（候选）。那次实验没有被独立复现；规则按定义成立：`-nographics` 不初始化图形设备，而渲染要走图形设备，默认不加没有代价。
- **失效条件**：Unity 改变该参数的定义时。

## 编辑模式拍局部特写：烘成静态网格、空闲层隔离、时间定死、关效果作对照

- **适用范围**：不进 Play、在编辑器里反复渲同一个局部（眼睛、手、配饰），做 A/B 比较或逐帧序列。
- **结论**：不进 Play 能省掉 ProjectSettings 被改写与域重载，但下面四件事缺一件，图就不可比。
- **判据**：
  1. **蒙皮陈旧**：`Camera.Render()` 在编辑模式渲的是上一帧的蒙皮；同一个同步块里改形态键再渲，两张图会逐像素相同。做法：`smr.BakeMesh(baked, true)` 烘成静态网格，挂到一个位置与旋转相同、缩放为 1 的代理物体（`MeshFilter` + `MeshRenderer`，材质用 `smr.sharedMaterials`）上再渲；换形态键就重设权重再烘一次。不要改现有渲染器的 `sharedMesh` 去换网格：绑定姿势与骨骼顺序对不上，整张脸会消失。
  2. **用空闲层隔离**：从 31 往 8 找 `LayerMask.LayerToName(i)` 为空的层，代理物体放进去，相机 `cullingMask = 1 << layer`；场景灯的 `cullingMask` 去掉这一层，另加一盏只照这一层的灯；渲完还原并 `DestroyImmediate` 临时物体。不去改别人渲染器的 `enabled` 或层，场景不会被标脏。VRChat 工程里 8–21 层常被占用，空闲层每次现查，不写死。
  3. **时间定死**：用 `_Time.y` 的着色器效果在编辑器里无法精确控制。给着色器加一个默认 0 的时间偏移属性，写成 `t = _Time.y * _TimeScale + _TimeOffset`；出图时把缩放设 0，时间完全由偏移决定，逐帧可复现。默认值不改变线上行为，可以长期留作测试钩子。临时改参数用 `new Material(src)` 的实例并设 `hideFlags = DontSave`，不改 `.mat`。
  4. **量化对照**：先渲一张「关掉效果」的同帧（强度设 0），之后每帧算与它的逐像素差，统计增量超过阈值的像素数与峰值增量。这两个数回答「效果上没上画面、哪一帧最强」，也能跨方案横向比。
- **证据等级**：单一案例（候选）
- **失效条件**：改在 Play 模式里出图时第 1 条不需要（仍要等帧），其余照做。

## 编辑模式改完形态键要渲两次，拍前先跑 0 与 100 的对照

- **适用范围**：编辑模式下调用 `SetBlendShapeWeight`（或任何改蒙皮的操作）之后立刻 `cam.Render()` 出图。
- **结论**：第一次 `Render()` 只触发蒙皮更新，拍到的是改之前的形状，第二次才对。材质属性的改动（`SetTexture`、`SetColor`）当场生效，不受影响——同一个脚本里改材质的部分是对的、改形态键的部分是假的，所以藏得深。
- **判据**：写成 `smr.forceMatrixRecalculationPerRender = true;`（或把渲染器 `enabled` 先关再开）后连续两次 `cam.Render()`。拍任何形态键相关的图之前，拿一个已知差异巨大的键（如全闭眼）做 0 对 100 的对照：成文时单次渲染的差异像素为 0（最大差 1/255），两种修正写法都是 88002 像素（23.28%）、最大差 191/255。对照没有差异，就是取图管线坏了，整批图作废。代价不对称：多渲一次是毫秒级，少渲一次会让整批验收图变成同一张，还会据此把厂商键误判成「没用」。
- **症状**：一组 5 张闭眼类键的验收图里，4 张 MD5 相同、第 5 张只差压缩噪声；随后用同一套工具「验证」某个键能否藏住瞳孔，得到「零影响」。
- **早期记录里的另一条做法（未实测）**：切一次渲染器 `enabled` 后调用 `EditorApplication.QueuePlayerLoopUpdate()` 再渲；诊断时先查形态键数据本身（例如最大顶点位移与非零顶点数），数据是好的才判为观测方法的问题；渲完量一个数值确认变化确实发生（例如虹膜包围盒占画面比从 45.7% 变为 8.7%）。
- **证据等级**：单一案例（候选）
- **失效条件**：在 Play 模式里等过至少一帧再渲时不适用。

## 收缩类形态键的验收只能进 Play：烘焙体里它们是 MA Responsive 动画层

- **适用范围**：使用 Modular Avatar 反应式组件（Shape Changer、Object Toggle、Material Setter），且被控物体由动画开关（衣服根挂在换装轮盘上）的工程。
- **结论**：反应式组件不总是静态烤进网格。被控物体由动画开关时，MA 只能把效果做成条件动画，生成名为 `MA Responsive: <网格名>` 的层。动画层在编辑期不求值，所以即使先烘焙一次，在编辑器里渲出来的仍是没有施加收缩键的样子。静态烤入只发生在被控物体构建时固定开着的情况。
- **判据**（不用渲图）：烘焙后读合并后的 FX 控制器，看有没有层写 `blendShape.Shrink*`、`blendShape.Toe_*` 这类收缩键。有，这些键就是动画层，编辑期渲图一律作废，只能进 Play（用 GestureManager 驱动）实拍或请人看；没有，才是静态烤入，编辑期渲图可信。
- **成文时的实测**：烘焙后合并控制器 109 层里有 15 层 `MA Responsive:`，写 `Shrink_Foot`、`Toe_heels`、`Toe_highheels`、`Shrink_Knees`、`Shrink_Elbow`；烘焙体在编辑器里渲出来，LUNALICE 的 `Shrink_Foot=100`（Delete 型）完全没生效，脚整只露在鞋外；据此白改过一轮换装 clip。顺带：这些层里 MA 会把形态键自动传播到所有 `BlendshapeSync` 的网格（身体、丝袜、袜子、脚甲一起写），手写「每个渲染器一条曲线」是多余的。
- **取舍**：编辑期渲图便宜但结论是错的；Play 实拍贵但对。错的结论会导致去改一个本来就对的东西。
- **证据等级**：单一案例（候选）
- **失效条件**：被控物体在构建时固定开着（没有换装）时，编辑期烘焙体渲图可信；MA 改变反应式组件的烘焙方式时要重核。

## 烘焙体里按源路径找物体会静默失败：四级回退并对结果查重

- **适用范围**：拿 NDMF 烘焙克隆体做任何「按路径找物体」的事（换装渲图、组合矩阵、强制显示被压物、性能定位），工程装了 Avatar Optimizer（AAO）。
- **结论**：AAO 的拍平会把 `_Acc/Acc_X/Ears` 搬到根下一层，改名成 `_Acc$Acc_X$Ears$138` 这类（数字后缀每次烘焙都可能变，不能写死）。`root.Find(源路径)` 返回 null，后面那句 `SetActive` 静默不执行，不报错、不警告。
- **判据**：解析器按四级回退，缺一级就会漏掉一整类件：
  1. `root.Find(源路径)`——没被动过的件；
  2. `源路径.Replace('/', '$')` 作前缀，匹配根下子物体——被拍平的件；
  3. 按末段匹配 `$<名字>` 或 `*$<名字>$*`——拍平后中段被截的件；
  4. 全树按末段裸名查找，**唯一命中才采信**——BoneProxy 搬走的件在烘焙体里是裸名（例如 `HeadDress`），不带 `$`。命中 ≥ 2 个就报「歧义」，不猜。
  渲完一批图逐张算 MD5，任意两张逐字节相同即状态没切到。
- **不是缺陷的情形**：AAO 会真的删掉从不启用的物件（例如某个轮盘各档全写 0 的装饰件），按路径找它们返回 null 是正确优化，不要去「修」。
- **成文时的实测**：冲突特写十格，前一版六张里有四张 MD5 相同——十张渲的全是「一件衣服都没穿」的同一个状态，根因是服装根的 `Find` 恒为 null。
- **证据等级**：单一案例（候选）
- **失效条件**：AAO 改变拍平命名规则时，第 2、3 级按新规则改；不用 AAO 的工程只需第 1 级，查重判据仍保留。

## 整机出图前清场：第二个头像根、插件摆位件与手动摆档

- **适用范围**：用 `Camera.Render()` 给整个头像出图：定妆照、发型或服装对照图、交付图。
- **结论**：整机出图时，镜头里常混进三类不该有的东西或状态——第二个头像根、插件的摆位预览件、手动摆出的错误档位——它们在图上都长得像穿模或装配缺陷。出图前逐项清场。
- **判据**：
  1. **场景里常不止一个头像根，而且位置完全重合**（源头像与面捕版、备份根、Quest 版并存）。症状不像「两个人」，像穿模：一次评审把面捕根上的另一套发型读成「双发型重叠穿模」，位置指对了、原因全错。出图前数一遍 `scene.GetRootGameObjects()` 里带渲染器的根，大于 1 就必须挡：对其余根的渲染器设 `Renderer.forceRenderingOff = true`（运行时标志，不序列化、不脏场景），`finally` 里逐个置回。不要用 `SetActive(false)` 或改 `renderer.enabled`——它们是场景改动，一旦存盘就成了真改。两个根通常在同一层，用 `cullingMask` 隔离在这里不好用。日志写出挡掉了哪些根。
  2. **插件的摆位预览件是真渲染器，构建时才删**：PCS（Penetration Contact System）在 `Target Objects/Placement Icons (Auto Remove)/…` 下挂着真的 `MeshRenderer`（`GUI/Text Shader` 的红圈靶标、「Insert」字样、箭头、小球），会盖住定妆照的胸口；成品里没有。先用 `cam.cullingMask = 0` 渲一张：非背景像素为 0，说明画面里的东西全是真渲染器而不是 gizmo（VRCFury 的 SPS 图示走 `Handles`（`[DrawGizmo]`），只画在 Scene 视图，`Camera.Render()` 拍不到）。匹配要窄：只认作者写明会被自动删除的字样（`Placement Icons (Auto Remove)`、`will be auto removed`），不用 preview、icon 这类词模糊匹配，否则会误伤真配件。
  3. **档位不能手动 `SetActive`**：一个档位的 clip 既开也关（外购发型档除了开自己，还要关掉素体自带的几块头发与发饰）。读参数资产的 `defaultValue`，只覆盖要扫的那一个参数，按控制器求值落地并带快照还原；档位取值从该层 AnyState 的转移条件反推（`Greater lo` 与 `Less hi` 取区间中点），不手写 `i/(N-1)`——MA、VRCFury 的分档是 `1/N` 带宽，手算差一点就落进相邻档。日志每档写一行「这档开着哪些头部件」。
- **证据等级**：单一案例（候选）
- **失效条件**：出图工具已内置「只渲活跃头像根」「排除自动删除的摆位件」「按参数求值摆档」三项时，只需核对它的日志。

## 穿衣命中比 activeSelf，画面里有没有比 activeInHierarchy 与渲染器

- **适用范围**：断言「定妆照或验收图里点名的 N 件都开着」，以及回答「游戏里看不看得见某件」。
- **结论**：这是两个不同的问题，要读不同的字段。动画写的是 `activeSelf`；父物体关着时，子件的 `activeSelf` 仍是 1，`activeInHierarchy` 却是 0。
- **判据**：
  - 「菜单选中了谁」（穿衣命中）：逐条比 `activeSelf == 求值结果`，对不上 0 条才算命中；场景里找不到对应物体的悬空绑定单独计数，不计入分母。用 `activeInHierarchy` 比会假失败：成文时这样比出「应开 172 件、实开 25 件」，差的 147 件全是假的。
  - 「画面里有没有」（例：换整套后原装件会不会漏出来）：判据是 `activeInHierarchy && Renderer.enabled && 材质非空`。只比 `activeSelf` 会假报：另一个工程据此报出 18 条「原装件被部位开关写回 1」，实际整套 clip 关的是父物体，补读 `activeInHierarchy` 并做渲图逐字节比对才推翻。
  - 另记一行给人看：镜头里真在渲的顶层件清单（遍历 `GetComponentsInChildren<Renderer>(false)`，往上找到顶层父物体）。这一行才是「图里穿了什么」。
  - 报缺陷前两个字段都读，并写明回答的是哪个问题。
- **证据等级**：多工程验证（两个工程各栽一次，方向相反）
- **失效条件**：无——这是 Unity 的激活语义。

## 捏脸与默认表情要在状态落地之后再读一次

- **适用范围**：按控制器默认态把头像摆好、再出图或记录「这张图用了哪些形态键」的流程。
- **结论**：控制器默认态落进场景后，其中的 blendShape 曲线可能覆盖渲染器上已经设好的形态键值。记录要取「真正拍下去那一刻」的值，不取进函数时的值。
- **判据**：落地后遍历目标渲染器的全部形态键，列出非零项，与进函数时的列表比。成文时进函数时 3 条、落地后 4 条，多出的 `extra_shy_1=100` 由默认值为 1 的腮红参数 `RJ_EyeBlush` 写入——即客户端默认就带腮红，只有落地后再读才看得见。
- **证据等级**：单一案例（候选）
- **失效条件**：出图流程不经过控制器求值时不适用。

## 叠加效果读不读得出来：先看底色余量，再把 ΔE 拆成明度与色相

- **适用范围**：叠在别的贴图上的效果（眼内特效、发光纹、贴花），判断能否被看见，或比较几个候选方案。
- **结论**：加法混合的效果能否被看见，取决于底色离 255 还有多远。底色亮度中位 ≥ 200 时，提亮度这条路是死的：成文时虹膜底色亮度中位 208/255，解除亮度封顶后像素数与峰值完全不变。明度满了还有色相、彩度、形态三条路。
- **判据**：用 CIELAB 把「效果像素对其局部背景」的 ΔE（CIE76）拆成明度 `ΔL*` 与「彩度+色相」两部分：效果像素取与「同设置但关掉效果」的同帧差 > 10 的像素；背景取每个效果像素周围 6–14 px 方环内**非效果**像素的均值（必须排除效果自身）；`dL = |L_pixel − L_bg|`，`dChromaHue = sqrt(max(dE² − dL², 0))`。成文时在低饱和的冷粉紫底色上：与底色同调的蓝白配色，色相通道 4.2；高饱和暖色 15.4；暖色加暗边 21.1；4× 降采样后的 ΔE 峰值从 32.7 升到 53.6，明度分量基本不变。
- **暗边的取舍**：在发光体周围压暗底色，单用往往是负收益——一例把拖尾亮像素从 832 吃到 556，ΔE 中位反而从 12.5 降到 10.8；只有叠在高饱和色相之上才转正（15.7 → 18.7）。暗边只当配角，主角必须是色相或形态。
- **证据等级**：单一案例（候选）；数值只在一个素体的眼部底色上测过。
- **失效条件**：底色明度有余量（中位明显低于 200）时，调亮度仍有效；换底色要重测。

## 凸显度数值证明不了「好看」：形态归类靠盲测复述

- **适用范围**：用 d′、ΔE、对比度给方案排序，而其中某个方案带暗边、描边或硬边缘。
- **结论**：人眼的边缘检测对高频黑白边界极敏感，凸显度指标分不清「信号显眼」与「瑕疵显眼」。成文时带暗侧翼的旧版在特写下确实更抓眼，但盲测被说成「一根睫毛」；去掉暗侧翼后 d′ 反而更高（33.62 对 30.31），盲测才第一次读成「发光流星」。机制：睫毛、划痕这类遮挡物物理上必然压暗底色，效果自带暗边时，大脑倾向把它归类为异物覆盖；纯加色、向头部展宽的外辉光没有负向凹陷，会被归类为光学效果。
- **判据**：把净压暗量（`darkflux`）与增亮量（`flux`）分开报，`darkflux` 涨得比 `flux` 快，就是在往瑕疵方向走。数值判据只能排除「看不见」；形态与归类用盲测复述（不给提示，问对方第一眼看到什么），出现「头发、睫毛、划痕、裂缝、脏印子」任一词即判负，数值再好也不算过。
- **证据等级**：单一案例（候选）
- **失效条件**：效果本身就要做成描边或线条时，判负词表要重写。

## 小尺度效果按目标视距的真实像素尺寸签字

- **适用范围**：贴在身上的小尺度效果（眼内、指甲、耳饰、纹身）定稿之前。
- **结论**：微距渲图通过评审，不代表游戏里看得见。成文时一个眼内效果在只框一只眼的 900×900 微距图与动图上通过了评审、也得到委托方认可，上传后游戏里连贴脸都看不见。逐条排除构建、着色器编译、优化器、顶点色遮罩、UV、FX 动画、材质属性块之后，24 帧时间扫描量出：整个周期里运动能量 > 30 的像素只占 0.71%，最大能量 147（满量程 765）——效果在渲、也在动，只是太细太淡。
- **判据**：先算视距账：`角尺寸 = 物体尺寸 / 观看距离`，`屏幕像素 = 角尺寸(度) × 屏幕竖向像素 / 竖向 FOV(度)`。面对面约 0.5 m、1080p、竖向 FOV 60° 时约 18 px/度，12 mm 的虹膜约 25 px；微距图里虹膜能占 500 px，相差 20 倍，微距里 2 px 宽的拖尾到游戏里只有 0.1 px。把渲图降采样到目标视距的真实尺寸再跑可读性度量（社交视距的一种做法是 4× 降采样，如 760 → 190）；微距只用来调形状，不用来签字。一个周期只出现几次的瞬态效果不能只看单帧：固定时间轴扫一整圈，看整周期的运动能量。
- **达不到时**：不要单靠提亮度（高明度底色上很快顶到 255），优先加尺寸（拖尾宽度、头部大小）与出现频率；定稿版留一张按目标视距降采样的对照图进交付记录。
- **证据等级**：单一案例（候选）；18 px/度是按上述距离、分辨率与 FOV 推算的，其他设备要重算。
- **失效条件**：目标观看条件（距离、分辨率、FOV）变了就重算。

## 效果位置要在有遮挡的真实环境里定：逐档量可见率

- **适用范围**：在空盘或无遮挡预览里调好了位置参数，贴到真模型上却看不见（眼内效果被眼睑挡住这一类）。
- **结论**：空盘里调出来的位置只能当起点。成文时一个眼内流星在黑底单渲镜片时峰值 211/255，贴到眼睛上完全看不见；逐层排除后，不是几何被挡死、也不是着色器没画，而是位置错了：流星带的 v 范围 0.58–0.95 是在空盘上调的，正好落在上眼睑后面。
- **判据**：渲两张：① 只渲目标面、涂纯色标记；② 目标面纯色加完整遮挡体。对 ① 里的标记像素逐个查它在 ② 里是否还是标记色，按位置分档统计可见率。成文时（该素体的眼盘）v 0.75–1.00 为 0%，0.70–0.75 为 8%，0.65–0.70 为 60%，0.60–0.65 为 93%，0.10–0.60 为 81–100%，0.00–0.05 为 5%；把范围改成 v 0.12–0.62 后，可见增亮像素 121 → 943（7.8 倍），峰值对比 41 → 99（2.4 倍）。取舍：可见率 ≥ 90% 的档当「可用」，60–90% 只做进出场过渡，< 10% 的不用。
- **证据等级**：单一案例（候选）；可见率表只对那个素体的眼睑形状成立。
- **失效条件**：换素体（眼睑形状不同）必须重测，不能照抄。

## 标注图上的中文要看渲出结果：默认字体没有中文字形

- **适用范围**：用 PIL 等库在图上写中文标注（评审图、对照表、交付说明图）。
- **结论**：`ImageFont.load_default()`，以及不指定字体的 `ImageDraw.text()`，没有 CJK 字形，中文渲成一串方框；脚本不报错、日志全 PASS，只有看图的人能发现。
- **判据**：显式加载含 CJK 的字体（例如 Noto Sans CJK 的 `NotoSansCJK-Regular.ttc`，集合索引 2 为简体中文；其次 Sarasa、Noto Serif CJK），加载后验证一个汉字（如「电」）与方框字符「□」的字形包围盒不相等再用；找不到就抛错，不静默退回默认字体。可查问句：这张图上的中文，看过渲出来的结果吗？
- **取舍**：宁可抛错也不静默降级——方框图发出去，比脚本崩掉更贵。
- **证据等级**：单一案例（候选）
- **失效条件**：出图库的默认字体已含 CJK 字形时。

## 透过半透明件看不见后面：先分抓屏时点、写深度、视锥剔除

- **适用范围**：「透过某个半透明特效看不见它后面的东西」，而且换个角度或换套衣服就好了；以 lilToon 材质为主的头像。
- **结论**：看起来随机，其实是确定的。三种机制都会造成「后面的东西没了」，判据完全不同：

| 类 | 可查判据 | 症状特征 |
|---|---|---|
| A 抓屏时点 | 有材质用 GrabPass 类着色器（lilToon 的 Refraction、RefractionBlur、Gem 及其 Multi 版） | 透过它看，队列在抓取点之后的东西全没了，背景却是对的 |
| B 半透明写深度 | `renderQueue ≥ 2500` 且 `_ZWrite = 1` | 先画的把后画的透明物整片深度剔除；先后由包围盒中心到相机的距离决定，所以换角度就变 |
| C 视锥剔除 | `SkinnedMeshRenderer` 的包围盒小于蒙皮后的实际范围 | 整个渲染器一起消失，不是少一块 |

- **判据**（一次取全）：每个渲染器、每个材质槽的材质名、`renderQueue`、`_ZWrite`、着色器名；着色器名含 `Refraction` 或 `Gem` 的按队列升序排，第一行就是抓取点；`SkinnedMeshRenderer.bounds` 对照它真正绑定的骨的位置——`smr.bones` 是全表，大半是别的部件用的骨，要按 `mesh.boneWeights` 里 `weight > 0` 的索引筛，否则误报一堆。C 类要在构建后的克隆体上量：源场景的包围盒常被构建期改写（例如 MA MeshSettings 统一改成 2×2×2），源场景里的小包围盒在交付件里可能根本不存在。
- **B 类修法**：透明覆盖层写深度基本都是作者笔误，改成 `_ZWrite = 0`，`ZTest` 不动（被不透明物挡住时照样看不见）。但先确认它的透明不是抓屏合成的，否则改完症状照旧。
- **证据等级**：单一案例（候选）
- **失效条件**：非 lilToon 的抓屏着色器，要按它自己的抓取名判断 A 类。

## 抓屏时点：具名 GrabPass 每帧只抓一次，修要两头夹

- **适用范围**：头像上有多个用 `GrabPass { "_lilBackgroundTexture" }` 的材质（lilToon 的 Refraction、RefractionBlur、Gem）：宝石、光环玻璃、眼部特效、全息面板。
- **结论**：具名抓取每帧只抓一次，抓取点是当帧第一个使用这个名字的物体，之后所有同名着色器共用那一张图。于是渲染队列 ≥ 抓取点的东西，透过任何一个抓屏物体都看不见——抓图的时候它们还没画上去。表现得像「偶发」有两个原因：特效恰好挡在目标前面的视角本来就少；抓屏件常挂在可开关的配饰上，配饰一开一关，当帧最靠前的抓屏材质就变了，抓取点跟着跳。
- **判据**：列出所有抓屏材质及其 `renderQueue`，最小值即抓取点；再列出 `renderQueue ≥ 抓取点` 的全部材质，这就是「透过窗体看不见」的完整清单，与报告的现象对上即坐实。动画里的材质替换（PPtr 曲线）也要查：它引用的抓屏材质，队列是否都 ≥ 抓取点。
- **修法**：两头夹。抓屏材质整体后移到足够大的队列（例如 3050），同时把要看见的东西前移到抓取点之前——只要还剩一个抓屏材质留在前面，抓取点就被它钉住。某个抓屏材质动不了时，宁可把要看见的东西拉到它前面，让各种开关组合下表现一致：「时好时坏」比「一直不对」更难查、也更难交代。
- **动手前两个陷阱**：厂商材质复制副本再改，不改原件；配色若是「平行目录换材质」（如 `Material/Black/X.mat` 与 `Material/Pink/X.mat`），换色时动画会把材质指回厂商那份，改副本会被顶掉。本工程自己生成的换色 clip 要把关键帧改指到副本。
- **证据等级**：单一案例（候选）（同一工程两次）；抓取行为与 Unity 具名 GrabPass 的规则一致。
- **失效条件**：lilToon 改变抓取名或背景采样方式时要重核。

## 离屏渲染能不能验抓屏类效果：先做正对照

- **适用范围**：准备用离屏图（`Camera.Render()` 到 RenderTexture）判断任何抓屏类（Refraction、Gem）现象之前。
- **结论**：取决于渲染路径，不能一概而论。一条编辑期的离屏出图路径里 GrabPass 不工作，抓屏类材质被渲成实心色块——拿这种图会把管线的限制当成模型缺陷，而且看起来非常像「复现成功」。另一条路径（Play 模式、Vulkan、`Camera.Render()` 到 RenderTexture）里 GrabPass 是生效的：窗体透射率约为 1；把另一个抓屏材质的运行时实例队列提前到 2450 来复现修复前的抓取点，检出 7 条并归因到发型，修复后的状态检出 0 条。
- **判据**：在 Play 里只改 `renderer.materials`（运行时实例，不落盘）的 `renderQueue`，人为制造一个抓取点问题做正对照；这条路径复现不出来，就不能当判据。「队列表」永远是第一判据（可证、可回读、状态一变就能重算，不用渲图）；离屏图只在正对照通过后做补充；最终观感以 Play 模式 Game 视图为准。
- **证据等级**：单一案例（候选）。两种结论在不同出图路径下取得，后者的环境是 Linux 宿主、Vulkan、Unity 2022.3、Play 模式；换图形 API 或出图方式要重做正对照。
- **失效条件**：出图管线（图形 API、编辑模式或 Play 模式、渲染管线）变了就重做正对照。

## 折射强度为 0 的材质，可能正拿抓屏当透明

- **适用范围**：厂商件用 lilToon 折射类着色器，而 `_RefractionStrength` 为 0 或接近 0 的材质，例如全息面板、窗体。
- **结论**：作者不是要折射，而是拿抓屏合成当「透明」用，材质本身没有 alpha。看到折射强度是 0 就顺手换成普通透明着色器是错的——实测换掉之后，窗体变成一块实心板。
- **判据**：换着色器之前先回答「它的透明从哪来」：抓屏类着色器、折射强度 0、材质无 alpha，三者同时成立，透明就完全来自抓屏；这种件的观感只能在能还原抓屏的出图通道里看。成文时的一例：队列 3000、`_ZWrite = 1`、`_RefractionStrength = 0`。
- **证据等级**：单一案例（候选）
- **失效条件**：材质本身有 alpha 且透明模式已开启时，换成普通透明着色器才可能成立。

## 自配透明材质：换 shader 不重置渲染状态，对照厂商件只比渲染状态

- **适用范围**：照着厂商那份做一个同款透明材质（复制素体材质、换透明着色器、挂遮罩），常见于厂商只给了别的素体的样例材质（成文时厂商只给了 Wendy 版，要自配 Shinano 版）。
- **结论**：`material.shader = x` 只换着色器引用。留在原地的至少有四类：`_SrcBlend`、`_DstBlend`、`_BlendOp`（`_DstBlend = 0` 即 Zero，混合退化成纯覆盖，渲成实心）；`_ZWrite`、`_ZTest`、`renderQueue`（透明件写深度，挡住身后的部件）；`m_ShaderKeywords`（从 Standard 带过来的残留关键字，lilToon 不认也不清）；`_TransparentMode` 这类模式枚举（按语义猜必错）。
- **判据**：别逐条猜，拿一份确定能用的对照件（厂商给别的素体的那份）逐属性比，只比渲染状态类：`_TransparentMode`、`_ZWrite`、`_ZTest`、`_Cull`、`_SrcBlend`、`_DstBlend`、`_BlendOp`、`_SrcBlendAlpha`、`_DstBlendAlpha`、`_AlphaToMask`、`_Cutoff`、`_AlphaMaskMode`、`_AlphaMaskScale`、`_AlphaMaskValue`，另外单独比 `renderQueue` 与 `m_ShaderKeywords`（它们不在着色器属性表里）。颜色、贴图、遮罩本来就该不同，比全表会被它们淹掉。最稳的写法反过来：复制厂商的对照材质，再把颜色与贴图换成本素体的，渲染状态天然是对的。验收渲一张纯色背景的图（例如绿底 RGB(0.20, 0.45, 0.30)）：透明件后面能看见背景色才算透；「颜色变浅」不算，不透明的浅色与半透明长得一样。
- **成文时的实测**：自配的两份材质渲成实心肤色——`_DstBlend` 是 0 而厂商是 10（OneMinusSrcAlpha），`_TransparentMode` 猜了 2 而厂商是 0，外加 9 个从 Standard 继承来的死关键字。三处全是「换 shader 没跟着换」的东西。
- **证据等级**：单一案例（候选）
- **失效条件**：无。

## 跨工程比材质：解析不到的引用不等于空

- **适用范围**：拿引用了本工程里没有的资产的材质做比较：厂商给别的素体的样例材质、旧工程搬来的材质、只解了一半的包。
- **结论**：`AssetDatabase.LoadAssetAtPath<T>()` 与 `material.GetTexture(p)` 在「引用存在、但目标资产不在本工程」时一样返回 null，在探针输出里与「字段是空的」长得一模一样，结论却相反。
- **判据**：读 `.mat` 的 YAML guid（`m_Texture: {fileID: 2800000, guid: …, type: 3}`，guid 全 0 才是真的空），或者把两种情况分成两个结果打印：`<空>`（guid 全 0）与 `<解析不到 guid …>`（有 guid、本工程查不到）。探针写完，拿一个已知在本工程里的材质和一个已知不在的材质各跑一次：前者不该出现「解析不到」，后者必须出现。
- **成文时的实测**：一份别的素体的样例材质被探针报成「`_MainTex = null`，44 条属性都像 `glass_*`」，据此断定「它本质是玻璃材质」，全错——那个素体没装进本工程，贴图引用全部解析不到，而 YAML 里的 guid 写得清清楚楚。缺失被替换成合法值时，输出看起来信息量很大，比「什么都没查出来」更容易让人下结论。
- **证据等级**：单一案例（候选）
- **失效条件**：无。

## 厂商给了 N 个材质变体：先做属性差异全表再接菜单

- **适用范围**：厂商一个目录下摆着一排同名不同色的材质，准备一一对应到菜单的 N 个档位。
- **结论**：不要假定「文件名不同即效果不同」，也不要假定差别在 `_Color`。成文时六色玻璃（`glass_water`、`Blue`、`purple`、`pink`、`green`、`white`）在 `_Color` 上只有 3 个不同值：`water` 与 `Blue` 都是 `#241F82`，`purple` 与 `white` 都是纯黑，真正区分它们的是法线波纹贴图与 matcap 贴图；按「动画写 `_Color`」实现，六档里有两对是死档，只有换整份材质才能把贴图差异带上。
- **判据**：遍历着色器的每个属性，只打印 N 份之间 `Distinct().Count() > 1` 的属性——这张表就是「颜色」的全部内容，它决定菜单用改属性还是换材质实现。生成档位后做两两可分校验：把每档的效果归约成集合两两比，或逐档渲图算 MD5，任意两档相同即有死档。
- **证据等级**：单一案例（候选）
- **失效条件**：无。

## 衣物折边处的黑斑：先怀疑描边外壳穿出

- **适用范围**：lilToon 带描边的衣物（着色器 `Hidden/lilToonOutline`，`_OutlineWidth > 0`，描边色接近黑），黑斑位于两层布贴得很近的折边或翻领处，且只渲这一件时黑斑仍在。
- **结论**：多半是内层布的描边外壳（向外扩的背面）从外层布之间透了出来。
- **判据**：把这件的描边宽度临时设 0，同机位再渲——在 Play 里改构建产物上的材质副本（例如 VRCFury 构建时的临时副本 `Packages/com.vrcfury.temp/...`），不动原件，退出 Play 自动丢弃。黑斑消失，是描边；仍在，就查网格缝隙或翻面（`_Cull`；lilToon 默认 `_Cull = 0` 已是双面，「改成双面」的要求往往本来就满足）。
- **修法取舍**：调高 `_OutlineZBias`（成文时取 0.005）把描边往后推，黑斑消失、轮廓线保留；材质复制一份只挂给这一件（厂商原材质常被多个预制体共用，不改原件）。描边宽度设 0 会丢掉整件轮廓线；描边色调浅只是把黑斑变成灰斑；画描边宽度遮罩或补面最准，但要做贴图或改网格，ZBias 不够时再用。ZBias 太大时，近处本该有的轮廓线会被自身布料盖掉：改完正面、侧面各渲一张确认。
- **验证**：同机位修前、修后的图混排做盲测（答案表只留本地），修后零指认。成文时两个独立评审里，一个准确指出了两张修前图；另一个把背后一个设计性的黑色大蝴蝶结误报了一次——同一个蝴蝶结在修前图里它没报，可据此判为误报。
- **证据等级**：单一案例（候选）
- **失效条件**：非 lilToon 的描边实现要按其参数改写。

## 洋红就是空材质槽：单独数槽位，从源头取回

- **适用范围**：编辑器里或构建后的头像上出现一片洋红。
- **结论**：一片洋红 = `Renderer.sharedMaterials` 里有 null，不是着色器出错。空槽没有材质，就取不到着色器，按着色器或材质列出的审计清单列不出它，跑完一片正常。
- **判据**：单独数槽位 `r.sharedMaterials.Count(m => m == null)`。见过的成因：生成的材质放进了会被整目录删掉重建的文件夹；「先删再建」的生成脚本给资产换了 GUID；两个包的公共材质在导入时撞车、一方被丢掉；还原逻辑写了 `if (mats[i] == null) continue;`，已经变空的槽永远修不回来。修法：预制体实例上的渲染器，用 `PrefabUtility.GetCorrespondingObjectFromSource` 找到源预制体里的同一个渲染器，把材质抄回；源头也坏了，就从素材包里按原 GUID 把资产连 `.meta` 一起取出重放。改材质之前先落一份台账（渲染器路径与槽号 → 原材质 GUID），不靠名字倒推。
- **证据等级**：多工程验证（空槽在多个工程出现过，成因各不相同）
- **失效条件**：无。
