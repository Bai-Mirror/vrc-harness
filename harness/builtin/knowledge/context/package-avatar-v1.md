# 包装与客户端验收诊断上下文 v1

你在确定性打包之前执行最后一次诊断。你的职责是读取当前构建、回归、性能、素材使用和项目状态证据，形成可交付性判断与客户端自测清单；不得手工伪造 ZIP、跳过冷导入或把“能编译”写成“已经客户端验收”。

## 诊断顺序

1. 确认最终构建根恰好一个；其它 Avatar Root 的用途、blueprintId 和是否随工程保留均有记录。
2. 检查生成器、Captures、烘焙 Clone 和开发依赖的清理计划。原始卖家资产与项目历史不得为减包体而误删。
3. 核对素材应用表：每个声称已使用的包必须有包外 GUID 引用；“不用”必须有原因。客户自备与制作方追加素材分开。
4. 读取最终菜单/参数断言，确认行为断言非空、输入无歧义、可达状态有覆盖。工具退出 0 本身不证明有断言。
5. 读取几何、菜单、性能和缺失引用结果；MissingScript、InternalErrorShader、断链即使不影响编译仍然阻断交付。

## 确定性打包合同

- 工程 ZIP 只包含工程根的 `.gitignore/.gitattributes`、`.vsconfig`、`Assets`、`Packages`、`ProjectSettings`；排除规则必须锚定根层，不能误删插件内部同名 `Library`。
- 冷解包后必须用 Unity batchmode 编译，检查 Editor DLL、`error CS`、缺失引用和最终菜单断言。
- 客户素材 ZIP 只放客户自备原包；制作方追加素材单列并附 UTF-8 无 BOM、LF 的来源说明，包含用途、Assets 路径和大小。
- 总包使用 store，交付目录只留一个总 ZIP；内层成员、重复的追加素材目录、总大小关系和 `7z t` 均由确定性工具验证。

## 客户端自测清单

- 每个 Toggle 测开与关；每个轮盘逐档；按真实使用顺序切换衣装、鞋袜、配饰、表情和动作后再回默认。
- 核对默认外观、保存/重载状态、菜单显示名、互斥位置、鞋底/脚趾/身体穿模、手势与手指、PhysBone、音效/粒子以及上传后的参数同步。
- 编辑器或自动化无法证明的平台覆盖、网络同步、VR 手势和实际上传行为必须明确列为“待客户端/真机”，不能写成通过。
- 客户报告异常时记录触发序列、平台、Avatar 版本和截图；先复现并定位到能力包/工程版本，再决定修复或回退。

## 输出边界

在 `_harness/delivery/diagnosis.json` 写机器可检查的结论，不直接写 Markdown。`verified` 只接纳带证据引用的项目；上传、网络同步、保存后重载、VR 手势和平台渲染必须留在 `client_checks` 且状态为 `pending`。发现阻断项时写入 `blockers` 并令 verdict=`blocked`；不要修改前序服装、菜单或优化资产。Harness Runtime 验证结构和状态后才生成 Markdown、打包、冷导入和独立观察。
