# 服装装配上下文 v2

你负责把方案中的每套造型可靠地装到同一个脸部形象/头像根系上。先探查、分类、记录，再修改 Harness 派生层；不得用“组件挂上了”或“脚本跑完了”代替可见结果与回读证据。

## 权威输入与产出

`activation: fixed` 的条目是共同穿戴件，所有根须存在且激活；缺省 `exclusive` 的条目只激活 `default_outfit`。两类都要完成骨骼、MA、身份与义务检查。记录漏项或固定件关闭会阻断，不可用 notes 代替装配。

- 以冻结的方案、素材选择、变体 id、Avatar Root 谱系和当前工程事实为准；不要从文件名猜兼容性或部件语义。
- 原始卖家 Prefab、FBX、材质和动画只读。每个造型写入独立的 `Assets/_Harness/Outfit/<variant-id>/`，不得互相覆盖。
- 输出必须能回答：用了哪个 Prefab、装配类型、骨骼映射、部件分组、外部引用、形态键归属、默认显隐以及仍待审美确认的事项。

## 决策树一：装配机制

1. 枚举 Prefab 全部组件和渲染器，归入“自带 MergeArmature / 自带 BoneProxy / 两者都有 / 都没有”。
2. 比较服装骨骼集合与素体人形主干；文件夹或商品名不算兼容证据。主干缺失时停止，不用相似骨名强配。
3. 自带 BoneProxy 的头部件优先保留其机制；不要再叠 MergeArmature。历史症状是映射 0 根骨。
4. 自带 MergeArmature 时回读映射骨数必须大于 0；`BaseToMerge` 在更换 FBX 后可能让对象存在但完全不渲染，此时重建该装配关系并重新施加派生材质。
5. 两者都没有时，只在明确的目标骨下建立 Harness 派生挂点；静态挂件用 `MeshFilter` 全量扫描，不能只查 SkinnedMeshRenderer。

## 决策树二：厂商变体与部件

- 先读厂商动画中的 `m_IsActive` 曲线确定实际分组与极性，再结合 solo 渲染识别语义；名字只作线索。
- 同套的兜帽、内衬等变体先比较层级、网格、材质和引用差异。只有确实需要同时存在并运行时切换，才复制最小差异对象；不要复制整套层级。
- 建 `_Outfit`、`_Hair`、`_Acc`、`_Gimmick` 分组，稳定命名并保留变体 id。整套服装互斥，配饰是否可叠加由方案决定。
- 每个导入素材都要有包外 GUID 引用；没有引用就是尚未接线，不得列为已使用。

## 决策树三：鞋型、袜子与穿模

1. 分开判断脚掌低于鞋底、脚趾穿鞋腔、脚型/高跟键未跟随、袜子与鞋的叠层冲突。
2. 形态键归“真正包住该部位的部件”，不机械归鞋。鞋套在袜外且袜按踮脚姿态建模时，鞋关掉后不能把脚恢复中性，否则脚会从袜子顶出。
3. 鞋开 → 鞋形态；鞋关且袜开 → 袜形态；两者都关 → 中性。多条件是“与”，表达“或”必须写两条转移。
4. 姿态类收缩键可随部件使用；删除身体区域的收缩键先量鞋/衣物包覆范围，只处理稳定被覆盖区域。
5. 不得粗暴缩小整只脚、隐藏无关身体或删除失败衣装状态。鞋底、脚趾和可见身体轮廓分别留证据。
6. 厂商自带 ShapeChanger 不是通过证据。先合并列出 ShapeChanger 与 FX 动画对同一身体键的全部写者；同宿主同目标键同时 Set/Delete 直接阻断，多宿主写同键必须解释先序与最终胜者。
7. 只要涉及脚型键，方案必须记录穿鞋袜、只穿袜、光脚三态；光脚必须恢复中性。像素更“干净”不能证明选择正确，因为删除脚部会系统性改善这类指标。

## BlendShape 与动画归属

- 厂商换装动画里直接写素体 `blendShape.*` 的曲线，迁移到派生 Shape Changer 后改值为 0，但保留曲线结构以避免状态残留。
- 同名键**由装配阶段自动同步**（`OutfitStage.SyncBodyShapeKeys`，`D-139` ②）：件上该键没有任何驱动、身体那侧可能不为 0（已装件的 MA Shape Changer `Set`、挂载控制器里非零的曲线、或素体默认权重）时，自动加一条 MA BlendshapeSync 跟随**写着这个键的那块素体网格**；补了什么写进 `outfit.json` 的 `blendshape_sync`（件、键、跟随网格、理由）与观测 `clothing.install` 的 `blendshape_sync_followed_keys`。它没覆盖的三类仍要交人：件上本来没有这个键（要补帧）、参照键在当前素体版本上不存在、厂商有意固定的件。
- 形态跟随触发它的部件，而不是整套衣装。脱鞋仍踮脚、换胸衣后衣物不跟随，通常是归属层级错误。
- 每条 MA BlendshapeSync 同时验证参照网格存在源键、服装本地网格存在目标键；组件存在但键名在当前素体版本缺失属于静默空转，必须阻断。
- 一条属性只能有一个权威写入者；发现菜单层、厂商层和装配层重复写时，只记录事实并把最终所有权交给菜单阶段处理。

## 完成与异常恢复

- 每件单独开启时可见；MergeArmature 映射非零；主干零缺失；静态挂件无遗漏；每套收缩键均有“需要/不需要及原因”。
- T-pose 只证明静态装配。袖口、裙摆、腋下、鞋底和动作组合交给正式回归状态集，不自行宣布通过。
- 修改必须幂等；重跑前识别并更新自己的派生对象，不叠加第二套组件。单项尝试无效时精确回退该 Prefab override，不使用全局撤销栈。
- 缺骨、引用不明、审美冲突或安全归属无法决定时，保持原形并报告最小决策缺口，不替用户重设计造型。

Runtime 随后执行受控 Unity 步骤并独立读取骨骼、引用、显隐和装配观测；你的文字说明不是证据。

`plan/0.3` 的装配成员由 `avatar_config` 的非材质组展开，不能只检查旧格式顶层 `outfits`。保存装配结果后，Runtime 另起只读的 `OutfitStage.Observe`，重新加载保存的头像并比较方案默认显隐与材质，产出 `avatar.observe.group_defaults_match`；`clothing.install` 的施工诊断不能替代这份观察。`assets.validate` 另从素材 GUID 与 Harness 资产引用测量包外引用，缺数据须补齐观察，不能视为通过。

## 局部方案复核与返工

装配发现原方案未覆盖写者时，AI 可在既有目标及素材授权内，通过 outfit goal 的 shrinkkey_review 操作提交局部修订。完整实际写者和顺序、来源观察、源资产、无冲突值及三态预期由 Runtime 校验；只登记技术方案补充，不改变原方案批准、接受脸型或旧证据，也不代表三态实测。多宿主须解释先后及最终胜者。缺证据应补探查/返工；超出授权或需外观取舍时给出中文具体选项，交已有确认入口，不让用户修改 YAML。
