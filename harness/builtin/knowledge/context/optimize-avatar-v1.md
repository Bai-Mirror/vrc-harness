# 性能优化上下文 v2

你负责在不破坏外观、功能、变体和菜单语义的前提下降低交付态成本。顺序固定为：基线 → 定位 → 一次一个可逆改动 → 重建测量 → 外观/功能回归 → 保留或回退。

## 证据口径

- 只在 NDMF/插件处理后的隔离克隆体上测交付态，同时保存源场景基线；不要在源对象上直接烘焙或把编辑期面板数当最终结果。
- 每份报告记录目标根、能力包版本、构建槽、纹理内存、网格/面数、材质、骨骼、BlendShape、PhysBone、碰撞开销、AABB 和 Console 错误。
- 优化前、每个中间动作、优化后分别留报告。任何差异都要能归因到一个动作；不能解释的差异必须回退并重测。
- 性能评级是观测，不是目标替代物。多套高模服装仍为 VeryPoor 可能是正常取舍，减面或删功能必须得到用户授权。

## 决策树一：死对象与材质

1. 仅当对象未激活、没有动画曲线指向它或祖先、也没有组件字段引用时，才进入删除候选。
2. `_Gimmick`、缩放为 0 的占位对象和构建期引用属于高风险假阳性，默认保留。
3. 清理空材质槽和真正无人引用的贴图；不得因为当前状态不可见就判断“未使用”。
4. 每次删除后回读引用、构建并比较骨架高度；失败时精确恢复该 override。

## 决策树二：纹理

- 格式以运行时 `Texture2D.format` 为准；`.meta` 中 `textureFormat: -1` 是 Automatic，不能证明没有 RGBA32。法线图的 DXT5nm 不按普通 DXT5 处理。
- 先查格式和死槽，再做尺寸分档。只降不升，保存逐项回滚表。主视觉图通常不低于 2048，遮罩/普通部件与小件按实际屏幕占比决定。
- `design.json` 必须逐 GUID 覆盖优化前构建实际使用的纹理；每项明确 keep/downscale、目标、理由和审美复核证据，不能让固定常量替 AI 作设计决定。
- 插件数据纹理不在此列：例如 VRCFury SPS 把浮点数据写进一张 RGBA32、无 mip 的宽 8192 纹理并绑到 `_SPS_Bake`（`SpsBakedTexture.Save`、`SpsConfigurer`）；压缩或缩放会破坏数据。它既不需要设计覆盖，也不进贴图方案；格式／分档／尺寸审计同样不算它（以材质属性判定，不按大小或格式猜），但 SDK 的总显存统计仍包含它。
- **「数据用途」与「视觉用途」是同一张图上的两件独立事实**：判据里的 `role` 是贴图方案的角色（数据写入保护优先），`visual_role` 才是审计按哪一档校验。同一张图既绑数据属性、又绑 `_MainTex`／辅助属性时是**绑定冲突**：它仍然不进方案（压缩会毁数据），但**照样按视觉角色**做格式／分档／Mip／主图红线检查，`perf.json` 里 `mixed_use=true`、notes 与 `optimize.json.data_textures` 都写明冲突；不能因为它带数据就把它从美术检查里放行，也不能为了让它过检查就去压缩它。同一张图被多个视觉属性绑定时取更严的角色（main > cube > aux）。
- 完整盘点后没有主图（合法纯材质颜色形态）是已证实的空适用集合，主图红线按现有规范化记 2048，不是 `no_data`；缺 pre 基线仍然是 `no_data`，不当零。
- **纹理尺寸对比要求基线里真的有一份纹理盘点**：`perf.json.textures` 必须是数组，明确的 `[]` 才是「完整的空盘点」（纯材质颜色形态）；键缺失、值为 null、类型不对、条目缺可用宽高（`max_size`／`source_size`，旧工具写的条目回退 `width`／`height`）时，`textures_above_baseline` 保持未测（`no_data`），不折成 0。0 会让「比基线大」恒不成立而假通过；旧基线的尺寸回退也要落在**有效宽高**上，缺尺寸不是 0。视觉角色只识别 `main`／`aux`／`cube`。**唯一豁免是明确的数据专用条目**（`role=data` 且没有 `visual_role`）：它本来就不参与视觉尺寸审计，可以没有尺寸；角色缺失、未知 `role` 或未知 `visual_role` 的条目一律保持未测，哪怕它记了有效宽高，或另一字段写了已知角色。未知视觉用途也不能归为数据专用——它可能正是没被比较的视觉图，放行等于让没量过的维度报 0。
- 所有显眼降档做同机位 A/B；被独立审查看出差异时恢复。平台覆盖在编辑器不可验证，应明确标记待真机。
- **审计只判「这次运行为它负责的贴图」**：pre 盘点里的贴图（优化设计拿到的就是这一份，方案必然覆盖它），加上本次套用方案真的写过的导入设置（`_harness_build/final/project/.texture_plan_applied.json` 的 `texture_changes` 里没有 `unchanged` 的条目）。两者都不在的贴图——只在构建期出现、菜单层与 pre 都没有的那些——设计从没点过、本次也没写过，交付的就是它原本的导入设置：它不进 `textures_without_mipstreaming`／`texture_tier_audit_failures`／`uncompressed_texture_count`，也不参与主图红线，只按路径记进 notes 并计入 `textures_carried_over_from_vendor`。这不是放松对 Harness 的检查：本次写过的贴图一律照判（拿套用明细里的改动前导入上限当「优化前」），pre 基线不完整时不豁免任何一张。
- Mip Streaming 是构建要求；修改后必须回读，而不是只记录脚本退出码。

## 决策树三：AAO、PhysBone 与 AABB

- Trace And Optimize 必须实际挂在活跃 Avatar Root；“安装了包”不等于有组件。AAO 可能重排材质槽、重打 UV、生成单色贴图并合并蒙皮，之后专门检查材质错位、接缝和死参数。
- PhysBone 256 是硬上限。先按链、参数、碰撞体和影响骨数清点；只有逐字段等价的重复组件才可去重。
- `perf.json.physbones` 给出对象、组件序号、根、影响 Transform 数、碰撞体数和 `redundant_with`；只有后者证明的“逐字段等价且碰撞体为子集”关系可进入自动删除，其他合并必须停下做动态验证。
- 合并 PhysBone 时把非源链加入 `ignoreTransforms`，防止 Spine、UpperLeg、眼睛等误入物理链。空的 MergePhysBone 会中止预处理。
- Harness 会在优化层与最终构建层同时阻断无效 MergePhysBone，以及任何未被 `ignoreTransforms` 排除的人形核心骨覆盖。无子骨且 `endpointPosition == 0` 的组件只列为 `noop_physbones` 候选，不会绕过设计记录自动删除；非零 Endpoint 代表虚拟末端，必须保留。
- AABB 上限按 5×6×6 m 检查，优先定位粒子和手柄撑大的渲染器，不用缩小整个头像包围盒掩盖根因。
- `aabb_contributors` 包含普通、粒子、Trail 和 Line Renderer 的世界包围盒与体积；先按贡献者定位来源，不能用排除粒子后的假 AABB 宣称通过。
- AAO 不保证减面。骨骼、BlendShape、蒙皮网格不应高于基线，面数若不变应如实记录。

## 回退矩阵

- 构建中止：撤销最近一个 AAO/PhysBone 配置，保留失败日志，不叠加第二个猜测性修复。
- 材质错位或接缝：回退材质槽重排/纹理优化，再单独验证其它 AAO 功能。
- 造型变形或静止姿态弹开：回退最近的 PhysBone/骨架动作，比较 Head–Foot 高度和人形映射。
- 纹理内存反涨：恢复本批导入设置，重新检查格式、平台覆盖和 mip，而不是继续降尺寸。
- 菜单或动画失效：优先恢复导致路径删除/改名的优化；不能删功能来让死参数检查归零。
- 只有性能数字未达目标但外观与功能正确：报告真实瓶颈并请求用户选择，不自行越过审美边界。
- 每次重试都从源工程重新镜像 final 构建副本，因此撤销某项只需把该 GUID 改回 keep；`texture_plan.json.rollback` 保存应用前导入设置，禁止在失败副本上继续叠加修改。

## 完成条件

优化后纹理内存不高于基线（合法无改动——preserve，或本来就合规、这一批全部 keep——与下降一样通过，反涨才失败）；无未解释的未压缩格式；PhysBone 不超过 256 且无确认重复；AABB 在界内；Console 无 Error；骨架、材质、菜单、所有正式衣装状态和鞋底/身体穿模回归均保持通过。前后报告和逐项回滚记录进入交付证据。

Runtime 将重新构建并独立比较所有指标。你的估计、Scene 目测或“已安装优化插件”都不算验收。
