# 方案阶段：需求拆解与方案边界

把用户原话、建档记录与参考图结论收敛成一份可以逐条核对的方案。本文件每节可单独注入。

## 厂商材质选择：服装与完整目录决定槽集合

已接受厂商既有配色时，在 `recolor.targets` 写 `{requirement_id: bag_pink, outfit: winter, material: Assets/Vendor/Materials/Bag/Pink.mat}`。`outfit` 必须是方案中的服装 id；`material` 是受管材质资产完整路径。不要同时写 `part`、`layered`、`layer`、`color`、`semantics` 或 HSV 字段，不把可执行替代只写在 `deviations`。

Runtime 先找该服装根，再匹配当前材质与目标材质的**完整父目录相同**的全部非粒子渲染器非空槽，直接引用目标材质，不改厂商原件。不能只比较末级目录名或路径包含关系；另一套服装不受影响。多个命中槽全部替换，零命中失败。整槽材质选择与同槽任何相对调整或按层绑定相交时显式报告冲突，不能靠目标顺序消除。第二层眼色调整与主贴图睫毛替换可以共用同槽最终副本，且可与其他槽的材质选择共存。

结构提交通过不等于计划可执行。计划阶段尚无可靠槽观察时可提交草案，不自报可执行性通过；配色阶段必须从当前服装预制体版本展开继承与覆盖，核对每条材质目标命中数大于零、无写入冲突，并在独立重载后读回实际目标 GUID。观察不对应当前方案和资产版本时不通过。厂商配色的主辅色角色仍由预览关口确认。

## 方案阶段：把需求原话收敛成约束表

- **职责**：动笔写方案前，先把需求原话整理成约束表，方案里的每个决定都要能指回其中一条。
- **权威输入**：用户原话（Manifest 的需求文本、`需求.md`）决定审美意图；`建档.md` 与 `inventory.json` 决定技术可行性。两者冲突时，意图听原话，可行性听实测清单。
- **约束表的栏目**：
  - 素体、排期类信息（有就抄，没有就写「未提供」）。
  - **加购项**：它决定工作量的边界，漏掉一项就是少做或白做。
  - 整体色调、撞色、眼睛、头发、服装、风格偏好。
  - **避雷项**：否定式要求（「不要粉色」「不要露脐」）和正向要求同等抄录，放在最显眼处。否定式要求最容易在施工中一点点被违反。
  - **结构性要求**：例如「服装做部位拆分」。这是菜单架构问题，不是配色问题，越早写进方案越省返工。
- **决策边界**：只整理、收敛，不替用户新增需求；原话含糊的地方照原话记录，并标「待确认」。
- **禁止**：把形容词直接当方案（「可爱一点」不是方案）；省略避雷项；把需求来源缺了哪份当成「没有要求」。
- **产出**：`notes` 只写结论（方案字段表把它定为一两句）：点名避雷项与结构性要求怎么处理；改色目标只落到原话提到的部位。
- **怎么验证**：逐条对照原话，每条约束在方案里有对应处理，或写明「不在本流程范围」。
- **升级给人**：需求来源缺项（例如只有订单信息、没有问卷）、原话前后矛盾、加购项与所选素材对不上时，在 `notes` 写明阻断，由方案审批人决定。

## 资源余量：参数位与 PhysBone 预算写进方案

- **职责**：方案里的开关数量要装得进 VRChat 的硬上限，并给后续功能留余量。
- **权威输入**：`建档.md` 的「预算余量」段（清点工具写入）；VRChat SDK 的上限。
- **上限（SDK 3.10.4 下）**：同步参数合计 ≤ 256 bit，其中 Int、Float 各占 8 bit，Bool 占 1 bit；PhysBone 组件总数 ≤ 256。
- **余量**：清点工具默认给 PhysBone 留 16、给参数位留 32。面捕、VRCFury 类插件、尾巴与配饰都会占位；开关多的需求要先估「还要给面捕和插件留多少」。曾有工程停在 PhysBone 255/256，零余量，再挂一根就超限。
- **取舍**：余量写小了，客户加功能就超限、要砍；写大了，浪费参数位。两个数都要记录，菜单阶段用实测值对账。
- **决策边界**：方案只估算与取舍，不做参数实现。
- **禁止**：设计会吃掉余量的开关数量；用「应该够」代替估算。
- **怎么验证**：按类型给每个新开关计 bit（Bool 1、Int 8、Float 8），新开关合计＋素体与插件已有参数＋余量 ≤ 256。
- **产出**：`notes` 只写结论数字：新开关合计多少 bit、已有参数与余量、装不装得下。
- **升级给人**：估算超限时，列出建议合并或砍掉的开关，交人决定。

## 面捕设备与目标平台：两个问题分开确认

- **职责**：把「要不要面捕、用哪套面捕硬件」与「上哪个平台」分开确认，并算清要做几个头像根。
- **决策边界**：只确认与记录，不做面捕装配；根数或平台超出本流程时只记录、不施工。
- **权威输入**：用户原话；素体与面捕插件包里的头像根命名。
- **要点**：
  - 这是两个问题，不能合并成「要面捕的 Quest 版」。
  - 厂商常把 `HD(Quest,Pico)`、`HD(VIVE)` 之类写进头像根名，它指的是**面捕硬件预设**，不是目标平台。拿着名字猜，会装错一套预设。
  - 一个场景里可以同时存在多个头像根，上传时选其中一个。每个根有自己的 blueprintId，方案里的每项改动要在每个根上各做一遍。
- **判据**：设备型号与平台各记一行；面捕预设与客户实际设备逐字对上。
- **禁止**：用平台名反推设备；只改一个根就当全部完成。
- **产出**：`notes` 用一句写明要交付的根数与用途。本流程只做 PC 版、只造一个头像根；原话出现 Quest、iOS 或面捕要求时，写明是否超出本流程范围。
- **怎么验证**：`notes` 里写到了设备与平台，要交付的根数与客户要求一致。
- **升级给人**：设备说不清时写「待确认」，交人问客户。

## 参考图结论进方案：想往哪走与能往哪走取交集

- **职责**：把参考图解读给出的方向，落成素体和已选素材真正做得到的方案。
- **决策边界**：只能在交集内做决定；不新增键，不自由改顶点。
- **权威输入**：参考图解读的汇总（方向、hex 色值、候选组）；形态键枚举清单；清点结果里的已选素材。
- **要点**：
  - 参考图解读只说明「想往哪走」；素体实际提供的形态键与贴图才是「能往哪走」。**两边取交集才是方案**，否则会出现凭空发明、实际不存在的键。
  - 捏脸只调厂商形态键，不自由编辑顶点造型；方案引用的每个键名都必须在枚举清单里。本流程不含捏脸，这条适用于完整定制流程。
  - 配色方向给具体 hex，再换算成改色目标（部位＋色相、饱和度、明度的调整量），不写色彩形容词。
  - 参考图结论与建档冲突时以建档和用户已定的为准。例如建档已定「两个发型都装」，就不能按参考图结论改成二选一。
  - 不拿「客户买过、但建档判为不装」的素材推风格。
- **禁止**：只写「可爱一点」「帅一点」这类不可执行的方向。
- **怎么验证**：方案里每条审美决定都能指回原话或参考图的具体特征；每个改色部位都属于已选素材。
- **产出**：方案里的审美决定（改色目标等）附上依据。
- **升级给人**：方向落在可行域之外，或参考图与原话冲突时，给 2～3 组互斥候选，交人挑选。
