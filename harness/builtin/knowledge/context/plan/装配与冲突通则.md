# 方案阶段：装配分诊与冲突语义

本文件给方案阶段：预判每件素材怎么装、哪些东西会打架、按什么语义处理，以及哪些决定只能留给人。方案阶段不打开 Unity、不施工；具体实现由后续阶段完成。每节独立成立。

## 装配分诊：按素材自带什么分类，不按名字

- **职责**：为方案里的每件素材预判装配方式与主要风险。
- **本流程（pc-recolor-outfit）只装①②两类**：装配由 Runtime 按 `plan.outfits` 逐项实例化，不读 `notes`：自带 MergeArmature 或 BoneProxy 的原样用，两者都没有的调 MA Setup Outfit（找不到 Hips 就抛错，整个装配阶段失败）。所以只有①②两类能进 `outfits`（⑦随所属那套一起进）；③～⑥类配饰本流程装不了，列进 `outfits` 会让装配阶段报错。遇到时在 `notes` 写明并作为阻断交审批人：改走有配饰阶段的流程，或由用户明确表示不要后列进 `unused`（reason 写 `client_declined`）。下面七类的具体装法只适用于有配饰阶段的流程。
- **权威输入**：素材清点结果里的组件与骨骼事实（预制体上有哪些组件类型、有无 `Armature`、骨名是否与素体人形主干对得上）。清点里没有这些事实时，标「待装配阶段探测」，不按名字猜。分类依据是「它自己带什么」，不是它叫什么。
- **七类与装法**：①整套服装或发型（有 `Armature`，骨名与素体人形主干对得上）→ Modular Avatar MergeArmature；常见错误是比文件名判兼容，应当比骨骼。②自带 BoneProxy 的件 → 原样用，不再加 MergeArmature（加了会映射 0 根骨）；BoneProxy 编辑期不生效，编辑期看着没动是正常的。③环状件（戒指、腕饰、头环、颈环：有孔、要套在肢体上）→ 算出孔轴与孔心后直接父子挂骨，位姿全部算出来，不靠手填。④带骨架的非人形配饰（耳、尾）→ 挂厂商的转接节点；挂完要查骨段长度，否则静态全对、动骨一跑就甩飞。⑤悬浮或贴面件（发饰、面板、光环：无骨或单骨）→ 按参照面摆，参照面是渲染出来的那个面，不是骨骼位置或包围盒，且多数是顶端对齐。⑥抱持类 → 物体挂在胸前，手臂姿势走 Additive 层；手臂放进 Gesture 层会在关掉时把手臂写死。⑦骨架内部的静态挂件（`MeshFilter` 加 `MeshRenderer`，塞在 `Armature/…` 下）→ 跟它所属的那组走；最容易整个漏掉，要按渲染器类型全量捞。
- **跨素体的通用配饰包**：面向别的素体做的配饰，装到新素体上先按素体尺寸等比缩放（比例从厂商渲染图上量），再调位置；先调位置会得到「位置对了、大小离谱」，返工两次。
- **位置几乎重合的相似件**：先问它们是同一个东西的两种样子（变体，二选一），还是本体加挂在上面的装饰（跟着本体一起开）——两者接线相反，不按包围盒或名字定；判不了就标「待装配阶段量」。
- **禁止**：按商品名或文件夹名判兼容；在方案里写死装配阶段才能探出的对象路径。
- **升级**：素体人形主干骨缺失、或某件无法归入任何一类时，在方案里记为阻断，不用相似骨名硬配。

## 方案里的装配字段：素体件剔除与收缩键复核怎么填

- **职责**：本流程的装配阶段只读方案，有两类装配决定必须在方案里写好：哪些素体自带件在构建时永久剔除（`hide_body_parts`），哪几套服装的收缩键要人复核（`outfits[].shrinkkey_review`）。**永久剔除仍归方案**：它是构建时整棵去掉、不能按套恢复的，改变它需要正式方案返工及批准。**可恢复的默认显隐改由装配执行方依证据决定**（`D-138`）：装配完成后 Runtime 给出默认状态下实际可见的部件与重叠量距，执行方用带理由的 `object_state` 关闭不该默认显示的件；只有取舍会改变用户要的外观时才请用户选。写者复核遗漏可以走装配局部方案复核。
- **`hide_body_parts`**：素体预制体根下的对象路径列表（相对素体预制体根，逐字照抄）。Runtime 把它们 `SetActive(false)` 并标 `EditorOnly`，构建时整棵剔除；这是永久的，不能按套切换，厂商开关也开不回来。怎么选：按厂商开关动画与菜单资产核对（哪条 `m_IsActive` 曲线、哪个参数管它，换上外购整套时厂商让它关还是开），不按名字猜。只填「每套外购服装下都不该出现、也不需要按套恢复」的件；需要按套切换的不填这里，交给菜单设计，菜单做不到时在 `notes` 写明交人。厂商开关还连带写骨骼或形态键的件，`SetActive` 剔除不会带出这些连带效果，要在 `notes` 写明风险。
- **`shrinkkey_review`**：逐套读服装预制体的 YAML，找 MA Shape Changer 组件（`m_shapes` 列表，旧版叫 `Shapes`；每项有目标网格 `Object.referencePath`、`ShapeName`、`ChangeType`，0 为 Delete、1 为 Set），列出宿主、目标、键名与类型。出现任一情况，这一套就必须填复核：①键名命中脚部（`foot|toe|ankle|heel|足|脚|踝|爪`，不分大小写）；②同一目标的同一个键被这一套里的多个宿主写。填法：`status: approved`；`rationale` 写键类别、宿主与鞋型为什么匹配，多宿主写清谁先谁后、最终谁胜；命中脚部键时，`scenarios` 必须含 `shoe_on_sock_on`、`shoe_off_sock_on`、`barefoot`。复核随方案一起由审批人批准，没做完不写 `approved`。
- **素材还没解包时**：方案在 setup 之前写，工程里还没有厂商文件，预制体 YAML 要从素材包的 `.unitypackage`（tar.gz，每个资产一个 GUID 目录，内含 `pathname` 与 `asset`）里读。读不到就在 `notes` 写「收缩键待装配探查与局部复核」，由真实 setup/outfit 证据补齐，不自报批准，也不因尚未导入而阻断整个方案。
- **禁止**：按名字猜素体件；把服装的路径写进 `hide_body_parts`；同一宿主同一键同时有 Set 与 Delete 时指望复核放行（装配检查照样阻断，要在 `notes` 写成阻断、换预制件）。

## 冲突语义：关一次、一直压、同位互斥

- **职责**：方案里凡是「开 A 时 B 怎么办」的需求，先按语义归类，写清用户可感知的行为；具体接线由菜单阶段实现。
- **唯一的分类问题**：用户之后还能不能自己把 B 打开？
- **甲·切换时顺手关**：关一次，用户之后还能再开 → 用 `VRCAvatarParameterDriver` 改 B 的参数。写成属性会让 B 永久打不开。
- **乙·开着期间压制**：A 开着就一直压 B，A 一关 B 自动回来 → 单独一层写 B 的属性，排在部位开关层与整套层之后；该层的默认状态 clip 不写任何曲线（WD=OFF 下未写的属性从前面的层原样透传）。用 Driver 会让用户手动开回来后又穿模。判据：关掉 A 之后 B 能自己回来；回不来就是被别的层写死了。
- **丙·同位置互斥**：两件同位置的东西不能同时出现 → 定优先级链，只压低优先级那一侧；两个方向都压会两边一起消失。
- **记法**：改参数 = 关一次；写属性 = 一直按着。
- **本流程的菜单能表达什么**：菜单由 Runtime 按 `design.json` 生成，每个开关是独立的两态层，没有 Parameter Driver、组合条件或压制层。只能表达乙的一种形式：把 B 并进 A 的开关（A 开时 B 关、A 关时 B 回来），B 不再有自己的开关。甲和「几个开关组合决定」的压制本流程做不到，方案里遇到时在 `notes` 写明并交人。
- **互斥接线的三层分工**：互斥的另一半归被控层自己（B 的层 On 写 `A=false`、Off 写 `A=true`）；排在后面的层只在需要强制时写，其余档位两个属性都不碰；「顺手关」用 Driver 改参数。把 `A=false` 无条件写进后面那层的每个 clip，等于把 A 永久压死。
- **禁止**：在方案里把三类笼统写成「互斥」；让同一对冲突两个方向都压。
- **升级**：用户原话分不出是「关一次」还是「一直压」时，在方案里列出两种行为与各自后果，交用户选。

## 同位互斥：一条全局优先级链，验收遍历组合

- **职责**：同一身体位置有多个来源（素体、各套服装、各档发型、外购配饰）时，方案给出一条全局优先级链（例：头饰 > 服装头部小件 > 耳朵），冲突一律按链压。
- **为什么**：两条方向相反的压制规则同时成立，会互相把对方压没，用户看到的是「这个位置什么都没有」，而不是「某一件没显示」；逐条检查规则查不出来，因为没有任何单条规则出错。
- **判据**：冲突表里同时出现「A 压 B」与「B 压 A」就是错的，不管是不是同一批加的；表里每一条都要说得出它在链上的位置，说不出的那条是多余的。
- **验收要求（写进方案，由后续阶段执行）**：遍历「档位 × 冲突开关」全组合，对每一格断言「这个身体位置至少有一件是开的」，死锁格为 0 才算过；断言用真实动画数据驱动，手动开关物体证明不了动画层会怎么写。
- **禁止**：方案里出现无序或成环的压制关系。
- **升级**：优先级取决于审美（例如两件都想露出）时，列出选项交用户定。

## 厂商已有的参数层与分组是权威答案

- **职责**：方案决定「沿用厂商开关，还是新建开关」时的默认取向。
- **规则**：凡是厂商已有参数层的东西，一律驱动参数，不直接写网格。一个厂商开关往往同时驱动网格显隐、骨骼姿势、别的网格上的形态键；只写网格必漏，症状是「网格在，但形状或位置不对」。
- **能驱动就别另写**：能直接驱动厂商参数的流程里，挂厂商参数不占新的同步位，厂商的联动（互斥、骨骼姿势、摆动动作）全都白拿。
- **本流程怎么接**：菜单由 Runtime 按 `design.json` 生成，控件不能绑定厂商参数（厂商已占用的参数名会被拒绝），也没有 Parameter Driver。接厂商机制的唯一办法，是把各套的厂商 ON/OFF 动画登记为部件开关的 `vendor_clips`，由 Runtime 把其中全部曲线（显隐、形态键、材质、骨骼）复制进本单的开关层；代价是厂商原菜单里对应的开关对这些属性不再起作用。任何阶段都不能写厂商的参数资产与控制器；默认值不合适时，在 `notes` 写明交人。
- **分组看厂商动画**：扫一遍厂商动画里所有 `m_IsActive` 曲线的路径，就知道哪几样是一组；比按名字猜可靠——同一个名字可能既是参数又是 GameObject，管的根本不是同一件事。
- **方案里怎么写**：`notes` 只写结论：哪些功能走厂商 ON/OFF 动画、哪些需要新增开关（新增的附一句理由）。
- **禁止**：为厂商已有的开关另设一套只控显隐的开关。
- **升级**：厂商参数层的行为与用户要求冲突（用户要的组合厂商不支持）时，列出冲突交用户选。

## 头像根的四种数法：交付与验收只认活跃根

- **职责**：方案与报告里凡是提到「几个头像根」，都要说清口径。
- **四种口径**：①场景根：场景里所有带 `VRCAvatarDescriptor` 的物体，含停用的，用于排查「改动做了几遍」；②全场景 descriptor：连预制体实例、备份预制体一起数，用于清存档、查 `blueprintId` 撞车；③**活跃根**：当前交付态、会被上传的那一个，交付与验收一律用这个口径；④含备份预制体：`Backup/`、`bk_*.prefab` 这类按头像生成的整份副本，用于清理与依赖盘点。
- **量级参照**（成文时的历史工程）：同一工程 15 个场景根、2 个活跃、存档里 2 个 descriptor；另一工程报的「7 个」其实是两次运行混在一起数。
- **判据**：写「只有 1 个」必须点明口径（默认指「只有 1 个进构建」）。备份预制体常常也带 `blueprintId`，会顶掉线上版本。
- **面捕安装会克隆头像**：安装器复制整个头像，场景里变成两个、原件被停用，按名字找头像的工具都会改错对象。面捕装完核对只有一个活跃根；模型修改一律做在原件上，面捕根可以重新生成。
- **旁证材料先核**：历史工程的个人存档里常有多根与坏引用残留，只能当反例，不能当「应该怎么做」的正样本；历史分析报告里的「事实」引用前回原文或文件核一遍。定妆照目录可能混着多次运行的出图，按文件名排新旧不可靠，取图前先看生成时间或运行批次。
- **禁止**：数不拢时删根；按名字认头像根。
- **升级**：数不拢或发现两个活跃根，停下报告；删除动作交人（删错根会丢线上版本）。

## 排期依赖：换 FBX 会作废配色与装配

- **适用**：方案里同时有「改素体 FBX」（捏脸烘焙、换网格）与配色、服装装配时。
- **机制**：换 FBX 会重置渲染器的材质数组 → 已施加的配色要重来；`ArmatureLockMode.BaseToMerge` 会把外套骨架同步到素体骨架，换 FBX 后必然错位，表现为「外套 GameObject 在、但完全不渲染」→ 已装好的每套服装要拆装一次。只改顶点、不动骨架的改动不受影响，但那是少数，默认按会作废来排。
- **排序**：改 FBX 的步骤排在配色与装配之前，否则就接受这两步返工。面部追踪被捏脸阻塞，捏脸未通过不能开工；面捕安装排在全部作业之后。
- **捏脸的手段**：只调厂商形态键的数值，不自由编辑顶点造型；动网格只作烘焙后的局部修复；形态键允许外推到 0–1 之外。
- **覆盖 FBX 之后**：重挂材质并扫一遍空材质槽，再进入配色或装配。
- **禁止**：在 FBX 定稿前做最终配色或装配验收。
- **升级**：用户要求的顺序与这条依赖冲突时，列出会返工的范围，交用户确认。

## 方案里的人工卡口：哪些决定只能留给人

- **职责**：方案标出哪些决定只能由人做，并按此安排其余工作。
- **本流程（pc-recolor-outfit）的卡口**：①清点后的素材缺口确认；②方案批准，配色方向随方案一起定；③配色落实后的外观批准（recolor 之后、菜单之前）；④SDK 上传与客户端实测。阶段严格串行，每个卡口都停下等人。配色不由模型评审自动定案：评审意见只写进说明供人参考，定档由人在外观批准时决定。
- **完整定制流程另有**：捏脸定形：键值由委托方亲自定、必须可复现，「这张脸对不对」只有本人能判，返工代价最高；出候选、烘焙、导出、校验可以全自动。
- **必须由人执行的素材操作**：面捕（FT Addon）安装会克隆整个头像，排在全部作业之后；指甲（如 HoroNail）的 GUI Execute 走「Play 模式触发、组件自毁」，结果不能持久化，界面是 UIElements 树、无法安全地脚本化点击，只能由人执行。本流程的装配阶段没有等人操作的步骤，Runtime 会照常装配并测量；用到这类件时在 `notes` 写成阻断。
- **等人的时候**（人工作业时）：卡在定方向时，可以清点、找缺件、准备工具；卡在捏脸调值时不动场景（委托方可能正在手调）。本流程阶段串行，等人期间不会推进别的阶段。
- **禁止**：把审美取舍伪装成技术决定写死在方案里；为赶进度跳过卡口。
- **升级**：`notes` 只写需要人给出什么（一句一项），不展开成清单。

## 装配与冲突的症状分诊表

- **适用**：装配或菜单完成后出现下列症状时，先按表找第一嫌疑，再取证，不按症状直接改。
- 某个开关怎么点都没反应 → 排在它后面的层无条件写了同一个属性 → 扫所有层，找写同名属性且无条件的 clip。
- 某个位置一件都不显示 → 两条方向相反的压制规则互压 → 查冲突表里有没有「A 压 B」且「B 压 A」。
- 网格在，但形状或位置不对 → 厂商参数层还在按旧值摆骨骼，只写了网格显隐 → 改成驱动厂商参数。
- 关掉某件后，有东西留在原地飘着 → 骨架内部的静态挂件漏了 → 按渲染器类型全量捞 `MeshRenderer`。
- 外套 GameObject 在，但完全不渲染 → 换过 FBX，骨架锁把外套骨架同步坏了 → 拆装一次即恢复。
- 配饰静态全对，一动就甩飞 → 转接节点的骨段长度异常 → 查骨段长度与动骨链。
- 编辑期看着没装上 → BoneProxy 编辑期本来就不生效 → 不是缺陷，不要去「修」。
- 上传选错根，或报告里根数互相打架 → 场景里有多个根、数法不同 → 按「活跃根」口径重数。
- 开了配饰只见光秃秃的本体，装饰不见了 → 把装饰当成变体接成了互斥。
- 两件长得很像的东西互相穿插 → 把色变体当成装饰接成了同开。
- 换了材质却渲成实心或不透明 → 换 shader 时没有跟着换渲染状态。
- **升级**：表内嫌疑逐一排除仍无解时，带着取证结果交回。

## 局部方案复核与返工

装配发现原方案未覆盖写者时，AI 可在既有目标及素材授权内，通过 outfit goal 的 shrinkkey_review 操作提交局部修订。完整实际写者和顺序、来源观察、源资产、无冲突值及三态预期由 Runtime 校验；只登记技术方案补充，不改变原方案批准、接受脸型或旧证据，也不代表三态实测。多宿主须解释先后及最终胜者。缺证据应补探查/返工；超出授权或需外观取舍时给出中文具体选项，交已有确认入口，不让用户修改 YAML。
