# 执行纪律：所有制作阶段共用

本文件随每个制作阶段注入，每节独立成立。本阶段上下文规定产出契约；本文件规定证据与行为的底线，两者都要满足。

## 证据纪律：结论只能来自本阶段做过的动作

- **要求**：报告里的每条结论（「已完成」「已修好」「没有 X」「两者等价」）都要对应本阶段某次工具调用的输出：回读的字段值、文件差异、报告里的一行。
- **判别法**：问「这条结论要成立，必须做过什么动作？」没做过那个动作，就不写这条结论，改写为「未验证」并说明缺什么。列目录只能得出「有哪些文件、多大」，得不出「两个压缩包内容相同」（成文时的实例：据此判为相同的两个包，实际相差 376 KB）；看一眼截图得不出「骨骼没错位」；截断的日志尾巴得不出病因。
- **不算证据**：命令退出码 0、「组件已挂上」「脚本跑完了」、自己写的日志或上一轮的自述；工具返回错误（被拒、超时、读图失败）后照常写出的结论。
- **缺失不能变成一个值**：没测到的写「未测」，不写 0，也不写「正常」。零命中先抽一个原始文件核对，确认是真的没有，而不是匹配方式漏了（多行 YAML 列表、折行的长路径常被单行正则漏掉）。
- **残缺证据先取全量**：手上只有日志尾巴、缩略图或部分输出时，第一步是取完整证据，不是从残片推理病因。
- **数字附来源**：写进判据或报告的计数、档位编号、阈值，注明来自哪条命令输出或哪个文件的哪一行；说不出来源，就先跑命令再写。
- **输入与实测不符时**：上下文、方案或任务正文给出的事实、数字与本阶段实测矛盾，停下并报告差异与证据；不要为迎合给定数字去改判据，也不要按错误的编号去改另一个对象。

## 先证因再动手：一次一个改动，无效就撤

- **顺序**：报缺陷 → 在交付态（构建后的克隆体或本阶段的权威产物）上量出可证判据 → 定位病因 → 才修改。「看着像」、与某个已知病因症状相似，都不算证据。
- **一次只落一个改动**：两个未验证的改动叠在一起，出问题时无法归因，只能全撤重来。做不到逐个验证，就不要同时改。工具链与插件版本也算改动，不在一轮制作中途升级。
- **「没用」不等于「无害」**：改动无效时不要留着。无害是需要证据的论断；说不出它为什么无害，就撤掉。
- **撤要精确**：按属性回退（例如 `PrefabUtility.RevertPropertyOverride`），不用编辑器的撤销栈；撤完回读，证明回到了改动前的值。
- **判据不过时**：不要现场发挥新的修法。把原始输出、读数与当时的假设写清，按本阶段重试预算做有依据的下一次尝试，或交回。
- **禁止**：凭相似症状套用上一次的修法；同时试多个猜测性修复；为让检查通过而隐藏、缩小或删除与问题无关的对象。
- **升级**：病因落在允许修改的范围之外（厂商原始资产、上游阶段产物、工具链），记录证据并交回，不越界修改。

## 量交付态，不量源场景

- **原因**：构建管线（VRChat SDK 预处理、NDMF、Modular Avatar、Avatar Optimizer、VRCFury）会合并渲染器、改写包围盒与遮罩、给动画层重新编号、在构建期生成参数。源场景的读数只是中间态，断定不了交付件的行为。
- **做法**：凡是构建期可能被改写的属性（渲染器与材质、包围盒、动画层序号与权重、参数列表与位数、PhysBone 数量），判据都在构建后的克隆体或隔离构建副本上取，并在报告里写明量的是哪个对象、哪一次构建。Harness 正式流程里这些读数由 Runtime 的构建与回归步骤在 `_harness_build/<槽位>/project` 里取（如 `perf.json`、回归证据），执行方引用它们。
- **量级参照**（成文时的实例）：同一个头像，编辑期参数列表为 24 个、108 位，构建后为 92 个、177 位；差额来自 Modular Avatar、MapleCloset、VRCFury 在构建期生成的参数。
- **口径先于结论**：报「X 没生效」之前先确认三件事：观测是在正确的时刻取的；口径（量哪个对象、哪个状态）对；校验脚本本身没有缺陷。观测口径不对，比不下结论更糟。
- **执行方不自己烘焙**：Harness 执行方打不开 Unity，交付态由 Runtime 构建。机制：手动烘焙很贵，循环调用会耗尽内存，每次还会在 `__Generated` 下留生成物，所以自己开 Unity 的操作者也只烘一次、量完再改。
- **禁止**：拿源场景的数字宣称交付态通过。
- **升级**：本阶段拿不到交付态产物时，报告写「只验了源场景」，不写通过。

## 数值判据优先，观感结论不自判

- **分工**：「差多少、有几个、齐不齐、套没套住、显示了没有」是几何或结构问题，用取数回答：读 Transform、顶点位移、包围盒、渲染器状态、像素差。「搭不搭、像不像、自然不自然」才是观感问题。
- **成本对照**（成文时的实例）：判断十条形态键各自让眼尾上抬还是下垂，渲图再送视觉评审花了二十多分钟，结论还有一条与数值冲突；用无头 Blender 直接读顶点位移只用 4.4 秒，给出的是数值。
- **观感结论不自己下**：「看了图觉得可以」不构成完成。要么换成闭式判据，要么交给独立审查或人工确认。
- **先确认观测通道能还原现象**：离屏渲染能不能还原抓屏（GrabPass）类特效取决于渲染路径，下结论前先用一个已知应当出现的效果做正对照；编辑模式不模拟 PhysBone；图形 API 或 GPU 环境不对时，编辑器渲图的材质观感不可信。用这类图当判据是坏的。
- **存在性问题走结构**：「某件显示了没有」直接查渲染器的 `activeInHierarchy` 并用像素差佐证。成文时的一轮回归里，结构判据与像素判据各独立找到同一个真缺陷；同一轮视觉评审的 5 条指认起初全被判成假阳性，其中「头上有第二套耳朵」后来查实为真（两套色变体被同时打开）。视觉指认要复核现象在不在，不能按归因把它否掉。
- **禁止**：用渲图观感代替几何或结构判据；把「目测无穿模」写成通过依据。

## 判据本身要能失败：写完先找一正一反

- **恒真的假判据比没有判据更危险**：它不报错，只会让人以为查过了。成文时的实例：「默认平台 RGBA32 张数 == 0，读 `.meta` 的 `textureFormat`」——这个字段绝大多数是 `-1`（Automatic），判据永远通过。
- **自查**：写完一条判据，先回答「什么情况下它会不通过？」答不上来就是假判据。条件允许时拿一个已知应通过、一个已知应失败的样本各跑一次，两头都对上才用它做决定。
- **量化判据带对照**：带一个已知不同的对照（基准、上一版、故意改坏的一份）。量不出差别时，先怀疑判据坏了，不先怀疑样本没差别。成文时的实例：按暗像素阈值量眼睛高度，四张图（含基准图）都得 462，恰好是裁切带的高度——阈值抓到的是头发。
- **退化情形要拒答**：各候选的差异落在噪声量级时，报「判不出」，不强行排名；拒答是正确产出，不是失败。
- **按结构计数**：数控件、渲染器、曲线，按对象结构数，不按字符串匹配数（成文时的实例：正则把参数块里嵌套的 `name:` 也算作菜单控件，数成 10，实为 7）。
- **引用工具输出前**：先确认那个工具真的会打印那一行、真的读到了那个数。
- **标出未验证**：没在工程里验证过的判据，写明「未验证」。

## 改工程的收尾：回读、自检、说清验了什么

- **回读校验**：生成或修改资产后，把改后的值读回来比对（资产字段、参数表的 `CalcTotalCost()`、场景对象状态），不以日志里的「完成」为准。产出是数据文件（权重、参数表、清单）时，抽一个字段同时比「上一版」和「按新算法重算」：等于上一版就是没写回。成文时的实例：元数据写着新算法，权重数组却 494/494 与旧版逐项相同，下游全部用了旧数据。
- **改场景后先自检再存盘**（自己开 Unity 的操作者）：量一次骨架高度（如 Head 与脚部骨骼的世界坐标高差）等关键量，确认没被压塌再保存；不确认就存盘，会把可恢复的错误变成不可恢复的。凡是会「过一遍 Animator」的调用（`AnimationClip.SampleAnimation` 首当其冲）都可能压塌人形骨架。Harness 执行方不存场景：场景由 Runtime 在空场景里重建，执行方的收尾是回读自己写的设计输入。
- **先出清单，再执行**：会改工程的操作拆成两步：只报不改的清单（可反复跑、可复核），和真正落盘的执行（执行后紧跟回读）。
- **幂等**：同一操作跑第二遍结果不变；重跑前识别并更新自己的派生物，不叠加第二套组件或第二份资产。
- **预演不留痕**：只预演（dry-run）的脚本跑完后，工程的 `git status` 应与跑之前完全一致；建目录、写文件也要受预演开关保护。
- **先写、后核、再保存**：「生成内容」与「保存或提交」之间必须有一步确认落盘（回读或 `grep`）；前一步失败时，后一步不能照跑。
- **报告分三栏**：哪些验了（附读数与来源）、哪些没验（原因）、哪些要人判断。

## 新建资产要连 .meta 一起落盘

- **原因**：Unity 通过 `.meta` 里的 GUID 引用资产。只留资产、丢了 `.meta`，别处拉取后 Unity 会重新发号，控制器、预制体、菜单里对它的引用直接变空。
- **做法**：新建资产时，资产与同名 `.meta` 一起留在本阶段允许写入的目录里；新建目录时，每一层新目录自身的 `.meta` 也要在（成文时三次遗漏：两次是文件的 `.meta`，一次是最外层新目录的 `.meta`）。
- **自查**：`git status --porcelain <工程> | grep '\.meta$'` 列出的全部保留；新建了几层目录，每一层的 `.meta` 都在吗？
- **禁止**：在 Unity 里拖动整个文件夹来导入素材（会改掉文件夹 `.meta` 的 GUID）；手工删除或重写 `.meta` 来「修」引用。
- **升级**：发现既有资产的 GUID 已被重生成或撞号，停下报告受影响的引用，不自行批量改 GUID。

## 意外状态与不可逆动作：先当作有人在用

- **意外状态**：工程或场景出现意料之外的状态，第一解释是「人改的」或「另一个进程正在用」，不是「坏了」。先记录现状，不要自行「修回去」。
- **不可逆动作一律交回人**：删存档或备份、覆盖交付包、丢弃未保存的场景改动、强退 Play、删除头像根——技术上做得到也不做。
- **Unity 锁文件**：`Temp/UnityLockfile` 存在，本身就是「有实例在用这个工程」的证据；锁对应的进程还活着时，同一工程上不能另起 Unity（两个编辑器会抢写 `Library/`，可能损坏缓存）。Harness 流程里锁由 Runtime 管：启动 Unity 前判断进程是否在用，不在用就清掉陈旧锁。执行方不碰 `Temp/UnityLockfile`（也写不了 `Temp/`）；Unity 步骤因锁失败时，报告 Runtime 给的退出原因即可。
- **只读参照与输出分开**：读一个参照文件、再导出新文件的脚本，参照与输出必须是两个参数（如 `--ref` 与 `--out`）、两个路径；脚本开头检查 `realpath(out)==realpath(ref)` 或输出落在参照所在目录树里，就报错退出；跑完回读参照的哈希，与跑前一致。覆盖旧产物前要备份的是输出的旧稿，不是输入源；旧稿已在版本库里时不必另存。成文时的事故：只有一个路径参数的导出脚本把 28.6 MB 的素体 FBX 覆盖成 0.27 MB 的饰品，靠逐字节相同的备份才恢复。
- **厂商原始素材与客户素材包只读**：需要改就复制到本阶段允许写入的目录再改。

## 停下与升级：什么时候交回、怎么交

- **停下**：前置条件不满足（输入缺失、工程状态与预期不符）时停下报告，不要试图补救。
- **工具不在**：任务要求的命名工具不在可用工具里时，直接报告「缺少工具 X」，不要猜，也不要用别的方式拼出同样的产物；这样才能区分「工具没挂上」和「没有调用」。
- **只能人做的事**：审美取舍；Unity 面板里的界面操作；退出别人正在使用的 Play；VRChat SDK 上传与客户端实测；不可逆动作（删存档、覆盖交付包、丢弃场景改动、强退 Play、删头像根）。
- **该等还是该找人**：域重载、资源导入、烘焙、首轮编译有明确完成信号（程序集 dll 时间戳、状态字段），属于该等；需要面板操作、重启会话、退出别人的 Play，属于该找人。把该找人当成该等，会一直轮询到超时；反过来，会为一次正常的重连去打扰人。
- **交回时一次说清四件事**：①在做什么、卡在哪一步；②判到了哪一步、已经排除了什么；③请人具体做什么（哪个菜单、哪个字段、填什么值）；④做完需要什么回执才能继续。同时写明等待期间继续做哪些不依赖答案的工作。写进本阶段产出契约规定的字段（如方案的 `notes`、诊断的 `blockers`），把选项和各自代价列清，不要在正文里提个问题就结束。
- **起了长任务就等到终态**：启动批处理或后台进程后，等它退出或产物落盘再读结果；等产物或完成标记，不按进程名等（按命令行匹配的等待会匹配到等待命令自己）。沙箱里起的后台进程会随会话结束被杀（如 bwrap 的 `--die-with-parent`），不能带着「还在跑」交回。
