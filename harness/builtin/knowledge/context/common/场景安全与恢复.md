# 场景安全与恢复：所有改工程的阶段共用

本文件随每个会打开或修改 Unity 工程的阶段注入，每节独立成立。它规定场景损坏的预防、恢复顺序和交回人的边界；证据与升级的一般底线另有规定。

## 不对人形头像调用 clip.SampleAnimation：验绑定只读数据

- **适用**：头像带 Animator 且是人形（Humanoid）绑定。判据看头像的绑定类型，不看 clip 里有没有肌肉曲线。
- **禁止**：`AnimationClip.SampleAnimation(avatar, t)`。它会把这段 clip 经 Animator 做一遍重定向；clip 里没有肌肉曲线时，整具骨架被写成零姿势塌掉。只含 `m_IsActive`、`m_Enabled` 这类布尔曲线的 clip 一样会塌。它直接写场景、不走 Undo，`finally` 里只还原 clip 碰过的对象救不回来；塌了以后再存盘，磁盘上的场景也坏了。
- **成文时的实测**：Kaguya 素体上，左眼骨世界 y 从 1.0551 掉到 0.339，Hips 从 0.7306 掉到接近 0。同一个工程里踩过两次；第二次是因为把「这条 clip 不是人形 clip」当成了安全判据，还把这条错误判据写进了工具注释。
- **做法**：验曲线绑定不采样。`AnimationUtility.GetCurveBindings(clip)` 列出绑定；`AnimationUtility.GetEditorCurve(clip, b).Evaluate(t)` 就是这一档应写的值；`avatar.transform.Find(b.path)` 判路径对不对，`GetComponent(b.type)` 判组件在不在。这足以回答绝大多数「这一档写了什么、写到了没有」的问题。非采样不可时，用 `AnimationMode.BeginSampling()`、`AnimationMode.SampleAnimationClip()`、`AnimationMode.EndSampling()`，它有自己的还原机制。运行时行为进 Play 用探针取数，不在编辑期模拟。
- **验证**：凡是可能经 Animator 写骨骼的调用之后，先比对几根已知骨骼的世界坐标，确认骨架没塌，再存盘。
- **升级**：已经塌了而且存过盘，按「场景已被改坏」的恢复顺序处理；恢复需要丢弃可能属于人的未保存改动时，交回人。
- **证据与适用条件**：机制属于 Unity 的人形重定向；实测只来自一个工程、一个素体。按禁止事项处理的理由是代价不对称：替代做法没有额外成本，误用的代价是整个场景。

## 开工记骨架基线，改场景后先自检再存盘

- **职责**：让每一次存盘前的场景状态都可证，不把可恢复的错误存成不可恢复的。
- **权威输入**：开工时量下的两三根已知骨骼的世界坐标（例如左眼骨与 Hips 的世界 y），写进本工程的状态记录。以后所有自检都与这组基线比。
- **做法**：工具里常备一个自检入口：读这几根骨的当前世界坐标，与基线的差超过容差即判坏，并把读数写进输出。源材料用的容差是 0.02 m，骨骼路径是 Kaguya 的层级 `Armature/Hips/Spine/Chest/Neck/Head/eye.L`；换素体时按该素体的实际层级取骨，容差按需要重新标定。
- **什么时候跑**：每次改完场景、存盘之前；进出 Play 之后，尤其是 Play 期间被脚本重编译打断过；调用过任何可能经 Animator 写骨骼的 API 之后。
- **顺序纪律**：先自检，后存盘。自检失败时不存盘，先按恢复顺序处理。
- **产出**：报告里写自检读数、基线与容差。
- **升级**：自检失败、而本阶段并没有做过会动骨架的操作（例如有人正在手动摆姿势）时，先当作人改的：停下，记录现状，交回，不要自行「修回去」。
- **证据与适用条件**：这套自检在一个工程里用于发现骨架塌陷和确认恢复结果；容差只在 Kaguya 上标定过。

## 场景已被改坏：按代价从小到大恢复

1. **还没存盘**：从脚本调用 `EditorSceneManager.OpenScene(path, OpenSceneMode.Single)` 重载。从脚本调用不会弹保存提示，直接丢弃内存里的改动。代价是重载会清空 Undo 栈，内存里若有人的未保存改动，会一起丢且撤不回来。`EditorSceneManager.ClearSceneDirtiness` 在 Unity 2022.3 不是公开 API，不要找它。
2. **已经存盘**：用 `Temp/__Backupscenes/0.backup`。这是 Unity 每次进 Play 时写的场景快照，二进制格式，Unity 能直接打开。先 `ls -la Temp/__Backupscenes/` 看时间：那次进 Play 必须早于损坏时刻，否则快照里也是坏的。步骤：复制成 `Assets/<某处>/_recover.unity` → `OpenScene` 打开 → 比对已知骨骼坐标确认这份是干净的 → `EditorSceneManager.SaveScene(场景, "<正式路径>.unity")` 写回（ForceText 设置下存成文本）→ 重新打开正式路径 → 删掉 `_recover.unity` 和它的 `.meta`，不要留进交付目录。
3. **快照救不回来的部分**：快照只在进 Play 时写。上一次进 Play 之后在编辑期做的人工改动（手摆的姿势、手配的组件）不在里面。
- **决策边界**：只有能确认内存里全是本阶段自己的改动时，才自行执行第 1 步。第 2 步会覆盖正式场景文件，执行前先留一份原文件副本，或确认它已在版本控制里。
- **升级**：场景里可能有人的未保存改动，或恢复会覆盖人的工作时，不执行，记录现状并交回。
- **证据与适用条件**：第 1、2 步在一个工程里实际救回过被压塌的场景（Unity 2022.3）；第 3 步是由快照写入时机推出的限制。

## 回退只撤自己的改动：按属性回退或回到记下的撤销组

- **禁止**：写「撤到判据满足为止」的 `Undo.PerformUndo()` 循环。撤销栈里不只有本阶段的操作，判据一有偏差，循环就会一路撤掉人的未保存工作，而且不报错。
- **成文时的事故**：循环的判据按名字找一根基准骨，而场景里有 14 个同名物体，`FirstOrDefault` 抓到的是另一个，永远对不上；循环撤了 300 步，把人刚在界面里配好、还没保存的美甲一起撤没了。最后靠逐步 `Undo.PerformRedo()`、以另一根骨是否离开原位为界才推回来。
- **做法**：
  1. 动手前记下撤销组：`int g = Undo.GetCurrentGroup();`（可配合 `Undo.SetCurrentGroupName` 命名）；要回退时 `Undo.RevertAllDownToGroup(g)` 一步回到起点，不需要循环。
  2. 预制体实例上的改动用 `PrefabUtility.RevertPropertyOverride` 按属性精确回退，撤完回读，证明回到了改动前的值。
  3. 实在要循环时，步数按本阶段实际做过的 `Undo.RecordObject` 次数封顶，不按判据封顶。
  4. 判据里定位物体一律用完整路径，不用名字。
- **升级**：回退范围可能碰到人的操作时，停下交回。判断能否靠重载场景回滚之前，先比较「场景最近一次存盘时间」与「人最近一次手工操作」：存盘版本里没有人的新工作，就说明重载会把它丢掉。
- **证据与适用条件**：事故来自一个工程；撤销组与按操作数封顶是该事故后定下的做法，没有在第二个工程上复现。「先比存盘时间」一条只见于早期经验记录，未实测。

## 会悄悄改坏场景或工程的调用：替代做法

| 调用或动作 | 后果 | 替代 |
|---|---|---|
| 对人形头像 `clip.SampleAnimation` | 骨架塌成零姿势，且不走 Undo | 只读 clip 数据；非采样不可用 `AnimationMode` 采样 |
| 循环调用 NDMF `AvatarProcessor.ProcessAvatar` | 每次克隆整个头像跑完整管线。成文时连跑 8 次：内存到 13.7 GB，主线程空转约 20 分钟，进度条没有取消按钮，只能结束进程，未保存的场景改动全丢 | 一次烘焙按一次完整构建计价：烘一次、量、改设置；要再比就单独再跑一次。每次前先清掉场景里残留的 `(Clone)` |
| 用 `DestroyImmediate(clone)` 收尾 | 只删场景物体，不删落在 `Packages/nadena.dev.ndmf/__Generated/<克隆名>/` 的生成资产（每次上百个，Unity 要逐个导入） | 每次烘焙后清掉那个目录 |
| Play 期间被脚本重编译打断 | 退出 Play 时的场景还原可能不完整：配饰全开、骨架停在动画姿势 | 进 Play 前先把脚本改完、编译完；退出后比对骨骼基线 |
| 直接改 `Assets/<厂商目录>/` 下的预制体或材质资产 | 厂商包重新导入时被覆盖，还会影响所有引用同一资产的物体 | 改场景实例上的组件，或复制到本工程自有目录再改 |
| 烘焙卡住时删掉正在执行的脚本源码 | 不会让它停下，反而排进一次域重载；主线程被占着，重载永远轮不到，看起来像彻底卡死 | 只能结束进程；重活事先不放进编辑器的单次同步调用 |

- **决策边界**：需要结束 Unity 进程时，先确认场景已存盘、没有人正在用这个编辑器；做不到就交回。
- **证据与适用条件**：各行分别来自单个工程的实测（烘焙循环一行在 Windows 宿主、Unity 2022.3 上发生）；「替代」一栏是事故后定下的做法。

## 批量破坏性改动：还原路径先落盘、读回，再动手

- **适用**：一次改很多资产、并由工具自己写「回滚日志、备份或清单」的步骤，例如批量改贴图导入设置、批量换材质、批量写形态键。
- **机制**：`JsonUtility.ToJson` 遇到元素类型没标 `[Serializable]` 的 `List<T>`，不抛异常、不打警告，直接略掉该字段。成员是属性而不是字段、类型是 `Dictionary`、嵌套超过 7 层，也都会得到同样无声的空文件。日志里的「已写入 N 条」如果读的是内存里的 `Count`，就与盘上内容无关。
- **成文时的事故**：日志写「原设置已追加 127 条（改动前已落盘）」，盘上的文件只剩两个时间字段；随后 127 张贴图被改，工具自带的「还原」菜单从此形同虚设。
- **做法**（缺一不可）：
  1. 元素类型补 `[Serializable]`；
  2. 落盘后立刻从文件读回、数一遍，与内存对不上就抛异常中止，绝不在没有还原路径时继续做破坏性改动：
     ```csharp
     File.WriteAllText(path, JsonUtility.ToJson(data, true));
     var verify = JsonUtility.FromJson<OrigList>(File.ReadAllText(path));
     int onDisk = verify?.entries?.Count ?? 0;
     if (onDisk != data.entries.Count) throw new Exception("原设置没写全，不改。");
     ```
  3. 还原清单写成本阶段 `allowedWrites` 内的一个文件（如 `<本阶段目录>/restore.json`），落盘后读回计数。不要自己提交版本控制：Harness 执行方沙箱里 `.git` 只读，HEAD 一动就判越界；版本由 Runtime 的产物指纹记录。
- **产出**：报告里写读回的条数和还原清单的路径。
- **证据与适用条件**：事故来自一个工程；序列化静默写空是 `JsonUtility` 的既有行为，读回校验的做法与引擎版本无关。
