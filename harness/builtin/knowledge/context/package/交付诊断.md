# 交付前诊断判据

## 缺失项判据：能编译不等于没缺陷

`MissingScript`、`InternalErrorShader` 与断开的引用都不影响编译，能编译的包照样会在客户那边变洋红或静默失效。打包前逐项过。本流程里你在打包之前运行、只写 `diagnosis.json`：能读文件判的照做，命中写进 `blockers` 并令 `verdict=blocked`，由人回对应阶段处理；运行层（烘焙克隆逐个读 shader）与冷导入后的脚本丢失由 Runtime 在你退出后测，你不自己烘焙、不开 Unity。

- **零 `MissingScript`**：两种都查——`m_Script == {fileID: 0}`，以及「GUID 没有对应的脚本」；源 prefab 里也要查，这类缺失常藏在 prefab 里。
- **零 `InternalErrorShader`**：它在 `.mat` 里 grep 不到。文件层把材质引用的 shader GUID 对照 `.meta` 与内置 ID；运行层对烘焙克隆逐个 Renderer 读 shader 名。
- **引用全能解析**：GUID 反查，断链为 0。
- **头像根**：本次选定进构建的根恰好 1 个；全部 Assets 及备份里的描述器（`VRCAvatarDescriptor`）另列清单（根名、用途、blueprintId）。有意交付的多个根保留并逐根验收，不把备用根的数量当失败。
- **`blueprintId`**：与线上那份一致；多个根共用同一个 ID 要报告。
- **说明与工程一致**：交付说明、来源说明里的每条 `Assets/` 路径与用途，都与工程实际相符；事后补归档的只写归档说明，不编造当时的设计意图。

有命中就不交付，回对应阶段处理；判据查不了的写「未核」，不默认通过。

## 进包前剥净：审查残留、临时目录与开发依赖

- **要清的**：生成器脚本目录（如 `Assets/Editor/AvatarGen/`）与 `Captures/`；`Backup/`；`com.vrcfury.temp`（构建临时目录）；`#GENERATED` 这类按头像生成的目录；`Packages/manifest.json` 与 `packages-lock` 里的开发用依赖（如 unity-mcp——留着它，客户打开工程时 Unity 会去拉一个他用不到的 git 包；多个历史工程都各残留过 1 行）。
- **审查工具的残留**：`Assets/AvatarAudit/`（及旧位置 `Assets/Editor/AvatarAudit/`）、`Assets/ZZZ_GeneratedAssets/`、`Packages/nadena.dev.ndmf/__Generated/`、`Library/AvatarAudit/`，以及 `ProjectSettings/` 相对交付基线的漂移（Play 与测量会改写部分设置）。
- **本流程里不剥不删**：打包工具在你退出后从交付副本出包，只剔除 Harness 自己的 `_HarnessTools` 与 `_BuildArtifacts`；你不得修改前序资产。上面这些残留，发现就写进 `blockers` 并令 `verdict=blocked`，由人回对应阶段处理。下面两条是人工作业时的做法。
- **用工具剥，不手删**（人工作业时）：剥离工具 `strip_audit.py --project <工程根>` 先 `--check` 列清单，在工程副本上 `--apply --baseline <交付基线提交>`，再跑一次 `--check`，必须退出 0。场景与 prefab 里遗留的审查组件只列不删；按脚本 GUID 从基线判不了的报 `undecidable` 并非零退出——**不可判定不等于零残留**。
- **在真拷贝的副本上剥**：硬链接副本（`rsync -H`、`--link-dest`）与正开着的工程共用 inode，`--apply` 原地改写 `manifest.json` 时会把原工程的依赖一起删掉。
- **删之前确认别处还有一份**：工程包排除了 `.git` 与生成器脚本目录，而那两样正是整单的历史与配方。

## 中间产物与交付物的分界

- 同一个工作目录里常混着两类东西。**交付物**：工作场景 `*.unity`，菜单与动画资产 `*.anim`、`*.asset`、`*.controller`——它们是生成结果，删掉生成脚本不影响它们。**中间产物**：探针日志 `*.txt`、`*_probe.txt`、`*_verify.txt`，诊断截图——要删。
- 打包前检查：`Assets/Editor/` 下有没有带订单编号的专用脚本，`Assets/` 下有没有中间日志与诊断截图。删脚本之前先编译一次，确认没有别的东西引用这些类。本流程里只查不删：发现就写进 `blockers`。
- **旧场景参考移出 `Assets/`**（本流程里发现就写进 `blockers`，不自己移）：旧场景、备份场景与预制体放到工程外（如 `旧场景参考/`），并在说明里注明「不要直接覆盖」；留在 `Assets/` 里又没有任何说明，是多个历史工程里的坏做法。
- AAO 在 `__Generated/` 下生成的 UV 重打包贴图与单色贴图每次构建重生成，不随交付包走。
- 插件的备份对象（分组换装插件常留下）不是交付内容。

## 素材归属与「导入不等于用上」

- **本流程的素材 zip 由打包工具生成**：`<名>_素材/` 目前建成空目录；清点里选中的、来自素材库的原始包进 `_追加素材（非客户自备）/`，附 `来源说明.txt`。非素材库来源的包不会被收进去，发现时写进诊断。
- **客户素材包里只放客户自备的原始包**；制作方自己找的一律进 `_追加素材（非客户自备）/`，附来源说明（`来源说明.txt`）：逐个写用途、对应的 `Assets/` 路径与大小（MiB）；没留原始包的只写清单。追加素材目录里的每一项在来源说明里都有条目，两边条目数相等。
- 追加素材的原始包可能散在客户素材目录之外（下载目录、别的工程的素材目录、素材库），打包前收齐；可以用硬链接集中，不占额外空间（只做只读收集，不在硬链接副本上原地改写）。
- **VPM 包不算追加素材**（GoGo Loco、Light Limit Changer 等）：随 `Packages/` 走、由 VCC 自动还原，写进交付说明的「工具链版本」一节（本流程的交付说明由 Harness 生成，写进诊断的 `material_summary`）。
- **导入 ≠ 用上**：拿素材清单逐条核销，用 GUID 反查每个素材包在工程里的引用，没有包外引用的就是没用上。一项素材只要被交付头像可达的文件引用到就算用上——贴图、着色器、脚本这类引用终点也算，不再要求继续解析它们的内容。应用表不留空白格，每个「不用」都写得出原因。本流程由 `package_usage_refs_closed` 检查：方案 `unused` 里、随方案批准的商品豁免，其余没用上的都阻断。
- **一致排除的商品不进交付**：方案同时写了 `unused`、唯一一条 `exclude` 义务（都带理由）且没有装配它的商品；setup 会在快照、导入和订单 VPM 安装前把它从有效选择中排除，intake 原始清点仍保留作证据。打包只核对排除商品的数据没有残留，发现导入目录、VPM 包或清单仍出现就阻断技术返工，绝不通过改写交付副本来掩盖；素材 zip 不收它，也不列进 `来源说明.txt`。交付说明.txt 会单列一节写明「本包不含其数据，需要时由客户自备厂商原件、按厂商安装工具自行安装」。这是按方案的排除处置运行的通用机制，不认商品名。
- 某个素材包完全没有包外引用，就是没接线：回对应阶段处理，不直接交付。

## 依赖可复现：客户机上能原样还原

- **版本冻结**：工程依赖由 `vpm-manifest.json` 的 `locked` 段冻结，客户在自己的 VCC 里打开工程时按它还原。交付说明写明锁定的版本，除非遇到问题不建议升级。
- **本知识标定时的工具链**：Unity 2022.3；VRChat SDK（`com.vrchat.avatars`）3.10.4；lilToon 2.3.4；Modular Avatar 1.18.1；NDMF 1.14.3；Avatar Optimizer 1.9.16；VRCFury 1.1414.0；GestureManager 3.9.9。工程所用版本明显不同时，涉及插件行为的判据先复核再用。
- **`Packages/manifest.json` 里不留开发依赖**；`file:` 与 git 依赖为 0。
- **本流程里**：工程 zip、排除项与冷解包编译都由打包工具与 Runtime 在你退出后做；你核查 `manifest.json` 里的开发依赖与 `file:`／git 依赖，命中就写进 `blockers`；锁定版本写进 `material_summary`。
- **冷解包编译**：把工程 zip 解到临时目录，`-batchmode -projectPath <目录> -logFile <log> -quit` 打开一次，`Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 存在、日志里 `error CS` 为 0。出现 `CS0234` 这类命名空间缺失时，回去查排除规则，不要手工往包里补文件。
- **工程 zip 的排除项**：`Library`、`Temp`、`Logs`、`obj`、`UserSettings`、`.vs`、`.git`、`Captures`、`*.sln`、`*.csproj`，外加生成器脚本目录；工程根只装 `.gitignore`/`.gitattributes`、`.vsconfig`、`Assets`、`Packages`、`ProjectSettings` 这 5 项。
- **排除规则锚定工程根**：上述目录只排工程根那一层；源工程里已有的插件内部同名目录（如 `Packages/**/Library/`）在 zip 里必须一个不缺。判据数的是这些目录在 zip 的相同相对路径上缺了几个（`delivery_zip_keeps_plugin_dirs`，缺 0 个才通过）：插件本来不带这种目录、源里没有的，不要求凭空造一个；换个路径放个同名目录也不算数。

## 交付说明必须写清的五件事

- **两档写法**：当单做完就写完整工作报告（做了什么、必须知道的几件事、打开工程后怎么做）；事后补归档的只写归档说明（包内容、工程里装了什么、工具链版本、打开工程后怎么做），**不编造当时的设计意图**。
- **至少覆盖**：① 附赠的付费资产是哪些；② 性能评级为什么是 VeryPoor（多套服装的面数）；③ 有哪些功能因取舍而失效；④ 此前给过客户的错误判断的更正；⑤ 工程已锁定的版本，除非遇到问题不建议升级。
- 末尾附「上传后请自测」清单。
- **本流程的交付说明.txt 由 Harness 生成**，你写不了；一致排除、客户自行安装的商品由它单列一节写明，你不用在诊断里重复。你能影响的是另一份《客户端验收与诊断》：①附赠资产与⑤锁定版本写进 `material_summary`；②VeryPoor 原因、③因取舍失效的功能、④更正写进 `performance_tradeoffs`，每条一行；自测清单写进 `client_checks` 的 5 个固定 id。
- 文本格式：txt 一律 UTF-8 无 BOM、LF 换行、框线排版；核对时读字节，不读解码后的字符串。
