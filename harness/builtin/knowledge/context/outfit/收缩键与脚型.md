# 服装装配：身体收缩键与脚型键

写给执行 outfit 阶段的 AI；判据部分也供回归修复阶段使用。每节独立成立。

## 身体收缩键挂在衣物部件上，厂商换装动画里写身体键的曲线归零

- **职责**：让防穿模的身体收缩键只在对应衣物可见时生效。
- **机制**：MA Shape Changer 是反应式组件（ReactiveComponent），所在物体失活即不生效，天然跟着衣物走。写在动画里的收缩键跟着「参数为真」走，会出现「明明穿着别的衣服，肩膀也被衬衫的收缩键收掉」：例如厂商的衬衫 ON 动画把身体的 `Shoulder_OFF` 设为 100，只要参数为 1，这条动画就一直在播。
- **做法**（人工作业时）：收缩写成挂在**衣物部件本身**上的 MA Shape Changer；厂商动画里打在素体网格上的 `blendShape.*` 曲线**全部改值为 0，不删曲线**（更安全、可回滚，也避免状态残留）。
- **本流程里做不到，停下交人**：`vendor_blendshape_curves_zeroed` 读的是厂商预制件上 MergeAnimator 引用的原 clip；厂商目录不可写，产物每次按方案重建，执行方加的 Shape Changer 和归零副本都进不了产物。读 clip 的 YAML 找出写素体 `blendShape.*` 的非零曲线，写明哪套、哪个 clip、哪些键，交人（换预制件或改方案）。
- **代价**：从动画搬到 Shape Changer 后粒度变粗。厂商原本能在「短袖」模式下把 `Upper_arm_OFF` 单独设回 0；整体挂到衣物上后，短袖时上臂仍被收掉。要保住这种精细度，得再加一层反应式条件。
- **禁止**：收缩键留在厂商的整套换装动画里；删除厂商曲线。
- **验证**：扫描全部动画 clip，打在素体网格上的 `blendShape.*` 曲线非零值为 0；逐套单独开启再关闭，身体对应部位随之收缩与恢复。
- **状态说明**：身体形态键适配服装的整体流程在已有工程中尚未完全验证；本节做法经过实际修复验证。遇到与本节不符的现象时，以本轮几何证据为准并报告。

## 收缩键逐套检查：六步流程

厂商给不给收缩键因套而异，必须逐套查，不能拿一套的结论推广到全部。

| # | 动作 | 判据／产出 |
|---|---|---|
| 1 | 列出素体网格的收缩键候选 | 遍历直挂在头像根下的 SkinnedMeshRenderer，筛形态键名含 `OFF`／`hide`／`shrink`／`消`／`非表示` 的 |
| 2 | 列出每套服装已有的 Shape Changer | `GetComponentsInChildren<ModularAvatarShapeChanger>(true)`，逐条导出 `ShapeName`／`Value`／`referencePath`／`ChangeType` |
| 3 | 差集＝候选补挂清单 | 有衣物覆盖该部位、却没有对应收缩键的，就是嫌疑 |
| 4 | 逐套判定真正需要哪些 | 用覆盖表与几何量判定，不想当然 |
| 5 | 需要的挂在衣物部件本身上 | 反应式组件，所在物体失活即不生效 |
| 6 | 厂商动画里写素体网格 `blendShape.*` 的曲线归零 | 改值不删曲线 |

- **挂法（MA，人工作业时）**：`Undo.AddComponent<ModularAvatarShapeChanger>(part.gameObject)`；`Shapes` 中每项为 `ChangedShape { Object = new AvatarObjectReference { referencePath = "<身体网格路径>" }, ShapeName = <键名>, ChangeType = ShapeChangeType.Set, Value = 100f }`；改完调用 `PrefabUtility.RecordPrefabInstancePropertyModifications(sc)`。
- **别想当然**：多套服装可能**一个脚部收缩键都不需要**——靴子完全包住脚、露趾凉拖（脚趾本就该露，加了反而错）、赤脚造型都不需要，即使素体备有完整的 `Foot_OFF`／`Toe_OFF`。
- **本流程里只做第 1～4 步**：第 5、6 步没有通道（产物由 Runtime 按方案重建，只含厂商预制件自带的 Shape Changer），前 4 步离线读 YAML 就能做。检查采信原批准方案的 `shrinkkey_review` 或 Runtime 按真实写者校验的局部方案补充；AI 自写批准或判定不被采信。脚部键或同套多宿主必须复核；方案缺这一项时，走局部方案复核通路：在受管 local-operations.json 提交 shrinkkey_review，写者/宿主/顺序绑定实际证据，Runtime 校验，三态预期与后续实测分开。
- **产出**：每套一行「需要／不需要＋原因＋证据」，没有例外；局部补充需按完整写者与来源版本接受独立校验，不能仅用这一行宣称通过。
- **禁止**：因为素体有某个收缩键就给所有套都挂；用一套的结论推广到其他套。

## 脚部形态键先分两类：贴合姿态键与删除／收缩键

素体的脚部形态键不是一类东西，选错类别比选错数值严重得多。

| 类别 | 典型键名（因素体而异） | 作用 | 用错的后果 |
|---|---|---|---|
| 贴合姿态 | `Foot_heels`、`Foot_highheels`、`Toe_heels`、`Toe_highheels` | 改变脚的角度（绷脚背、踮脚），几何量守恒 | 姿势不贴合，看得见但不致命 |
| 删除／收缩 | `Foot`、`Toe`、`Shrink_Foot`、`Shrink_Ankle`、`Foot_OFF`、`Toe_OFF` | 删顶点，或把体积缩到 0 | 鞋一旦不是全包，露出来的地方是空的、畸变或拖丝 |

- **本流程里**：姿态键与收缩键都只能来自厂商预制件自带的 Shape Changer 或厂商 clip，执行方选不了档位；下面的分类用来核对厂商配置、写方案复核的理由，不对就交人。
- **默认动作**：按鞋跟高度挑一个贴合姿态键；平底鞋不上姿态键。不是先问「要不要把脚缩掉」。候选里出现 `Shrink_*`、`*_OFF`、`hide` 这类名字时，先停下量鞋的包覆范围。
- **删除类的前提**：鞋**完全包住**那个部位。长靴、高帮鞋成立；船鞋、乐福鞋、露趾凉鞋、任何露脚背的款式都不成立。
- **为什么容易搞反**：「脚从鞋里穿出」这个症状，两类键都能看起来缓解；但收缩键是用破坏几何换遮挡。收缩过头会把顶点折到一处，渲出尖锥和细长拖丝；鞋也不会跟着变，缩多了就是脚缩进鞋里「消失」。
- **自检问句**：正在给一双鞋选「收缩多少」时，先问：这双鞋的跟有多高？对应的姿态键档位试过没有？没试过就先试那个。
- **姿态键能否叠加因素体而异**：有的素体上两个姿态键是互斥的档位（同时为 100 会叠成「踮脚尖＋抬脚跟」，腿变成一根尖）；有的素体上两个脚趾姿态键叠加才贴合。叠加必须有渲图或几何证据，先查素体专属知识。
- **仍然穿模时**：往「把鞋改大／加内衬」的方向走，不要回头去删脚。
- **禁止**：用删除类键解决露脚款式的穿模。

## 收缩键的宿主：按覆盖表拆到真正盖住那一段的件上

- **职责**：决定每个收缩键挂在哪件衣物上。本流程里宿主由厂商预制件决定，执行方挂不了、拆不了；覆盖表用来判断厂商配置对不对、写进方案复核的理由，不对就交人。
- **第一步·覆盖表**：把部位分段，逐件填「盖不盖」。脚分三段：脚踝／脚背脚掌／脚趾。看**鞋帮高度**与实际渲图，不看件名——厚底不等于高帮，鞋底厚薄和鞋帮高度无关。其他部位同理：袜子可能覆盖膝、小腿、脚踝、脚、脚趾，袖套覆盖肘与前臂，衣身覆盖肩。
- **第二步·按覆盖拆件**：

| 键 | 影响哪一段 | 挂在谁身上 |
|---|---|---|
| `Ankle`（`Ankle_L/R`） | 脚踝 | 盖脚踝的那件：中筒袜、堆堆袜、长靴 |
| `Foot`（`Foot_L/R`） | 脚背脚掌 | 鞋，以及盖脚的袜（两件都挂，值相同） |
| `Toe`（`Toe_L/R`） | 脚趾 | 同上；露趾款不挂 |

- **开口鞋**（踝带、浅口）：不让鞋收脚踝与脚背——露出的那段会塌；只收脚趾。脚背从鞋口露出属于设计，对照「袜开」时的参考图判断。
- **禁止**：把收缩键全挂在鞋上、整套根上或头像根级容器上。后果是单向的：盖住那一段的件一关，身体还缩着——脚踝或小腿塌成细线、尖锥，而关掉那件衣服的人正好在看那个位置。
- **多宿主**：同一个键挂在多件上不冲突（MA 多写者按层级先序、后者覆盖，值相同就无所谓）；但同一物体同一键不许同时 Set 和 Delete。本流程的装配检查把同一套里多宿主写同一个键判为「待复核」：方案的 `shrinkkey_review` 要写清谁先谁后、最终谁胜，否则阻断。
- **自检问句**：这个键影响的顶点，在当前状态下还有没有可见的衣服盖着？
- **验证**：逐件「单关一件」渲图或量几何，露出的部位不塌陷。
- **证据**：两个工程、两种素体上出现同一类故障，并按此修复（多工程验证）。

## 贴合姿态键跟鞋走，改之前列全这个键的全部写者

- **职责**：为每双鞋选姿态键，并确认没有第二个写者在同时写脚型。
- **归属**：贴合姿态键表示「脚摆成什么角度」，由鞋跟高度决定，挂在鞋上。平底不上姿态键；有跟的按跟高选一个档位，用实测的候选比较来定。
- **候选比较要有清零域**：比较几个姿态键候选时，每个候选都要先把其他候选键清零（排序工具里的 `candidates_zero` 一类参数），否则各候选量到的是同一个姿势，等于没测。
- **只穿袜时**：袜子若按踮脚姿态建模（例如到脚的连裤袜），「只穿袜」状态也要写姿态键——这一档的默认值不是「无」。否则关掉鞋后脚回到中性，而袜子是刚性网格跟不动，脚会从袜子里顶出来。袜子只到脚踝时，「只穿袜」一律不写。
- **写者清单**：一个脚部键常常同时有两个写者：
  1. 衣物上的 MA Shape Changer：全场 `ModularAvatarShapeChanger` → `EditorJsonUtility.ToJson` 读 `ShapeName` 列表；该物体 active 时生效。
  2. FX 里的脚型层：全工程 `AnimationClip` → `AnimationUtility.GetCurveBindings` 筛 `blendShape.<键名>`，再回查哪个控制器的哪个层／状态用了这个 clip、转移条件是什么（常见为整套档位 × 鞋开关 × 袜开关）。

  两张表合起来才是完整写者集。只查一边，改完还是错的。
- **禁止**：同一状态下两个互斥档位的姿态键同时为 100（除非该素体的专属知识说明它们设计为叠加）。
- **升级给人**：两个写者意图冲突（例如厂商层与本工程层给同一双鞋写不同姿态），且无法从鞋型判断时，报告两边的写者与条件。

## 鞋袜四组合与成对判据：光脚是对照组

凡涉及脚部键，每套都要检查下表四个组合。

| 组合 | 鞋 | 袜 | 该开的收缩键 | 姿态键 |
|---|---|---|---|---|
| 全穿 | 开 | 开 | 两件覆盖范围的并集 | 鞋那档 |
| 只穿鞋 | 开 | 关 | 只有鞋盖住的那几段 | 鞋那档 |
| 只穿袜 | 关 | 开 | 只有袜盖住的那几段 | 袜按踮脚建模才写，否则不写 |
| 光脚 | 关 | 关 | 全 0 | 全 0 |

- **判据必须成对**，单边判据一定会被「把东西删掉」骗满：
  1. 没穿出：身体穿出衣物的面积或顶点数为 0（poke 类探针）；
  2. 没有白缩：没有任何「键开着，但它影响的那段没有可见衣物盖住」的情况。
- **光脚是对照组**：必须两条都过，且所有脚部键为 0；过不了，说明判据本身坏了。
- **量之前**：把内搭的连体袜、丝袜关掉——它会盖住脚，量不出鞋合不合脚。
- **验收图**：每套三行——鞋开袜开／鞋关袜开／鞋袜全关，第三行必须是中性裸足。「全关」这一格能暴露归类错误：例如兽爪鞋套被归在「腿饰」下，关掉鞋袜后爪子还套在脚上；平时它跟着别的开关一起亮着，看不出归错。
- **产出**：每套四组合的读数与判定；涉及脚型键时，方案要记录穿鞋袜、只穿袜、光脚三态。本流程里读数由 Runtime 在回归阶段取，outfit 阶段写不出；方案的 `shrinkkey_review.scenarios` 必须含 `shoe_on_sock_on`、`shoe_off_sock_on`、`barefoot`。

## 脚部几何量与定点渲图：怎么出数、怎么看图

- **先出数，再看图**：先用几何数据缩小范围，再只渲有疑问的那一格。
- **本流程里由 Runtime 出数出图**：执行方不开 Unity，`BakeMesh` 与渲图都做不了；回归阶段的构建副本里由 Runtime 取（Run 目录的 `fit/geo_state_*.json`、`photos/`），你读结果，按下面的口径判。outfit 阶段写「交回归阶段」。
- **几何量**（用 `BakeMesh` 取带当前形态键的实际网格）：

| 量 | 期望 |
|---|---|
| 脚部顶点包围盒长度 | 施加键前后变化 < 5%（姿态类只改角度，不该改长度） |
| 脚部体积或有效顶点数 | 同上；掉一半就是被删了 |
| 脚最低点与鞋最低点之差 | 为负（脚在鞋内） |

- **包含测试**：判断点是否在封闭鞋体内，对「鞋开袜关」这一格有用。例：厂商只把收缩挂在袜上时，鞋开袜关状态下脚趾只有 2% 在鞋内；鞋上补挂后为 100%。
- **不能用的判据**：像素方差、边缘数、「画面整洁度」这类整体统计量。把脚删掉会让它们全部变好，判据会稳定地推荐最坏的选项。自检问句：如果把被测物删掉，这个指标会不会变好？会，就不能单独用。
- **像素差只做初筛**：凉鞋、鱼嘴鞋、露趾袜按设计就露脚，残留大不等于装错；「角度不对」（平脚塞进高跟鞋）在差分里可能只是中等数值。数值排序缩小候选后，每个候选都要看特写渲图判角度。
- **定点看图**：只渲有疑问的那一格；4 个方位加脚部特写（以 `LeftFoot` 等脚骨为中心、半径约 0.22 个 Unity 单位，能看清脚踝到鞋口）。结论交独立视觉复核时只给图、不给结论。
- **覆盖探针**：「键权重 > 0，但影响顶点未被任何可见衣物遮住」的覆盖探针（`shrink_cover`）未标定之前只作线索：它的 `ok` 不能当通过，先看 `uncovered_ratio` 与 `nearest_cover_path` 自己判；已知躯干上段（`Chest_2`／`Spine_2` 一带）的覆盖判定不可靠。

## Set 与 Delete 的取舍：先问能不能退回去

MA Shape Changer 的 `ChangeType` 只有两个值：Delete=0、Set=1（序列化里就是 0/1，别按面板文字猜）。

| | 能回退吗 | 什么时候用 |
|---|---|---|
| Set | 能（宿主物体停用即恢复） | 默认选它 |
| 随开关变化的 Delete | 能（运行时用 NaN 骨骼缩放隐藏） | 顶点必须真的消失：镂空、透视布料下面 |
| 常驻 Delete | 不能（构建期物理删除顶点） | 确定这套永远用不到那批顶点，且已和用户确认 |

- **硬规矩**：
  1. 禁止同一物体、同一键同时 Set 和 Delete——Delete 删的是顶点，Set 作用的顶点已被删或隐藏，等于白设。扫到就报，不要「两个都留着更保险」。
  2. 常驻 Shape Changer 单独声明，不和随开关的混在一张表里：前者构建期就把顶点删了，不可回退。
  3. 滑块或轮盘抢同一个键时先查层权重：动画层与 MA 反应层谁赢，只有构建产物或运行态知道；默认权重为 0、又没有任何 LayerControl 抬权的层，拨了也没反应。先读烘焙后 FX 每层的 `m_DefaultWeight`，对照全部 LayerControl。
- **升级给人**：需要常驻 Delete 时，先把影响范围与理由交用户确认。

## 袜子用 Delete 删脚部时，要对照可同穿的鞋款

- **机制**：袜子把 `Toe`／`Foot`／`Ankle` 删掉，在默认的包脚鞋下看不出问题；换上露趾或镂空的鞋就会缺脚趾、出空洞。
- **做法**：列出全部对脚部键的 Delete → 按厂商展示图把可同穿的鞋分成露趾／镂空／包脚三类 → 每类各渲一次脚（低机位＋俯视）。本流程里前两步读 YAML 与展示图就能做，渲图交回归阶段；有风险的组合写进方案复核的理由，或交人。
- **判据**：三类鞋下脚部都没有缺失或空洞。有缺失的组合，按「收缩键的宿主」与「Set 与 Delete 的取舍」重新决定写者（本流程里重新决定写者要改方案或换预制件，交人）。
- **升级给人**：袜与某类鞋的组合无论怎样都会露出删除区，而方案要求两者可同穿时，报告该组合。

## 局部方案复核与返工

装配发现原方案未覆盖写者时，AI 可在既有目标及素材授权内，通过 outfit goal 的 shrinkkey_review 操作提交局部修订。完整实际写者和顺序、来源观察、源资产、无冲突值及三态预期由 Runtime 校验；只登记技术方案补充，不改变原方案批准、接受脸型或旧证据，也不代表三态实测。多宿主须解释先后及最终胜者。缺证据应补探查/返工；超出授权或需外观取舍时给出中文具体选项，交已有确认入口，不让用户修改 YAML。
