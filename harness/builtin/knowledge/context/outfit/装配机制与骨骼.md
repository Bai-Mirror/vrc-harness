# 服装与发型装配：装配机制、骨骼与渲染确认

写给执行 outfit 阶段的 AI。每节独立成立，可单独注入。

## 本流程的装配：Runtime 按方案与局部操作重建

- **逻辑成员与共享对象**：原始预览为每个菜单成员保留源路径；正式装配允许等价成员共享物理实例。局部操作仍填写观察中的逻辑路径，Runtime 根据装配记录的成员 `id → object` 映射解析根与子路径；回执 `logical_objects` 展示映射。重复变换、对象状态、材质槽按解析后的物理目标检查冲突。材质操作只更新点名逻辑成员的有效 material_presets，以持久身份贯通配色与菜单，保留其他变体；共享槽恢复默认成员的有效预设。写者复核按共享物理对象和实际写者证据校验，供等价成员复用；一致别名可合并，矛盾证据拒绝，逻辑身份保留。独立验证从源重新装配并重建映射，不以回执证明成功。

- **产物怎么来**：Runtime 在空场景里实例化方案的 `body_prefab`，按方案挂装服装与隐藏点名素体件，再消费 `Assets/_Harness/Outfit/local-operations.json`（可选），保存 `Avatar.prefab` 并独立重载。setup 的 `object-observation.json` 提供真实对象路径、材质槽、shader属性、批准导入的引用和版本；当前 goal 给出局部操作字段。AI 根据效果目标填写操作，普通用户不用填写这些技术字段。
- **先观察、后装配**：setup 的 `phase: source_preview` 只展开素体与方案源件，保留厂商组件、蒙皮骨槽、根骨、层级和姿态，不先运行 MA Setup Outfit 或要求挂点。`inspect-local-objects --section sources` 包含授权源 prefab 与模型。catalog 的 `models` 来自选中 Unity 包的实际安装路径，实例的 `prefab` 字段也可引用这些 Unity 模型 GameObject 源；观察其真实形态后补配方。模型安装不证明厂商安装工具的特定行为已实现。
- **受管装配配方**：在同一个 `local-operations/0.1` 输入中提交 `assembly`，`path` 是已批准成员的 `_Outfit/Outfit_<id>`。`mode: mount` 使用 `mounts: [{source: 实例内相对路径（根为""）, path: 已观察素体对象路径, pose: preserve 或 relative, position/rotation: relative 时必填三项数组}]`；多挂点源须不重叠。`mode: merge` 用于实际蒙皮骨架，由 MA Setup Outfit 生成装配组件。已有厂商 MA 装配组件不覆盖。Runtime 在装配前核对观察哈希、方案与源资产身份；不改变业务实例、来源、菜单归属或义务。
- **兼容性实测**：`assembly_compatibility_verified` 检查包括默认关闭成员的真实合骨映射、可解析挂点和配方姿态；独立重载重新装配并比对组件与完整对象状态。骨名或组件存在不是通过证明；位置、动作和外观仍须后续回归实测。失败证据保留并技术返工，不能自动改成豁免；`other` 须证明自己的安装实例，材质依赖仍可明确承载。（`决定记录/D-115`）
- **可执行的局部动作**：将任一实际观察槽中的授权材质复制到精确目标槽（含空槽或丢失shader的槽）后修改 float/color/vector 或引用已批准导入且观察到的贴图；按精确父对象挂已观察预制体子件；调整已观察子对象的局部 position/rotation/scale；通过 foot_writer 按实际组件序号移除点名脚型键的条件写者、保留默认网格与其他键（须说明取舍，不是批准或三态实测）；以 object_state 调整已观察非根对象的显隐，或明确标 EditorOnly 排除不需要交付的附件。不能排除必需素体网格、骨骼或已接受脸型；单纯关掉对象不等于构建排除，也不证明骨引用已修好。输入绑定原始观察摘要及源资产版本，重复争用、旧版本、外部引用拒绝。独立验证重载实际产物核对动作后置条件及未授权目标，不信任 AI 写的 pass 或操作回执。
- **所以你的改动进不了交付**：对 `Avatar.prefab` 的改动（加 Shape Changer、改 BlendshapeSync、换网格、调根缩放、建分组）会被覆盖；放在 `Outfit/` 下的派生资产（归零曲线的控制器副本、补帧网格、变体预制件）没有被产物引用；厂商目录不可写。下面各节的这类修法是机制说明，用来判断原因、写清交人的证据。
- **本阶段修不了的检查**：下列读数只取决于厂商预制件和方案（装配阶段自己补的同名键同步会一并被这些判据检查，见 `形态键跟随.md`），每次重试结果都一样：厂商换装动画写身体形态键（`vendor_blendshape_curves_zeroed`）；厂商自带 BlendshapeSync 的参照键或本地键缺失（`blendshape_sync_missing_keys`）；同宿主同键同时 Set 与 Delete（`shrinkkey_set_delete_conflicts_zero`）；精确 foot_writer 可根据真实观察移除不适合目标的脚型写者，风险由产物组件重新清点，不能伪造已批准复核；服装必需的人形主干骨没吸附上（`skeleton_missing_zero`）；不交付的可选附件可经 object_state 明确排除，不能把排除说成修骨。遇到时写明哪套、哪个 clip 或组件、哪些键，停下交人（改方案、换预制件）。
- **你能做的取证**：读预制体、clip、控制器、`.meta` 的 YAML 文本（组件清单、`m_IsActive` 曲线、BlendshapeSync 绑定、Shape Changer 键），核对 Runtime 写的 `outfit.json`。渲染、贴合、几何与动作由 Runtime 在回归阶段的构建副本里测，本阶段报告写「交回归阶段」，不写成缺口。
- **产出**：逐套写清源形态、观察身份、配方、实际映射/挂点/姿态与失败证据；技术返工走现有受管操作。改变来源或目标、减交付时才提出正式方案修订。

## 装配前先探测预制体自带的装配组件（四类）

- **职责**：对每个待装的服装、发型、配饰预制体，先枚举组件，再决定装配方式。厂商预制体的装配方式各不相同，不能一律按同一种挂。
- **权威输入**：预制体实例上 `GetComponentsInChildren<Component>(true)` 得到的组件类型名清单。物体名、目录名、商品名只是线索。
- **决策边界**：四类为自带 MA MergeArmature／自带 MA BoneProxy／两者都有／两者都没有。前三类沿用厂商机制；无 MA 时按实际蒙皮或刚性形态补观察绑定的合骨/挂点配方，多挂点逐项定位，不按商品名或默认骨名猜。分类记进 `outfit.json`，真实映射与姿态由 Runtime 重载复核。
- **禁止**：探测之前加任何组件；不看探测结果一律加 MergeArmature。
- **产出**：每件的分类、组件类型清单、采用的装配方式及理由、蒙皮网格数。
- **验证**：MergeArmature 回读映射骨数 > 0；BoneProxy 的目标骨在头像骨架中存在；分类结果能被组件清单复现。
- **升级给人**：组件组合无法归入四类，或厂商机制与方案要求冲突（例如方案要求换挂点，而厂商用 BoneProxy 固定在头上）时，保持原样并报告最小决策缺口。

## 兼容性判定：比 FBX 骨骼名集合，不比文件名或目录名

- **职责**：判断一件服装能否装到当前素体上。
- **权威输入**：服装 FBX 的骨骼名集合与素体的人形主干骨名。「包里有 `avatar/<素体名>/` 文件夹」「文件名里有没有素体名」都不是证据。
- **判据**：服装骨架里与素体人形主干同名的骨必须全部吸附（这就是 `skeleton_missing_zero` 的口径）；服装本来不含的主干骨不算缺失，缺失项对照服装覆盖范围判读（鞋不含 Head、Hand 不是错配）。主干 19 项：Hips、Spine、Chest、Neck、Head，以及左右各一的 Shoulder、UpperArm、LowerArm、Hand、UpperLeg、LowerLeg、Foot。服装多出来的骨（带包前缀，或 `.001`～`.00N` 链）是它自带的动骨链，MA MergeArmature 会一并带入，不算缺失。
- **两个方向都会错**：①很多日系素体属于共用素体企划，服装按企划名发布，文件名里没有角色名也可能完全适配；②通用服装包里叫本素体名字的文件夹，可能属于另一个同名素体，比对下来缺主干骨。后者在编辑期看起来「装上了」，要到动骨或换姿势才暴露。
- **离线取骨名**：不必导入，可直接读 FBX 二进制：每个对象名后紧跟两个控制字节（NUL＋SOH）再接 `Model`，据此用正则捞出对象名。Python 里用 `chr(0)+chr(1)` 拼接，不要写字面转义（shell heredoc 会吃掉一层反斜杠）。
- **命名手癖是强指纹**：同一素体体系的 FBX 往往连拼错的骨名都一致，可用来确认两个包是否同源（具体见各素体的专属知识）。
- **禁止**：主干缺失时硬装，或用相似骨名强行映射。
- **产出**：每件的兼容结论与实际缺失映射清单。未知件先试装；失败时保留证据、修正受管配方或请求相关观察。确需换来源、变更目标或减交付时才修订正式方案并取得接受；不能以写 `defer` 解除交付义务。
- **升级给人**：缺主干骨时报告缺失项；若素材包里可能有真正的变体（开包列出 unitypackage 各条目的 `pathname` 看 prefab 名即可初查，不必先导入），把候选列给用户确认。

## 合并后逐根核对人形主干的吸附，不能只看骨槽是否落在素体骨架下

- **职责**：确认服装的人形主干骨在合并后真正对齐到素体同名骨，而不是只被重挂到素体骨下面。
- **机制**：两种结果的「骨槽读数」一样——服装蒙皮用到的骨都在素体 `Armature` 子树里、未合并骨为 0。但若主干骨只是被重挂、保留着原素体的姿势，袖子会按原素体的手臂角度悬在半空。
- **权威输入**：合并后（NDMF/MA 处理后的克隆或构建产物）的骨骼映射，以及**合并前**的素体骨名集合。统计「有无同名骨」必须拿合并前的集合比：合并后的集合里已含被重挂进来的服装骨，会自己证明自己。
- **判据**：两条同时过——①人形主干骨（上臂、前臂、手、大腿、小腿、脚等）逐根列「吸附到哪根素体骨／未吸附」，未吸附的主干骨必须为 0；②正面、侧面、背面三视图交独立视觉复核，专看袖子、袖套是否悬空。本流程里①由 Runtime 的装配观测给出，②的图在回归阶段由 Runtime 出；本阶段报告写「交回归阶段」。
- **禁止**：用「骨槽全在素体骨架下」「未合并骨 0」宣布贴合。
- **产出**：逐根吸附表与三视图路径。
- **升级给人**：未吸附的主干骨无法通过修正根缩放或换用正确变体解决时，停止装这一件并报告。本流程里根缩放和变体都由方案决定，本阶段改不了，直接写明证据交人。
- **证据**：同一工程的两件服装上出现过（候选）；这里只作为验证步骤使用，不据此推断具体成因。

## 实例化厂商预制件时保留根 Transform（厂商可能把适配缩放烘在根上）

- **职责**：把厂商服装预制件实例化到头像下时，不破坏厂商为适配素体做的根变换。
- **机制**：部分厂商用同体系另一个素体的网格制作「适配版」，把尺寸差烘在预制件根的 `m_LocalScale` 上。脚本在 `InstantiatePrefab` 之后又把根的 localPosition／Rotation／Scale 设成默认值，就会把这个缩放覆盖成 1：整件大一圈、整体上移，袖子悬在手臂上方。MA 合并**保留网格的世界外观**（MA 源码 `MeshRetargeter` 改 bindpose，不改位姿），所以根缩放错了，合并后照样错位，而主干骨照样读成「全部吸附」。
- **权威输入**：`PrefabUtility.GetPropertyModifications` 中实例根的 `m_LocalScale` 覆盖项，与厂商预制件原值对照。
- **禁止**：实例化后无依据地改写根 Transform；为了「对齐」自行猜一个缩放值。
- **决策边界**：同体系、不同尺寸的素体之间，若厂商只给了另一尺寸的版本，可按**同一厂商**在别的适配版里用过的比例换算根缩放；比例必须有出处（哪个预制件的哪个值），写进装配记录。本流程里 Runtime 实例化时保留根 Transform，执行方改不了根缩放：需要换算时写明比例与出处，交人。
- **验证**：根 `m_LocalScale` 无意外覆盖；三视图无整体上移或悬空。
- **升级给人**：需要按换算比例缩根时，先把比例与出处交用户确认再落地。
- **证据**：单一工程（候选）。

## 挂上后确认每件真的渲染，并全量扫描骨架内的静态挂件

- **职责**：确认装上的东西真的画得出来，且骨架里的附属件都归了组。
- **判据一·渲染**：每件单独打开时在渲图里**看得见**。只看层级里物体存在不算——「物体在但不渲染」是装配错误的典型表现。本流程的渲图由 Runtime 在回归阶段出（换装照），本阶段写「交回归阶段」。
- **判据二·静态挂件**：服装本体多是 SkinnedMeshRenderer，而骨架内部的挂件几乎都是 MeshFilter＋MeshRenderer。按组件类型全量扫描 MeshFilter，逐个确认归属分组。只扫 SkinnedMeshRenderer 会漏掉它们：例如包里的小玩具挂在骨架内的包内容挂点下，关掉包之后它仍留在原处飘着。
- **例外·零缩放占位物**：厂商预制件里常见缩放为 0 的占位物，enabled 且 active 却画不出任何东西，还常带空材质槽。它是厂商有意放的，不要当作「不渲染」去修。
- **判据三·用上了**：每个导入素材都要有**包外引用**（按 GUID 反查，命中数 > 0）；没有包外引用就是没接线，不能列为已使用。本流程由打包阶段的 `package_usage_refs_closed` 检查，方案 `unused` 里的商品豁免。靠组件配置而不是动画曲线引用的件（如互动插件的插槽标记）要按组件字段查，只查动画引用会漏。
- **禁止**：只凭层级截图或「脚本跑完」宣布挂好。
- **产出**：骨架内静态件清单与归组；渲染证据交回归阶段。
- **升级给人**：某件怎样都不渲染，又无法定位到装配关系或材质原因时，报告该件与已排除的原因。

## 厂商开关动画决定哪些件是一组；分组结构按组遍历

- **职责**：确定部件的实际分组与开关极性，并把装配结果组织成可按组遍历的结构。
- **权威输入**：厂商目录下动画里的全部 `m_IsActive` 曲线——一个开关一次写了哪几件，这几件就是一组；参数为 `true` 时是显示还是隐藏，也以曲线为准。例：一个看起来是「包」的部件，实际是包体＋名牌＋包里的小玩具三件。
- **只认厂商的**：本工程或上游阶段生成的动画、场景里的菜单项反映的是当前工程状态，不是厂商事实，不能混进分组依据（出现过某素体原装包的 29 条开关曲线里有 11 条其实来自本工程生成的目录）。
- **厂商开关不一定在 MA 组件里**：有的厂商不用 MA MenuItem，而是随预制件附带一份 VRCExpressionsMenu 资产（`menuToAppend`），再加上 `MA_Animator/` 目录里的 FX；只查 MA 组件会得出「厂商没有开关」的错误结论。两处都要读。
- **厂商没有开关机制时**：写「无厂商开关」并注明查过哪里，分组改看部件之间的连接关系与渲图。
- **结构由 Runtime 定**：本流程每套挂在 `_Outfit/Outfit_<id>` 下，不另建 `_Hair`、`_Acc` 之类的分组物体；整套互斥由菜单阶段生成的衣装轮盘保证。分组表是菜单阶段写 `design.json` 的依据：组成员进 `objects`，厂商开关 clip 进 `vendor_clips`。
- **产出**：分组表（组、成员完整路径、厂商开关与极性、依据的 clip 路径）。
- **升级给人**：厂商 clip 与商品说明对分组的说法冲突时，列出两边证据交用户判断。

## 上游更换了素体 FBX 时，装配成果需要复核

- **职责**：捏脸等上游步骤若更换过素体 FBX，确认已有装配没有因此失效。
- **机制**：换 FBX 会作废装配的一部分成果——材质数组被重置；MA MergeArmature 的锁定模式 `ArmatureLockMode.BaseToMerge` 会把服装骨架同步到素体骨架，表现为服装 GameObject 仍在层级里，却完全不渲染。只改顶点、不动骨架的捏脸不受影响，但这种情况是少数。
- **顺序**：装配排在换 FBX 的捏脸之后；已装配后又换了 FBX，就按下面的方式复核，不假设装配仍然有效。
- **修法**（人工作业时）：受影响的件拆掉重装一次即恢复渲染，然后重新施加配色（材质数组已被重置）。本流程里装配和改色每次都由 Runtime 从零重建，等于每次都重装，执行方不用做。
- **验证**：逐件单独开启确认可见；逐件核对材质数组与配色记录一致。
- **升级给人**：重装后仍不渲染，或配色无法按记录复现时，报告受影响的件。
- **证据**：机制与修法来自实际工程（候选，未在多个工程上系统复测）。

## 装配验收：逐项取证，不抽查

每一项都要有本轮的截图或数值证据；「组件挂上了」「脚本跑完了」不是证据。本流程里渲染、配饰位置、组合三项的截图与几何由 Runtime 在回归阶段取，本阶段写「交回归阶段」。

| 项 | 判据 |
|---|---|
| 骨架 | 人形主干零缺失；MergeArmature 映射骨数 > 0；主干逐根吸附 |
| 渲染 | 每件单独打开时看得见（不是「物体在但不渲染」） |
| 收缩键 | 脚部键或多宿主写者都有原方案复核或 Runtime 校验的局部 shrinkkey_review（不采信自写批准）；几何与照片交回归阶段 |
| 配饰位置 | 每个配饰逐个确认装位与大小，不能只看层级里挂对了 |
| 组合 | 每套服装 × 每个配饰 × 各开关组合都检查过，无穿模、无装错位 |
| 遗漏 | MeshFilter 全量扫描，骨架内挂件都已归组 |
| 用上了 | 每件都有包外引用（GUID 反查命中 > 0），否则就是没接线 |

- 静态渲染只能查 T-pose。袖口、裙摆、腋下这类地方要过动作（例如在 Gesture Manager 里）才看得出来，交给正式回归的状态集与动作检查，本阶段不自行宣布通过。
- 动骨（PhysBone）的观感编辑期不模拟，只能在 Play 里看。

## 局部方案复核与返工

装配发现原方案未覆盖写者时，AI 可在既有目标及素材授权内，通过 outfit goal 的 shrinkkey_review 操作提交局部修订。完整实际写者和顺序、来源观察、源资产、无冲突值及三态预期由 Runtime 校验；只登记技术方案补充，不改变原方案批准、接受脸型或旧证据，也不代表三态实测。多宿主须解释先后及最终胜者。缺证据应补探查/返工；超出授权或需外观取舍时给出中文具体选项，交已有确认入口，不让用户修改 YAML。
