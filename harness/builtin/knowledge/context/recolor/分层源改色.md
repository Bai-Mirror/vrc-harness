# 分层源改色：区域来自作者的层，不是猜出来的像素

**何时用**：需求说「只改某部件」（睫毛、内缘、一缕头发）或「某色只允许出现在某些表面」时用按层目标；只是整件换色调时仍用相对改色。

## 开工前必须成立

1. **登记的素材有分层源文件**：方案里 `layered` 必须逐字取自清点登记的列表。多数服装包不带源稿——那一项就不能按层改色，**不要用像素猜测冒充精确**。
2. **层路径唯一命中**：路径是逐级名称的数组，名称里的空格属于名称本身，**不得去掉首尾空白后匹配**。零匹配与多匹配都失败，不许挑一个。
3. **源文件与工程贴图的对应关系已证明**：作者合成未必能复现，而且**差异量级随素材变，不能按一次标定推广**。两条实测（同一套 `layer_source.py` 判据）：
   - 一套素体的脸部 PSD：59.8% 像素有差异，其中 55.48% 只差 1 个码值，alpha 只差 0.042%——几何对应、颜色解释差一点。
   - 一套素体的眼睛 PSD：两份候选源（包内直接条目与它嵌套的 `unitypackage` 里那份，两者本身不同字节）与工程贴图比，**都在 `baseline` 上 62.2% 不同**；超出 4 个码值的像素占已绘制差异的 **16.6%**，alpha 有 **2.638%** 的像素带不同的非零值。覆盖面对得上（已绘制像素数 11,399,528 / 11,399,444 对 11,399,299，绘制／透明翻转只有几百个像素），**但颜色与 alpha 解释不对应**。
   **后果**：`resolve` 的两个阈值（`alphaAgreement ≥ 0.999`、`nearShare ≥ 0.95`）在这套素材上分别只有 0.9736 与 0.8959（另一份候选源 0.9751 与 0.8960），**`apply` 也会以「找不到对应贴图」阻断**——不只是严格的 `baseline` 过不去。**不得为了避免阻断而调低这两个阈值**：那等于把「没证明」写成「已证明」。**这条结论只覆盖这份眼睛贴图的这两份候选源（`eyes.psd` 对工程引用的 `eyes.png`）与现行阈值**，不是对按层路线的一般判决；换一份源或换一套素材都要重新标定。
   因此这两份候选源在现行阈值下**过不了对应证明**；**取遮罩**是另一条路线——区域取作者的层，改色发生在工程实际引用的那张贴图上，它要在该素材上**独立证明遮罩对齐**才成立（D-74 的脸部取遮罩路线正是这样获准的），**不是重合成失败后的静默补救**。**不得**用「重新合成再整体替换」冒充局部改动，那是全局基线迁移，需单独授权。

## 颜色语义逐目标声明

- **`shade`（作者底色替换）**：保住作者明暗，按自身相对亮度挪到目标色。**算法是逐像素写明的**：**目标色的每个通道**乘以「本像素最亮通道 ÷ 目标色最亮通道」，双精度，取整规则是 `floor(x + 0.5)`。**被乘的是目标色，不是原像素**——乘原像素是另一条承诺，而且原像素最亮通道等于目标色最亮通道时它要求的正是「原样不动」，于是一个没改过色的区域会被读成正确的 shade。只承诺**层输入值精确**，**不承诺每个像素等于色号**。
- **`flat`（最终区域纯色替换）**：区域内**可见**（alpha≠0）像素**精确等于目标色**，代价是丢掉作者渐变。

两条路线的取整与混合规则必须分开记：**按网格区域**使用二值 UV 足迹；`flat` 直接写目标色，`shade` 先按上面的目标色亮度比例计算，再用双精度 `floor(x + 0.5)` 逐通道取整，alpha 保留原值。**按作者分层**使用 0–255 的软遮罩，先把原像素与语义产出的目标像素按 `w / 255` 线性混合，再沿现有执行器使用 NumPy `.round()` 转回 8 bit；这里不能把区域路线的 `floor(x + 0.5)` 推广过来，否则半值边界会改变按层路线的既有结果。

**验收不是数颜色**：只数「通道值有几种」既会放过一个原样没改的渐变，也会误拒一个正确的纯色区域。按区域改色时，观察器**独立算出该语义应当产生的像素**再与产物比；按层改色时按作者遮罩的权重同样算出预期值。**全透明像素没有颜色可改**：掩膜内 alpha=0 的像素 RGB 必须原样保留，一个区域里一个可见像素都没有时整条阻断，而不是只留一条说明。

**顺序不能反**：`flat` 的精确断言套到 `shade` 上会误报，反过来会放过未兑现的承诺。

## 验收看什么

1. **局部性**：执行前固化的允许范围之外，RGBA **逐通道零差异**，全图 alpha 零差异，全透明像素的 RGB 也保留。范围不得从差异反推，也不得为通过而纳入阴影或整张画布。
2. **区域内**：按该目标声明的语义断言。
3. **运行时兑现**：新贴图确实绑到声明的材质与槽位；贴图比对**不能**替代这一步。
4. **叠加图**：区域选得对不对必须出图核对，**不能替代**数值检查。

## 执行顺序

1. **先证明对应关系**：`resolve` 把未修改的源文件合成一次，对候选贴图比对，只在**明显最优**时给出对应贴图。近似并列或无吻合都失败——那说明还没证明，不该开工。
2. **再按配方出图**：`apply` 读配方里的 `layerOps`，逐个取作者层的遮罩、按该目标声明的语义改色，把新贴图写进 `Assets/_Harness/Recolor/`，**证据固定写到 `Assets/_Harness/Recolor/layer-apply.json`**——Unity 步骤就从那里读绑定清单，写到别处等于没做。**原贴图不被改写**；绑定到新贴图是另一件可单独核对的事。
3. **Unity 侧只做绑定**：把新贴图挂到**所有正在用原贴图的槽位**上，包括 lilToon 一类的多个别名属性（`_MainTex`／`_BaseMap`／`_BaseColorMap` 指向同一张图，只改一个会让它们分叉），并按原件的导入设置对齐新贴图的读取方式，然后**读回 Unity 实际生效的值**。像素那一侧已经验过，这里不做第二次改色。
3. **证据留给别人核对**：`apply` 记录区域像素数、改色前后的均值、以及区域外与 alpha 有没有动。**它不判断好不好看**，也不代替验收。

## 容易弄错

- **层名不是最终可见区域的证明**：分组里可能有阴影层、叠色层与本次不要的层，同一分组内也可能有非 normal 混合模式（本批睫毛分组里就有 `multiply`）改变合成值。哪些层属于本次要求是订单语义，要订单方确认。
- **两种语义的数字本来就不同**：同一区域同一色号，`flat` 的均值应当落在目标色上（实测 `#5B5B66` → 均值 `91.68, 91.51, 102.43`），`shade` 的均值**不会**等于目标色（同区域实测 `117.1, 116.93, 130.97`）而保住明暗。**拿 `flat` 的数值去卡 `shade` 会误报，反之会放过未兑现的承诺。**
- **贴图局部性不等于屏幕局部性**：过滤、mipmap 与 shader 影响邻近采样，显示层面须另查。
- **「只改指定区域」≠「某色只允许出现在指定表面」**：后者还要检查基线里是否已有越界用色，并明确判定对象是配色归属、贴图值还是最终渲染颜色。
- **不支持的输入必须失败**：缺源稿、层路径不唯一、效果超范围、依赖缺失——一律阻断，不用近似冒充。

## 区域来自网格 UV 足迹：同一材质上左右分色

**何时用**：需求要在一张贴图、一个材质上把两处表面改成不同颜色——左右异色瞳是典型。这时按层这条路先输在**对应关系**上：本单眼睛的两份候选源在现行阈值下都过不了证明（见上节，实测读数），而层的名字说的是**作者文件里的一块区域**，不是**网格上的一块表面**——要「这只眼」，得说出哪块表面。区域只能从网格来。

**形态**：目标写 `region: {renderer, submesh, bones}`，配 `color` 与 `semantics`，与按层同一套语义判据。

- `renderer`：表面所属渲染器在头像里的层级路径（观察里的路径原样照抄）。
- `submesh`：它的第几个子网格／材质槽，从 0 起。
- `bones`：**厂商自己用来标注这块表面的骨骼名**。区域就是「三个顶点都被这些骨骼影响」的那些三角形在 UV 上的足迹。

**为什么不能切矩形**：矩形（例如 `u >= 0.5`）能通过局部性、alpha 与语义**全部**检查——因为它与它自己做出来的产物自洽。只有把区域从网格重算一遍才能说它不是那个区域。所以掩膜必须由网格导出，观察器会拿同一份网格数据重算并逐像素比对。

**骨的判据，不是名字的判据**：这套判据不写死资产名、目录或骨名。骨名从观察或该素体的知识条目里取得，**报不出来源就不要写**；写错的名字不会静默失效——执行时找不到那根骨就整条阻断。

**两个区域不能分开时必须阻断**：镜像共用 UV 的件（本批实测 `bag`／`loafer` 的左右两侧 UV 重叠率 1.0）没有排他像素，给它上任何一种颜色都会染到另一侧。两个区域共有的像素**两边都不上色**，并把共有像素数报出来；某个区域一个排他像素都没有时整条阻断，不许两边都刷。

**回读用区域自己的掩膜**：左右两边分别按各自区域的掩膜取样。用合成后整张图的 alpha 取样会把肤色选进来，两边量到同一个色（案例：异色瞳回读两边同色）。区域在贴图上全是透明像素时也回读不到颜色，那要报出来而不是当成 0 差异。

**掩膜按原文件的尺寸算，导入设置随后继承**：导入器的 `maxTextureSize` 是运行期的显存预算，不是区域的尺寸。本单的眼睛原图是 **4096**、导入上限 **2048**，所以顺序必须是「先解码原文件 → 按它的宽高生成掩膜与产物 → 再把原件的导入设置复制给产物」。反过来会拿 2048 的掩膜去对 4096 的解码，把这张贴图整条挡在门外。

**两端的算术只有一套**：都用 float64（UV 来自网格的 float32，精确加宽）；**零面积三角形不覆盖任何像素**；像素中心恰好落在边上算在内（`>= 0` 或 `<= 0`，不用 `>`）。这三条不是「实现细节」——真实编辑器夹具里用一颗三角形把前两条钉住了：float32 会多算一个像素，去掉零面积规则会让那颗三角形填满它的包围盒（4096² 上多 4 个像素）。放宽掩膜比对的容差**不是**这些分歧的解法。

**记录不能自己定义要核对的东西**：观察器从**批准方案**建立唯一的需求映射，逐操作核对 `renderer`／`submesh`／`bones`／`color`／`semantics`，并拒绝重复、遗漏与额外的记录；区域也按**方案里的骨骼**重算，不按记录里的骨骼。否则把记录和产物一起改成另一个区域，每个读数都彼此自洽，整条通过。

**台账逐需求一行**：同一张贴图上的每条需求都要有自己的台账行（同一槽位几行不等于改了几个槽——F21 仍按去重后的槽数判）。只记第一条需求，另一条在独立读者眼里就是「没落上」。

**绑定只许落在它声明的表面上**：归属与排他是**逐块表面**算出来的，所以一组区域的产物只许绑到它声明的那个渲染器与子网格；同一张贴图还被别的表面读着时（别的渲染器、或同一渲染器的另一个子网格）整条阻断——那块表面的 UV 从未参与推导。这条同时挡住了「两组区域各写同一张贴图」：每一组的绑定集合都包含对方那块表面，先撞上的就是它。此外源贴图必须是**工程原有的文件**，不是本层自己写出来的产物——否则是在拿自己的算术核对它自己。

**属于两个区域的三角形，足迹要从每一块区域的可绘制掩膜里扣除**：它的表面是共用的，那块像素没有主人，和「两个区域的足迹都覆盖到」是同一种情况。只把它从归属里去掉、仍让相邻区域照原样上色，就等于把一只眼染到了另一只。
