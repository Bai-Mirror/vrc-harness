# 配色：非破坏性施加、规则表与撞色

## 服装改色走副本：复制厂商材质再改颜色参数，并落台账

**职责**：整体压暗、偏冷、做撞色点时，只改颜色参数，不动贴图，不动厂商材质。

**本流程由 Runtime 施加**：复制材质、挂槽、出候选图、写台账与决策记录，都由 Runtime 的改色步骤在你退出后完成：按「渲染器 × 原材质」各复制一份，每次从原件重抄；带 `_MainTexHSVG` 的材质（lilToon）写 HSVG：色相偏移 = hue_shift/360（折回 [-0.5, 0.5)），饱和 × saturation，明度 × value；没有这个属性的才改 `_Color` 的 HSV。然后重建 `Avatar.prefab`，整份覆盖 `ledger.json` 与 `配色决策.md`，删掉 `Materials/` 下不是本次生成的材质。

**你要做的**：
1. 调用 `generate-recolor-candidates`，由它按方案写 `recipe.json`；
2. 核对方案里每个 target 能不能落到材质槽上：`hair`＝素体上名字含 hair 或 髪 的渲染器；`eye`＝素体上材质名含 eye 或 瞳 的槽；`outfit:<id>`＝`Outfit_<id>` 下的全部渲染器。落不上的写明原因。

**机制**（人工作业时的做法，供判断）：lilToon 的 `_Color` 乘在 `_MainTex` 上，只改颜色参数、不动贴图就能调色；副本放在本阶段目录，台账记 `渲染器路径|槽号 → 原材质 GUID`，还原全靠它。

**禁止**：手写 prefab、台账或决策文件；自建材质副本（放在 `Materials/` 下会被删，放在别处没人引用）；改厂商材质原件。

**验证**：Runtime 核对台账与实际槽绑定、空材质槽及骨架高度。被修改的材质副本在本阶段目录下；纯选择厂商材质时直接引用原资产，按计划指定 GUID 与当前版本的独立回读核对。

**升级给人**：需要改贴图本身才能达到的颜色（本流程没有贴图改色通道）。

## 改色规则表：台账只记原件，每条从原件起算，逐件列规则

**职责**：一张规则表里有多条改色规则时，保证可以还原、倍率不叠加、不误伤。

**权威输入**：规则表；台账；材质共用清单。

**本流程里**：配方由方案 `recolor.targets` 决定，粒度只有 `hair`／`eye`／`outfit:<id>`；Runtime 对 `outfit:<id>` 会改该套下全部渲染器的可调材质槽，每档都从原件起算。需要排除小件、只改部分部件、或只给一两件做撞色时，本阶段做不到：写明原因交人（应在方案阶段提出）。不得手改 `recipe.json`：配方可重算检查会用方案重算、比哈希，手改的条目会让它阻断，新写的部位名会让 Unity 步骤报错。

**决策边界**（人工作业时的规则表，供理解机制）：
- 台账只记第一次触碰时的原件。规则表后面的条目覆盖前面的条目时，第二条规则读到的已经是第一条做出的副本；照记的话，下一轮还原会指向一个已被删掉的资产 → 材质槽为 null → 洋红。
- 每条规则都从原件起算。先整套乘 0.26 压黑、再把撞色件乘 0.78，会叠成约 0.20，撞色点反而比周围还暗，等于没做。
- 规则逐件列（按渲染器与槽），不用 `("Outfit_XXX", "*", tint)` 这种通配。染色器为每个被点名的槽单独复制一份材质，没点名的槽原封不动；材质跨渲染器共享时，这是「只染袜子、不染绷带」的唯一办法。

**禁止**：通配规则；在已生成的副本上继续乘倍率。

**产出**：逐件的规则表与台账。

**验证**：规则表里没有通配；台账每一行都指向存在的原件 GUID；从原件重跑配方，输出哈希不变。

**升级给人**：规则之间意图冲突（同一件被要求两种颜色）时。

## 配色按件判断：换了颜色还认得出的才刷

**职责**：决定哪些部件跟着配色方案改色。

**权威输入**：部件清单；需求。

**决策边界**：判据是「这件东西换个颜色，还认得出是什么吗？」认不出就别刷。
- 能刷：外套、裙、上衣、袜、鞋、手套、腰带、包。大面积布料，颜色属于配色方案，换了还是同一件衣服。
- 不能刷：玩偶、绷带、纱布、血袋、输液管、徽章、贴纸。有独立叙事身份的小件，颜色就是造型元素本身，刷成单色等于把它从画面里抹掉。

**本流程里**：`outfit:<id>` 就是把整套当一块布，Runtime 会连玩偶、绷带一起染；逐件排除本阶段做不到。用这个判据检查每个改色目标：套内有不该刷的件时，写明哪套、哪几件，交人（应在方案阶段拦下）。

**禁止**：把整套衣服当成一块布统一着色（本流程做不到逐件时，交人而不是照刷）。

**产出**：逐件的「刷／不刷」清单与理由。

**验证**：「不刷」清单里各件的材质未被替换（本流程里这条过不了就交人）。

**升级给人**：面积较大、又难以判断是否有叙事身份的部件。

## 撞色点：小面积件要主动提亮提饱和

**职责**：在暗色基调里做出能被一眼读到的撞色。

**权威输入**：需求里的撞色要求；同机位候选渲图。

**本流程里**：改色粒度是整套，只给一两件做撞色本阶段做不到；需求里有撞色要求时写明交人（应在方案阶段提出）。

**决策边界**：撞色点必须主动提亮、提饱和，而且只给一两件（面积小，且是叙事核心）。不能指望「把周围压暗，原本的颜色自然就浮出来」：厂商原色常偏灰，在纯黑底上会读成一块灰片。大面积换色会毁掉暗色基调。

**禁止**：用压暗周围代替提撞色；给大面积部件做撞色。

**产出**：撞色件清单与各自的调整量。

**验证**：同机位渲图里撞色件能被一眼读到，交评审确认。

**升级给人**：选哪一两件做撞色会影响造型叙事时。

## 配色改完：依赖材质的菜单生成要重跑，材质曲线要回读

**职责**：保证菜单动画用的是改色后的新材质，不把改色盖回去。

**机制**：多配色合并成一份实例时，配色层的材质曲线是从场景里当前的材质采集的；配色改了之后，菜单生成必须重跑，否则会被旧曲线盖回去。流程里菜单阶段在配色之后；配色在菜单之后被改动时，菜单要作废重跑。

**本流程的 recolor 阶段**：检查 `recolor_menu_curves_repointed` 数的是改色层头像里（描述符动画层与 MA Merge Animator）仍把被替换槽切回原材质的曲线；这时菜单还没生成，数到的多半来自厂商或服装自带的换色动画。你改不了厂商 clip，也写不了 `Menu/`，改色层每次还会被 Runtime 重建。不为 0 时，列出涉及的 clip 与槽，交人。菜单由后续 menu 阶段整层重建，改色变了会让它失效重跑。

**本流程的 menu 阶段**：Runtime 把 `vendor_clips` 的曲线原样复制进本单的部件层，不会把材质引用重定向到改色副本，menu 阶段也没有检查拦这件事。登记 `vendor_clips` 前，先查它的 ON/OFF clip 里有没有 `m_Materials` 曲线指向已被改色的槽；有就写明并交人，不要登记后当作没事。

**验证**：生成的 `.anim` 里 `m_PPtrCurves` 指向新材质，指向旧材质的曲线 == 0。

**升级给人**：上面两种情形；还原时台账指向已删除的资产（出现洋红）。
