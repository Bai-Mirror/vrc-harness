# 配色：候选、交叉评审与决策记录

## 配色候选：每个维度出 3–5 档，同机位同布光并排渲染

**职责**：给每个配色维度出几档候选并排渲染，让评审或用户挑，而不是自己拍板一个。

**权威输入**：需求 ↔ 来源对照表；逐件的规则表；非破坏性施加路线（副本＋台账）。

**本流程里**：候选档是全部改色部位联动的一组，数量取方案 `recolor.candidates`（3–5），固定为 A 方案原值／B 收敛／C 加强／D 低饱和／E 高饱和，每档同时缩放全部 targets；由 `generate-recolor-candidates` 算出，Runtime 按「每档 × 每套衣服」同机位各出一张图，写在 Run 目录的 `candidates/`。不要按维度自拆档，也不要自己出图（你开不了 Unity，也写不进 Run 目录）。

**决策边界**（人工作业时，供理解机制）：
- 每个维度出 3–5 档，每档都从原件起算。
- 所有候选用同一套机位规格渲染（同机位、同布光、同分辨率），规格作为结构化记录与图一起保存。
- 直接猜一档大概率返工。例如睫毛颜色出 5 档（RGB 216 → 126），最后选中的是中间那档。

**禁止**：用不同机位的图做 A／B 对比（没有可比性）；只出一档。

**产出**：候选图；每张图的机位规格记录；每档的参数。

**验证**：档数在 [3, 5] 内；所有候选图的机位规格逐字段相同，不同就重渲，不能拿来比；空材质槽 == 0；Head 与 Foot 骨的世界 y 之差不变。

**升级给人**：维度太多、在档数范围内覆盖不了需求时。

## 配色交叉评审：逐档打分，两个模型都无 blocker 才通过

**职责**：用多个模型交叉评审代替逐档问人，并留下可追溯的决定。

**权威输入**：同机位候选图；需求原文。

**本流程里**：定档由人在 `recolor_approval` 闸门决定；Runtime 默认落 A 档；人驳回时在修改意见里写「选 B」，下一轮 `generate-recolor-candidates` 读修改意见重算。闸门界面直接显示本版本 Run 目录里的候选图：决定卡上是方案选定档 × 每套服装的精简缩略条，并指向旁边的「Unity 场景预览」卡，完整档位 × 服装网格在那张卡上；没有图就不给批准，所以不要在回复里复述候选图片或代替人看图。你可以评审候选、把意见写进报告供人参考，但不得改 `recipe.json` 的 `chosen` 或 `feedback`：改 `chosen` 会让配方重算检查阻断，连 `feedback` 一起改等于伪造用户意见。决策记录 `配色决策.md` 由 Runtime 整份重写。

决定卡和场景预览卡中的每张候选图都可点开，**在应用内**按原始像素尺寸查看：显示的是缩略图已校验的同一张已绑定图片（不重新取图、不新开窗口、不重新编码），图片大于窗口时可上下左右滚动，关闭按钮或 `Esc` 退出。桌面宿主会拦截新窗口，`data:` URL 又不能作为顶层导航，所以「打开原图」只能做成应用内图层，做成新窗口链接等于死按钮（`D-42`）。界面不得把固定百分比裁剪标作脸部、上身或下装，也不得另做渲染。批准仍绑定整份图片清单摘要、Run 与产物版本；任一必要的档位 × 服装组合缺失或完成后的图片字节变化，整组证据撤下。

**决策边界**（有自动定案策略的流程）：
- 配色是审美卡口，但在需求问卷已写清方向（色调、撞色、各部位颜色、风格偏好）时，可以交给多模型评审决定，只在评审有分歧时上报。捏脸不在此列，捏脸定形必须由人判。
- 评审提示要写清：需求原文，让模型有判据；逐候选打分并说明理由，不要笼统说哪个好；指出哪一档偏离了需求的哪一条；明说禁止编造、禁止软化。
- 候选合批一次问完，不要一档问一次。
- 单个模型的指认降级为「待核」，自己复核，不直接丢，也不直接信。
- 选定后写决策记录，三项齐全：选了哪档、为什么、被否掉的是哪些以及原因。

**禁止**：把单个模型的结论当定论；只记结果不记理由。

**产出**：逐模型、逐档的分数、理由与偏离项；配色决策记录。

**验证**：某一档有 ≥2 个模型判为无 blocker → 通过；决策记录三项齐全。

**升级给人**：没有任何一档拿到 ≥2 个模型无 blocker；模型之间结论有分歧；需求方向本身不清。
