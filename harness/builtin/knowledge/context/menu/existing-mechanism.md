# 菜单阶段：先查清现有机制

## 本流程的菜单：Runtime 生成什么，design.json 能写什么

本节仅用于 plan/0.2 的旧单轮盘设计，不适用于 plan/0.3。新版读取已接受 avatar_config 与 menu.tree，见必需的多组配置合同。

菜单 prepare 的工程位置由 Runtime 的 AVH_PROJECT_DIR 提供；Run 工作目录不是工程目录，模型不负责补内部部署路径。

Runtime 的轮盘曲线和 selector_owned_paths 只记录构建保留的衣装根与 BoneProxy 可视件：自身或祖先为 EditorOnly 的可视件不写曲线，普通未激活对象仍必须覆盖。路径缺失或整套衣装已被排除仍拒绝；不能通过删除前序台账、改标签或放宽独立绑定检查来过关。


**保留原装例外**：已批准方案 `outfits: []` 且 `menu.mode: preserve` 时，不适用下文新增衣装轮盘的生成合同。不要写入控制器或修改厂商菜单；Runtime 从改色层保存没有改动的菜单层变体，核对来源与覆盖记录，仍进行构建、参数和动画检查。空服装列表不代表没有产物，也不允许虚构一套服装来满足流程。新增衣装或需要新菜单交互时不能使用这条保留路线。

**你只写 `design.json`，Runtime 实现**：你退出后，Runtime 从改色层重建 `Menu/Avatar.prefab`，删掉旧控制器与 clip 再生成：在根菜单下挂「造型」子菜单；固定生成一个 Float 衣装轮盘（新增 8 bit，档位就是方案里的每套，默认参数名 `AVH/Outfit`）；每个 control 生成一个 Bool 开关和一层两态（ON/OFF，WD 关）。轮盘层是这份控制器的第 0 层，部件层依次追加在后；整份控制器用 MA Merge Animator 合并在厂商层之后。厂商菜单原样留在原位，不调整 `installTargetMenu`。

**能写的**：`component_groups` 最多 7 个区，每区 1～8 个 control；每个 control 的 `targets` 按衣装列 `objects`（开时显示、关时隐藏）、`disable_when_on`（开时关、关时回来）、`vendor_clips`（厂商 ON/OFF clip：Runtime 把其中全部曲线原样复制进本层，含显隐、形态键、材质、骨骼；ON clip 会打开预制体里默认关闭的对象时，先按备选件排除，只有说明书与单独预览证明它属于该功能时，才在 `allow_default_off` 里显式列出）。

**违反就抛错、整个阶段失败**：①`objects`、`disable_when_on` 的路径必须在该衣装根下，素体对象进不来；②一个路径只能归一个 control（两个列表共用一张所有者表），一条动画属性也只能由一个 control 写（`vendor_clips` 的曲线同样登记）；③`parameter` 不能用厂商已占用的参数名；④同一 control 不能要求同一路径既开又关；⑤缺 `design.json`。

**表达不了的**：Parameter Driver、组合条件与「或」、压制层、多档轮盘（control 一律是 Bool，type 字段被忽略）、第二个轮盘、换材质的配色切换、改厂商参数默认值。所以：要让位的对象不能再有自己的开关，要么并进触发它的 control（写进 `disable_when_on`），要么保留独立开关、放弃让位并写明穿模风险；由几个开关组合决定显隐的件、素体对象、同一衣装内多件同位置件的互斥，本流程做不到：按用户任务选一件做开关、其余保持默认，写明并交人。各来源分属不同衣装时，由衣装轮盘天然互斥。

**没有等人的闸门**：menu 阶段不停下等人，必须交出一份能实现的 `design.json`。知识里写「两案并列」「待用户定」的地方，按默认动作选一案实现，另一案和理由写进 `design.json` 的附加字段（如 `pending`）：整份设计会原样记进 `menu.json`，打包阶段的诊断会读到。

**已知口径**：menu 阶段按 NDMF 处理后、VRCFury 压缩前计参数位，超 256 阻断；`vendor_clips` 里的材质曲线不会重定向到改色副本；构建、Play 与渲图验证由 Runtime 在 build_pre 与 regression_pre 做。

## 改菜单前先追清现有机制：谁驱动、几档、层权重

**职责**：提出任何菜单或动画层方案之前，把工程里已有的切换机制查清并写进设计记录。菜单树、组件表、参数表只是结构；机制是「谁驱动谁、按什么顺序、当前取值是什么」。只看结构就提方案，等于在没读懂的代码上重构。

**权威输入**：构建（NDMF 与各插件合并）后的控制器层列表及每层 `defaultWeight`、各状态 clip 的曲线（路径＋属性＋关键帧取值）、Parameter Driver、`VRCAnimatorLayerControl`、MA 与 VRCFury 组件、厂商的 Expressions 参数资产。层名、物体名、参数名只作线索。本流程里执行方拿不到构建后的控制器，读厂商控制器、clip 与参数资产的 YAML（层的 `m_DefaultWeight`、状态、转移条件、曲线）来回答。

**每个现有功能都要回答三问**：
1. 由什么驱动：哪个参数、哪一层或哪个组件；这一层权重是多少，有没有 LayerControl 给它抬权。
2. 数据怎么流到最终效果：一路追到 clip 的关键帧取值和最终被写的物体属性。
3. 现在实际有几档、每档是什么。Motion Time 轮盘要读 clip 的关键帧时间与停止时间，不按参数名猜档数。

**决策边界**：优先扩展现有机制，不另起一套。已有机制可能是用户自己搭的，例如一个 Float 参数拖动一条阶梯关键帧 clip 切整套、厂商换装层已停用；这时加一套衣服应当是给那条 clip 加一档（参数增量为 0），而不是新建互斥轮盘去抢同一批 `m_IsActive`、再多占 8 位。plan/0.2 使用旧生成合同登记 `vendor_clips` 与部件区。plan/0.3 消费已接受配置：能证明简单厂商消费者完整行为时显式 adopt，不能证明时阻断；技术调查不得改动已批准的多组成员和默认值。现有机制与方案冲突时报告证据，不靠层序覆盖。

**禁止**：
- 看到层名写着厂商的换装、耳朵等功能就当它在工作。权重为 0 且无人抬权的层整层不输出曲线，它引用的厂商参数实际是死的。
- 把同一素体另一个工程的结论照搬过来：同一素体包在不同工程里，厂商层可能一个启用、一个已被停用。

**产出**：在所有权表的每一行补上「层权重/抬权来源」「现有还是新增」两列；现有机制的三问答案写进设计记录。

**验证**：每个现有参数都能在构建后控制器里找到消费者（转移条件、Motion Time、BlendTree、Driver 之一）；每个被认定「在工作」的层，权重非 0 或存在可解析的 LayerControl。

**升级**：现有机制是用户自建、且方案必须推翻或替换它时，停下交用户决定，附上三问的答案与替换代价。

## 厂商参数层的连带效果：改参数，不直接写它管的物体

**职责**：厂商已用参数层管理的功能（帽子、外套、背包、尾巴条数等），菜单通过改这个参数来切换，让厂商层完成全部联动。

**权威输入**：厂商 ON/OFF clip 的全部曲线，不止本体的 `m_IsActive`，还包括写在其他网格上的 `blendShape.*`、骨骼 Transform、塞在骨架里的静态件；以及厂商层的状态机结构。

**连带的典型形态**（同一素体包内实测的三例）：一个帽子参数同时管帽子网格、一个发饰、猫耳网格和猫耳骨骼姿势；一个外套参数同时写上衣网格上的两个防穿模收缩键；一个背包参数同时管包、名牌和骨架里的玩具。只写网格的后果依次是：耳朵网格开着但骨骼还折在头里；关了外套上衣仍缺一截、露出肚子；玩具留在原地飘着。

**风险方向**：关掉一件网格时，它自己的骨骼姿势无关紧要；出问题的是「网格开着而骨骼或形态没复位」，以及厂商参数顺带写在其他可见物体上的状态没有复原。

**plan/0.3 怎么接**：只按配置显式 adopt 已有公开参数，核对类型、默认、保存、同步、消费者及完整联动。未知复杂接管或相关 ParameterDriver 不能认证时阻断，不复刻单个网格显隐。

**plan/0.2 怎么接**：厂商参数层管着的件，一律把厂商 ON/OFF clip 登记到对应 control 的 `vendor_clips`（`root` 写厂商动画相对的对象根），Runtime 把其中全部曲线（显隐、收缩键、材质、骨骼）复制进本单的部件层，排在厂商层之后。不要把 `parameter` 写成厂商参数名（会被拒绝），也不要设计 Parameter Driver（schema 不支持）。代价是厂商原菜单里对应的开关对这些属性不再起作用，在 `design.json` 的说明里记一条，供交付诊断写给用户。

**做法**（能用 Driver 的流程）：
- 部件开关要与厂商参数同步时，在开关层的 On/Off 状态上挂 Parameter Driver，把厂商参数设成对应值，厂商层会把它顺带写的形态键等还原。
- 厂商用「一个 Float 参数＋一棵混合树」实现的功能，不复刻它的 clip；单开一层，每档一个状态，状态上用 Driver `Set` 该参数。AnyState 转移关闭 `canTransitionToSelf`，否则条件成立期间每帧重进、每帧写参数，把用户调过的值一直按回去。
- 厂商参数本身就能当开关用时，菜单控件直接绑定该参数：不新增层、不新增参数位。

**禁止**（能用 Driver 的流程）：在自己的 clip 里写厂商参数所管的属性。那等于一直按住它，厂商层之后再也打不开它。plan/0.2 的旧合同只能这样接（登记 `vendor_clips`），按上面的代价写明；plan/0.3 不沿用这个覆盖许可。

**验证**：对每个被驱动的厂商参数，列出其 ON/OFF clip 写到的全部路径，确认开、关两态在构建后都由厂商层写回；Driver 的效果只在 Play 中验证，离屏渲染模拟不了 Driver。本流程里构建与 Play 由 Runtime 在 build_pre 与 regression_pre 做，你在 `design.json` 里写清每个 control 的预期即可。

**升级**：厂商 clip 写到的对象语义不明（可能是二选一的备选件）时，按「部件语义待定」报告，不擅自收进开关组。

## 介入强度：先判断厂商菜单够不够用

**职责**：在衣装轮盘与部件开关之外，决定对厂商已有功能菜单（表情、动作、宠物模式、尾巴摆动等）改动到什么程度。

**权威输入**：厂商 Expressions Menu 树，连同 MA Menu Item、MA Menu Installer 在构建期挂进来的部分；用户需求；方案中的衣装清单。

**已见过的三种强度**（来自三个不同工程）：
1. 直接使用厂商菜单；
2. 最小介入：只往厂商菜单里加一个衣装轮盘；
3. 自建根菜单，把厂商子菜单以引用方式挂进来。

**plan/0.3 里**：按已接受 menu.tree 生成多个独立组入口，preserve_and_merge 保留来源厂商入口；构建后独立对账布局、名称、入口与允许差异。不能把参数仍在当作菜单树完整。

**plan/0.2 里**：介入强度固定：Runtime 在根菜单下挂「造型」子菜单（衣装轮盘＋最多 7 个部件区），厂商菜单与插件菜单原样留在原位，不复制、不改 `installTargetMenu`。分区与命名按默认动作定一案，另一案写进 `design.json` 的附加字段。

**决策边界**：从弱到强选，够用就不升级。分几个区、每区叫什么、哪些归一组是软的，按这台模型的内容重划，以简洁明了为准（见过的分法如「换装/外观/动作/素体」「服装/功能/玩具/头像」）；照搬别的工程的分组可能不合适。

**禁止**：
- 复制厂商菜单资产：一律引用原资产。
- 为塞菜单项去改插件或厂商预制体：插件自带的 MA Menu Installer 用 `installTargetMenu` 指向目标子菜单即可。

**产出**：设计记录写明采用哪一级介入及理由；列出每个厂商子菜单和插件菜单在新菜单树中的落点。

**验证**：构建后的菜单树里，厂商子菜单仍可达；插件菜单落在指定子菜单下，而不是掉回根菜单（`installTargetMenu` 或描述器的 `expressionsMenu` 引用变空时就会掉回根菜单）。

**升级**：分区与命名需要用户审美决定时提交两个候选；介入强度本身按「从弱到强、够用即止」决定，不作为审美候选。
