# 面部追踪：装完之后的五项核查

## 面捕装完：场景里只能有一个活跃的头像根

**职责**：面捕安装之后、任何验收之前，确认后续工具操作的是正确的头像。面捕安装本身由用户亲手做，排在全部作业之后。

**权威输入**：四种口径的头像根计数：场景根、全场景的 avatar descriptor、活跃根、含备份的 prefab。

**决策边界**：面捕安装器会克隆整个头像：场景里变成两个头像，原件被停用；所有按名字找头像的工具都会改错对象。面捕那份是下游产物：模型修改一律做在原件上，面捕根可以重新生成。

**禁止**：自己删掉多出来的根（删错会丢掉线上版本）。

**产出**：四种口径的根计数，以及各根的路径与启用状态。

**验证**：活跃根 == 1。

**升级给人**：发现两个活跃根就停下报告，由用户决定留哪个。

## 面捕根与原生根：改材质前先核是否共享材质和贴图

**职责**：改材质或配色之前，弄清面捕根与原生根是否共用材质、贴图。

**权威输入**：两个根所有渲染器 `sharedMaterials` 的资产路径与 GUID。

**决策边界**：停用另一个根不等于省掉它的开销：两个根共享材质或贴图时，停用省下的只是渲染器，效果不如预期；改共享材质也会同时改到两个根。是否共享，用「改一处会不会同时改到两个根」反查。

**禁止**：查不清时按「不共享」处理。

**产出**：两根的材质对照表与共享对清单。

**验证**：每对共享的材质都列出；查不清的按「共享」处理（改材质走副本），并在产出里标「未核」。

**升级给人**：共享关系会影响交付结构时（例如两个根都要交付，或要决定删哪个）。

## 面捕 BlendShare 大文件：工具跳过不等于没有

**职责**：确认体积很大的 BlendShare 数据被检查过，而不是被工具静默跳过。

**权威输入**：工程 `Assets` 下全部 `*.blendshape` 文件与名字含 `BlendShare` 的文件（`find <工程>/Assets -name '*.blendshape' -o -name '*BlendShare*'`）。

**决策边界**：指纹或审查工具可能跳过大文件。实测出现过一个 >30 MB 的 BlendShare 被指纹工具跳过、捏脸因此没被查到的情况。

**禁止**：拿工具的空结果当「没有」；工具跳过的是「没查」。

**产出**：全量清单；>30 MB 的单独列出。

**验证**：每个大文件都确认对应哪个根、哪张脸；确认不了的写进「未查」清单。

**升级给人**：大文件的对应关系无法从数据确认时，请人确认。

## 面捕参数位账：装之前先算同步参数与 PhysBone 余量

**职责**：面捕要加在已有很多开关的头像上时，先算预算，别到菜单或优化阶段才发现超限。

**权威输入**：现有同步参数占用与面捕新增的同步参数；现有 PhysBone 数与面捕根要挂的骨链。

**决策边界**：
- 同步参数上限 256 bit（Int、Float 各 8 bit，Bool 1 bit）。
- PhysBone 总数上限按流程阈值表（规程口径 256）。
- 两个数都写进参数位账，并用构建后的实测值对账。
- 余量 ≤ 0 时，只能裁功能，或上 VRCFury 的 UnlimitedParameters 这类方案。

**禁止**：超限时自行删控件。

**产出**：参数位账：现有＋新增＝总量，以及对上限的余量。

**验证**：实测总量 ≤ 上限。

**升级给人**：余量 ≤ 0 时，交用户决定裁什么。

## 面捕根与原生根：组件差异要逐条说出理由

**职责**：面捕根是交付根、而审查只跑它时，确认它与原生根的组件一致。

**权威输入**：两个根逐个预制体实例的 `PrefabUtility.GetRemovedComponents` 结果与组件类型清单；场景文本里的 `m_RemovedComponents:` 条目。

**决策边界**：克隆出来的面捕根可能和原生根不一样。出现过的情况：身体收缩用的 ShapeChanger 在面捕根上被预制体覆盖「删除」，而原生根上还在；合并后相关的身体键被 AAO 当成无人写入而删掉，弯肘时袖套穿模。数据上的特征是「写者清单里有这个键，读值却从不为非 0」。

**禁止**：放过说不出理由的删除。

**产出**：两根的组件差异清单，每条附理由。

**验证**：`m_RemovedComponents:` 非空的每一条都能说出理由。说不出理由的按「克隆或手滑」处理：还原后做键 0／100 的弯关节对照（停掉 Animator，手动转骨，只渲身体与该件）再定。

**升级给人**：还原会改变交付行为，或对照结果不确定时。
