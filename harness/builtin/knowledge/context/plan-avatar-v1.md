# 头像方案阶段上下文 v1

这是 Harness 为 `plan` 阶段编译并随能力包发布的上下文，不是让执行代理自行浏览的 SOP 索引。

## 本阶段职责

把用户的审美目标、已选择素材和素材清点结果收敛成唯一可执行方案。不要施工，不要打开 Unity，不要扩展用户没有提出的需求。

## 权威输入

1. Workflow 冻结的 Manifest：用户原话、共同脸部设定、衣装方案及每个方案关联的素材。
2. `_harness/intake/inventory.json`：Harness 实测的素材清单与兼容性结论。
3. `plan_inspect`：Runtime 清点生成、绑定 inventory 与原输入的预制体候选；分页给出精确路径，不返回全 Prefab YAML。
4. `_harness/intake/需求.md`：由 Harness 归一化但保留原意的需求。

发生冲突时，用户原话决定审美意图，实测清单决定技术可行性。不得用猜测填补缺失素材。

## Harness 收权边界

- 只使用 Manifest 已选择且清点为可用的素材；不得搜索素材库或网络补充商品。
- 不得自行改变素体、服装变体、默认造型或用户明确的审美选择。
- Manifest 已声明 `variants` 时，每项就是用户可感知的一套衣装方案；保持其稳定 id、名称、说明和素材归属，不得合并成一套或把插件派生根误当成衣装方案。
- 技术实现细节由确定性流程处理；方案只暴露仍需用户审美决定的缺口。
- 缺少关键输入时，在方案的 `notes` 中准确记录阻断，不得假装已经确认。
- 不读取知识目录中的其他文件；本上下文已经包含本阶段所需规则。

## 产出契约

设计由你完成，字段与类型以任务正文为准。把设计写成 `_harness/plan/draft.json`，调用 `plan_submit --draft _harness/plan/draft.json`；工具检查商品与候选路径归属并写 `_harness/plan/plan.yaml`（JSON 是可解析的 YAML 子集）。工具报错是具体输入反馈，修正后再提交；不能伪造通过说明。

骨架、运行时形态写者、补偿、材质槽和精确隐藏对象需要实际导入后的观察，交后续阶段完成。计划里保留设计目标与未测事项，不能把它们标为已验证；也不为了预先完成下游施工而读取全部素材 YAML、仓库源码或 Run 的权限内部文件。已经取得合法候选后应产出可审批方案。

### 每个登记素材都要有一条处置

清点每项必须**且仅有一条** `obligations`：`input` 原样引用登记路径，`role` 用清点给出的角色，不得改写。`action` 取 `use`／`exclude`／`defer`：`use` 承诺本次使用，须写 `target`，并把 `due_stage` 写成真正会核对产物的阶段（当前只有 `outfit`）；`exclude` 明确排除，`defer` 表示不承诺本次交付使用，两者都须写 `reason`。义务要与方案的其他声明一致——方案挂载的素材不能又被排除，标为 `unused` 的素材只能写 `exclude`。材质与插件包自己没有产物证据，`use` 的 `target` 要指向承载它的那条已 `use` 的素体或服装义务。

清点若把独立材质／贴图包识别为 `role: texture` 并给出 `dependency_refs`，须按方案实际选中的预制体（含组成员选用的变体）判断依赖：引用闭包命中的依赖只能 `use`，`target` 必须是实际选用该预制体的承载输入；不能保留承载服装却排除或延期必需依赖。只被未选候选引用的包可按既有非 `use` 义务处置。只有顶层 PSD／CLIP 等 `source_only` 分层源没有装配对象，按分层源记录并用 `unused`／`exclude` 处置，不要把它写成服装预制体或骨骼待比对实例。

**遗漏与沉默都不算处置。** 少写一条、或只声明装配成功的那几条，都会被工具拒绝。

`outfits[].activation` 缺省为 `exclusive`：一个轮盘只选一档，`default_outfit` 必须指向其中一档。衣服、袜、发型、道具需要共同穿戴时逐件写 `fixed`，仍须真实 prefab 与义务，不能只写 notes。fixed 全部激活且不进入轮盘；全 fixed 时省略默认档，可用 `menu.mode: preserve` 保留厂商菜单。preserve 加任何 exclusive 会在方案阶段被拒。独立衣装/发型与配饰开关用 plan/0.3 的 avatar_config（必需上下文），不能把两款应互斥的发型都标 fixed。

清点只列包内 prefab 路径和分层文件名，没有读 prefab 内部或 PSD 层表。`plan_inspect.items` 保留全部登记输入，并标明 missing／unselected／source_only／selected；源文件包不因未选中导入而消失。源文件名不能证明某个部件或层不存在。每条 deviation 的 `evidence` 引用可读清点、包内成员或探针文件的 `path`、`sha256`、逐字 `quote`；必须先读到相关内容再引用，不能把未探查写成不存在。工具核对引用字节，审批仍须核对推理与接受降级。

读到证据后调用 `plan_evidence --path _harness/intake/inventory.json --quote "逐字读数"`（也可指向已生成的结构化层表／对象探针 JSON），取得可直接写入 `evidence` 的引用。工具只读，不生成事实；普通方案文字不能作为探针证据。

## 菜单交互意图也是方案，不是施工补丁

- 每个 exclusive 组默认独立 Float 轮盘；Int 可选，0 为默认成员。不得用互不约束的 Bool 代替互斥组。
- 鞋、袜、外套等部件开关采用横向语义：一个“鞋”控件应管理所有衣装中对应的鞋，而不是每套衣装复制一个“鞋”开关。
- 精确对象归属需要 Unity 探查，留给 menu 阶段的 `design.json`；plan 只冻结轮盘交互和横向部件策略，不猜对象路径。
- 用户可见名称与稳定内部参数名不得混用。

## 完成条件

- 每个装配件都有稳定 id、短标签和精确预制体路径。
- 菜单意图明确到各独立组、默认和跨实例共享开关。
- 有 exclusive 时默认造型属于 exclusive 列表；全 fixed 时无默认档。
- 改色目标具体到可执行部位，候选数量处于任务约束范围。
- 装配预制体来自清点候选；分层目标可引用清点保留的 source_only 源包，须继续读取层表。不把技术不确定性伪装成审美决定。
