# 回归修复：装配类失败的定位与判据

写给执行 regression_pre 与 regression 阶段的 AI，用于穿出、鞋底、形态键不跟随这类装配失败。它补充回归修复上下文里的证据优先级与修复约束，不重复那些条目。每节独立成立。

## 穿出类失败：先定位状态、宿主与写者，再决定改哪一层

- **职责**：拿到「身体穿出衣物」的失败证据后，找到根因所在的那一层，而不是就地加一个收缩键。
- **定位顺序**：
  1. 失败出在哪个状态（参数组合）、哪件衣物、身体哪一段、穿出多深。只在部分状态失败时，对比通过与失败的状态差在哪个开关。
  2. 列全这段身体相关形态键的写者：衣物上的 MA Shape Changer（宿主路径、目标网格、键名、Set／Delete）＋ FX 里写 `blendShape.*` 的曲线（所在层、状态、转移条件）。两张表合起来才是完整写者集。
  3. 归类：
     - 覆盖这段的衣物开着，收缩键却没生效 → 宿主挂错（挂在别的件、整套根或已关闭的物体上），或被层权重、多写者先序覆盖；
     - 这段没有收缩键，且这套从未做过「需要／不需要」判定 → 补判定，按覆盖表决定挂在哪件；
     - 衣物跟不上身体的体型键 → 按「形态键不跟随」排查，不是收缩问题；
     - 脚部穿出 → 先查姿态键是否与鞋跟匹配，再考虑收缩。
- **修法边界**：修改对应的写者或宿主；只处理被稳定覆盖的区域。本流程里写者与宿主都在装配层（来自厂商预制件，由 Runtime 按方案重建），回归阶段改了也不持久：写明状态、宿主、写者与根因，交人（改方案或换预制件）。
- **禁止**：为消除读数在失败状态上叠加删除类键；把收缩键挂到整套根上图省事；删除或合并失败状态。
- **升级给人**：衣物本身太小、只能靠删身体才不穿出（如露脚款式），或需要常驻 Delete 时，报告取舍交用户。

## 鞋底与脚部失败：用覆盖表与四组合分辨成因

鞋类失败有四种成因（脚掌低于鞋底、脚趾穿出鞋腔、脚型或高跟键未跟随、袜与鞋的叠层冲突）。按现象分辨：

| 现象 | 优先怀疑 | 修法方向 |
|---|---|---|
| 穿这双鞋的所有状态都是脚掌低于鞋底或脚跟穿出 | 姿态键缺失，或档位与鞋跟高度不符 | 按跟高换姿态键档位；平底鞋不上姿态键 |
| 只在「鞋关袜开」失败，脚从袜子里顶出 | 姿态／收缩只挂在鞋上，而袜子按踮脚姿态建模或盖住了脚 | 袜那一档也写对应的键（挂到袜上） |
| 只在「鞋开袜关」失败，脚趾露出鞋外 | 收缩只挂在袜上 | 鞋上也挂盖住那几段的收缩键（值相同） |
| 腿或脚变成一根尖、拖丝 | 两个写者同时写了互斥的姿态键，或删除类键叠加过头 | 列全写者，同一状态只留一个姿态档 |
| 露趾、开口鞋上脚趾或脚背塌陷、空洞 | 删除类键用在了不全包的鞋上，或袜子的 Delete 碰上露趾鞋 | 换成姿态键；删除类只留给全包款 |
| 关掉鞋袜后脚上还有东西 | 鞋套一类的件被归到了别的开关组 | 按穿法重新归到鞋 |

- **本流程里**：表中各「修法方向」都要改装配层，回归阶段修不持久，写明哪一格、哪双鞋袜、怀疑哪类成因，交人。
- **每次修完都跑四组合**：全穿、只穿鞋、只穿袜、光脚；光脚必须所有脚部键为 0，且脚上没有残留物。
- **量之前**关掉内搭连体袜、丝袜，否则量不出鞋合不合脚。

## 修复穿出的成对判据：没穿出，也没有白缩

- **机制**：回归读的 `fit_pierced_vertices` 是**画面上成立的穿出**。探针先用射线找候选——每个状态下「被某件衣物顶穿」且「没有任何衣物盖住它」的身体顶点，按顶点去重（被外层盖住的内层穿出不算；同一件衣物自带内衬与外壳两层、身体夹在两层之间的不算；外层可开关的服装由状态集逐个状态量）——再把这些候选从一组固定视角（前、后、左、右、前上斜、后上斜；取景按骨骼高度，同定妆照规格）各渲两张**渲染器编号图**（替换材质输出渲染器编号，不用颜色比较）：一张全部可见、一张只关掉素体。候选投影到像素后，只有在至少一个视角里同时满足「全部可见时该像素最前面是素体**且深度就是这个顶点**」与「关掉素体后该像素最前面正好是它穿出的那件衣物」才计入。确认到的顶点再按**「衣物 × 部位」分组**：组内确认顶点达到噪声界（8，与衣物互穿同一个 `t.visible_interpenetration_min_vertices`）的组才计入 `fit_pierced_vertices`；不足界的组只作证据，记在 `fit_pierced_vertices_below_gate` 与观测 `details.fit_pierced_groups` 的逐组明细里（衣物、部位、确认数、机位、像素）。**判据仍是 `== 0`、仍阻断。**
- **为什么必须渲图**：射线看不见头发卡片这类非封闭表面，也说不出「同一像素里更靠前的是别的素体面」。FP1 在 A 上实测：射线口径留 41 个候选，逐视角投影核对后只有 4 个的像素确实以素体为最前面。所以「射线说穿出」只是候选，不是结论。
- **三类不计**：①该像素最前面是衣物（被盖住）；②素体在最前面但不是这个顶点（深度不符，容差写在读数里）——额头与刘海交界那种「本来就露皮肤」的点属于这一类；③关掉素体后该像素是背景或**别的**件（只露在背景前、或穿出的那件被另一件挡着）。
- **排查观测不参与判据**：`fit_pierced_vertices_ray` 是射线 + 遮挡口径（FP1 的读数）只作候选筛选；`fit_pierced_render_views` 是用了几个视角；`fit_pierced_render_states` 是完成了渲图确认的状态数；`details.fit_pierced_confirmed_garments` 是逐件确认数（每件同时给确认数与射线数）；`fit_pierced_vertices_below_gate` 与 `details.fit_pierced_groups` 是**不足噪声界的组**（衣物、部位、确认数、机位、像素，只作证据、不参与判据）；`fit_pierced_depth_tolerance_mm` 是这次用的深度容差（默认 2 mm，越大越松）。**数组类读数都在观测的独立 `details` 字段，不在 `metrics`**（`metrics` 只接受数值、真假值或 null，放数组会被 Runtime 判成 error）；素体取用的网格路径在 `details.fit_body_paths`（计数仍是标量 `fit_body_mesh_count`）。逐件原始穿出数在 `geo_state_*.json` 的 `garments[].total.pierced`、`visible_piercing.raw_vertices`／逐件 `raw_vertices` 里（旧口径就是逐件相加，读数会随多层面料与射线预算走）；`fit_pierced_vertices_raw`、`fit_depth_saturated_vertices`（深度顶到射线预算 15 mm 的可见顶点数）、`fit_pierced_no_data_vertices` 同理。**饱和数大**说明读数可能由射线长度决定而不是真实深度，用请求里的 `pierce_mm` 放长再量来区分，不要当真实穿出深度。
- **逐点复核**：证据在 `<Run>/fit/geo_state_*.json` 的 `visible_piercing.render` 块与 `<Run>/fit/render/` 的编号图/定妆图。块里 `renderers` 是编号图 1..N 对应的渲染器路径（解码编号图用），`confirmed` 每个候选一行：`codes` 逐视角给 `hit`（该视角确认）／`bg`（那里是背景）／`other`（最前面不是素体）／`deep`（素体在最前面但不是这个顶点）／`miss`（素体与深度都对，但关掉素体后露出的不是它穿出的那件）／`out`（不在画面内），`views` 是确认它的视角，`min_body_depth_delta_mm` 是它在素体占住像素的视角里离「就是这个顶点」最近差多少毫米。图里的绿框是确认过的候选、橙框是没确认的。定论前先看这三样，不要只看计数。
- **no_data 的方向**：区域映射失败（`scope=no_data`）的衣物在「是否被盖住」上不算盖住（没量到的衣服不能把穿出判成看不见），但它量到的命中照常算穿出（不能因为范围没量到就当 0），代价计在 `fit_pierced_no_data_vertices`。探针没跑完、状态不全、或**渲图确认没跑完**（`visible_piercing.render.valid=false`，含渲染器编号图着色器缺失、头像与请求的素体路径对不上）时 `fit_pierced_vertices` 是 `null`（no_data），不是 0，也不回退到射线口径；渲图块在 `valid=true` 时若缺逐点明细（`render.confirmed`），同样记 `null`——分不了组就不能当 0。
- **成对判据的动机仍在**：把身体顶点删掉或缩成一点，这个数就会降到 0——检测通过了，身体却缺了一块。像素方差、边缘数、「画面整洁度」同理，删掉被测物会让它们全部变好。
- **自检问句**：如果把被测物删掉，这个指标会不会变好？会，就不能单独当通过判据。
- **成对判据**：
  1. 没穿出：失败状态下穿出顶点数或面积为 0；
  2. 没有白缩：每个开着的收缩或删除类键，它影响的顶点在该状态下都有可见衣物盖着；
  3. 几何守恒（只用姿态键修脚部时）：脚部包围盒长度变化 < 5%，体积或有效顶点数没有减半。
- **对照组**：光脚（鞋袜全关）状态下所有脚部键为 0，两条判据都要过；过不了，说明判据坏了。
- **覆盖探针（`shrink_cover`）未标定时**只作线索，它的 `ok` 不能当通过；用定点渲图（有疑问的那一格，4 方位＋特写）交独立视觉复核确认，只给图、不给结论。
- **禁止**：只凭穿出数归零宣布修好。

## 同名形态键不跟随：先分机制，数值失配先量几何

- **先分机制**：
  1. 衣物有同名键但没人同步 → 每件加 MA BlendshapeSync（`ReferenceMesh` 指同一头像根下的身体），多个头像根各做一遍；
  2. 有 BlendshapeSync，但参照键在当前素体版本不存在 → 在实例上把参照键改指素体的对应键；
  3. 衣物本来没有这个键 → 在 Unity 里给原网格副本补帧，再加同步。
- **通道与量距**：机制 1（衣物有同名键、没人同步）**装配阶段已自动补**（`OutfitStage.SyncBodyShapeKeys`，`D-139` ②），补了什么在 `outfit.json` 的 `blendshape_sync` 里；剩下的机制 2、3（改指参照键、补帧）仍要改装配层，没有通道，写明哪件、哪个键、差多少交人。判据不是只看值差：规则是「值差 ≤ 5 **或** 同名键几何 p95 < 1 mm」，Runtime 会量 p95（`key_follow_geometry_p95_mm`），几何几乎不动时判据本来就通过——报告里给「无可见后果」的理由，而不是把它当成已经修好。
- **数值失配不等于看得出来**：报告里衣物键与身体键差了几十，衣物却可能落在该键几乎不动的区域。判「要修」之前，在编辑模式把身体与衣物各按失配的两个值 `BakeMesh`，比较衣物到身体最近距离的分位数；变化 < 1 mm 记「无可见后果」，不改交付件。例：某外套键值失配 38，但失配两值下衣物到身体的 p50 都约 5.8 mm。
- **修后读回**：驱动 0／默认／1 三档，衣物键值与身体逐值相同；多个头像根分别读。
- **禁止**：只改报告数字，或把衣物键手设为固定值。

## 缺写者的收缩键有没有可见后果：冻结 Animator 渲 0／100 对照

- **触发**：读数显示某个身体收缩键（如 `Shoulder_OFF`、`Upper_arm_OFF`）在「衣服穿着」时是 0，而厂商 clip 的本意是 100（例如厂商层权重为 0、写者缺失）。
- **做法**：
  1. 把头像摆到目标状态（衣服穿着），不要每步复位；挡在前面的外层先关掉（例如针织背心盖住肩部，就先关背心）。
  2. 关掉头像根 `Animator.enabled`（冻结，否则下一帧就被动画写回），手动 `SetBlendShapeWeight` 取 0 渲一组、取 100 再渲一组，相机参数完全相同。
  3. **正对照**：同样两组值、只渲身体（渲图工具的 `only_renderers` 一类参数），差异像素要明显（某例约 35,000 px／512²）。正对照不过，说明键没生效或相机没对准，后面的「0 像素」不能用。
  4. 穿衣两组逐像素比（阈值 24／255）。
  5. 做完恢复键值，并重新打开 Animator。
- **判据**：穿衣组差 0 或只有几十个散点 → 这个姿势下看不出来，记「待机无可见后果，动作中待查」，不急着修；差异成片 → 有可见后果，补写者（Shape Changer 挂在衣服上，或补 clip）。
- **取景**：看图前先看取景——隐藏头发、尾巴、挎包等遮挡物（`hide_renderers` 一类参数）（出现过后视图被头发整个挡住，差 0 毫无意义）；拼一张 2×2 小图先扫一眼再比。
- **复核**：结论交独立视觉复核；复核指出与被测键无关的问题（如缝线描边）时，用「0／100 两组是否逐像素相同」区分。

## 「关掉 X 之后 Y 还留着」：按真实顺序连续切换，不要每步复位

- **机制**：状态驱动工具若每一步都先复位到声明的默认状态，会把上一步留下的残留洗掉——「关掉袜子后脚踝还缩着」「脱了鞋脚还踮着」这类问题就测不出来。
- **做法**：检查残留时按用户真实会做的顺序连续切换（例如「全穿 → 关袜子」），关闭每步复位（状态请求里写 `"reset":"none"`；默认的 `declared` 会每步复位）。
- **适用**：收缩键宿主、姿态键归属、菜单串档类问题。
- **判据**：真实顺序下的结果与「从默认直接跳到目标状态」的结果一致；不一致即为残留或串档。

## 静态之外：袖口、裙摆、腋下与动骨要过动作

- **静态渲染只能证明 T-pose 下的装配**。袖口、裙摆、腋下这类穿模要在动作里（例如 Gesture Manager）才看得出来。
- **动骨（PhysBone）编辑期不模拟**，观感只能在 Play 里看；要看的动作：静止、低头、侧头、走路、原地转身。本流程的 Runtime 不跑动作与动骨（在 `coverage.json` 的 `not_ran` 里），写进报告的未测项。
- **只在某些档位复现的头发穿身体**：先查现成的身体碰撞体是不是挂在可开关的部件（尾巴、某套衣服的碰撞体组）下面——那个部件一关，碰撞体就失效。碰撞体要挂在永远激活的物体（主骨架的躯干骨）上。本流程里碰撞体挂点属于装配层，回归阶段改不持久，写明交人。
- **升级给人**：动态穿模需要在服装形状与动骨手感之间取舍时，报告交用户。
