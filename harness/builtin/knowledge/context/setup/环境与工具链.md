# 工程初始化：环境与工具链判据

本文件给初始化阶段：确认 Unity 与依赖版本、让工程编译通过、导入素材时保住 GUID，并在环境出问题时正确诊断与交回。每节独立成立。

## 工具链基线（成文时）：Unity 2022.3.22f1 与冻结的 VPM 版本

- **职责**：让工程的 Unity 版本与 VPM 依赖落在一套已知能协同工作的版本上，并在报告里写明每个包的实际版本、与基线的差异。
- **权威输入**：`ProjectSettings/ProjectVersion.txt`、`Packages/vpm-manifest.json` 的 `locked` 段、`Packages/manifest.json`，以及本节基线。上一个工程的依赖记录只说明「那一次用了什么」，不是依据。
- **成文时的基线**（成文时核对的版本，不是永久规定）：Unity 2022.3.22f1。VPM：VRChat SDK `com.vrchat.avatars` 3.10.4（`com.vrchat.base` 同版本，由解析器隐式带入）；`jp.lilxyzw.liltoon` 2.3.4；`nadena.dev.modular-avatar` 1.18.1；`nadena.dev.ndmf` 1.14.3；`com.anatawa12.avatar-optimizer` 1.9.16；`com.vrcfury.vrcfury` 1.1414.0；`vrchat.blackstartx.gesture-manager` 3.9.9（`3.9.9-pr6` 是预发布，不算更新）；`gogoloco` 1.8.6；`dev.vrlabs.av3manager` 2.1.2；`de.thryrallo.vrc.avatar-performance-tools` 1.3.7；`io.github.azukimochi.light-limit-changer` 2.12.3；`com.triturbo.face-blendshape-fix` 0.1.3；`world.anlabo.mdnailtool` 0.10.61；`com.vrchat.core.vpm-resolver` 0.1.29；隐式依赖 `jp.lilxyzw.avatar-utils` 2.1.2。
- **冻结**：一轮制作中途不升级任何包——工具链和素材同时变，出问题时无法归因。交付后 `locked` 段就是冻结；客户在 VCC 里不点更新就不会升，交付说明写明「工程已锁定版本，除非遇到问题不建议升级」。
- **验证**：`ProjectVersion.txt` 存在；`locked` 条目数等于 `Packages/` 下的 VPM 包目录数（上述全部装上时为 14 个点名包加 2 个隐式依赖，共 16 个目录）；依赖一律写成 VPM 版本号，`file:` 与 `git#master` 这类写法为 0（它们会让存档在别的机器上打不开）。
- **禁止**：为「用最新」而升级；自行降级；手改 `locked` 段绕过冲突。
- **升级**：工程已有版本与基线不同、且后续判断依赖插件行为时，写明差异，交人决定沿用还是对齐；工程不存在或 `ProjectVersion.txt` 缺失时停下，问清工程在哪。

## 项目可选 VPM 依赖：由清点登记，受管环境安装

- **适用**：素材包里没有 `.unitypackage`，只有指向 VPM 仓库的安装入口（VCC 安装链接，或只写仓库清单地址的短文本）。清点把这类商品判为「项目依赖」，并写 `_harness/intake/vpm-requirements.json`。
- **机制**：`environment` 阶段除了冻结配方里的固定包，还读这份登记，按仓库清单解析出**包身份、版本、下载地址与 zipSHA256**，与配方包同样方式装进基准工程的 `Packages/` 并写进 `vpm-manifest.json` 的 `dependencies` 与 `locked`；解析出的 pin 与请求一起写进环境锁。`setup` 从基准工程把已解析的 VPM 包目录复制进工程（`Packages/` 加包后需重启 Unity 才出 dll，本流程由 Runtime 的新进程完成），并把它记进导入报告与素材应用表，使交付头像对它的引用能追回登记商品。
- **判据**：`locked` 里有该包且版本与 pin 一致；`Packages/<包 id>/package.json` 的 name／version 与 pin 一致；它的 `vpmDependencies` 全部在 `locked` 里（传递闭包）；**每个依赖声明的版本范围都满足实装版本**——范围读不出或装不上就是环境问题，不能只查「这个 id 存在」；环境锁的 `vpmRequirements.requests` 与 `vpm-requirements.json` 一致；`vpmRequirements.packages` 的每一条都要与依赖锁、`Packages/<包 id>/package.json` 的身份／版本／依赖声明以及安装时记录的归档哈希逐条对上（缺项、映射错误或哈希对不上都算不一致，不是「以文件为准」）；登记项与 pin 按**（登记商品、仓库地址）**成对核对——每条登记都要有对应 pin，每条 pin 的仓库必须是 HTTPS 且出现在本单登记里（缺项、错配、明文仓库都算不一致；只看商品名不看仓库，会把别的来源当成这一单的依赖）。范围里的**每个 `||` 分支都要先解析完再判定**：前半段满足就返回，会把后面读不出的写法当成通过。任何一条不成立就是环境问题，不是「跳过这个包」。
- **复用同身份同版本时**：同样要核对归档哈希与实际内容来源（重新读归档并与实装目录逐字节比较）；同一身份、同一版本出现不同归档哈希时**硬失败**，不得登记一个没有下载兑现的 pin。核验通过后要把来源哈希**补记**进依赖锁——原锁缺摘要时不能只核验不记账，否则刚发布的环境会被自己的 `verify` 拒掉；同一个（登记商品、包身份、仓库）只登记一条 pin。**全部闭环核验都在发布基准与锁之前**对候选目录先跑一遍，被拒的输入因此不会留下一个没人能接受、也无法重试的环境。
- **包名先校验再落盘**：远端索引里的包名在被拼进任何路径之前就按身份校验；解包目录与安装目录都检查规范化后的目标严格位于对应目录内。入口解析阶段拒绝的包名，其后续不得发生任何解包或复制（不能先写出候选目录再在发布时拒绝）。
- **索引与归档的依赖声明要一致**：索引条目的 `vpmDependencies` 与归档 `package.json` 里的声明不一致时报错，不挑一个信。
- **仓库不可达或索引不合规**：索引必须 HTTPS；取不到、不是 JSON、没有 `packages` 列表、条目缺 HTTPS 地址或 `zipSHA256`、仓库含多个包而入口没有点名包身份——每一种都**直接报错并保留现场**，不静默降级成「没有这个依赖」。哈希是固定的前提，仓库不声明摘要就不能叫固定依赖。
- **setup 观测的待导入清单**：不只看 `.unitypackage`；`kind: vpm` 的选中件也要进待导入项。观测独立比对清点（inventory）、依赖登记、已接受的 pin、工程里的实际包目录与导入记录；缺导入记录计入未导入项，记录与其它四处对不上则算冲突。
- **禁止**：手改 `vpm-manifest.json` 的 `locked` 段或 `vpm-requirements.json` 绕过冲突；把仓库不可达当成「本单不需要这个插件」；在 `Assets/` 下解包 VPM 包冒充安装。
- **升级**：仓库要求的环境包不在冻结配方里（传递依赖缺失）时，停下，把包名、版本范围与缺失项交人决定加进基线还是换版本。

## 插件兼容的判据：从依赖范围读天花板，按事件复核

- **职责**：判断素材与插件能否在基线上共存；有冲突时给出可复核的依据。
- **权威输入**：各包在 `locked` 段里的 `dependencies`，厂商 `package.json` 的 `vpmDependencies` 与 README 声明。不按版本号新旧、包名或商品名推断。
- **成文时读到的天花板**：`com.anatawa12.avatar-optimizer` 要求 SDK `>=3.7.0 <3.11.0`；`dev.vrlabs.av3manager` 要求 `3.2 - 3.10`；`vrchat.blackstartx.gesture-manager` 要求 `>=3.10.4 < 3.11.X`。SDK 升到 3.11 会同时打断这三个，所以成文时「用最新 SDK」不是可选项。NDMF 侧：Modular Avatar 要 `>=1.14.3 <2.0.0-a`，Light Limit Changer 要 `^1.9.0`，Avatar Optimizer 要 `>=1.8.0 <2.0.0`；NDMF 在 1.x 内升级安全，但没有单独升它的理由。
- **何时重新核对（按事件，不按日历）**：①VRChat 更新迫使 SDK 升级（上传被拒是硬信号，不靠猜）；②某个包的缺陷卡住流程（NDMF 烘焙中止、MA 装配失效、AAO 优化出错）；③新素材声明更高版本；④一个工程交付后的空档（此时升级代价最低）。
- **成文时可升未升的候选**：MA 1.18.1→1.18.7、NDMF 1.14.3→1.14.8、AAO 1.9.16→1.9.18、VRCFury 1.1414.0→1.1426.0、Light Limit Changer 2.12.3→2.13.0；只作为下一次基线的候选，不在制作中途升。核对可升版本的方法：比对 VCC 设置目录下 `Repos/*.json` 缓存与工程 `locked` 段。
- **验证**：报告列出每个冲突的依赖范围原文及出处（哪个包、哪个字段）。
- **禁止**：放宽依赖范围、手改 `locked` 段或厂商 `package.json` 来消除冲突。
- **升级**：素材要求的版本超出现有天花板，或必须升级才能继续时，停下，把冲突的依赖范围与受影响的包列出，交人决定。

## UPM 侧依赖：散装进 Assets 的厂商包不会解析依赖

- **职责**：VPM 之外，核对 `Packages/manifest.json`（UPM）里必须存在的包。
- **机制**：厂商把一个 UPM 包作为 unitypackage 散装解进 `Assets/Packages/` 时，UPM 不读 `Assets/` 下任何 `package.json`，它声明的依赖永远不会自动解析；同一个包装在 `Packages/` 下时，依赖会被自动拉入。
- **成文时的实例**：`com.triturbo.blendshare` 1.0.3（随 Triturbo 面捕框架一起来）依赖 `com.autodesk.fbx` 4.2.1。散装后编译失败约 72 个错误，全是 `Autodesk.Fbx` 命名空间下的类型（`FbxManager`、`FbxScene`）找不到，报错本身看不出根因。另外，该包 `BlendShapeDataSOEditor.cs` 第 235 行在 `#if !ENABLE_FBX_SDK` 分支里缺一个分号；装上 FBX SDK 后这个分支不参与编译，平时不暴露。
- **判据**：编译由 Runtime 在你退出后的那次 Unity 步骤完成，看 Run 目录 `unity-*.log` 里的错误与 `Library/ScriptAssemblies/` 下的 dll；错误集中在某个外部命名空间时，先查散装包 `package.json` 的 `dependencies`。
- **修法**：缺的依赖要补进 `Packages/manifest.json`（如 `"com.autodesk.fbx": "4.2.1"`），不改厂商源码。本流程里执行方自己不加：`setup-project` 每次都用基准覆盖 `manifest.json`，加了也留不住，而 Runtime 的 Unity 步骤断网，基准之外的包未必解析得到。写明根因、包名与版本，交人把依赖加进基准工程后重建。厂商源码自身的语法缺陷同样交人授权：就地改会在下次解包时被计为内容冲突。
- **编辑器桥依赖**：本流程不用编辑器桥，不要往 `manifest.json` 加 `com.coplaydev.unity-mcp` 或任何 git／URL／`file:` 依赖：setup 阶段当场检查它们为 0，下一次 `setup-project` 也会删掉。git 依赖在客户没网或仓库改 tag 时还会让工程打不开。
- **禁止**：凭记忆改写包地址或子路径；把缺依赖造成的错误当成厂商代码缺陷去改源码。
- **升级**：缺的依赖需要联网获取而本阶段不能联网时，列出包名与版本交回。

## 编译成功的判据：看程序集 dll，不数日志

- **职责**：判断工程（含本阶段写入的编辑器脚本）是否真正编译通过。
- **判据**：自己的编辑器脚本编译成功 = `Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 存在且时间戳晚于源码；Console 按 error 级筛选，没有 `CS` 开头的错误。
- **交互编辑器里不数 `Editor.log` 的 `error CS`**：全新工程首轮编译失败、后续轮成功是常态，跨会话的旧日志里两轮错误混在一起，按日志判会连续误判。Harness 的 setup 验收不同：它只数 Runtime 这一次 Unity 步骤的日志（Run 目录的 `unity-*.log`），`error CS` 行数为 0 才算通过，出现即失败。
- **厂商自带 asmdef 的程序集另查**：它们编译失败时，`Assembly-CSharp-Editor.dll` 照样会是新的；要逐个确认该程序集自己的 dll 存在（首开或迁移验收：拿原来的 `*.csproj` 名单逐个对 `Library/ScriptAssemblies/*.dll`）。
- **Unity 是否在干活**：看 `Library/` 是否还在增长，不看进程是否存活。
- **Play 与域重载**：Play 模式期间不编译脚本，改了 `.cs` 不退出 Play 永远不生效；改 `.cs` → 编译 → 域重载，编辑器桥的连接会断，等 dll 时间戳晚于源码才算完成。
- **交互编辑器里编译失败会卡死**：弹出 `Enter Safe Mode?` 模态框，编辑器桥全部失联，只能由人点。改完编辑器脚本先离线预编译（用工程自己在 `Library/Bee/artifacts/*.dag/` 下的 `.rsp` 调 Unity 自带的编译器），通过后再调用 `AssetDatabase.Refresh` 或编辑器桥的刷新（如 `refresh_unity`）。已经弹出时：先修好文件、离线编译通过，再请人点 **Ignore**，不是 Enter Safe Mode。
- **禁止**：以「日志里没看到错误」或「进程还在」判编译成功。
- **升级**：dll 长时间不更新且不在 Play：可能停在 Safe Mode 对话框，交回人处理。

## 新工程首轮编译失败的三个已知成因

- **适用**：新建或重建的 VCC 头像工程批量导入第三方包之后；这时首轮编译几乎必然失败。
- **① 缺 SRP core**：有些工具用 `CommandBufferPool`（在 `com.unity.render-pipelines.core` 里），而 VCC 头像模板是内置管线、没有这个包 → 几十个 `CS0103` → 直接触发 Safe Mode。往 `Packages/manifest.json` 加 `"com.unity.render-pipelines.core": "14.0.11"` 即可；这不会切换渲染管线（切管线要在 Graphics 设置里指定管线资产）。
- **② `VRC_SDK_VRCSDK3` 死锁**：很多脚本把 `using VRC.SDK3.Avatars.Components;` 包在 `#if VRC_SDK_VRCSDK3` 里，而这个宏是 SDK 在首次成功编译后才写进 Player Settings 的：编译失败 → 宏未定义 → 更多脚本失败。手动往 `ProjectSettings/ProjectSettings.asset` 的 `scriptingDefineSymbols` 加 `Standalone: VRC_SDK_VRCSDK3` 打破死锁。
- **③ lilToon 2.x 的编辑器程序集是 `autoReferenced: false`**：`Assembly-CSharp-Editor` 看不到 `lilToonInspector`，按旧形态写的第三方 `CustomInspector.cs` 全部 `CS0246`。把该包 `*.asmdef` 的 `autoReferenced` 改成 true 可一次解决；但这是对 VPM 包的本地改动，重装会还原，VPM 包目录也不进版本库，所以必须写进本阶段报告与工程说明。
- **做法**（人工作业时）：错误属于这三类时按对应做法修，不需要找人；不属于时，按「编译成功的判据」逐个程序集定位，先查缺失依赖。
- **本流程里交人修基准**：`setup-project` 每次都用基准覆盖 `manifest.json` 与 `ProjectSettings/`，并逐文件还原基准里的 VPM 包目录，三种修法都留不住。这三类错误若出现，多半是基准工程本身的缺陷：写明属于哪一类、错误原文与所属程序集，交人修基准。
- **验证**：由 Runtime 的下一次 Unity 步骤编译验证：日志里 `error CS` 为 0，dll 已产出。
- **禁止**：改厂商源码或删除厂商脚本来消除编译错误。
- **升级**：同一错误修完仍复现，或错误来自无法判断归属的程序集时，交回并附错误原文与所属程序集。

## 加包与解包：重启 Unity，保住 GUID

- **加包后必须重启 Unity**：往 `Packages/` 加包之后，刷新资源与解析包都不够——`packages-lock.json` 会更新，但 `Library/ScriptAssemblies/` 里不会出现该包的 dll。判据看 dll 在不在，不看 lock 文件。本流程里 Runtime 在你退出后用新进程打开工程，等于重启，不必为此交人。
- **不开 Unity 解 `.unitypackage`**：它是 gzip tar，每个资源是 `<guid>/pathname`、`<guid>/asset`、`<guid>/asset.meta` 三项；两遍流式读（先收 pathname、再落盘）即可还原到 `Assets/`，原始 GUID 一字不动，还能精确排除条目。这比在 Unity 里拖文件夹安全：拖文件夹会改掉文件夹 `.meta` 的 GUID。包里没有文件夹条目时，文件夹 GUID 会由 Unity 新生成，用官方导入对话框也一样，这是包本身的问题。
- **导入串行**：同一商品的几个分包常共用文件夹与材质 GUID，并发导入会互相吞资产；清点与完整性判定可以并行，导入动作本身必须串行。
- **Linux 上建工程与装包**（人工作业时；本流程的执行方不用 vrc-get 或 ALCOM，VPM 包由 `setup-project` 从基准工程离线复制）：官方 VCC 没有 Linux 版，用 ALCOM（图形界面）或 vrc-get（命令行），两者共用 VCC 的设置目录 `~/.local/share/VRChatCreatorCompanion/`（`settings.json`、`Repos/` 社区源）；这里的 `Repos/` 只有源清单 JSON，没有包的 zip 缓存，所以从缓存离线解包装包这条路不通。按基线执行 `vrc-get install <包 id> <版本> -p <工程>`，再 `vrc-get resolve -p <工程>` 补齐 locked 依赖；工程要在 ALCOM 里可见，需写进 `settings.json` 的 `userProjects`。从现有工程复制骨架时只复制 `ProjectSettings/`、`Packages/manifest.json`、`Packages/vpm-manifest.json`，不复制 `Assets/` 与 `Library/`。纯命令行建工程的完整流程成文时未实测。
- **验证**：`locked` 条目数等于 `Packages/` 包目录数；新包的 dll 出现在 `Library/ScriptAssemblies/`；导入前后同一 GUID 只对应一个路径，原始 GUID 未被重生成。
- **禁止**：并发导入同一商品的分包；在 Unity 里拖文件夹导入。
- **升级**：导入需要人在对话框里确认时，交回。

## Unity 实例、锁文件与崩溃：不删活锁，不同开一个工程

- **职责**：Unity 由 Runtime 调度；执行方不在同一工程上另起编辑器。遇到锁、崩溃或连不上时，先诊断、再报告。
- **本流程里你能做的**：Unity 只由 Runtime 在你退出后启动，进程与锁也由它管（启动前判断进程，陈旧的锁它自己清）。Unity 步骤失败时，读 Run 目录的 `unity-*.log` 判断崩溃形状并报告 Runtime 给的退出原因；下面的进程、锁、退出操作只适用于自己开 Unity 的操作者。
- **锁文件**：`Temp/UnityLockfile` 存在，就是「有实例在用这个工程」的证据。锁对应的进程还活着就不许删；两个 Unity 同开一个工程会抢写 `Library/`，可能损坏缓存。
- **崩溃但进程还活着**：编辑器桥连不上时，先看进程状态（`ps -o stat,etime,%cpu,rss -p <pid>`）和 `Editor.log` 末尾；末尾是崩溃栈或 bug reporter，就判「崩溃未退出」，停下报告，不删锁、不另起实例。无人操作时自己崩的，先去 `Editor.log` 末尾认栈的形状（原生崩溃时日志先出现 `Got a SIGSEGV`，再是 `Exiting early due to double fault`；完整的调用栈在崩溃报告的 `External Debugger Dump` 段），不默认是上一次的原因。
- **被强杀的 Unity**：残留 `Temp/UnityLockfile` 与 `mono_crash.*.blob`（约 10 MB），下次打开同一工程会静默秒退，日志里只有 `Server::Kill`。操作者确认没有 Unity 进程后再清锁，编辑器桥的实例状态文件（如 `~/.unity-mcp/unity-mcp-status-<哈希>.json`）也删对应的那份，否则请求会被路由到死实例（报 instance not found）。Harness 执行方不碰锁，也写不了 `Temp/`。
- **崩溃后先看 git**：这类崩溃不损坏已保存的资产，`git status` 干净就说明盘上与提交一致；清 `Editor.log`（Linux 上在 `~/.config/unity3d/Editor.log`）前先另存崩溃日志，否则下次启动会覆盖，查不到栈。恢复检查先只报告（进程、日志尾、锁、编辑器桥状态、未提交改动），进程还在就停；确认后才清陈旧锁；恢复过程绝不自动保存场景、不 `checkout`。
- **退出交互编辑器**：用 `File/Exit`，返回「Could not connect」是已经退出。退出前先读 `scene.isDirty`：脏且不是本阶段要的改动，交人决定保存与否——保存框弹在桌面上时，编辑器桥全部超时、CPU 接近 0；卡住时可以截屏看（如 `xwd -root` 截取、`ffmpeg` 转成 png）。
- **找进程**：起 Unity 前先 `pgrep -x Unity` 加 `ps -o pid,lstart,args` 看有没有活着的实例；按进程名精确匹配，不要用 `pgrep -f`/`pkill -f` 按命令行匹配——会匹配到发出这条命令的 shell 自己，`pkill -f` 会把它杀掉（退出码 144）。
- **无害噪音**：Linux 编辑器每隔几分钟报一次的 `GLib-GIO-CRITICAL g_dbus_proxy_call_sync_internal` 不是故障线索。
- **禁止**：删活锁；在同一工程上另起 Unity；用 `kill` 代替正常退出（人已确认的除外）。
- **升级**：需要结束卡死的进程，或需要关闭别人正在使用的编辑器时，交回人。

## 编辑器桥（MCP for Unity）连不上：按阶梯判，不跳步

- **适用**：通过 MCP for Unity（`com.coplaydev.unity-mcp`，成文时 10.1.2，stdio 传输）驱动交互编辑器时。批处理模式下编辑器桥不启动，这个阶梯不适用。
- **阶梯**（每格都有下一步；走到「交回人」就停，不继续试）：①报 `No Unity Editor instances found`：先重试一次，重启或重编译后第一次调用报这个是正常的，重连要一拍。②重试仍失败：查 Unity 进程在不在；不在就按本流程的约定启动，起完回到第①格。③进程在但调用超时：读编辑器状态的 `play_mode.is_playing`，为 true 说明有人在 Play 里，Play 期间不编译，交回人退出 Play。④不在 Play 仍不通：查是否正在域重载或资源导入，是就等，以 dll 时间戳判完成；刷新调用超时但事后完成是常见的。⑤面板显示绿色的 `Configured`、却一个工具都没有：比对面板的 `Client Project Dir` 与本会话的启动目录，不一致要人改面板并重启会话——这是最容易误判成「桥坏了」的一种。⑥以上都排除：交回人，附上已排除的各项。
- **配置事实**：首次使用要在 `Window → MCP for Unity` 面板里把 `Transport` 选成 Stdio（默认 HTTP），选过一次就持久化；面板 Advanced 里的 `AutoStartOnLoad` 只对 HTTP 生效。Unity 每次启动都会按自己的传输模式重写客户端配置，Unity 侧的设置才是权威。
- **健康检查**：读 `mcpforunity://editor/state` 与 `manage_scene get_active`，应返回 `is_batch_mode=false`；服务端成文时为 `mcpforunityserver==10.1.2`。
- **写操作**：通过编辑器桥执行的代码（`execute_code`）只做短小、幂等的读数或设值——判据是「跑两遍结果一样、几秒内跑完」。调用超时（`Timeout receiving Unity response`）后同一段代码可能被再发几次：成文时一次生成调用 4 分钟里执行了 4 次，FX 控制器从 125 KB 涨到 38 MB。长的、非幂等的写操作改成工程内的编辑器菜单：读 `Library/…/request.json`、分帧执行、写 `status.json`，用 `execute_menu_item` 触发后立即返回，轮询状态文件等结果。已经超时时，先看日志里是否在重复同一操作（时间戳成簇），不再发第二个调用；确认是自己的生成物后停 Unity、`git checkout` 恢复生成物、删掉新增产物。
- **禁止**：手改客户端配置文件；点面板上「Transport Mismatch」黄字旁的 Configure（会重写客户端配置，可能冲掉本来能用的那条）；给服务加 `--offline`（缓存缺依赖时它失败关闭，工具静默消失）。
- **升级**：面板操作、重启会话、退出别人的 Play 都只能由人做；求助时说清判到了第几格。

## 本阶段交回人的操作：面板、重启、Play 与上传

- **适用**：初始化与环境处理中，遇到只能由人完成的操作。
- **清单**：①Unity 面板里的界面操作（如 MCP for Unity 面板选 Stdio、改 `Client Project Dir` 并 Configure）：面板是 Unity 内的 GUI，进程起来了也点不到。②客户端配置改完后重启代理会话：不重启不加载。③退出别人正在使用的 Play：Play 期间不编译，且人可能正在里面测试；为检查而自己进入的 Play 可以自己退出，结束后还原 Play 改掉的 ProjectSettings。④往 `Packages/` 加包后重启 Unity（本阶段无法自行重启时）。⑤VRChat SDK 上传与客户端实测：Linux 上没有 VRChat 客户端，Build & Test 不可用，要在客户端里看只能由人私密上传后查看。⑥编辑器卡在模态框（Safe Mode、是否保存场景）：编辑器桥全部失联，只能人点。
- **做法**：交回时一次说清卡在哪一步、已排除什么、请人具体点哪里填什么、需要什么回执；等待期间继续做不依赖 Unity 的工作。
- **禁止**：为绕过人工操作去改客户端配置、删锁或强杀进程。
- **升级**：本节清单里的操作本身就是升级条件；遇到清单外、同样只能在 GUI 里完成的操作，按同样方式交回。
