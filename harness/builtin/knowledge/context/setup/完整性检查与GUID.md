# 素材导入阶段：完整性检查与 GUID

导入后只读地查一遍，几分钟就能发现缺包、断链与撞号。每节可单独注入。

## 导入后完整性五查

- **职责**：导入完成后、交给装配之前，做五项只读检查。
- **权威输入**：工程文件系统、`.meta` 里的 GUID、清点清单。
- **决策边界**：只读检查；发现问题按对应修法处理，需要改厂商资产 GUID 时交人。
- **五查与判据**：

| 查什么 | 怎么查 | 合格 |
|---|---|---|
| 有没有没解开的包 | 在素材与工程目录里找 `*.zip`、`*.unitypackage` | 需要导入而未解开的为 0 |
| 有没有漏公共／材质包 | 文件名含 `material`／`shader`／`common`／`core`／`dlc` 的包是否都装了；日文命名的附加材质包人工再看一眼 | 缺失为 0 |
| 材质是不是父级缺失的变体 | 数 lilToon 材质文件的行数 | 完整材质 700 行以上；只有几十行的是父级缺失的变体 |
| 一 GUID 多路径（撞号） | 全工程穷举 `.meta` 的 GUID | 为 0，是硬判据，非 0 必须修 |
| 断链 GUID | 全部引用对照 GUID 索引 | 扣掉假阳性后为 0 |

- **索引范围**：GUID 索引必须同时含 `Assets/`、`Packages/`、`Library/PackageCache/`。有一次只扫了 `Assets/`，误报 3 个 GUID 解析不了，其中 2 个其实是 `com.vrchat.avatars` 与 GoGo Loco 里的组件脚本。
- **700 行的标定环境**：lilToon 2.3.4。换 lilToon 版本后先拿一个确定完整的材质重新标定。
- **禁止**：按包分组去查撞号（共享边界是厂商，不是商品）；把「控制台没报错」当成没有断链——撞号被 Unity 静默改号时日志什么都不报。
- **怎么验证**：五项各有读数；撞号与断链的读数来自全工程扫描。
- **产出**：五项读数与处置记录。
- **升级给人**：撞号或真断链修不掉、或修法需要改厂商资产的 GUID 时，写明路径与 GUID 交人。

## 断链 GUID：扣掉假阳性再判

- **职责**：把断链扫描的结果分成「真缺陷」「假阳性」「厂商本来就没发」三类，只修真缺陷。
- **权威输入**：全工程 GUID 索引（`Assets/`＋`Packages/`＋`Library/PackageCache/`）、引用扫描结果、源包清单。
- **决策边界**：只修真缺陷；厂商缺件不补造。
- **假阳性，不要修**：
  - 落在 lilToon 可选槽的引用：`_OutlineTex`、`_BumpMap`、`_EmissionBlendMask`、`_ReflectionColorTex`、`_GlitterColorTex`。对应的 `_UseXxx` 开关关着时，这些槽是惰性的。
  - `0000000000000000f000000000000000`：Unity 内置资源。
- **lilToon 的功能开关是 `_UseXxx`，不是 `_XxxBlend`**：`_MatCapBlend: 1` 但 `_UseMatCap: 0` 时，那一层根本不生效。判断一个槽「有没有在用」看 `_UseXxx`。
- **厂商本来就没发的**：分两种。**材质贴图**的证明是**引用的来源**——实际导入的那个归档成员本身就引用着同一个缺失 GUID（按 GUID 比，不按下标）；**渲染器槽位等其余引用**的证明仍是**文件字节与实际导入成员一致**：厂商的着色器包会在导入期迁移自己的材质，改掉大量字节却不增删任何引用，但它不改写预制体，所以预制体上的槽位缺件不要跟着放开字节证明。两种都要求该 GUID 在所有已登记输入、素材池归档、工程 `Packages/` 与 `Library/PackageCache/` 都找不到；setup 不因该发现阻断，但必须列出文件、渲染器、槽位和 GUID。`Assets/_Harness/` 下生成的材质一律仍阻断；登记原件里没有该 GUID 的引用是导入之后才出现的，也仍阻断。
- **原文件证明**：以实际 setup 导入回执中的归档摘要、选用成员、资产 GUID 与内容摘要为准；不能用其他已登记但未导入的包作字节证明。旧回执缺少这些证明时不作豁免，应重跑 setup 实际导入生成证明。按 GUID 比对，不按数组下标——导入期迁移会挪动下标。
- **只在同商品旧版本里找得到的**：不要直接把旧版本文件塞回来。更可能是厂商在新版重构或改名了，留下一条没清干净的旧引用；硬补旧文件可能重新触发同商品分包共用 GUID 的问题。先确认新版是否已有等效功能。
- **本流程的检查口径**：`guid_refs_resolved` 搜索已登记输入、素材池所有归档、工程 `Packages/` 与 `Library/PackageCache/`。任何已拥有归档能提供缺失 GUID 都算「漏装」，包括未登记包；观察说明指出应登记的包。只有「材质原件即引用」或「文件字节未改」、且所有已拥有来源都完全找不到的引用才是厂商缺件。setup 只在自身观察输出记录分类，不写跨阶段清单。
- **禁止**：为了让计数归零去补假阳性；把缺件问题留到交付前才发现。
- **怎么验证**：每条断链都有归类；检查计数（假阳性已由观测扣除）为 0，过不了的写明后交人。
- **产出**：断链分类表（真缺陷、假阳性、厂商缺件、旧版本遗留）与处置。
- **升级给人**：Unity 装配自行遍历素体、衣装与嵌套实例的有效序列化材质槽。真实缺件只有位于子网格之外、且处于可安全删除的连续尾部时才在 Harness 实例上移除；显式 null 不作缺件推断。自身子网格槽或被有效叠加槽隔开的缺件须停下，请订单方决定替换成哪个已有材质或接受缺失。回执与交付说明只列实际删除的槽及前后数量。独立 Observe 重新加载持久化头像，检查实际生效的材质槽和其他有效依赖，正式判据要求零阻断断链。Unity 序列化里「对象为空、实例 ID 为 0、且来源文本定位不到该属性」的字段是默认空值（Unity 省略默认字段，FBX 导入的对象没有文本可读），不是断链：它们单独计数为 `unlocated_null_refs`，并按「对象类型＋属性路径（下标归一）」分组写进观察 notes，不阻断；定位到的指针解析不到对象、或实例 ID 非 0 而对象为空，仍然阻断。材质 m_SavedProperties.m_TexEnvs 下的贴图引用若实际导入的登记原件本身就引用着同一 GUID、且所有已拥有来源均无提供者，setup 与装配后的 Unity Observe 只记录缺件提醒，并写入交付说明（缺失贴图使用着色器默认贴图；m_Shader 或其他对象引用缺失仍阻断）；渲染器槽位不适用这项提醒豁免。`Assets/_Harness/` 下生成的材质引用仍阻断；登记原件里没有该 GUID 的（导入之后才出现的悬空引用）也仍阻断。Unity 从实际材质引用发起只读来源核对，不接收 setup 缺件清单。

## 一 GUID 多路径：原因与修法

- **职责**：保证全工程没有一个 GUID 对应两个路径；出现了就按原 GUID 修，不重新发号。
- **权威输入**：全工程 `.meta`；源 `.unitypackage` 的 `<guid>/pathname` 条目。
- **决策边界**：只按厂商原始 GUID 修；两份内容不同时交人。
- **机制**：Unity 不允许一个 GUID 对应两个路径。真出现时，它在打开工程时会**静默给其中几个（有时是两侧）重新发号**，引用它们的预制体当场断链、渲染成洋红，日志里什么都不报。
- **已知的两种撞法**：
  - **厂商升版挪了文件位置却保留 GUID**：同一厂商的公共素材目录里，商品 A 的旧版在旧路径、商品 B 的新版把同一文件挪进了子目录，两者 GUID 相同，两个发型预制体因此断链。
  - **配饰包自带 lilToon 兜底副本**：包里带着 `lts.shader` 等文件，GUID 与 `Packages/jp.lilxyzw.liltoon` 相同，落到 `Assets/` 下后会波及**全工程所有 lilToon 材质**。
- **两种都逃过了逐包的冲突计数**：那种计数只查「同路径不同 GUID」。共用资产的边界是厂商，不是商品，甚至跨越 `Assets/` 与 `Packages/`，所以判据必须全工程穷举。
- **修法**：去源 `.unitypackage`（tar.gz，条目为 `<guid>/pathname`）取回厂商原始 GUID，原地改 `.meta`，并删掉重复的那一份。lilToon 兜底副本的情形，直接删掉那几个文件（连 `.meta`）和随之新建的空目录，再逐个确认材质仍指向包里的着色器。
- **禁止**：删了重建——会再换一次号。
- **怎么验证**：由 Runtime 在你退出后的那次 Unity 步骤验证（执行方不开 Unity）：GUID 没有被再次改写、旧路径没有被重建、受影响预制体的未解析引用为 0。
- **说明**：本流程的解包工具遇到「GUID 已在别处存在」时不再写入，能挡住这两种情形；但检查仍要对全工程做，因为后续补装和手工操作都可能引入撞号。
- **产出**：修复记录（哪个 GUID、保留哪条路径、删了哪份）与复验读数。
- **升级给人**：需要在两份内容不同的同 GUID 资产之间取舍时，交人决定。

## 材质变体缺父级：按行数识别、按原 GUID 修

- **职责**：找出父级缺失的材质变体，恢复完整设定，且不改变它的 GUID。
- **权威输入**：材质文件（行数、变体链）与素体的同类材质。
- **决策边界**：只恢复完整设定、保留作者的覆盖值，不换 GUID。
- **症状**：厂商打包时漏发了父材质，变体只序列化了寥寥几条属性（有一例只有 8 条）；其余约 700 行 lilToon 设定全部回落到着色器出厂默认值。渲染带一层不该有的色差，例如 `_ShadowColor` 变成 lilToon 默认的 (0.820, 0.760, 0.850)，而不是素体调好的 (0.980, 0.920, 0.875)。
- **识别**：完整的 lilToon 材质有 700 行以上；只有几十行的就是断链变体，差一个数量级，很好认。同一个包里可能一个材质完整、另一个是断链变体，打包方式不一致。
- **修法**（人工作业时）：就地断开变体链 → 用 `CopyPropertiesFromMaterial` 从素体的同类材质取完整设定 → 再盖回作者真正有意义的那几条覆盖值。
- **本流程里修不持久，停下交人**：就地改厂商解出的材质，下一次 `setup-project` 会把它计为内容冲突；复制到别处修，又没有下游会引用它（装配与改色都从厂商原件重建）。写明材质路径、行数与可参照的同类材质，交人。
- **禁止**：换 GUID 或删了重建。渲染器按 GUID 引用材质，换号会让已有引用断链。
- **标定环境**：行数阈值在 lilToon 2.3.4 上得出，只在一个工程的一个材质包上遇到过；换版本先重新标定。
- **怎么验证**（人工作业时）：修后行数回到完整材质的量级；对比修前修后的渲染，色差消失。
- **产出**：修复前后的行数与渲染对比。
- **升级给人**：找不到可参照的同类材质、或看不出作者本意改了哪几条时，交人决定。
