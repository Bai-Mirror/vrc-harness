# 素材导入阶段：解包导入与包落位

素材以原始 GUID 进工程，每个包落在它该在的位置。每节可单独注入。

## 解包导入：保 GUID 解包，不拖文件夹、不走导入对话框

- **职责**：素材一律用保 GUID 的解包工具直接解 `.unitypackage`（`setup-project` 已这样做）。本流程不手工补装：导入记录（`import.json`、`imported.txt`）只来自选中的 zip、每次重写，补装的内容不在其中，打包时该商品还可能被判「没用到」。需要补装时写明文件名与原因后交人，由人调整 Manifest 的分包指定，让工具去装。
- **权威输入**：清点结果中选中的包、源 `.unitypackage`。
- **决策边界**：只导入选中的包，不增删素材。注意检查的对照范围比这大：断链检查把商品目录里任何一个包（含旧版本、其他素体分包、未选中的包）能提供的 GUID 都算作可补；公共包检查对目录里所有文件名像公共／材质包的 zip 都生效。这两类缺口本阶段过不了检查，写明后交人。
- **禁止**：把解出的文件夹拖进 `Assets/`；用 Unity 的导入对话框导包；并发导入多个包。
- **为什么不拖文件夹**：`.meta` 没跟着时，Unity 会给文件夹和资产**重新生成 GUID**。有的插件用硬编码的 `AssetDatabase.GUIDToAssetPath("<guid>")` 定位自己的目录，GUID 一变就解析失败 → `Instantiate(null)` → 构建时弹模态框中断。症状极具迷惑性：Console 不报缺资源，报错点在插件自己的代码里，看起来像插件 bug。
- **为什么必须串行**：同一商品的几个分包会共用文件夹、材质的 GUID。用 Unity 导入第二个包时，它会搬走第一个包的文件，并静默丢掉同路径资产。
- **解包工具的行为**：内容相同的重复项跳过；同一路径已有不同 GUID 的文件时保留旧的、报告冲突，让人判；排除 `.exe`、`.bat`、`.cmd`、`.ps1`。
- **怎么验证**：冲突项为 0（检查数的是最近一次工具写进 `import.json` 的冲突计数，处置记录不算）；素材目录里剩余未解开的 `.zip`／`.unitypackage` 为 0（用 `find` 数一遍）。
- **产出**：导入报告（每包的写入、跳过、冲突）。
- **升级给人**：出现内容不同的同路径冲突时，交人判断保留哪一份，不要自己选一个覆盖，也不要手改 `import.json`；本阶段会停在检查不通过，等人处理。

## 导入报告怎么读：冲突、共享 GUID 与未装条目

- **职责**：逐包读 `_harness/setup/import.json`，给每个非零项一个处置。
- **权威输入**：`_harness/setup/import.json`、源包的条目清单。
- **决策边界**：只处置，不重选包；内容取舍交人。
- **字段含义**：
  - `entries`：包里的资产条目数；`installed`：GUID 已落在包内指定路径的条目数；`wrote`：本次实际写入的文件数。
  - `shared_elsewhere`：包里有、但该 GUID 事先已存在于**另一路径**的条目数。工具不再写入，包内引用会解析到已有那份。常见来源：同厂商跨商品共用的公共素材；配饰包自带的 lilToon 兜底副本（GUID 与 `Packages/jp.lilxyzw.liltoon` 相同）。一般无害，但厂商升版时可能挪了位置、改了内容而保留 GUID，此时工程里用的是先装那份的内容。
  - `content_conflicts`（冲突计数）与 `guid_conflicts`（冲突明细：路径、保留的 `kept`、没写入的 `incoming`）：同一路径上已有别的 GUID 的文件，工具保留旧的，新的没写入。新包里引用 `incoming` 的预制体会断链。
  - `not_installed`：既没装上、也不算共享的条目（最多列 50 条），多半与上一项有关。
  - `error`：选中的文件在素材库里找不到。
  - `roots`：包落进 `Assets/` 下的顶层目录，会记进本阶段产物的成员清单。
- **禁止**：只看工具末行的「解包 N 个」就当完成；删掉冲突的一方后重新生成 GUID。
- **怎么验证**：每个包 `installed + shared_elsewhere` 与 `entries` 的差额都能解释；`shared_elsewhere` 的条目能说出共用的是哪一份、内容是否一致；冲突与缺失都有处置记录（记录用于说明，不改变冲突检查的计数：计数只看最近一次工具写进 `import.json` 的冲突）。
- **产出**：每个非零项的处置记录。
- **升级给人**：`guid_conflicts` 非空、`error` 非空、`shared_elsewhere` 里有明显内容不同的新版资产时，写明包名、路径与两个 GUID，交人决定。

## 清点结果里「不可导入」的文件要逐个过目

- **职责**：清点工具把包里没有 `.unitypackage` 的文件记为「不是可导入的包」，你要逐个确认这个判断对不对。
- **权威输入**：`建档.md` 的「不装的文件」清单、压缩包内容列表（如 `unzip -l`）。
- **决策边界**：只核对；确属必装的内容写明文件名交人，不手工补装（见上一节）；源稿不导入。
- **判对的情形（不导入）**：PSD／PNG 美术源稿包（有的包附带几百 MB 的分层 PSD）；说明文档、商品图；与本素体无关的附件。
- **会误判、可能漏掉必装内容的情形**：
  - **嵌套压缩包**：`X.zip` 里套 `X_12_Avatars.zip`，再套 `.unitypackage`，要往下挖两层。
  - **`.rar` 包**：有的包只有 `.rar`；部分解压工具会报「Unsupported Method」解不开。
  - **VPM 包 zip**：功能插件常以带 `package.json` 的 zip 发布，里面没有 `.unitypackage`，但必须作为包装进 `Packages/`；本流程做不到（见「功能插件的 VPM 包必须落在 Packages/」），写明后交人。
- **怎么验证（判据）**：「不装的文件」清单里每一条的理由你都认可；需要的内容没有留在未解开的压缩包里。有过这样的事故：贴图被手工拖进工程，关键材质（带自发光、MatCap、Alpha 遮罩）却还留在没解开的 `.unitypackage` 里，只换贴图槽拿不到这些效果。
- **禁止**：把美术源稿导入工程；因为工具判了「不可导入」就不再看。
- **产出**：逐条确认结果；需要补装的写明文件名与原因（交人）。
- **升级给人**：必装内容只存在于解不开的格式里，或需要从嵌套包里取但清点结果没选中时，写明文件名交人。

## 功能插件的 VPM 包必须落在 Packages/

- **职责**：带 `package.json` 的厂商插件 zip 要作为包安装在工程根的 `Packages/` 下，不能解进 `Assets/`。
- **当前工具边界**：`setup-project` 仍不直接安装任意厂商插件 zip；正常的受管内嵌 UPM 包允许存在，`vpm_locked_match` 按已接受环境与实际解析锁逐项验证，不要求 VPM 数量等于所有包目录数。不要自行搬包、手改 `locked` 或退而解进 `Assets/`；记录插件来源、zip 与消费方，为受管环境修订提供依据。当前执行无法受管换版时保留阻断证据，不能通过修改提示词宣称插件安装已完成。下面的机制与判据用于识别这类问题。
- **权威输入**：插件 zip 里的 `package.json`、依赖它的 asmdef 的 `versionDefines`、编译产物。
- **决策边界**（人工作业时）：只搬迁与验证；不改插件源码，不加宏。
- **机制**：解进 `Assets/` 的包只是一堆源码，Unity 的包管理器不认识它。于是：① 依赖它的插件在 asmdef 里写的 `versionDefines` 永远匹配不上，插件编译进 `#else` 分支；② 它自己 `package.json` 里声明的依赖永远不会被解析（UPM 不读 `Assets/` 下任何 `package.json`）。
- **症状（不报错）**：asmdef 的 `references`（按 GUID）照样解析，编译零错误，控制台干干净净，唯一的表现是一句「框架未检测到，请导入」之类的提示，而框架就在盘上、几百个资产一个不少。读起来像「你没装」，第一反应去重装，方向就错了。依赖没解析的一侧，则表现为几十个「某某类型找不到」的编译错误。
- **反过来也成立**：`versionDefines` 的 `name` 只认包管理器注册的包（`Packages/` 下的内嵌包、VPM 包、注册表包），不认 `Assets/` 里的任何目录。判据是「包管理器里有没有它」，不是「文件在不在」。
- **怎么验证（判据）（成对给出）**：
  1. 看编译产物：`Library/ScriptAssemblies/<插件>.dll` 里，`#if` 分支独有的类型名必须命中，`#else` 分支独有的符号必须不命中（一例里前者是基类 `FaceTrackingInstaller`，后者是字段 `addonConfig`）。只查前者会被两个分支都引用的通用符号骗到（例如 `EditorWindow` 两边都有）。`.csproj` 不算数，它只在脚本变动时重新生成，包位置变了它不动。
  2. 搬迁不能断引用：搬之前把「消费方指向包内的 GUID 集合」存成基线，搬完比对完全一致。连 `.meta` 一起搬就不会变。
  3. 包顶层目录搬进 `Packages/` 后，删掉它自己的 `.meta`（包根不需要）。
- **做法**（人工作业时）：关掉 Unity 再搬。`Packages/` 下的内嵌包只在启动时扫描，开着 Unity 搬完不重启，define 不会生效，会得出「搬了没用」的错误结论。代价是一次全量重导入（一例 472 个资产、约 3 分钟）。
- **禁止**：手工加 Scripting Define Symbols 代替搬迁。那样 define 与包是否存在脱钩，包一旦被移除或换版本，插件会编译失败，或者编译通过但行为不对。
- **产出**：搬迁前后的 GUID 集合比对与编译产物读数。
- **升级给人**：插件需要的依赖不在基准工具链里时，写明依赖名与版本，交人授权。
