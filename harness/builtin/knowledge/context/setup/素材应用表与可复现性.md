# 素材导入阶段：素材应用表与依赖可复现性

每件素材的去向要记清，工程换一台机器也要打得开。每节可单独注入。

## 素材应用表：行数、用途与三类不用原因

- **职责**：维护素材应用表，让每个商品都有「用途」或「不用的原因」。`setup-project` 会写出初稿 `_harness/setup/usage.md`（商品、角色、导入的包、已装条目数、用途）。
- **权威输入**：`usage.md` 初稿、清点清单、方案、需求原话。
- **决策边界**：只填用途与原因，不改导入结果。
- **怎么验证（判据）**：表的行数＝清点清单里的商品数（Runtime 会独立检查：`usage.md` 里所有以 `|` 开头的行减去表头两行）。所以这个文件里只放这一张表，不加第二张表或别的 `|` 行；加列时每一格都要填，交付检查不允许空格子。初稿里的「用途」只是按角色填的占位，每一行都要落到具体用途或原因。
- **合格的不用原因只有三类**：① 不支持这个素体（列出包里有哪些素体版）；② 与已装的东西功能重叠（点名是哪一件）；③ 客户明确不要。写不出原因，就是漏了。本流程以方案里已批准的 `unused`（`unsupported`／`overlap`／`client_declined`）为准，表里照抄；方案没列进 `unused`、又用不上的件，打包时会被 `package_usage_refs_closed` 阻断，只在表里写原因不能豁免，要写明后交人重做方案。
- **区分「未导入」与「导入了但 0 引用」**：「未导入」可能是包本身缺文件（有的商品目录里只有商品图，没有本体）；「导入了但 0 引用」才是真漏用。
- **0 引用不等于漏用**：写「导入了没用上」之前，先查已有的方案文档。例如某个挑染包在配色方案里被明确排除，它的 0 引用是有意的。
- **查「素材里有没有 X」要连压缩包清单一起查**（例如 `unzip -l`）：解出的目录可能不全；聊天截图、需求表这类东西常常根本没进素材包。
- **重新生成会冲掉手写栏**：`setup-project` 每次运行都整张重写 `usage.md`，用途栏回到按角色的占位。手填放在本 Run 最后一次调用工具之后；再调工具就要按商品号重填。
- **为什么要有这张表**：素材包动辄二十几个商品，做到一半记不住哪个上了、哪个没上、哪个是故意没上。交付前才回头数，就会出现「客户买了但压根没用」。
- **禁止**：用「待定」「以后再说」当原因；在表的判据没过反查之前拿它做决定（挑一件确定用了的，数必须大于 0；挑一件确定没用的，数必须等于 0）。
- **产出**：每一行都有用途或三类原因之一的应用表。
- **升级给人**：一件素材既不能用、又不属于三类原因中的任何一类时，交人确认。

## 统计类结论出数前先做已知答案反查

- **职责**：凡是「覆盖率、使用率、完整性、断链数、参数预算、性能数」这类数出来的结论，交出之前先证明判据本身是对的。
- **权威输入**：统计脚本的输出；已知「确定用了」「确定没用」的样本。
- **决策边界**：先证判据，再出数。
- **为什么**：错误的判据跑出来的数看着都合理，一个都不报错。
- **三个已经踩过的判据坑**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 按目录名猜商品对应 | 全错：解出来的目录名常与商品名毫无关系（例如一款心形戒指解出来叫 `HINO shop`，一款妆容眼睛贴图叫 `cumulus`） | 用 `.unitypackage` 里的原始 GUID 与工程 `.meta` 取交集 |
| 用扩展名判断条目是不是文件 | `.prefab` 被当成目录漏掉，而预制体正是场景引用的主体，「引用」列大面积假 0 | 目录＝它是另一个条目的父路径。包里目录和文件同列，这个判据是确定的 |
| 可达性从所有场景（`Assets/**/*.unity`）出发 | 厂商演示场景、生成器场景把整包资产都标成「用上了」 | 只从自己的工作场景出发 |

- **已知答案反查（出数前必做）**：挑一个**确定用了**的素材，它的数必须大于 0；挑一个**确定没用**的素材，它的数必须等于 0。两头都对上，表才能拿去做决定。有过的反例：某插件明明挂在头像上却显示 0；某配饰刚导入、没装到头像上，却显示 56。
- **工具化与查证分开做**：先用最粗的方式拿到答案，工具化是下一件事；两件事缠在一起，每次判据修正都要重跑全量。补丁脚本的内容先写成文件再执行，不要用 shell heredoc 传含 `\n` 或反引号的代码。
- **禁止**：反查没做就出数；两头有一头对不上还继续填表。
- **产出**：反查读数＋统计结果。
- **怎么验证**：反查两头都对上（用了的大于 0，没用的等于 0）。
- **升级给人**：反查不过、又找不到判据错在哪时，交出反查读数，不交统计结果。

## 依赖可复现性：file:、git 引用与孤儿包

- **职责**：保证 `Packages/manifest.json` 里的依赖在另一台机器上能原样解析。
- **权威输入**：`Packages/manifest.json`、锁文件、`Library/PackageManager/ProjectCache`、`Packages/` 目录。
- **决策边界**：只核对与报告，不引入新依赖。本流程里三份包清单每次都被 `setup-project` 用基准覆盖，转写或登记都留不住。
- **不可复现的写法**：

| 写法 | 含义 | 为什么不行 |
|---|---|---|
| `file:` | 指向工作区外的目录 | 换机器或移动目录就打不开（Unity 直接以返回码 1 退出） |
| `git#<分支>` | 直接引分支 | 能打开只是因为 `Library/PackageCache/` 里有当年的副本，删掉 Library 就变了 |
| `.git?path=…#<分支>` | 子目录引 git | 同上，且更隐蔽，历史核查漏过 |
| `http(s)://` | URL 来源 | 离线或源变动即失效 |

- **现状**：`setup-project` 会从基准工程的依赖里删掉这类条目；后续补装的厂商包或手工操作仍可能引入。setup 阶段当场检查命中数为 0（`dependency_reproducible`），所以任何阶段都不要往 `manifest.json` 加 git、URL 或 `file:` 依赖，包括编辑器桥 `com.coplaydev.unity-mcp`。
- **查当年真正用的版本**：读 `Library/PackageManager/ProjectCache`（文本）。该文件里 `version:` 字段在 `name:` **之前**，往后找会取到相邻条目的值。`source:` 枚举：1＝Registry、2＝Builtin、3＝Embedded、4＝Local、5＝LocalTarball、6＝Git。
- **孤儿包**：目录在 `Packages/` 下，却既没有受管 VPM 来源，也没有 UPM 声明或传递依赖与解析锁来源。今天能编译不证明可恢复。Runtime 按已接受环境逐包核对身份、版本、内容和依赖闭包；正常内嵌 UPM 包允许与 VPM 并存，不按目录数量判断。不要搬进 `Assets/` 或为凑数量手改 `locked`；确需增加依赖时，记录来源与需求，走受管环境修订后重新独立验收，当前执行没有环境换版入口时保留阻断证据。
- **禁止**：保留分支或本地路径依赖「先用着」。
- **产出**：依赖清单（每条的来源与版本）与孤儿包登记。
- **怎么验证**：`manifest.json` 内 `file:`、git、URL 依赖命中数为 0；Runtime 独立验证 VPM 与 UPM 的完整声明、解析锁、实装身份、版本和冻结内容，未知来源或孤儿依赖不得通过。UPM 锁内受管内嵌包的 `file:<包名>` 不等同于 manifest 中指向工作区外的本地依赖。
- **升级给人**：转不成 VPM 版本号的依赖，在导入报告里点名，交人决定归档时怎么处理。

## 厂商包升级与付费原包：先登记、再请示

- **职责**：弄清每个包从哪来、是什么版本、升级会不会冲掉生成物；有付费件时提前做许可决定。
- **权威输入**：各包的版本、下载时间、升级注意；应用表里的生成物登记。
- **决策边界**：本阶段不升级。
- **每个包记三项**：版本、下载时间、升级注意。写在 `_harness/setup/` 下另一个文件里，不写进 `usage.md`：那张表的行数必须等于商品数。
- **升级厂商包之前**：先把当前包移走，或登记好，因为升级会覆盖同名路径。头像工具按头像生成的目录各异（见过 `#GENERATED/`、`Backup/` 两种命名），都要登记（同样写在另一个文件里，不用 `|` 开头的表格行写进 `usage.md`），否则升级后分不清哪些是生成物、哪些是原件。
- **付费原包升级是一个许可决定，不是顺手升**：厂商原件（Booth 付费 zip、Patreon 发布的着色器等）不进交付。要随交付附上、要升级，都要用户点头，并写进交付说明。
- **本阶段的边界**：不升级任何包。看起来需要升级时停下，写明原因。
- **禁止**：把厂商原件打进交付包；未登记生成物就覆盖升级。
- **怎么验证**：登记文件里每个包都有版本与来源；生成物目录都已登记；`usage.md` 的表格行数仍等于商品数。
- **产出**：每个包的三项记录与生成物登记（`usage.md` 之外的文件）。
- **升级给人**：任何升级、任何付费原件随交付的需求。
