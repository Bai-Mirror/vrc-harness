# 素材导入阶段：工具链与工程初始化

把素材包变成一个能打开、能编译、GUID 没被动过的 Unity 工程。本文件讲初始化与工具链。每节可单独注入。

## 工程初始化：setup-project 做了什么、你还要核什么

- **职责**：调用 `setup-project` 冻结工具，逐条处理它报告的问题，让 Runtime 的独立检查能通过。工具跑完不等于完成。
- **权威输入**：Manifest、方案 `plan.yaml`、清点结果 `inventory.json`、基准工程。
- **工具做的事**：
  1. 从基准工程复制 `ProjectSettings/` 与已解析的 VPM 包（离线，版本与工具链基准一致）。
  2. 从 `Packages/manifest.json` 与锁文件里删掉不可复现的依赖（`file:`、git、http、ssh 来源）。
  3. 把 Harness 自己的编辑器工具放进 `Assets/_HarnessTools`（交付时移除）。
  4. 按清点结果，把选中 zip 里的每个 `.unitypackage` 以原始 GUID 解进工程，素体先装；某个 GUID 已在别的路径存在时不再写入（厂商跨商品共用的资产）。
  5. 写出 `_harness/setup/import.json`（逐包导入报告）、`imported.txt`（本阶段产物的成员）、`usage.md`（素材应用表初稿）。
- **每调一次都按基准重置**：用基准覆盖 `ProjectSettings/`（并删掉基准里没有的文件）、`Packages/manifest.json`、`vpm-manifest.json`、`packages-lock.json`，逐文件还原基准里的 VPM 包目录，从头重写 `import.json`、`imported.txt`、`usage.md`。所以修复都放在本 Run 最后一次调用工具之后；重试时再调一次，前面的修复会被还原。不要就地改厂商解出的文件：下次解包会把它计为内容冲突。
- **Unity 在你退出后才跑**：Runtime 用新进程打开工程（相当于重启），做首次导入与编译并记录骨架基线；编译错误与 dll 读数来自那一次运行，失败时随检查结果注入下一轮。你的工作是改文件，让那一次启动能编译通过。
- **你要核的**：`import.json` 里每个包的 `error`、`guid_conflicts`、`content_conflicts`、`shared_elsewhere`、`not_installed`；清点结果里标为「不可导入」的文件有没有必装内容被漏掉。解包冲突的检查数的是最近一次工具写进 `import.json` 的 `content_conflicts` 与 `guid_conflicts` 之和，处置记录不算：GUID 冲突消除成因后重跑工具，直到它不再报；同路径同 GUID、内容不同的冲突本阶段消除不了，写明后交人。不要手改 `import.json`。
- **Runtime 随后独立测量**：工程版本文件存在；按已接受环境分别核对 VPM 锁定来源、内嵌 UPM 身份与完整解析闭包，不按所有包目录数量判断 VPM 是否完整。源基准及回执仍逐文件完整核验；只有两类元数据派生例外：冻结源已有且无对应文件或目录的有效孤儿 `.meta` 缺失，记录原源 SHA；冻结源配对文件或目录已有但缺 `.meta`，允许实机验证的最小文件夹、文本、JSON 包描述和 ShaderInclude 导入器格式，记录配对源身份与 SHA、新元数据 SHA 和 GUID。新增 GUID 必须有效、唯一且不占用冻结源 GUID，配对源字节与类型必须未变，目录须有冻结源子文件路径证明，后加空目录不能取得冻结身份；源中已有元数据改删、实际文件改删、未知配对、新孤儿、额外导入配置和无效 GUID 不属于例外。`Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 存在；控制台 C# 编译错误为 0；解包冲突计数为 0；未解开的压缩包为 0；公共／材质包不缺；lilToon 材质没有父级缺失的变体（候选检查）；一 GUID 多路径为 0；断链 GUID 为 0；应用表行数＝商品数；`file:`／git 依赖为 0。不要手改基准或为凑通过循环恢复引擎会清除的孤儿元数据。
- **决策边界**：只写 `Assets/`、`Packages/`、`ProjectSettings/`、`_harness/setup/`；不提前装配、改色、做菜单；不替换用户选定的素材。
- **禁止**：内容不同的同路径冲突自己挑一个覆盖；中途升级任何包；手工加 Scripting Define Symbols 冒充某个包已安装。VRChat SDK 的标准宏 `VRC_SDK_VRCSDK3` 应在 `ProjectSettings.asset` 的 `scriptingDefineSymbols` 里、Android 与 Standalone 两个平台上都存在，基准工程通常已带，缺了才补。
- **怎么验证**：以上每项都能用工具输出或文件系统读数说明，而不是「工具说成功了」。
- **产出**：`import.json` 每个非零项的处置说明（写进报告，不改变检查计数），以及对「不可导入」文件的确认结果。
- **升级给人**：内容冲突、选中的文件在素材库里找不到、必装内容只存在于工具处理不了的格式里；首轮编译错误在基准工程上就会出现（属于基准缺陷，交人修基准）。

## 工具链冻结：单子进行中不升级，按事件重核

- **职责**：用基准工程给的版本组合施工，不自行升级。
- **权威输入**：Harness 基准工程的 `vpm-manifest.json` 与包锁；素材包声明的版本要求。
- **决策边界**：本阶段不升级、不降级任何包。
- **基准快照**：Unity 2022.3.22f1、VRChat SDK 3.10.4、Modular Avatar 1.18.1、NDMF 1.14.3、Avatar Optimizer 1.9.16、lilToon 2.3.4、VRCFury 1.1414.0；配套 vpm-resolver 0.1.29、gesture-manager 3.9.9、GoGo Loco 1.8.6、Light Limit Changer 2.12.3、av3manager 2.1.2、avatar-performance-tools 1.3.7。以 Harness 的基准工程为准，快照只用来对照。
- **为什么冻结——依赖图本身不给选择空间**：三个包同时把 `com.vrchat.avatars` 卡在 3.11 以下，读各包 `locked` 段的 `dependencies` 可见：`com.anatawa12.avatar-optimizer` 要求 `>=3.7.0 <3.11.0`，`dev.vrlabs.av3manager` 要求 `3.2 - 3.10`，`vrchat.blackstartx.gesture-manager` 要求 `>=3.10.4 < 3.11.X`。SDK 升到 3.11 会同时打断这三个，「用最新 SDK」目前是空选项。
- **补丁级升级的取舍**：MA、NDMF、AAO、VRCFury、LLC 都有补丁版。升级的收益是「可能修了没遇到的 bug」（推测）；代价是「一次只落一个改动」失效，工具链和素材同时变，出了问题无法归因（确定）。所以默认冻结，单子进行中一律不升。
- **什么时候重核（按事件，不按日历）**：① 上传被 SDK 拒绝（游戏更新的硬信号）；② 某个包的 bug 直接卡住流程；③ 新素材包声明要求更高版本；④ 一单交付完的空档。交付说明里写一句「工程已锁定版本，除非遇到问题不建议升级」。
- **失效条件**：上述三个包发布支持 SDK 3.11 及以上的版本后，天花板不再成立，需要重核。
- **禁止**：在本阶段改基准版本。
- **产出**：工程包版本与基准一致的读数；需要重核时写明触发事件。
- **怎么验证**：`vpm-manifest.json` 的 `locked` 版本与基准逐项一致。
- **升级给人**：素材包声明需要的版本高于基准时，停下交人决定，不要自行升级。

## 核对 VPM 版本的三个坑

- **职责**：核对工程里的包版本、判断「有没有更新版本」时，不被三种假象骗到。
- **权威输入**：`vpm-manifest.json`、`Packages/` 目录、VCC 的 `Repos/` 快照。
- **决策边界**：只核对与报告版本，不改。
- **坑一：预发布版号后缀不统一**。除了 `-alpha`、`-beta`、`-rc`、`-pre`，还有 `-pr6` 这类写法。判断是不是预发布，一律看版号里**有没有连字符**，不要枚举后缀；漏一个就会把预发布报成最新版（gesture-manager `3.9.9-pr6` 被这样误报过）。
- **坑二：VCC 的 `Repos/` 下同一个源有多份带哈希的历史快照**。要取所有快照的并集，只读最新一份会漏版本。
- **坑三：`Packages/` 目录数比点名的包多**。有一次是 16 个目录＝点名的 14 个＋隐式依赖 `com.vrchat.base`、`jp.lilxyzw.avatar-utils`。这 2 个是解析器自己带进来的，不是漏项，也不是多余项。
- **怎么验证（判据）**：Runtime 的 `vpm_locked_match` 独立读取已接受环境基准、工程实装包和两个解析锁；逐项核对 VPM 身份与版本、UPM 声明与传递依赖、实装来源及冻结内容。合法内嵌 UPM 包不计作 VPM 包，目录数不要求等于 VPM 锁条目数。不能靠删除合法 UPM 包或把它们加入 VPM `locked` 通过检查；依赖集合需要变化时须形成新的受管环境修订，再独立验收。
- **禁止**：凭「目录名看着像」判断包的来源与版本。
- **产出**：版本差异清单，每项写明来源。
- **升级给人**：发现工程里的版本与基准不一致、又说不清来源时，写明差异交人。

## 编译判据：厂商独立程序集的错误要单独查

- **职责**：确认工程真的编译通过，而不是只有默认程序集通过。
- **权威输入**：Unity 编译日志、`Library/ScriptAssemblies/` 下的各程序集。
- **决策边界**：只判断与定位根因；改厂商源码或加依赖要授权。
- **机制**：`Assembly-CSharp-Editor.dll` 存在或更新，只说明默认编辑器程序集编译过了。带独立 asmdef 的厂商包编译到各自的 dll；其中一个失败时，`Assembly-CSharp-Editor.dll` 照样会更新（有一次 24 个错误时它也是新文件）。
- **本流程的验收口径**：两条编译检查，一是 Runtime 这一次 Unity 步骤的日志（Run 目录的 `unity-*.log`）里匹配 `error CS\d{4}` 的行数为 0，不分首轮、次轮，出现即失败；二是 `Assembly-CSharp-Editor.dll` 存在。按日志计数在这里是验收口径，不是可选参考。
- **定位用**：该厂商程序集自己的 dll 是否产出（在 `Library/ScriptAssemblies/` 下，例如 `Triturbo.BlendShapeShare.Data.Editor.dll`），用来判断是哪个包出错。
- **影响范围**：Unity 批处理模式下，工程里只要有一个编译错误就整体中止，一个厂商包的问题会挡住所有依赖编译的检查。
- **厂商源码疑似有 bug 时**：先用源 `.unitypackage` 里的原始字节做哈希比对，确认是厂商原样而不是解包弄坏的；再查是不是依赖没解析（例如散装在 `Assets/` 下的包，其 `package.json` 声明的依赖永远不会被解析）。只补表层语法错误往往还剩几十个错误。
- **禁止**：未经用户授权修改厂商源码；用「控制台看着干净」代替日志计数。
- **产出**：编译结论（各厂商程序集是否产出、错误数）与根因说明。
- **怎么验证**：日志里 `error CS` 计数为 0，且各厂商程序集 dll 都已产出。
- **升级给人**：需要改厂商源码、或需要往 `Packages/manifest.json` 增加基准之外的依赖时，写明根因与改法，交人授权。本阶段自己不加依赖：下一次 `setup-project` 会用基准覆盖 `manifest.json`；首轮编译需要的新依赖（如 SRP core、FBX SDK）属于基准工程缺陷，交人加进基准工程后重建。
