# 贴图优化判据

## 贴图格式：一张格式错误顶几十张，根因在源图的默认平台条目

- 未压缩格式每像素 4 字节，DXT5 每像素 1 字节：一张格式错误的图顶得上几十张正常图。一个工程 208 MB 的贴图内存里，有 170 MB 来自四张 2048² 的 RGBA32；只改导入设置、不减尺寸，贴图内存就从 208.4 MB 降到 92.4 MB。
- **必须查源图导入设置里 `DefaultTexturePlatform` 那一条**，不能只查平台覆盖：上例四张图的 Standalone 覆盖是「自动」，只看覆盖会以为一切正常，写死 RGBA32 的是默认平台条目。
- 构建时生成贴图克隆的插件（如 Light Limit Changer）读的是源贴图的导入设置，所以根因总在源图上。
- 判「未压缩」（`RGBA32`、`ARGB32` 这类）按运行时格式名：含 `RGBA`/`ARGB` 且不属于 DXT/BC 系，不按枚举数字判。
- `.meta` 的 `textureFormat` 多数是 -1（Automatic；一个工程 777 张贴图里 563 张是 -1、214 张是 1），按它数 RGBA32 恒为 0，不能用；但 `streamingMipmaps: 1` 这个字段确实写在 `.meta` 里，可以直接读回核对每张图的 Mip Streaming（VRChat 要求开启，不开会构建报错）。
- **本流程里**：导入设置只由 Runtime 在构建副本里改（只降不升、开 Mip Streaming、未压缩的改成压缩），执行方不改厂商 `.meta`。它判断「是否已压缩」时看 `textureCompression` 与 Standalone 覆盖，不看默认平台条目的显式格式：默认平台条目写死 RGBA32 的图可能漏修，随后被性能检查的格式项阻断。`design.json` 没有字段能修这类图，遇到时写明哪几张、证据在哪，交人。
- 验收：优化后贴图内存低于基线，且没有默认平台条目为 RGBA32 的残留。

## 贴图用途按着色器属性判：主图用白名单

- 判「是不是主图」用白名单。Harness 的优化与性能检查用的是正则 `^_Main\d*(st|nd|rd|th)?Tex$|^_BaseMap$|^_BaseColorMap$`，即 `_MainTex`、`_Main2ndTex`、`_Main3rdTex`、`_BaseMap`、`_BaseColorMap`；不在白名单里的属性一律当辅助图。同一张图只要被任一材质当主图用，就按主图算。
- **不能用辅助图黑名单**：lilToon 的辅助贴图属性有几十个（`_RimColorTex`、`_MetallicGlossMap`、`_ReflectionColorTex`、`_Bump2ndScaleMask`、`_MatcapBlendMask` 等），黑名单必然漏。漏掉的会被当成主图给 2048 档，而厂商原本把它们设成 512——一抬就是 16 倍内存；实测贴图内存从 102.6 MB 反涨到 139.9 MB。
- **按着色器属性判，不按文件名**：一件服装的法线图叫 `N01.png`，名字里没有 normal，但它挂在 `_BumpMap` 上，按属性判一目了然。文件名里的 mask、normal、emission、highlight、matcap、alpha、reflection 只作兜底。
- 分档后贴图内存反涨时，先回头查有没有把辅助图当成主图抬高，而不是继续降别的图。

## 分档看屏幕占比，主图红线 2048

- **红线是观感**：主图（底色、花纹、皮肤、面部）不降到 2048 以下；辅助图（遮罩、法线、发光、高光、MatCap、alpha）1024，极小件的辅助图建议 512；只做金属反射的 Cubemap 512。一张 1024 的 Cubemap 就要 16 MB。
- **主图不受档位上限约束**：没有审美确认时一律 `keep`，导入上限是 4096 也可以 keep，不会被拒（性能报告里记为按设计保留）。主图要降档，必须已有 `visual_review.status: approved`，而且降档后不低于 2048：低于 2048 会被性能检查（`perf_texture_size`）阻断，厂商原本就小于 2048 的主图不算。小件主图（美甲、发带、被外衣遮住的内衣底色）即使屏幕占比很小，也保持不低于 2048；确有必要时作为审美缺口报告给用户，不在优化阶段自行降。
- **辅助图与 Cubemap 的档位是硬上限**：超过档位的必须降到档位（写 `downscale`）。它们不需要审美闸门；A/B 看得出差异时，在 `rationale` 写明，并作为风险报告给人。
- **档位按导入上限比，不按实际像素**：Runtime 用导入上限（有 Standalone 覆盖取覆盖值）对档位。实际只有 512 的辅助图，导入上限写着 2048，也要写 `downscale` 到 1024（像素不变，只改上限）；导入上限 4096、实际 2048 的主图，把上限降到 2048 也算降档，同样要审美确认。
- **辅助图的分档依据是这张图在全身照里占多大**，不是它的名字。一个工程里降下来的例子：美甲的发光遮罩 2048→512（二十片甲在全身照里加起来不到 40 像素）；只影响宝石、金属高光的反射 Cubemap 512→256。
- 档位按工程实况定，别照搬；这组档位不因工程用途（自用或交付）放宽。
- **只降不升**：`target_max_size` 不能高于该图当前的导入上限，`action` 只有 `keep` 与 `downscale`。要撤销一次降档，改回 `keep`，或把 target 调大（不超过原上限）；本流程每次都从源工程镜像副本再往下降，不存在「点名抬高」。无差别地双向设置，会把厂商刻意压低的图全抬上去。
- `maxTextureSize` 是上限不是实际尺寸：512 的源图设 2048 上限，占的仍是 512。估算内存时取 min(源图长边, 导入上限)；性能检查也这样算。

## 降档前做 A/B：判据是看不出差异

- **本流程里**：执行方出不了 A/B 图。主图降档靠人的审美确认（`visual_review.status: approved`），没有就 keep；辅助图与 Cubemap 按档位降，观感变化看最终回归的换装照与优化前那一轮对比，看得出差异时在 `rationale` 写明风险、交人（档位是硬上限，不能恢复到档位以上）。
- 要降的显眼图先做 A/B：同一视角渲两张，算最大像素差与「差值 >8 的像素占比」，再裁出该材质最密的区域放大 4 倍并排看。
- 可降的例子：一张格纹图 4096→2048，最大像素差 56/255，差值 >8 的像素只占 1.18%，且全在细白条纹上。
- **判据不是「省了多少 MB」，而是「A/B 看不出来」。** 省得多但看得出，就不能降。
- A/B 结论交独立评审，不自己下观感结论；主图被 ≥2 个独立评审指认看得出差异，就不降。
- 降档后的观感复核放在最终回归：用同一机位与降档前比较，主图被看出差异就改回 keep；辅助图与 Cubemap 写明风险交人。

## 贴图收益估算只是上界

不开 Unity、按「场景 → 预制体 → 材质 → 贴图 → `.meta`」的文本链路估算贴图收益时，有三个坑：

1. **`maxTextureSize` 是上限不是实际尺寸**：按上限估会虚报（一例估 1107 MB，烘焙体实测 160.7 MB，约 7 倍）。要读图像文件头拿真实尺寸，再取 min(源图长边, 导入上限)；读不出尺寸的（exr、hdr、tga）标问号，不用上限顶替。
2. **只看场景 YAML 里直接出现的 GUID 会严重漏**：预制体实例上的材质挂在 `.prefab` 里，场景只引用预制体。要对 prefab、controller、asset 做传递闭包（一例只找到 10 个材质，实际有 79 个）。
3. **前两项修对了，总量仍只是上界**：闭包会算进构建后被 AAO 剔掉的材质，压缩格式也只能假设。

- 真实收益只有一个判据：改完重新构建、在克隆体上测量，对比前后报告。
- 逐张的档位建议可以用（按属性判档与总量无关），总量数字不要拿去汇报。
