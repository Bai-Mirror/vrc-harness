# 素体：Rurune（IKUSIA）

只在素体为 Rurune 时注入。每节固定写适用范围、结论、判据、证据等级、失效条件。

## Rurune：外购上衣的同名胸型键常无人同步

- **适用范围**：Rurune 素体，胸型会被菜单驱动（厂商胸型轮盘或自建胸型档）时；已知 PLUMARIUM 的 Re-Poppin。
- **结论**：Re-Poppin 的衬衫、外套、领带和两个兜帽带有与身体同名的胸型键（`Breast_small_____胸_小`、`Breast_big(limit)`、`Breast_Big_____胸_大(mizuki)` 等），但预制体没有 BlendshapeSync，也没有说明书。默认胸型（0.31）下看不出来，胸型拉满时双乳整片穿出（正面肤色像素 6,822，同步后 837）。开襟外套（AQUA 的派克）不挡胸，里面的件同步后就不必再管；包带类固定值件（`Breast_Big(mizuki)=100`）是按大胸调好的，不动。
- **判据**：驱动 0／默认／1 三档读回，衣物键与身体逐值相同；拉满时肤色穿出像素接近 0。
- **证据等级**：单一案例（候选）。
- **失效条件**：厂商更新预制件、自带同步之后。

## Rurune：贴身小件缺胸型键时，两头都会出事

- **适用范围**：Rurune 素体上的乳贴类贴身小件（已知 Esmera 的乳贴）。
- **结论**：缺 `Breast_small` 时，身体 `Breast_small=38` 下乳贴外浮 4–8 mm；缺 `Breast_big(limit)` 时，胸型推到大的一侧会陷进皮肤。在 Unity 里给原网格副本补帧并加同步后，p50 为 1.33 → 1.28 → 1.13 mm（原件在 38 档为 5.74 mm、100 档为 14.48 mm）。补不补大胸一侧由用户拍板。
- **判据**：编辑模式三档量距；0 档新旧逐值相同。不要在 Blender 里补键后直接导回（出现过偏 71 mm）。
- **在 Harness 流程里**：补帧要改装配层，本流程没有通道，写明哪件缺哪个键、三档读数，交人；件上有同名键只是没人驱动的，装配会自动补 BlendshapeSync（`D-139`）。
- **证据等级**：单一案例（候选）。
- **失效条件**：厂商补齐这些键之后。

## Rurune：普通版与面捕版两个头像根，同步与收缩都要按根、按覆盖件做

- **适用范围**：同时有普通版与面捕版头像根的 Rurune 工程。
- **结论**：BlendshapeSync 等修正要在两个根上各做一遍。收缩 Shape Changer 挂在面捕根或整套根上时（已知 Velvet China 的 8 个收缩键），关掉袜子等部件后小腿塌陷；按覆盖关系拆到各件后修复：袜＝膝、小腿、踝、足、趾；袖套＝肘、前臂；衣身＝肩。
- **判据**：两个根分别读回；逐件「单关一件」渲图。
- **在 Harness 流程里**：本流程只造一个头像根（方案的 `body_prefab`）；按覆盖件拆收缩键要改装配层，做不到，写明交人。
- **证据等级**：单一案例（候选）。
- **失效条件**：只有一个头像根时，第一条不适用。

## Rurune：IKUSIA 同体系服装的尺寸关系

- **适用范围**：Rurune 素体；为同体系 Mizuki、Kaguya 制作的服装，或按 Rurune 制作后给别的尺寸用的服装。
- **结论**：同一厂商的适配版根缩放为：Rurune 版 0.95、Mizuki 版 1、用 Mizuki 网格制作的 Kaguya 版 0.807521。按 Rurune 做的服装原样套到 Kaguya 会上移 13–18 cm。反方向（只有 Kaguya 或 Mizuki 版、要套到 Rurune）在 Rurune 工程上没有实测，应先按同一厂商的比例推算，并交用户确认。
- **判据**：根缩放与厂商原值或同厂商比例一致；主干逐根吸附；三视图无悬空。
- **证据等级**：未实测（就 Rurune 方向而言；比例数据来自 Kaguya 工程）。
- **失效条件**：厂商改变适配方式时。

## Rurune 脚型键：默认是高跟姿态，穿包趾鞋要写 Foot_heel_OFF

- **键**：`Body_b` 上的 `Foot_heel_OFF_____足_ヒールオフ`（100 = 放平）与 `Foot_Hiheel_____足_ハイヒール`（更高的跟）。两键为 0 时是默认的高跟姿态。
- **症状**：一套服装（Rurune-Black）的厚底包趾鞋没有任何组件写平脚键，脚趾从鞋头穿出。
- **当时的修法**（人工作业，供理解机制）：从同场景里已正确的鞋（`Lockon_shoes`）原样复制 MA Shape Changer 到这双鞋上：`Foot_heel_OFF` = 100、`Foot_Hiheel` = 0 → `Body_b`；两个头像根各挂一份。验收：穿鞋（全穿或只穿鞋）时读回 100，脱鞋时 0，修前修后同机位盲测。
- **未决**：同一套服装的两双袜子网格上带着 `Foot_Hiheel` 键，「只穿袜」时脚型该取多少没有结论；自动的同名键跟随检查匹配不上这两双袜子。另一套服装（Velvet）的「关袜子」状态被记为「衣服没了、脚部收缩键还开着」的正样本。
- **在 Harness 流程里**：装配层由 Runtime 按方案重建，补不了 Shape Changer；写明哪双鞋缺平脚键、在哪个状态穿出，交人（换预制件或改方案）。
- 证据等级：单一案例（候选）——一个 Rurune 客户工程的修复与读回；脚型键语义与 Kaguya 一致。

## Rurune 胸型：服装件与乳贴要同步胸型键

- **键**：`Body_b` 的胸型键与 Kaguya 同名：`Breast_small_____胸_小`、`Breast_big(limit)`、`Breast_Big_____胸_大(mizuki)` 等，由厂商胸型轮盘（`Breast_size`）驱动。
- **症状一**：Re-Poppin' Cat（PLUMARIUM）的 Rurune 版五件（衬衫、外套、领带、两个兜帽）带着同名胸型键却无人同步，恒为 0；胸型拉满时双乳整片穿出。修法：五件各挂 MA BlendshapeSync（源 `Body_b`），**件上有哪个键同步哪个**（两个兜帽只有后两个键）；两个头像根共 10 个组件。修后件上键与身体逐值相同，正面肤色像素 6822 → 837。
- **症状二**：一款乳贴（Esmera 套装的 `Breast_Bandage`）只有 `Breast_Big(mizuki)` 一个胸型键；该工程身体 `Breast_small` 默认 38，乳贴外浮 5.74 mm，胸型拉满时错位 14.95 mm。修法：在 Unity 内按身体位移场给乳贴网格副本烘焙 `Breast_small_____胸_小` 与 `Breast_big(limit)` 两帧，再接 BlendshapeSync；修后间隙 p50 为 1.28 / 1.66 mm。在 Blender 离线副本上做的方案偏了 71 mm，已弃用。
- **查过没问题的**：`Lockon_leotard` 与 `Nipple_On` 的组合（可见 3 态，最大差 0）。
- **在 Harness 流程里**：给网格副本烘帧要改装配层，本流程没有通道，写明哪件、哪个键，交人；件上有同名键却没人驱动的，装配会自动补 BlendshapeSync（`D-139`），值差仍由 Runtime 的同名键检查复核。
- 证据等级：多工程验证——两个 Rurune 客户工程各自修复并读回。

## Rurune 厂商换装轮盘的末档选不到

- **症状**：服装轮盘拨到最末端，想要的那一档（例：素体基础装、全关态）出不来。
- **机制**：厂商 `Assets/IKUSIA/rurune/Animation/Clothes.anim` 用 Motion Time 驱动，`m_LoopTime` = 1，而最后一个关键帧在归一化时间 1.0：参数 1.0 会回绕到 0，采到的是第 0 档；末键处 `m_IsActive` 又有独立变化（`acce`、`cloth`、`gloves`、`jacket`、`knee-socks`、`boots` 置 1，Re-Poppin' Cat 置 0），所以这一档只存在于 t = 1.0，永远选不到。
- **判据**：`m_LoopTime` = 1 且末键归一化时间 = 1.0，**并且**末键相对前一键有独立变化——两条同时满足才是真缺陷（末键与前一键完全相同时只是收尾，不算）。
- **当时的修法**（人工作业，供理解机制）：做一份不循环的副本或给轮盘加一档，让该档有自己的区间；Play 下按每档中点 (i+0.5)/n 以及 1.0 逐档读回；两个头像根都改。
- **在 Harness 流程里**：本流程不改厂商轮盘与 clip（厂商菜单原样保留），修不了；方案要的某档只存在于厂商轮盘末键时，写明交人。Runtime 自己生成的衣装轮盘另算。
- 证据等级：多工程验证——两个 Rurune 客户工程各发现一例（一例用厂商原片段，一例是工程内同型片段），均修复并读回。

## Rurune 工程里的多头像根与形态键登记

- **多根**：一个 Rurune 历史工程里，面捕安装器生成的两个同名面捕根共用同一个 blueprintId（一个启用、一个停用），原生根 `rurune_None` 也处于启用状态；一个客户工程同样有两个启用的头像根。上传时选错根会覆盖线上版本；修补若只改一个根，其他根照旧。
- **形态键登记**：该历史工程的 Shape Changer 条目里 Delete 1146 条、Set 6 条，几乎全用 Delete；与发髻 `bun` 相关的 Shape Changer 在三个根上各有一套（共 12 个组件，每个物体 1 个，不是同一物体上的重复组件）。
- **当时的做法**（人工作业，供理解机制）：上传前确认只有一个启用的根、blueprintId 已核；所有补丁按根逐个施加并逐根核对。
- **在 Harness 流程里**：本流程只造一个头像根（方案的 `body_prefab`），补丁也不由执行方施加；打包阶段按 Runtime 的根数检查写诊断，多根或共用 blueprintId 写进 `blockers`。
- 证据等级：单一案例（候选）——一个历史工程的静态核查，多根现象另有一个客户工程佐证。
