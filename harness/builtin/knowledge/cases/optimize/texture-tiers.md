# 优化：贴图分档降尺寸的案例

## 贴图分档工具读错了生效尺寸：一整张「建议下调」清单都是假的

- **症状**：离线分档脚本在两个工程里分别报出 48 张和 78 张「需要下调」的贴图，照着改了；其中还有一张 2048 的主图被降到 1024。
- **机制**：
  1. 判断「当前生效尺寸」时直接取了 `.meta` 里 Standalone 平台块的 `maxTextureSize`，没看它的 `overridden` 标志；平台块全都 `overridden: 0` 时，真正生效的是 `DefaultTexturePlatform` 那一条。
  2. 主图白名单漏了 lilToon 第四层主色 `_Main4thTex`，这张主图被当成辅助图降档，碰了「主图不低于 2048」的红线。
- **判据**：离线读出的每张贴图生效尺寸，要与 Unity 自己导出的贴图清单逐张核对：旧口径 195 张里只有 54 张对得上，修正后 191/195 一致（剩下 4 张是非 2 的幂取整与 BMP 读不出文件头）。
- **当时的修法**（人工作业，供理解机制）：全部用回滚文件还原，修正脚本后重出方案：两个工程实际各只需下调 1 张（一张是主图 4096→2048，必须先做 A/B；一张是辅助发光遮罩 2048→1024，编辑模式同口径 204.4 → 202.4 MB）。主图判定同时保留显式白名单和按属性名的正则，防止以后出现第五层主色时再漏。
- **在 Harness 流程里**：design.json 的 textures 以 perf.json 列出的实际使用 GUID 与生效尺寸为准，不自己从 .meta 推断；读数与导入设置不一致时写明证据交人。
- **适用条件**：用离线脚本读 `.meta` 判断贴图尺寸的工具；lilToon 材质。
- **证据等级**：多工程验证

## 贴图分档的判据：按 shader 属性分主图与辅助，只降不升，收益以构建后实测为准

- **症状**：头像性能等级为 Poor 或 VeryPoor，想靠降贴图尺寸改善。
- **机制**：同一张图是不是主图取决于它挂在哪个 shader 属性上，不取决于文件名（lilToon 的法线图常叫 `N01.png`）；离线脚本估的收益是上界：它按引用闭包把构建后被 AAO 剔掉的材质也算进去（一例上界 623 MB，烘焙体实测只有 160.7 MB），并按每像素 1 字节估算，而 DXT1 只有一半。
- **判据**（用户定的红线与做法）：
  - 主图（`_MainTex`、`_Main2ndTex`、`_Main3rdTex`、`_Main4thTex`、`_BaseMap`、`_BaseColorMap`、`_Albedo`）上限 2048，不再往下；
  - 遮罩、法线、发光、高光、MatCap、alpha 等辅助图上限 1024；反射 Cubemap 上限 512；
  - 只降不升：已低于目标的一律不动（厂商可能刻意压低）；
  - 主图降档前做 A/B：同视角两张渲图，算最大像素差与「差值 >8 的像素占比」，裁最密区域放大 4 倍并排看；判据是「看不出来」，不是省了多少 MB。
- **当时的修法**（人工作业，供理解机制）：真实收益只看改完后重跑构建后性能报告的前后对比。两个工程修正后都几乎没有贴图空间可省，瓶颈在多边形、蒙皮网格、骨骼与物理骨（一例新头像根：66.5 万三角、88 个蒙皮网格、943 根骨、215 个 PhysBone，贴图 242 MB，综合 VeryPoor），要降等级得从这些方面入手，并由用户决定取舍。
- **在 Harness 流程里**：在 design.json 的 textures 里：主图不受档位上限约束，没有 visual_review.status=approved 就 action=keep（4096 也可以 keep），要降必须已批准且不低于 2048；辅助图超过 1024、Cubemap 超过 512 的必须 downscale 到档位（按导入上限比），rationale 写明它挂在哪个 shader 属性上，A/B 看得出差异时写明风险；只降不升。
- **适用条件**：Kaguya、Shinano 两个素体的多套服装头像；lilToon 材质。
- **证据等级**：多工程验证

## 在用贴图没开 mipmap：开 mipmap 与 Mip Streaming，脚本带预演与还原

- **症状**：上传前检查发现少数正在使用的贴图既没开 mipmap 也没开 Streaming Mip；SDK 面板也会对这类贴图报错。
- **机制**：不开 mipmap 的贴图远距离会闪烁，也无法流式加载；开启后显存约多 1/3。
- **判据**：从交付头像根的渲染器 → 材质 → 贴图反查「在用」贴图，逐张读导入设置：一例 105 张里 101 张两者都开、4 张两者都关（内裤与丝袜贴图），`mip 开而 stream 关` 为 0；执行后导入器读回 mip 与 stream 都为 true、mip 层数 11–12，再跑一次预演应为 0。
- **当时的修法**（人工作业，供理解机制）：用户同意后执行（该例用户接受多 1/3 显存换抗闪与流式加载）；脚本提供「预演 / 执行 / 还原」，执行前把原设置写进备份 JSON。另一工程在上传前自检时用 SDK 自带修复一次给 29 张贴图开了 Streaming Mip。
- **在 Harness 流程里**：optimize 的设计输入没有改导入设置的字段；在 rationale 或诊断里列出未开 mipmap 的在用贴图，交用户决定。
- **适用条件**：Unity 2022.3 + VRChat SDK3；执行前确认当前启用的头像根就是交付根。
- **证据等级**：多工程验证
