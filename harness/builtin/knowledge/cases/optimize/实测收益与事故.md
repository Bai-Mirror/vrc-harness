# 性能优化实测案例

## 贴图内存减半只靠改导入设置：四张默认平台条目写死 RGBA32

- **症状**：一个四套衣服加三套发型的头像，贴图内存 208.4 MB，其中 170 MB 来自四张 2048² 的贴图。
- **机制**：这四张图源导入设置的默认平台条目写死了 RGBA32（每像素 4 字节，DXT5 是 1 字节）；Standalone 平台覆盖是「自动」，只查覆盖看不出来。
- **判据**：读运行时 `Texture2D.format`，并检查源图 `DefaultTexturePlatform` 条目，而不只是平台覆盖。
- **修法**：把默认平台条目改为压缩格式，不减尺寸：贴图内存 208.4 → 92.4 MB。同一轮挂 AAO 默认设置：骨骼 758 → 588、形态键 536 → 157、蒙皮网格 64 → 51，面数 391,865 不变。
- **适用条件**：导入设置被显式写死未压缩格式的工程；在一个工程中实测。

## 八套服装的重工程：AAO 加三档分级，贴图从 VeryPoor 到 Poor

- **症状**：8 套服装、贴图全为 2048 且部分 4096，贴图内存 254.4 MB，评级 VeryPoor。
- **机制**：多套服装的贴图按厂商原始尺寸全部进包；AAO 只去掉部分冗余，尺寸分档才是大头。
- **判据**：每一步单独出报告：挂 AAO Trace And Optimize 后 226.8 MB（蒙皮网格 105 → 82、骨骼 1526 → 1180）；三档分级（主图全留 2048）后 116.4 MB，贴图一项评级 Poor。
- **当时的修法**（人工作业，供理解机制）：先挂 AAO，再按主图 2048 / 辅助图 1024 / 小件 512 分档，显眼图先做 A/B。同一轮的其它收益：同一套衣服的多个配色合成一份实例、改为换材质数组，省 43 个渲染器；死参数改为 NotSynced，省 8 bit；VRCFury 的 UnlimitedParameters 备着，面捕装上去参数超限时自动接管。
- **在 Harness 流程里**：AAO 由 Runtime 挂上（安全配置）；你在 `Optimize/design.json` 里分档：主图没有审美确认就 keep，辅助图超过 1024、Cubemap 超过 512 的降到档位。配色合成一份实例、改参数同步这两项本流程没有通道。
- **适用条件**：多套服装的 PC 头像；在一个工程中实测。

## 分级把辅助图抬成了主图：贴图内存反涨

- **症状**：贴图分级之后，贴图内存不降反升，从 102.6 MB 涨到 139.9 MB。
- **机制**：判「是不是主图」用了辅助图黑名单，漏掉了 lilToon 的若干辅助属性；这些图被当成主图给了 2048 档，而厂商原本把它们设成 512，一抬就是 16 倍内存。分档脚本又是双向设置，把厂商刻意压低的图也抬了上去。
- **判据**：主图用白名单（`_MainTex`、`_Main2ndTex`、`_Main3rdTex`、`_BaseMap`、`_BaseColorMap`、`_Albedo`）；分档后逐张核对有没有「上限被抬高」的图。
- **修法**：改用白名单判主图；只有设计里点名的图才允许抬高，其余只在当前上限高于目标时才改；重新构建测量。
- **适用条件**：lilToon 材质为主的工程；在一个工程中实测。

## 空的 MergePhysBone：预处理返回 false，日志里却没有异常

- **症状**：构建时 `VRCBuildPipelineCallbacks.OnPreprocessAvatar` 返回 false，日志里没有任何异常文本，排查了很久。
- **机制**：某个工具批量挂了 10 个 AAO MergePhysBone，却没有填 `componentsSet`。AAO 的验证阶段为它们报 `MergePhysBone:error:noSources`，NDMF 预处理返回 false，整条构建链断掉。
- **判据**：预处理莫名返回 false 时，先数 `componentsSet.mainSet.arraySize == 0` 的 MergePhysBone。
- **修法**：给每个 MergePhysBone 填上源列表，或者删掉，不留空的。
- **适用条件**：使用 AAO MergePhysBone 的工程（AAO 1.9 系列）；在一个工程中实测。

## AvatarPoseSystem 的抓取手柄把包围盒撑到 9.6 m

- **症状**：头像的 AABB 超过 5×6×6 m，量到约 9.6 m。
- **机制**：AvatarPoseSystem 的抓取手柄故意把渲染器的 `localBounds` 撑到 9.6 m，于是整个头像的包围盒被它拉大。原因在插件，与素体无关。
- **判据**：列出各渲染器（含粒子、Trail、Line Renderer）对世界包围盒的贡献，定位撑大者；不要只看静止包围盒，也不要排除某类渲染器后宣称通过。
- **修法**：把该手柄渲染器的 `localBounds` 改回网格的真实包围盒。同一做法适用于其它故意把 `localBounds` 撑大的插件部件。
- **适用条件**：装了 AvatarPoseSystem 的头像；在一个工程中实测。粒子 bounds 撑大包围盒是另一类原因，要分开查。

## 死重物体清理：一轮清出的东西与两个假阳性

- **症状**：一个多套服装工程里挂着大量没人用的渲染器与材质槽，占顶点与贴图。
- **机制**：改走材质换色后，多余的银色 prefab 还留着；客户不用的腕饰没删；挂载配饰时复制过八份的戒指源件留在原地。
- **判据**：带渲染器的物体同时满足三条才算死重：生成的动画层里没有曲线指向它或它的祖先；没有组件字段引用它；当前未激活。两个假阳性：SPS / VRCFury 的插槽标记（`_Gimmick/Gimmick_SPS/**`，构建期按组件配置引用、不走动画曲线；该例 16 个渲染器合计 736 顶点，不值得冒险）；缩放为 0 的占位物（如厂商预制体里的 `Advanced/AvatarHight`，enabled 也 active 却画不出东西，还常带空材质槽）。
- **修法**：一轮清出 7 个物体、44,189 个顶点、25 个材质槽；删完扫一遍空材质槽（渲染为洋红），回读并做骨架高度自检。
- **适用条件**：多套服装、做过换色与配饰复制的工程；在一个工程中实测。

## 别名槽清掉厂商眼图：贴图内存按去重后的资产算

- **症状**：贴图清单里有一张厂商原始眼图 `eyes.png`（10.67 MB），看起来还挂在材质上。
- **机制**：VRChat 的贴图内存按去重后的贴图资产算，不按材质槽算：同一张 `face.png` 挂在 `_MainTex`、`_OutlineTex`、`_BaseMap`、`_BaseColorMap` 上只占一份，清掉多余的槽一点都省不下来；只有某张图除了死槽以外没人引用时，清槽才真省。lilToon 的 `_BaseMap` / `_BaseColorMap` 是 URP/HDRP 转换用的兼容别名，着色器不采样。该眼图只被这两个别名槽引用，而 `_MainTex` 早已换成新做的异色瞳，实际渲染出来是异色瞳——这就是别名槽没被采样的直接证据。
- **判据**：不要用「清空槽 → 重渲 → 逐像素比对」判断是否被采样：遮挡会骗人（脸在身体网格上、被头发挡住，清空主图也看不出差别）；噪声也会骗人（同一配置连跑两次，差值在 0 与 2 之间跳，判据的分辨率比要测的量还粗）。
- **修法**：清掉只被别名槽引用的贴图，重新构建测量。
- **适用条件**：lilToon 材质、贴图只被兼容别名槽引用的情形；在一个工程中实测。
