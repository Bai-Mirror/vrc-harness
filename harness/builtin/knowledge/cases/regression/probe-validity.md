# 回归取证：探针与测量口径的失败案例

## 穿出斑块假阳性：先看带符号距离，再问这件该不该盖住

- **症状**：探针报出大片穿出，渲图里却看不到：只穿袜的状态报约 50 cm²，红色身体渲图一个红像素都没有；环形腿饰正下方的赤脚被判成「被覆盖」；开口鞋只收脚趾时报 116 cm²；一双运动鞋现状报 31.2 cm²，渲图无可见穿出。
- **机制**：
  1. 判定起点沿皮肤法线外偏 0.5 mm；贴身薄袜与皮肤只隔 0.2–0.5 mm，袜内皮肤全被算成穿出。
  2. 「从皮肤向上发射线、命中衣物即算覆盖」会把环、带类配件下方本该裸露的皮肤算进覆盖区。
  3. 开口鞋的脚背开口、鞋内的结构件，会被当成皮肤穿出鞋面。
- **判据**（按顺序问）：
  1. 报穿出的顶点到衣物外壳的带符号距离是正的吗？全部为负（一例约 −0.22 mm）就是贴合假阳性。
  2. 这件衣物真的该盖住这块皮肤吗？环、带、镂空件下方和鞋口开口不属于覆盖区。
  3. 同机位的红身体渲图（身体换纯红材质、衣物保留）有没有红像素。
- **当时的修法**（人工作业，供理解机制）：斑块面积只用来出候选；每个候选都用带符号距离和红身体渲图复核后再定案。比较改法时用同一口径比相对大小（例：运动鞋现状 31.2、平脚键 50 时 32.9、100 时 81.6 cm²，现状最好）。
- **在 Harness 流程里**：读 Runtime 的穿出读数时按以上顺序先排除假阳性；判为测量假阳性时不改造型，在修复说明里写明带符号距离与渲图证据。
- **适用条件**：顶点对外壳的穿出斑块判据（斑块下限 0.5 cm²、起点偏移 0.5 mm 是该探针的标定值，换探针要重新标定）；在 Kipfel、Rurune 两个素体上遇到。
- **证据等级**：多工程验证

## 批处理渲图不重新蒙皮：修前修后两张图逐像素相同

- **症状**：在无界面批处理的编辑模式里替换 SkinnedMeshRenderer 的 sharedMesh 或改形态键权重后，Camera.Render 出的修前、修后对比图逐像素相同。
- **机制**：批处理编辑模式下改了网格或权重，Camera.Render 不会重新蒙皮，渲出来的仍是旧的蒙皮结果。于是「修复无效」和「修复有效」都无法从这组图判断。
- **判据**：修前修后两张图的文件哈希是否相同？相同就先怀疑渲图没有重新蒙皮，而不是修复没生效。
- **当时的修法**（人工作业，供理解机制）：渲图前用手工线性蒙皮（或已验证等价的烘焙方式）把当前状态烘成静态网格，再对静态网格渲图。直接改 SkinnedMeshRenderer 拍出的那组对比图作废重拍。
- **在 Harness 流程里**：执行方不渲图；Runtime 的修前修后渲图逐像素相同时，先怀疑取证口径，写明证据交人。
- **适用条件**：Unity 批处理（`-batchmode`）编辑模式下的渲图取证。Play 模式和带界面编辑器没有在该案例里验证。
- **证据等级**：单一案例（候选）

## 探针读构建后的网格：AAO 合并会把形态键改名

- **症状**：探针在预处理或构建后的头像上按原名读不到形态键：表情探针 8 个表情全报 `route_not_found`；身体脚型键、收缩键「消失」，或被读成 0。
- **机制**：
  1. Avatar Optimizer 合并网格后，身体被并进 `$$AAO_AUTO_MERGE_SKINNED_MESH_0` 之类的合并网格，形态键改名为 `<序号>_<原网格名>__<原键名>`（如 `6_Body_b__Foot_heel_OFF`、`9_Body_Base__Foot_down`）；另一例里看到 `AAO_Merged_<原名>_<序号>` 形式。
  2. 构建期没有任何写者的键会被 AAO 当成无用键删掉，于是「键从未非 0」可能只是写者被删了。
  3. 表情层由手势参数驱动，只按菜单参数找路由会找不到。
- **判据**：
  1. 在 AAO/NDMF 预处理之前，先读源网格的原名键表与目标 clip 的 `blendShape.*` 曲线终值。
  2. 预处理后把合并名解析回原网格与原键名，同时保留实际权重。
  3. 路由要递归扫子状态机、AnyState 与普通转移，并按 `GestureLeft`/`GestureRight` 0–7（GestureWeight 取 1）逐个尝试。
  4. `route_not_found` 或 `*_not_weighted` 只说明探针没找到路由，不能据此断言表情不存在或已经修好。
- **当时的修法**（人工作业，供理解机制）：探针同时输出源读数、映射回原名后的权重，以及每个表情的条件与实际生效的 clip；键「从未非 0」时先查写者组件是否被删或被禁用。
- **在 Harness 流程里**：读 Runtime 的构建后读数时把合并名映射回原名；「路由找不到」不当作「不存在」，写明证据交人。
- **适用条件**：启用了 Avatar Optimizer 网格合并的工程（Kipfel、Rurune 两个素体上都遇到；一例版本为 AAO 1.9.16）。
- **证据等级**：多工程验证

## 探针把源场景标脏：克隆和渲图放进预览场景

- **症状**：批处理探针跑完后，源场景的 `isDirty` 从 False 变成 True（场景文件 MD5 未变，也没保存），ProjectSettings 也被改写了。
- **机制**：探针在源场景里克隆头像、跑 SDK 预处理和渲图，任何改动都会标脏源场景；SDK 预处理和形态键 clamp 开关的强制切换会写 ProjectSettings。
- **判据**：跑完后比对三样东西的前后值：源场景 `isDirty`、场景文件 MD5、ProjectSettings 相关项（如形态键 clamp 开关）。任何一项变了，探针就判失败。
- **当时的修法**（人工作业，供理解机制）：克隆、预处理和渲图都放进 PreviewScene，收尾时销毁预览场景并回到源场景。ProjectSettings 的副作用先用版本控制还原，再提交。该案例中，渲图段调用 SetActiveScene 切到预览场景时异常中止过，源网格和 clip 的读数不受影响。
- **在 Harness 流程里**：执行方不运行探针；Runtime 报源场景变脏或 ProjectSettings 变化时写明证据交人。
- **适用条件**：在 Unity 批处理里运行自写的编辑器探针。
- **证据等级**：单一案例（候选）

## 穿模检测先做正对照：故意制造穿出，确认探针会报警

- **症状**：探针在所有状态上都报 0 穿出，无法区分「真的没穿」和「探针失明」。一例早期校准时，「包含率」和「交叉边计数」两种量法都失效了。
- **机制**：没有阳性样本，0 报警就没有信息量。
- **判据**（两个工程用过的正对照，数值只作量级参考；斑块定义为三个顶点都穿出的三角面，面积 ≥0.5 cm² 才计）：
  - 身体整脚下移或抬跟键拉满：Kipfel 的 `Foot_down=100` 让靴子报 32.9 cm²、只穿袜报 248 cm²（红像素增加约 20 万）；Rurune 的 `Foot_Hiheel=100` 让各双鞋报 70–90 cm²。
  - 把鞋壳上移 10 / 20 mm：乐福鞋 4.5 / 114 cm²，拖鞋 1.5 / 147 cm²，靴 69.5 / 156 cm²。
  - 撤掉厂商的删脚处理：原本用 Delete 删脚的鞋报 9.7 cm²。
  - 隐藏袜子：小腿红像素 13 → 154235。
  - 正对照必须报警、原状态报 0，才采信原状态的 0。
- **当时的修法**（人工作业，供理解机制）：每种穿模判据投入使用前，以及换到新工程时，都用可控扰动（让身体变大、把衣物移开、撤掉删除或隐藏遮挡件）造阳性样本。修前修后必须用同一脚本、同一口径。
- **在 Harness 流程里**：判读 Runtime 的穿模读数时确认它带有正对照；没有正对照的 0 不采信，写明并交人。
- **适用条件**：鞋袜与脚的几何贴合检测，在 Kipfel、Rurune 两个素体上实测；数值随网格和探针而变。
- **证据等级**：多工程验证

## 世界坐标口径：BakeMesh(true) 乘完整矩阵，别乘去缩放的 TRS

- **症状**：自写探针导出的身体与鞋袜世界坐标偏离真实位置，造出大片假穿出：一例头像根缩放 1.12，偏 15–240 mm；另一例服装件缩放 1.052，偏 7–30 mm，凭空多出 104 cm² 的「穿出」。
- **机制**：把 `BakeMesh(mesh, true)` 的结果乘上一个去掉缩放的 TRS 矩阵，缩放不为 1 的层级会整体错位；层级越深、离缩放中心越远，偏差越大。
- **判据**：
  1. 这件或它的父级 `lossyScale` 是 1 吗？不是 1 就必须核对口径。
  2. 我的世界坐标和手工线性蒙皮对过没有？两例中 `BakeMesh(true)` × 完整 `localToWorldMatrix` 与手工蒙皮最大差 0，去缩放 TRS 口径则出现上述偏差。
- **当时的修法**（人工作业，供理解机制）：用 `BakeMesh(true)` × 完整 `localToWorldMatrix`（已有的审查工具就是这样做的），或手工线性蒙皮；任何新探针先与另一种口径逐点对账再用。
- **在 Harness 流程里**：执行方不写探针；读到可疑的大面积穿出时先问缩放口径，写明证据交人。
- **适用条件**：头像根或服装件带非 1 缩放的工程（Kipfel 根缩放 1.12、Rurune 服装件缩放 1.052 实测）。
- **证据等级**：多工程验证

## 临时探针源码：删除前先存进取证产出目录

- **症状**：临时编辑器探针用完就从工程里删掉，事后需要复核口径或复跑时找不到源码，结论无法复现；两个工程都这样丢过探针源码。
- **机制**：临时脚本放在工程 `Assets/` 下，交付前必须删除；删除时没有另存，取证链就断了。
- **判据**：结论引用的每个数字，能否追到一份仍然存在的探针源码与原始输出（JSON、渲图）？
- **当时的修法**（人工作业，供理解机制）：删除探针前，先把源码以 `.txt` 形式复制到取证产出目录，与输出放在一起；删除时连同 `.meta` 与空目录，删前逐一列出核对，删后确认工程版本控制状态干净。此后三个工程的修复脚本都是先存档再删除。
- **在 Harness 流程里**：执行方不在工程里放临时脚本；诊断引用的每个数字都要能追到 Runtime 的输出文件。
- **适用条件**：所有在工程内临时放置编辑器脚本做测量或批量修改的场合。
- **证据等级**：多工程验证

## Unity 网格导进 Blender 量穿模：坐标镜像后要翻转三角绕序

- **症状**：把 Unity 里导出的身体与鞋袜顶点按 (x, z, y) 换轴导进 Blender 量穿出，结果法线全部朝内，穿出判定整体反了。
- **机制**：Unity 是左手坐标系，(x, y, z) → (x, z, y) 的换轴是一次镜像；镜像会翻转三角形的绕序，而法线方向由绕序决定。
- **判据**：导入后抽查一个凸起部位（如脚背）的法线是否朝外；或者对一个明显在外的顶点算带符号距离，符号应为正。
- **当时的修法**（人工作业，供理解机制）：换轴时同时把每个三角形的顶点顺序反过来（例如交换第 2、3 个索引），再计算法线与穿出。
- **在 Harness 流程里**：执行方不做 Blender 测量；遇到法线全反的读数时写明证据交人。
- **适用条件**：自写导出脚本把 Unity 网格搬到 Blender 做几何测量。
- **证据等级**：单一案例（候选）

## 不进 Play 验证菜单效果：先跑完整预处理链，再手动求值构建后的 FX

- **症状**：想在批处理里验证「改了开关之后各档服装的显隐」，直接调 `Animator.SetFloat` 抛异常，或 Animator 根本不求值；直接读编辑态又会漏掉构建时生成的层；构建后 Animator 的参数默认值多为 0，「默认穿外套」会被当成不穿。
- **机制**：
  1. 编辑模式下 `Animator.SetFloat` 会被 VRCFury 的补丁拦截并抛异常；`cullingMode=CullUpdateTransforms` 的 Animator 在批处理下不求值。
  2. 菜单与开关的真实效果要到 NDMF、MA、VRCFury、AAO 预处理之后才存在（如「MA Responsive: <物体名>」层、Write Defaults 修正）。
  3. 构建后控制器里的参数默认值不等于表达参数表的声明默认值。
- **判据**：
  - 克隆头像，跑完整的 `VRCBuildPipelineCallbacks.OnPreprocessAvatar`（或 `IVRCSDKPreprocessAvatarCallback` 链），各步都返回成功；返回失败必须报错退出（一例探针曾拿未构建的控制器继续出数）。
  - 用 PlayableGraph + `AnimatorControllerPlayable` 驱动构建后的 FX，参数按构建后表达参数表的声明默认值复位，逐帧 `Evaluate` 若干帧后读 `activeSelf`、`activeInHierarchy`、材质、形态键；求值时只在克隆上临时把 cullingMode 设为 AlwaysAnimate。
  - 逐格对比改前改后（例：换装轮盘 6 个取值 × 开关 2 态），断言与本次无关的物体每格不变；参数总开销 `CalcTotalCost` 前后相等。
- **当时的修法**（人工作业，供理解机制）：把「应用改动」和「求值验证」写成两个批处理入口；验证全过才保存场景，保存后用版本控制差异回读。Motion Time 型轮盘的档值按 clip 算（一例三档为 0、1/3、2/3，不是 0、1、2）。
- **在 Harness 流程里**：执行方不求值 FX；以 Runtime 构建后的读回（含 activeInHierarchy）为准。
- **适用条件**：装有 VRCFury 的 MA 工程，Rurune 与 Kaguya 两个素体上都用过；单次预处理 75–135 秒。
- **证据等级**：多工程验证

## Play 里临时换回原网格做对照无效：构建后骨骼数组已重排

- **症状**：想在 Play 里把渲染器临时换回修复前的原网格做对照，量到约 100 mm 的垃圾距离，渲图逐像素不变。
- **机制**：进 Play 时 NDMF、AAO 已经跑过：骨骼数组被重排，身体被合并进 `$$AAO_AUTO_MERGE_SKINNED_MESH_0`。运行时把 `sharedMesh` 换成编辑态的网格，顶点权重对应的骨骼已经不是原来那些。
- **判据**：对照组的读数是否在合理量级（该例的正常间距为 1–15 mm，出现 100 mm 级就是口径错了）；修前修后图是否逐像素相同。
- **当时的修法**（人工作业，供理解机制）：修前对照在编辑态做（量距或渲图），或者在 Play 里用「停 Animator、把新加的键置 0」来等价模拟修前状态，不在运行时换网格。
- **在 Harness 流程里**：执行方不在 Play 里换网格；修前对照以 Runtime 的修前构建读数为准。
- **适用条件**：启用 NDMF 与 AAO 网格合并的工程，在 Play 模式下做修前修后对照。
- **证据等级**：单一案例（候选）

## 探针用反射找类型与方法：按参数类型挑重载，按类型名遍历程序集

- **症状**：审查或探针脚本在不同工程里运行时报错：按名字取 Gesture Manager 的方法抛 AmbiguousMatchException；按「类型名, 程序集名」取 `VRCAvatarDescriptor` 得到 null，随后空引用。
- **机制**：
  1. 该工程的 Gesture Manager 同时有 `GetModuleFor(GameObject)` 与 `GetModuleFor(<描述符类型>)` 两个重载，按名字取方法有歧义。
  2. SDK 类型所在的程序集名随版本或工程而不同，写死程序集名会取不到。
- **判据**：脚本在目标工程里离线编译 0 错误后，还要在该工程实跑一次反射路径；取到 null 或抛歧义异常就是这两类问题。
- **当时的修法**（人工作业，供理解机制）：取方法时按参数类型挑选重载；取类型时遍历已加载程序集、按类型全名匹配，不写死程序集名。
- **在 Harness 流程里**：执行方不写探针脚本；工具报反射类错误时写明证据交人。
- **适用条件**：跨多个工程复用的编辑器探针（两个工程分别遇到这两类问题）。
- **证据等级**：多工程验证

## 状态复位写坏 VRChat 内置参数：头像缩成一点，渲图全是背景

- **症状**：审查工具在每个状态前「把全部参数恢复默认」，之后环绕渲图 24 张全是纯背景，7 个半透明候选的掩码像素为 0；本该检出的正样本没检出。
- **机制**：复位把 VRChat 内置参数（`ScaleFactorInverse`、`EyeHeightAsMeters`、`Grounded`、`TrackingType` 等）也写成了 0，头像根的 localScale 变成 (0,0,0)。这是工具失效，不是问题不存在。
- **判据**：每个状态先做健全性检查：Head 与 Hips 的世界高度在合理范围（该例 Head y=1.002、Hips y=0.722），头像根缩放不为 0；重复默认态两次，只有眨眼等自动播放的面部键不同。自动识别这类易变键并排除。
- **当时的修法**（人工作业，供理解机制）：只复位用户参数（该例 314/750 个），默认值取表达参数的声明值；审查期间摘掉工程里其他编辑器回调，避免它们在 Play 中改参数。
- **在 Harness 流程里**：读 Runtime 状态扫描时先看健全性字段（头像高度、缩放）；不健全的结果不采信，写明并交人。
- **适用条件**：Play 模式下用 Gesture Manager 驱动状态、批量复位参数的审查工具。
- **证据等级**：单一案例（候选）

## 包含率与穿越计数：能抓整段伸出，但会被厂商删顶点和不水密网格骗

- **症状**：
  - 一例射线贴合探针在全穿态报鞋的穿出为 0，真实病灶却是脚趾整段伸在鞋外；改用包含测试（脚部顶点是否在鞋的封闭网格内）后，修前脚趾 2% 在鞋内、修后 100%。
  - 另一例两双没有穿模的鞋包含率只有 3–19%，一只长手套 0%；「表面穿越计数」在正常态报 36 条，把脚压平塞进高跟鞋反而只有 25 条。
  - 第三例在校准时，包含率与交叉边计数两种量法都失效。
- **机制**：沿法线的射线只量「皮肤离衣物表面多深」，整段在外时没有交点可量；包含测试补上了这一类，但厂商用 Delete 删掉了鞋内的脚部顶点、鞋网格不水密时，包含率会很低；贴身靴内壁擦边会产生大量穿越边，而脚趾整段出靴时区域交界的边又不计入。
- **判据**：
  - 包含率要结合款式解读：包趾鞋 80–96% 属正常；浅口乐福鞋 47%、浅口玛丽珍 60%、半指手套指尖 0% 是设计，要看厂商展示图原图；
  - 配对只按物体名的词元，按路径配对会把名字带「Boot」的窗口件当成靴子；
  - 任何几何度量先用正对照标定：把脚型键设 0 或把鞋移开，度量必须明显变坏。
- **当时的修法**（人工作业，供理解机制）：几何度量只作候选与参考，不单独作为卡口；定案靠带符号距离、红身体渲图与隔离渲图。
- **在 Harness 流程里**：包含率只作候选，判定时结合带符号距离与渲图；款式导致的低包含率写进说明，不改造型。
- **适用条件**：Kaguya、Shinano、Kipfel 三个素体上的鞋袜与手套检查。
- **证据等级**：多工程验证

## 透明消失检测的正样本：先读工程自己的病因记录再选

- **症状**：透明消失检测在事先选好的「正样本」状态上报 0，看起来像检测器失明。
- **机制**：那个问题早已在工程里查清并修过（抓屏材质队列已调），正样本选错了；执行方没先读工程自己的病因记录。另一个旧结论「离屏渲染里 GrabPass 不生效」也只适用于当时那条渲染路径：换成 Camera.Render 路径后窗口透射率约为 1，GrabPass 生效。
- **判据**：正样本要能证明检测器有检出力：在 Play 里只改运行时材质实例（不落盘），把某个抓屏材质的队列调回修复前的 2450，同状态重跑，检测报 7 条，消失的主要是发型合并网格（份额 0.95–1.0，消失率 6–40%）；改回后为 0。
- **当时的修法**（人工作业，供理解机制）：选正样本前先读工程的病因记录与修复历史；用「只改运行时实例」的方式制造阳性，不改资产。
- **在 Harness 流程里**：执行方不制造正样本；Runtime 的检测报 0 时查工程病因记录确认是否已修，写明依据。
- **适用条件**：透明与抓屏类检测；Kaguya 素体、lilToon 宝石材质。
- **证据等级**：单一案例（候选）

## 编辑模式渲图：forceRenderingOff 对场景根预制件实例不生效

- **症状**：编辑模式下用 `Camera.Render()` 渲单件试穿图，已把原头像根的 280 个渲染器 `forceRenderingOff` 全设为 true，原头像仍整身出现在画面里，侧视图左右各截进半个身体。
- **机制**：该标志在这种渲染路径下对场景根上的预制件实例不生效。
- **判据**：渲后检查画面边缘有没有非目标物体的像素（该例改法后左缘前景像素 386 → 0）；渲前对全场景渲染器状态做快照，渲后还原并复读，不一致为 0。
- **当时的修法**（人工作业，供理解机制）：要隐藏的整个头像根用 `SetActive(false)`，渲完恢复；取景后用像素包围盒检查不触边。
- **在 Harness 流程里**：执行方不渲图；Runtime 的渲图出现非目标物体时写明证据交人。
- **适用条件**：Unity 编辑模式、Vulkan 下的单件渲图取证。
- **证据等级**：单一案例（候选）

## 穿出方向定号：按锚骨向外判在脚和胸部会错，改用奇偶或绕序

- **症状**：脚型候选打分时，正常贴合的状态（鞋垫面距离中位 −0.03 mm、倾角 0.3°）反而报出 19.1 cm² 的穿出，而把脚型键设为 0（明显错误）只报 2.67 cm²，按面积排序把错误选项排第一；另一工程的上衣在厂商默认态报 82.6 cm²、17 块斑块，且收缩键从 0 拉到 100 面积反而变大（73.2 → 82.6 cm²），渲图里完全看不到皮肤。
- **机制**：判断「在外壳外面」时用锚骨向外的方向定号，在脚、胸部这些形状下方向是错的；只改外壳规则仍然错。
- **判据**：
  - 剂量检验：把对应的收缩或脚型键从 0 拉到 100，穿出面积应单调朝合理方向变化；方向反了就是定号错。
  - 改用 `normal_sign: parity`（或 `winding`）后排序符合预期：正常态 0 cm² 排第一，脚型键设 0 的 56–61 cm² 垫底；上衣默认态降到 33.4 cm²、剂量 0→100 为 34.05→33.37（近乎平），剩余部分是同一件蝴蝶结下的自遮挡（已知局限）。
  - 同一请求跑两遍逐位相同。
- **当时的修法**（人工作业，供理解机制）：探针的定号默认值从锚骨外向改为奇偶；打分同时看鞋垫面有向距离与跟隙，不单按面积排序。
- **在 Harness 流程里**：读 Runtime 的穿出读数时做剂量检验（相关键 0→100 面积应单调）；方向反了判为测量问题，写明证据交人。
- **适用条件**：Shinano 靴子与 Kaguya 水手服上各标定一次；换探针或换部位要重做剂量检验。
- **证据等级**：多工程验证

## 渲图的噪声底：独立进程或重复渲染同一状态并不逐字节相同

- **症状**：「正序渲与倒序渲的候选图应逐字节相同」的判据三组都没过；另一工程里同参数重复应用后重渲，全身差 0.1–0.4%。
- **机制**：两次独立的 Unity 进程渲同一状态，抗锯齿与浮点求和顺序会带来子像素差（该例每组差几到几十/255，只占 0.001%–0.006% 的像素）；重复渲染还可能受时间相关曲线或未收敛状态影响。
- **判据**：不用「逐字节相同」做判据，改看量级：同组对比的像素差之和比跨组对比小 4–5 个数量级，且施加前回读值等于目标值，就判为噪声；跨状态比较像素时先扣掉同状态重复渲染的噪声底。
- **当时的修法**（人工作业，供理解机制）：判据写成「同组差 ≪ 跨组差」并记录噪声底；首次遇到时按规矩交用户确认是否接受。
- **在 Harness 流程里**：比较 Runtime 的前后渲图时先扣掉噪声底，不用逐字节相同作判据。
- **适用条件**：批处理渲图取证（Shinano、Kaguya 两个工程）。
- **证据等级**：多工程验证
