# 回归取证：状态扫描与缺陷定案的案例

## 静态审查的嫌疑：多数被实机状态扫描推翻

- **症状**：只读工程文件（场景、预制体、控制器、动画的文本解析）列出的「最可疑」缺陷，到实机上多数不成立：三个工程共 9 条嫌疑，只有 1 条成立。
- **机制**：静态阅读只看单个 clip 或组件写了什么，看不到运行时多个层同时写同一属性时谁赢、菜单里能不能触发，也容易读错组件字段语义和预制体实例的覆盖值。
- **判据**（在 Play 里用 Gesture Manager 驱动状态集读实际值；推翻的例子）：
  - 「厂商参数没有菜单控件、常驻写内层收缩键，外套关后不恢复」：外套开时内层 `Necktie_spine_OFF`/`Shirt_spine_OFF`=100、关时=0。
  - 「长裤开关关闭时不写回被它关掉的三件」「兜帽被帽子、外套两个开关反向控制，结果取决于生成动画次序」：按真实序列、两种先后顺序切换，结果都正确且一致。
  - 「MA Object Toggle 的 Active=0 且目标默认隐藏，所以永远不显示」：开关语义是「点亮＝脱掉」，默认全关＝全穿。
  - 「脚型键不随鞋走」：鞋自带的 Shape Changer 反应式写 `High_heel`，鞋显 50、鞋隐 0。
  - 「肩臂收缩与短袖 clip 冲突」：冲突参数在实际菜单树里没有控件，不可达。
  - 「场景里两个头像根都启用」：实际是非面捕根开、面捕根关；「部件开关参数名是 `__MA/AutoParam/<名>`」：构建后实名带哈希后缀。
  - 唯一成立的一条：厂商换装层权重全 0，整组菜单无效（36 个状态零变化）。
- **当时的修法**（人工作业，供理解机制）：静态审查只产出「待验嫌疑」，逐条标「无 / 未确认 / 未查」并附文件行号；每条都用实机读数、构建后导出或真实切换序列定案后，才进入修复清单。
- **在 Harness 流程里**：静态阅读得出的嫌疑只写进诊断的「待验」；以 Runtime 的状态扫描读数定案，不据静态嫌疑改设计。
- **适用条件**：厂商 FX 层、MA 组件与自制换装层并存的头像（Kipfel 两例、Rurune 一例）。
- **证据等级**：多工程验证

## 参数冲突先查可达：实际菜单树里没有控件的参数触发不到

- **症状**：厂商参数（如短袖切换）的动画会与 MA Shape Changer 冲突，交付说明里也记着这个副作用，但用户在游戏里无法触发它。
- **机制**：厂商子菜单没有挂进描述符实际使用的菜单树，对应参数只剩默认值，冲突路径不可达。
- **判据**：
  1. 从描述符引用的根菜单资产出发，递归遍历所有子菜单，列出实际可达的控件与参数（该案例实际菜单树共 9 个菜单）。
  2. 冲突涉及的参数不在可达集合里，就记为「不可达」，不算当前缺陷。
  3. 反过来，改动菜单结构（把厂商子菜单接回去）会让这条冲突重新变成真缺陷，改菜单时必须复查。
- **当时的修法**（人工作业，供理解机制）：冲突清单按「可达 / 不可达」分开记录；不可达项写进交付说明备注，不花工时修。
- **在 Harness 流程里**：在 design.json 里只为实际可达的参数设计控件；诊断时把不可达的冲突记为「不可达」。
- **适用条件**：厂商参数与自制菜单并存、厂商子菜单未全部接入的工程。
- **证据等级**：单一案例（候选）

## 浮点轮盘取值用 (i+0.5)/n：边界值会停在上一档、回绕或落到相邻档

- **症状**：用 i/n（0、0.25、0.5、0.75）或 1.0 作为换装轮盘的测试取值时，测得的状态与菜单实际选择错位；有一例最后一档在菜单里根本选不到。
- **机制**：轮盘有两种常见实现，边界处都不可靠：
  1. AnyState 加严格的 Greater/Less 浮点条件选 clip（转移时长 0、无退出时间）：0.25、0.5、0.75 不满足任何一条严格不等式，状态停在上一档。
  2. Motion Time：状态的 `m_TimeParameterActive:1` 指向轮盘参数，采样时间 = 参数 × clip 长度；clip 用常量阶梯切线（`tangentMode:103`、in/outSlope=Infinity），边界恰好落在跳变点上。若 clip 的 `loopTime=1`，参数 1.0 回绕成第 0 档，只放在 1.0 处的最后一个关键帧永远选不到。
- **判据**：
  - 先在控制器里确认机制：`m_TimeParameterActive:1` 的个数、BlendTree 个数、AnyState 转移的条件模式；Motion Time 型读 clip 的 `m_StopTime`、关键帧位置和 `loopTime`，由归一化跳变点推出档数 n。
  - 测试取值一律用 (i+0.5)/n：n=4 取 0.125/0.375/0.625/0.875，n=3 取 0.1666667/0.5/0.8333333；不用 1.0 做档值。
  - 档边界不一定是 i/n：一例发型轮盘 clip 的 `StopTime` 为 1.0166667，边界落在 0 / 0.3279 / 0.6557；另一例取 0.2857（略小于 2/7）落进了上一档。边界一律用关键帧时间 ÷ clip 长度算。
  - Motion Time 型若关键帧切线不是常量（一例切线为 0），相邻两档之间会平滑混合，出现「半件」状态；自建轮盘改成每档一个状态、用中点阈值切换更稳。
  - VRChat 同步的 Float 按 1/127 量化，等价性检查要覆盖 k/127（k=0..127）与各档中点 ±0.1（一例共 139 个取值、3895 组组合，WD on/off 下都无不一致）。
  - 菜单 radial 的 `labels` 为空时，档数只能从控制器或 clip 推出。
- **当时的修法**（人工作业，供理解机制）：状态集请求按档中心取值。要让被回绕吃掉的末档可选：不动厂商 clip，做一个等分 n+1 档、`loopTime=0`、常量切线的新 clip（1.0 与末档同值），复制控制器换上新 clip，再把 MA Merge Animator 指向副本；按 (i+0.5)/(n+1) 逐档读回，并确认 1.0 不再回绕。
- **在 Harness 流程里**：设计输入里的档位与测试取值按 (i+0.5)/n，不用 1.0 做档值；发现末档被回绕时写明证据交人。
- **适用条件**：浮点参数驱动的换装、发型、配色轮盘（四个工程：AnyState 条件型一例，Motion Time 型三例；其中两例 `loopTime=1`，都用上面的副本 clip 方法补出末档，一例 7 套加「全关」补成 8 档）。
- **证据等级**：多工程验证

## 状态集请求：每个状态显式写全参数，并用运行时参数名

- **症状**：状态扫描只写本状态关心的参数时，上一个状态留下的值会漂进下一个状态：一例里「头饰一直不显示」其实继承了上一轮的兜帽整套，「某套全开」的图其实是关袜状态。按静态推测的 MA 自动参数名写请求，参数根本没被驱动。
- **机制**：头像参数在状态之间不会自动复位；复位工具若把「每次启动时的实际值」当默认值，上一轮停在哪里就把哪里当默认。厂商参数不 pin 住，会掩盖「厂商参数保持默认」才暴露的问题。MA 给没有显式参数名的菜单项分配 `__MA/AutoParam/<菜单项物体名>`（物体名可以含斜杠），构建后实名还带哈希后缀；描述符引用的菜单资产也可能只是空壳（`controls: []`），真菜单在 Play 或构建时才由 MA 装入。
- **判据**：
  - 复位只用表达参数声明的默认值，并且只复位用户参数；每个状态显式写全所有服装相关参数（四个工程分别为 25 个、17 个加轮盘、8 个部件加两个轮盘、全部相关参数）；
  - `settle_frames=30`；追踪 Hips、双脚、双脚趾、Head；同时挂抓屏链、重合面、越界值、包含四类数据探针；
  - 参数名以构建后导出的菜单与 `param_defaults` 为准；场景里有多个头像根时，扫描前确认只选中一个。
- **当时的修法**（人工作业，供理解机制）：状态集 = 默认态 + 每套服装 ×（全穿、逐个部位关、全裸）+ 相互影响的组合；另跑「真实切换序列、不复位」验证串档。各例为 49、63、71–83、83 个状态。
- **在 Harness 流程里**：执行方不写状态集请求；读 Runtime 的扫描结果时确认参数写全、名字是构建后的实名。
- **适用条件**：Play 模式下用 Gesture Manager 驱动的状态扫描。
- **证据等级**：多工程验证

## 客户反馈复现不了：穷举手势、表情与开关，再列全写者

- **症状**：客户反馈「做手势表情时会自动戴上眼镜」，两个同素体工程里都复现不了。
- **机制**：未确定。可能的来源包括手势层写入、参数驱动器，或 Unity 预览与 VRChat 游戏内行为的差异。
- **判据**：
  1. 穷举状态：眼镜开关 0/1 × 左右手势 1–7 × 表情动作 `VRCEmote` 0–8，另测双手同手势（两工程分别 46 个与 30+11 个状态）；眼镜显隐只跟开关走，脸上的 `Item_Glasses_OFF` 恒为 0。
  2. 证明手势确实被驱动了：同批状态里表情确实变化（例：左手 1 改了 7 个脸部键，右手 7 改了 14 个）。
  3. 全工程搜写眼镜的 `.anim`/`.controller`：只有厂商眼镜 ON/OFF 两条 clip；自制层的参数驱动器只会把眼镜参数置 0（切整套时摘眼镜），没有置 1 的。
- **当时的修法**（人工作业，供理解机制）：复现不了就挂起，向用户要细节（哪个手势、在 VRChat 里还是 Unity 预览里看到、哪套服装），不猜着改；若能复现，同素体的工程一并修。
- **在 Harness 流程里**：复现不了的反馈在诊断里写明穷举范围与写者清单，停下向用户要细节，不猜着改。
- **适用条件**：Kipfel 素体的两个工程；方法适用于任何「偶发显隐」类反馈。
- **证据等级**：多工程验证

## 看起来像缺陷的，先对照交付说明与厂商原包

- **症状**：审查列出的「缺陷」里，有一部分是有意设计或厂商原样：8 个表情的竖瞳不生效；厂商菜单里有一个空的子菜单；包含测试显示手套指尖 0% 在手套内、乐福鞋 47%、玛丽珍鞋 60%。
- **机制**：
  - 竖瞳：该头像把 `eye_pupil_OFF` 静态设为 100，8 个表情 clip 也都写 `eye_pupil_OFF=100`（同时写瞳形键），瞳孔被永久关闭并换成猫爪形，交付说明已写明「8 个表情瞳形不生效」。
  - 空子菜单：对照厂商原包，该菜单资产本来就是空的。
  - 包含率低：看厂商展示图原图，分别是半指手套、浅口乐福鞋、浅口玛丽珍，属款式设计。
- **判据**：
  1. 在预处理前读源网格静态值和相关 clip 的曲线终值，证实机制；
  2. 对照交付说明、厂商说明书、厂商原包与展示图，确认是不是已告知的取舍或厂商原样；
  3. 是取舍或原样，就把「改不改」交给用户决定，不自行修。
- **当时的修法**（人工作业，供理解机制）：竖瞳一例用户决定不改；空子菜单记为厂商原样关闭；款式类记入声明，不再报。若要改已交付的包，需要另出一次。
- **在 Harness 流程里**：在 diagnosis.json 里先对照交付说明与厂商原包，已告知的取舍或厂商原样标为「非缺陷」，改不改交用户。
- **适用条件**：接手已交付或半成品工程的审查阶段（Kipfel、Kaguya 素体各有实例）。
- **证据等级**：多工程验证

## 待机姿势 0 像素不代表动作中不穿：收缩键要做姿势扫描

- **症状**：身体肩、上臂收缩键从未生效，但待机姿势下把键在 0 与 100 之间切换，穿衬衫时渲图差 0 像素，看起来「没有可见后果」。
- **机制**：待机姿势下衬衫完全盖住肩臂；抬臂、耸肩、趴、坐等动作会让皮肤从衬衫下穿出。只渲身体时 0↔100 差约 35,000 像素，说明键本身有效。
- **判据**：
  - 姿势扫描：85 个姿势 × 6 个方位，键取 0 与 100 各渲一次比较像素差并做射线露出检查；正对照差 1015–3177 像素。
  - 该例 28/85 个姿势有穿出：举手欢呼 140 像素、趴 74、耸肩抬臂 66、坐姿系列 20–44；待机和素体自带坐姿为 0。
- **当时的修法**（人工作业，供理解机制）：在衬衫对象上挂 MA Shape Changer（目标 `Body_Base`，`Shoulder_OFF`、`Upper_arm_OFF` Set 100，写法照同工程外套已有的 Shape Changer）。复扫 85 个姿势，修后与「键恒为 100」的参照差全 0；Play 里默认 100/100，菜单关上衣→0/0。
- **在 Harness 流程里**：收缩键要不要写进 shrinkkey_review，并以 Runtime 的姿势扫描读数为依据；只看待机姿势的 0 像素不够。
- **适用条件**：Kipfel 素体配厂商默认衬衫；任何「待机下被衣物遮住」的收缩或穿出判断都要补动作姿势。
- **证据等级**：单一案例（候选）

## 裸体或敏感状态的渲图不外送：按可见件数据判定

- **症状**：检查「全关」状态下乳头键为 100 是否是缺陷时，需要看全裸或近裸的渲图。
- **机制**：这类图不应发给外部的第二个模型；而这个问题本身可以用数据回答：全关时哪些件仍可见、胸部有没有被遮挡。
- **判据**：Play 读回每个全关态仍可见的件（一例只剩兜帽与包，或颈圈、项链、手臂绷带），胸部没有任何可见件遮挡时，乳头键为 100 就是正确的；全穿态该键应为 0。早先报的违例是旧判据把合并件和领带算成上衣造成的伪影。
- **当时的修法**（人工作业，供理解机制）：敏感状态只在本地看图，结论写成「可见件清单 + 键值」，不外送；判据修正后重跑全部状态。
- **在 Harness 流程里**：敏感状态只用可见件数据判定，不把渲图发给外部模型；结论写成可见件清单加键值。
- **适用条件**：所有涉及裸体、内衣状态的回归检查。
- **证据等级**：单一案例（候选）
