# 交付打包实测案例

## 客户一打开交付工程就编译不过：排除规则误删了插件内部的 Library

- **症状**：客户打开交付的工程即报 `error CS0234: 命名空间 BlackStartX.GestureManager 中不存在类型或命名空间名 Library`。
- **机制**：打包时用了 `-xr!Library` 这类排除规则，它会递归匹配任意层级的同名目录，把 `Packages/vrchat.blackstartx.gesture-manager/Scripts/{Editor,Runtime}/Library/` 下 19 个 `.cs`/`.meta` 一起排掉了。只查「违规条目数为 0」查不出这一类，因为被误删的是插件内部文件，不在违规清单里。
- **判据**：`Library`、`Temp`、`Logs`、`obj`、`Captures` 在工程根层命中 0，同时 zip 内 `Packages/**/Library/` 命中数 **>0**；把工程 zip 解到临时目录，用 Unity batchmode 打开一次，`Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 存在、编译日志 `error CS` 为 0。
- **当时的修法**（人工作业，供理解机制）：排除规则只锚定工程根那一层，重新打包并做冷解包编译；出现命名空间缺失时回查排除规则，不要手工往包里补文件。
- **在 Harness 流程里**：排除规则由打包工具固定（只锚定工程根），冷解包编译由 Runtime 做；诊断者只在证据里看到这类失败时写进 `blockers`。
- **适用条件**：用归档工具按目录名排除来打包 Unity 工程；同一时期的四次交付里有一次中招，其余三次没有。

## 订单专用脚本与诊断截图跟着工程发给了客户

- **症状**：一晚的工作下来，通用生成器目录里堆了 5 个订单专用脚本，共 243,639 B（最大一个 106 KB），外加 7 张诊断截图、19 个中间 `.txt`；它们会跟着工程打包发给客户。
- **机制**：多个执行者各自往同一个目录里加菜单方法，没人负责清理；中间产物与交付物混在同一个工作目录里。
- **判据**：打包前查 `Assets/Editor/` 下有没有带订单编号的脚本、`Assets/` 下有没有中间日志与诊断截图；区分探针日志（`*_probe.txt`、`*_verify.txt`）与菜单、动画资产（`*.anim`、`*.asset`、`*.controller`，这些是交付物）。
- **当时的修法**（人工作业，供理解机制）：订单专用脚本放到单独的目录（如 `Assets/Editor/<订单号>/`），不混进放通用工具的目录，打包前整个目录删掉；删之前先编译一次，确认没有别的东西引用这些类。
- **在 Harness 流程里**：诊断者不删文件：发现订单专用脚本、诊断截图留在 `Assets/` 里，写进 `blockers` 并令 `verdict=blocked`，由人回对应阶段处理。
- **适用条件**：多人或多个执行者并行往同一工程里加生成脚本的情形；在一个工程中实测。

## 客户给了 6 个素材包，收尾时发现只有 1 个接了线

- **症状**：做到收尾才发现，客户提供的 6 个素材包里只有 1 个真正用在了头像上。
- **机制**：素材「导入」工程不等于「用上」：导入后没有接线的包，在工程里没有任何包外引用。
- **判据**：拿接单时的素材清单逐条核销，用 GUID 反查每个素材包在工程里的引用；没有包外引用的就是没用上。应用表不留空白格，每个「不用」都写得出原因。
- **当时的修法**（人工作业，供理解机制）：没接线的包回到对应阶段处理（接上，或与客户确认不用并写明原因），不直接交付。
- **在 Harness 流程里**：没接线的包由 `package_usage_refs_closed` 阻断；与客户确认不用的件要在方案的 `unused` 里写明原因并随方案批准，才会被豁免。
- **适用条件**：客户提供多个素材包的工程；在一个工程中实测。
