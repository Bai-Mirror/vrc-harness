# 交付：重交与清理的案例

## 重交前清理：审查残留、开发依赖与 ProjectSettings 都要回到交付基线

- **症状**：已交付的工程为了审查被加了东西：`Packages/manifest.json` 里的远程驱动编辑器用的开发依赖（一个 git 地址的 Unity MCP 包）、`Assets/` 下的审查代码副本（含 asmdef、shader、VERSION）、`Library/` 下的审查中间态，以及跑 Unity 带来的 ProjectSettings 漂移。不清掉就重打包，客户会拿到开发工具和被改过的设置。
- **机制**：审查与修复阶段需要这些工具，交付阶段不需要；它们散落在 `Assets/`、`Packages/`、`Library/`、`ProjectSettings/` 四处，靠记忆逐个删容易漏。
- **判据**（一例的清理验收）：
  - 清理脚本先 `--check`：列出 5 项残留（审查代码目录及其 `.meta`、`Library` 下中间态、`manifest.json` 与 `packages-lock.json` 里的开发依赖）；`--apply` 后再 `--check` 为 0 项。
  - `manifest.json` 与 `packages-lock.json` 中开发依赖的计数都为 0；修复用的资产目录仍在。
  - ProjectSettings 基线：查该路径的版本历史（一例只有 4 个提交：初次入库、iOS `m_Automatic` 0→1、`legacyClampBlendShapeWeights` 0→1、把两处还原），并直接读服务器上的交付包逐字节比对：交付包是存储模式的 ZIP，可用 Python `zipfile` 流式读内层工程包里的 `ProjectSettings/`，与工作区 `diff -rq` 返回 0。
  - 交付包里审查目录、生成物目录（如 `Assets/ZZZ_GeneratedAssets`、`Packages/nadena.dev.ndmf/__Generated`）的条目数为 0。
- **其他要清的东西**：厂商美甲工具在 `Assets/` 里生成的整只头像备份预制体（两个工程都有；按 GUID 查无引用、`blueprintId` 为空后移出 `Assets/` 到工程根的备份目录，不删，打包时排除该目录）；NDMF 历史构建产物（`Assets/ZZZ_GeneratedAssets/` 里上千个、`Packages/nadena.dev.ndmf/__Generated/`）；工程根残留的离线编译 `.dll`/`.pdb`；本地开发包在 `manifest.json` 里用的绝对 `file:` 路径；放在通用工具目录里的订单专用生成脚本（一例 5 个脚本共 243,639 B，还带诊断菜单项；删前先编译确认没有别的引用，生成出的菜单与动画资产要留）、诊断截图与中间日志。AAO Trace And Optimize 组件是交付件的一部分，要留；`manifest.json` 里的 git 地址依赖会让客户打不开工程，必须删。
- **当时的修法**（人工作业，供理解机制）：清理后还要开 Unity 做构建自检（无 Missing Script、无 InternalErrorShader、描述符进入构建、T1 抽查修复点读回），再重打包。
- **在 Harness 流程里**：执行方只写 diagnosis.json：列出交付副本里残留的开发工具、审查代码、生成物目录与 ProjectSettings 差异，作为上传阻断项；清理由 Runtime 与人执行。
- **适用条件**：接手已交付工程做审查修复、再重交的场合；四个工程都要做同一套清理。
- **证据等级**：多工程验证

## 已交付的包要重打：覆盖前单独确认，旧包改名留底

- **症状**：修复了已交付工程，需要替换服务器上的交付总包；直接覆盖会丢掉客户手里那一版的原件。
- **机制**：交付包是对客户的正式记录；覆盖属于不可逆动作。
- **判据**（一例的重打验收）：原包加 19 个补件，文件数 11361 → 11380；新增 19、删除 0、原有文件的 CRC 与大小变化 0；在全新目录冷导入，导入前没有 `Library/`、`Temp/`、`Logs/`，11380 个文件逐个 CRC 一致、补件 SHA256 逐项一致；冷导入退出码 0、编译与依赖错误 0。
- **当时的修法**（人工作业，供理解机制）：几个工程修完一起重交，但覆盖服务器上的交付包前要单独问用户；得到授权后先核对原包 SHA256，再把原包改名留底，新包用原文件名入库。客户总包与工程存档按用途用不同格式（给客户的是存储模式 ZIP，存档是 7z），不要把存档规则套到客户包上。
- **在 Harness 流程里**：diagnosis.json 里写明「覆盖已交付包需要用户单独确认」；执行方不操作交付包。
- **适用条件**：已交付单的重交；四个工程的用户决定一致。
- **证据等级**：多工程验证

## 交付包缺了依赖包里名为 Library 的子目录

- **症状**：客户拿到的工程打开后缺 Gesture Manager 的 19 个脚本：`Packages/vrchat.blackstartx.gesture-manager/Scripts/{Editor,Runtime}/Library/` 下的文件不在交付包里，要额外发一个修复件补回（例如 `GmgAnimatorControllerHelper.cs`）。
- **机制**：与「打包排除规则没有锚定工程根，把依赖包里同名的 `Library/` 子目录当成 Unity 的 `Library/` 一起排除」一致；本案只记录了缺失现象，没有单独复现打包规则。
- **判据**：打包后列出所有路径中含 `/Library/` 的条目，确认只有工程根下的 `Library/` 被排除；在干净目录冷导入后编译错误为 0。
- **当时的修法**（人工作业，供理解机制）：排除规则写成只匹配工程根（如 `/Library/`），不要用不带锚点的目录名；已发出的包用修复件补齐后重打新包。
- **在 Harness 流程里**：diagnosis.json 里核对依赖包中路径含 /Library/ 的文件是否都在包内；缺失时写明证据交人。
- **适用条件**：用目录名排除规则打包 Unity 工程，且依赖包内含同名子目录。
- **证据等级**：单一案例（候选）

## 交付说明：内部版带出处，客户版只留客户用得上的信息

- **症状**：重交时交付说明要写清修了什么、额外素材从哪来；一例原本没有交付说明，另两例要补「额外附赠素材」的来源。
- **机制**：同一份说明有两类读者：内部复核需要每条事实的出处，客户只需要操作与授权信息。
- **判据**：
  - 客户版不含出处编号、待补标记、Markdown 粗体、内部路径与工具名（一例用 `grep -c` 检查这些模式为 0）；内部版每条事实在文末列「文件:行」出处。
  - 额外素材逐个厂商目录核查：在不在客户素材包里、是否付费、在工程里被哪些材质或场景引用（按 GUID 引用扫描确认）。一例核出 5 个目录里 3 个是额外付费素材、2 个其实来自客户素材包，纠正了「5 个都找不到来源」的旧说法。
- **当时的修法**（人工作业，供理解机制）：客户版结构：包内容（工程包、原始素材包、说明；不含 `Library`、`Temp`、`Logs`、`UserSettings`、`.sln`、`.csproj`，依赖由 VCC 按 `vpm-manifest.json` 还原）、工程里装了什么（场景、上传用的头像根、构建后菜单）、本次修了什么、素材来源、工具链版本、打开工程的步骤。额外附赠的付费素材注明「不在客户素材包内，客户如需更新或重装请自购」。
- **在 Harness 流程里**：diagnosis.json 里逐条写出处，供内部版使用；客户版说明由人整理。
- **还要写进说明的**：客户素材包里没有装的件及原因（例：骨骼比对不兼容，写明「不是漏做」）；从包外补装的素材与客户自备件分开列来源。
- **适用条件**：重交或首次交付的说明文档；四个工程按同一格式补写或预先挂进交付清单。
- **证据等级**：多工程验证

## 场景里有面捕版与非面捕版两个头像根：交付时只启用上传用的那个

- **症状**：同一场景放着两个结构相同的头像根（一个带面捕组件、一个不带）。审查工具因候选根不止一个而报错；静态解析误以为两个根都启用，实际读到的是非面捕根开、面捕根关；面捕根下还有一套服装默认启用，而另一根与换装轮盘默认档都不启用，编辑态和上传缩略图里会看到两套叠穿。
- **机制**：两个根各自带一份服装实例、MA 菜单和合并动画，所有修复都要两根一起做；哪个根启用决定了构建和上传的对象，默认显隐不一致只在运行时被换装轮盘掩盖。
- **判据**：
  - 场景里启用的头像根恰好一个，且是约定上传的那个（这几例为面捕根）；
  - 每次修复后，两个根的对应组件都已改（逐根列出差异）；
  - 两根下各对象的默认显隐与换装轮盘默认档一致。
- **工具口径要一致**：另一工程里，一个生成工具以原件根为主、再回填克隆根，另一个工具的形态键写入只写面捕根，两套口径相反，结果两个根上的 Shape Changer 不一致，重装面捕根后会丢失；改为所有同源根都写。
- **当时的修法**（人工作业，供理解机制）：按用户定下的惯例，交付时启用面捕根、关掉非面捕根但保留在场景；把默认显隐不一致的对象改成与另一根和默认档一致（场景差异只有一行）。这类惯例要写进方案，后续同类工程照做。
- **在 Harness 流程里**：在 plan.yaml 的 notes 里写明上传用哪个头像根；诊断里核对只启用这一个根。
- **适用条件**：Shinano、Rurune、Kaguya 素体的多个工程（面捕组件只在一个根上）；该惯例最早由用户在一个 Shinano 工程上定下，之后的工程照做。
- **证据等级**：多工程验证

## 洋红材质与空材质槽：先查是不是缺厂商前置包或厂商原样

- **症状**：上传前自检发现 1 个洋红材质、1 个空材质槽，原来的头像根也有同样问题。
- **机制**：洋红材质引用的 shader GUID 在工程、Packages、Library 里都找不到；该厂商工具的 17 个历史版本安装包里也都没有这个 GUID；读厂商说明才知道这个 shader 属于另一个需要单独购买的前置包，工程里从未导入。空槽则是厂商预制件本身就写着 `m_Materials: - {fileID: 0}`，且该对象缩放为 (0,0,0)。
- **判据**：按 GUID 在工程、依赖包、厂商各版本安装包（按 GUID 目录列 tar）里逐一查找；再读厂商说明找前置依赖。都找不到时就是缺前置包，不是导入遗漏或版本差异。
- **当时的修法**（人工作业，供理解机制）：两类都是厂商遗留；是否补买前置包、是否处理空槽交用户决定，在交付说明里写明。该例用户选择维持现状（计时圈出现时仍是洋红），不装前置包、不关该功能。
- **在 Harness 流程里**：diagnosis.json 里把洋红与空槽按「缺厂商前置包 / 厂商原样」分类写明，交用户决定。
- **适用条件**：带第三方小工具（计时器、姿势系统等）的头像。
- **证据等级**：单一案例（候选）

## SDK 面板的导入设置类错误：用 SDK 自带的修复，并确认不是本次引入

- **症状**：上传前 SDK 面板报 3 条错误：模型需要开 Read/Write、需要 Legacy Blendshape Normals、贴图需要开 Streaming Mip。
- **机制**：这些是厂商 FBX 与贴图的导入设置问题，不是菜单或装配改动引入的；修它们要改厂商资产的 `.meta`。
- **判据**：先确认错误是否由本次改动引入（原根是否同样报）；修后 SDK 面板错误为 0，剩余警告逐条判断是否需要处理（一例剩 5 条，都不需处理）。
- **当时的修法**（人工作业，供理解机制）：用 SDK 自身提供的修复函数处理（该例 2 个 FBX 开 Read/Write 与 Legacy Blendshape Normals、29 张贴图开 Streaming Mip），不手改 `.meta`；阶段任务若限定「只改派生层」，要先向用户说明需要动厂商资产的导入设置。
- **在 Harness 流程里**：diagnosis.json 里列出 SDK 面板错误及是否由本次改动引入；导入设置类修复由人或 Runtime 执行。
- **适用条件**：Unity 2022.3 + VRChat SDK3 上传前自检。
- **证据等级**：单一案例（候选）
