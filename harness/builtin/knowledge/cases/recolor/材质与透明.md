# 材质与透明案例

## 案例：照厂商样例自配的透明腿部材质，渲出来是实心肤色

- **症状**：厂商只给了别的素体的透明腿部样例材质，于是复制本素体的皮肤材质、换成 lilToon 透明着色器、挂上遮罩，做了「半透」与「全透」两份；渲出来都是实心肤色。
- **机制**：`material.shader = x` 只换着色器引用，渲染状态全留在原地：`_DstBlend` 是 0（Zero，混合退化成纯覆盖），厂商样例是 10（OneMinusSrcAlpha）；`_TransparentMode` 按语义猜了 2，厂商是 0；另有 9 个从 Standard 继承来的死关键字。
- **判据**：拿厂商样例逐属性比，只比渲染状态类（`_TransparentMode`、`_ZWrite`、`_ZTest`、`_Cull`、各混合因子与混合操作、`_AlphaToMask`、`_Cutoff`、`_AlphaMask*`），另比 `renderQueue` 与 `m_ShaderKeywords`。验收渲一张纯色背景图，透明件后面能看见背景色才算透，「颜色变浅」不算。
- **修法**：反过来做：复制厂商样例材质，再把颜色与贴图换成本素体的，渲染状态天然正确。
- **适用条件**：自己配一份与厂商同款的透明材质时（lilToon）。

## 案例：探针报「44 条属性都像玻璃」，其实贴图全部解析不到

- **症状**：拿一份别的素体的样例材质做逐属性比较，探针报「`_MainTex = null`，44 条属性都像玻璃类」，据此断定「它本质是一个玻璃材质」。结论全错。
- **机制**：那个素体没装进本工程，样例材质引用的贴图全部解析不到；`LoadAssetAtPath` 与 `GetTexture` 在「引用存在但资产不在本工程」时一样返回 null，被读成了「字段是空的」。`.mat` 的 YAML 里 guid 写得清清楚楚。
- **判据**：探针里的 null 要分清「guid 全 0 的真空」与「有 guid、本工程查不到」；写完先拿一个已知在本工程、一个已知不在的材质各跑一次。
- **修法**：读 `.mat` 的 YAML guid，或把两种情况分成两个结果打印。
- **适用条件**：跨工程或跨素体比较材质时。

## 案例：玻璃颜色染到了躯干，猜了两次机制都错，纯红满强一张定案

- **症状**：给腿部做玻璃叠色，颜色却染到了躯干、腿上一点没有。先后猜「遮罩 RGB 是全白」「读的是 alpha 通道」，两次都错，各改了一版代码；期间用 α = 0.45 的淡蓝紫渲了好几张，一张都分不出来。
- **机制**：淡色叠在肤色上，「没生效」与「效果反了」长得一样，看图对两个假说等价。实际是遮罩的极性与叠色层的预期相反。
- **判据**：把 lilToon 的 `_Color2nd` 设成纯红、alpha = 1 渲一张：躯干整片猩红、腿一点没染，「极性反了」一眼定案。
- **修法**：按正确的极性改接遮罩，再回到正常取值复验一次——极端值下成立的结论，在正常值下还要再验。
- **适用条件**：lilToon 叠色层配遮罩；任何低对比度、看图分不出差别的旋钮类问题。

## 案例：针织衫领口翻折处左右各一块黑斑：内层布的描边外壳穿了出来

- **症状**：一件 lilToon 带描边的针织衫（LOVACE Fog Knit），领口翻折处左右各有一块黑斑；只渲这一件时黑斑仍在。
- **机制**：两层布贴得很近，内层布的描边外壳（向外扩的背面）从外层布之间透了出来。
- **判据**：在 Play 里把构建副本上这件材质的描边宽度临时设 0，同机位再渲：黑斑消失，就是描边；仍在，再查网格缝隙或翻面。
- **修法**：复制材质只挂给这一件（厂商原材质被 8 个预制体共用，不改原件），把 `_OutlineZBias` 调到 0.005：黑斑消失、轮廓线保留。改完正面、侧面各渲一张，确认近处的轮廓线没被自身布料盖掉。修前修后同机位混排盲测，修后零指认。
- **适用条件**：lilToon 带描边、两层布贴近的折边与翻领。

## 案例：发型「罕见视角下透过面板看不见」，按小包围盒去修，偶发变成了常驻

- **症状**：透过一块半透明的全息面板配饰看后面的发型，罕见视角下发型不显示。源场景里发型各渲染器的包围盒只有 0.1–0.5 m，看着像典型的「包围盒太小、被视锥剔除」，于是把包围盒改大，同时改了材质的 `_ZWrite`；改完现象从偶发变成了常驻。
- **机制**：三个错叠在一起。① 没在交付态上证实病因：烘焙后一量，AAO 已把 13 个渲染器合并成一个，MA MeshSettings 把包围盒统一改成 2×2×2，出界骨为 0——交付件里根本没有小包围盒。② 把「改了没用」当成「改了无害」：渲染器包围盒的中心决定透明排序（按中心到相机的距离排），盒子从贴着头撑到约 1.1 m 的骨云盒，中心一挪，原本时前时后就变成恒定在后。③ 两个未验证的改动同时下去，出了回归无法归因，只能全撤重来。
- **判据**：报缺陷先在烘焙克隆体上量；透明类现象先出队列表（每个材质槽的 `renderQueue`、`_ZWrite`、着色器名，抓屏类按队列排序），用可证判据定位后再改。
- **修法**：用 `PrefabUtility.RevertPropertyOverride` 精确撤回无效改动并回读计数；一次只落一个改动，验完再下一个。
- **适用条件**：透明件与发型、配饰叠在一起的头像；使用 AAO 与 MA MeshSettings 的工程。

## 案例：离屏验收图里全息面板成了实心色块，换成普通透明着色器又成了实心黑板

- **症状**：离屏验收图里，一块本该透明的面板是一整块不透明的肤色矩形，被当成「缺陷复现」并据此判了病因。随后想「换成普通透明着色器就好了」，面板变成了一块实心黑板。
- **机制**：面板材质用的是 lilToon 折射类着色器（走具名 GrabPass），队列 3000、`_ZWrite = 1`，而 `_RefractionStrength = 0`——作者不是要折射，而是拿抓屏合成当「透明」用，材质本身没有 alpha。当时那条离屏出图路径里 GrabPass 不工作，于是被渲成实心；换掉着色器等于拿掉了唯一的透明来源。
- **判据**：离屏图里「本该透明的东西变成实心」时，先查它的着色器是不是抓屏类；再用一个人为制造的抓取点问题做正对照，确认这条出图路径能还原抓屏，才拿它的图当判据。
- **修法**：以队列表为第一判据；观感在能还原抓屏的通道里（Play 模式 Game 视图，或已过正对照的离屏路径）确认；不替换折射强度为 0 的抓屏着色器。
- **适用条件**：厂商件用抓屏类着色器做透明的头像；离屏出图路径的能力随图形 API 与编辑模式或 Play 模式而不同。
