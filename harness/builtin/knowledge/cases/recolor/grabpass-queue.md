# 改色与透明：抓屏材质队列的案例

## 透过抓屏宝石看不见头发：换色 clip 把高队列副本换回了厂商原件

- **症状**：用户反馈「开启头部发饰时，透过它看到的发型是透明的」。数据上，48 个头饰开启状态里有 24 个的抓取点在 2450，队列 ≥2450 的头发（2460）、脸部透明层、丝袜、嘴部挂饰透过头饰宝石与窗口消失。
- **机制**：lilToon 的宝石、折射类材质用具名 GrabPass `_lilBackgroundTexture`，每帧只抓一次，抓取点是当帧第一个用它的材质的队列；队列不低于抓取点的透明物不会出现在抓屏图里。早先已把场景里的抓屏材质推到 3050、把熊和前辫绒毛拉到 2890 修过一次，但自建的「头饰色」换色动画仍引用厂商原件（队列 2450），构建后每帧又把副本换回原件。
- **判据**：
  - 用数据直接算抓取点：可见材质里谁用这个 GrabPass、最小队列是多少、队列不低于它的可见物有哪些；逐状态算，不必每次渲图。
  - 修后该例 28/28 个头饰开启状态抓取点为 3050；透明消失检测报数 24 → 1（剩下的是两个同队列窗口互相看不见，用户签字接受）；盲测两家只指认修前。
- **当时的修法**（人工作业，供理解机制）：复制厂商材质为队列 3050 的副本，把换色 clip 的 `m_Materials.Array.data[3]` 四个关键帧改指副本；生成器按路径替换，副本放在固定目录就会被自动命中。
- **在 Harness 流程里**：改色产物不让换色动画引用低队列的厂商原件；Runtime 的抓屏链读数显示抓取点过低时写明证据交人。
- **走过的弯路**：更早的一次修法怀疑是视锥剔除，改了发型包围盒与窗体材质，结果客户说「本来是偶发，改完变成常驻」，两处改动全部撤回。源场景里的小包围盒只是烘焙前的中间态：构建后 AAO 把 13 个发型渲染器合并，MA Mesh Settings 统一改写了包围盒，出界骨为 0。
- **未证实**：具名 GrabPass「同相机、同帧、第一个同名批次抓一次」经 Unity 手册部分印证，lilToon 2.3.4 的五个抓屏 shader 把纹理名写死为 `_lilBackgroundTexture`；因此别人的头像或世界里先用它的低队列材质可能把抓取点提前，这可能是「偶发透明」的来源，未在 VRChat 实机验证。用户选择的对策是复制抓屏 shader、改成私有纹理名，实施结果未见记录。
- **适用条件**：Kaguya 素体、lilToon 宝石/折射材质与自建换色动画并存的工程。
- **证据等级**：单一案例（候选）

## 抓屏材质挡住身后的高队列物体：先做隐藏或抬队列对照，无可见后果就不改

- **症状**：两个工程里，小件的宝石、液滴、折射丝袜等用 lilToon Gem 或 RefractionBlur（抓屏，默认队列 2900），抓取点在 2900，身后队列 2980–3001 的物体（身体附加层、眼镜、头发阴影、绒毛辫、目元粒子、包的半透明壳）理论上透不出来。
- **机制**：抓取点之后渲染的物体不在抓屏图里；但件很小时，看不到的区域也很小。
- **判据**：
  - 同机位渲「原样」与「隐藏这几件」：像素差只在这几件自身（2–5 千像素），没有别的东西消失、没有黑块；
  - 或在运行时把这些材质实例抬到 3050 再渲头部 8 个方位：像素差只在随机发射的粒子上；第二个模型盲测判两半相同。注意渲图工具每次渲完会还原材质，运行时改队列只在当次渲图内有效。
- **当时的修法**（人工作业，供理解机制）：判定无可见后果，不改厂商队列（抬队列会改变与 3000 档透明物的先后，没有可见收益）；若要改，修后抓屏链全部状态的抓取点应 ≥3000。
- **在 Harness 流程里**：判为无可见后果时在诊断里写明对照证据，不改厂商队列。
- **适用条件**：Rurune、Shinano 素体配带 lilToon 抓屏小件的服装；另一工程（Kaguya）的同类问题有可见后果：换色动画把已调到 3050 的材质副本换回了队列 2450 的厂商原件，头发透过宝石消失。
- **证据等级**：多工程验证
