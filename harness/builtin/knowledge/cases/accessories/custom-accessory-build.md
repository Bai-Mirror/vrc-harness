# 配饰：自建饰品装配与构建期校验的案例

## Unity 导入会按 UV 缝拆点：顶点数与索引类判据要先按位置焊接

- **症状**：一件口腔饰品的装配脚本反复在几何判据上失败：Blender 里网格 2368 个顶点，导入 Unity 后顶点数对不上，断言失败并回滚；舌面按原始索引算连通块得到 2 块，构建被拒。
- **机制**：Unity 导入 FBX 时会沿 UV 缝与硬边把一个位置拆成多个顶点（该例 540 个拆分顶点只对应 494 个位置；刚性饰品 1701 个拆点只对应 412 个唯一位置）。按顶点数、顶点索引判断的连通性、归属和分类都会因此失效。
- **判据**：几何判据先把顶点按位置焊接成组再算：容差取 1e-6 m（0.001 mm），过小会漏焊浮点拆点，过大会误焊近邻；连通性按焊接后的三角索引判断，再映射回全部原始索引；同一位置的拆点若骨权重分类冲突，要明确报错。用带 UV 缝的小网格做自测：原始索引 2 块、焊接后 1 块。
- **当时的修法**（人工作业，供理解机制）：所有基于顶点的断言改成「按位置焊接后的口径」；不要把 Blender 顶点数写进 Unity 侧的断言。
- **在 Harness 流程里**：执行方不写构建插件。读 Runtime 的几何读数时，按顶点数或索引算的判据先怀疑拆点；本流程没有对应通道，遇到时写明证据，停下交人。
- **适用条件**：在 Unity 里对导入网格做拓扑或顶点级判断的脚本（Kaguya 素体上的自建口腔饰品）。
- **证据等级**：单一案例（候选）

## 按名字找骨会命中服装骨架里的同名骨：用 Animator 的人形骨定位

- **症状**：装配脚本按名字找 `Head`，报「Sequence contains more than one」，命中了服装预制体自带骨架里的同名骨。
- **机制**：合骨前，服装预制体里带着一整套与素体同名的骨骼（Hips、Head 等）；按名字全局查找会拿到多个结果，甚至拿错。
- **判据**：查找结果是否唯一、是否位于素体的 `Armature` 之下。
- **当时的修法**（人工作业，供理解机制）：用 Animator 的人形骨映射取骨（`GetBoneTransform(HumanBodyBones.Head)`），或只在素体根下的直属骨架里查；需要身体网格时优先取头像根下直属的身体对象。
- **在 Harness 流程里**：执行方不开 Unity、不改场景；挂点要由有对应设计输入的阶段落实，用人形骨（Head、Hand 等）确定，不按骨名全局查找；出现同名骨歧义或没有这样的设计输入时，写明证据，停下交人。
- **适用条件**：场景里有未合并的服装预制体（MergeArmature 在构建时才合骨）的工程。
- **证据等级**：单一案例（候选）

## 构建期校验器：一次收集全部问题再报，装配验收要对照方案清单回读

- **症状**：
  - 校验器遇到第一个问题就停，于是一轮只暴露一条（先是某个形态键分类，再是另一个无驱动的键，再是构建期生成的口型键），来回十几轮；
  - 装配脚本的验收只看它自己写的安装报告，漏装的 PhysBone 直到第 12 轮验证才被发现。
- **机制**：首错即停的校验把一次能看完的问题拆成多轮；「安装脚本自报成功」不等于「方案要求的组件都装了」。
- **判据**：校验器输出全部问题的汇总（一例一次汇总 16 条，其中 13 条同属一类，一次裁定）；装配验收按方案清单逐项回读实际组件（PhysBone、碰撞体、材质槽、菜单项、参数），不读安装脚本的自报字段。
- **当时的修法**（人工作业，供理解机制）：校验器改为「收集全部、分级（记录级 / 致命）后再报」；验收脚本以方案清单为准逐项读回；预算类检查（例如「整只头像表达参数预算通过 = false」）一律当作上传阻断，不能只记录。
- **在 Harness 流程里**：在设计输入里逐项列出方案要求的组件（PhysBone、碰撞体、材质槽、菜单项、参数），让 Runtime 的回读有清单可对；预算类检查失败一律按上传阻断写进 diagnosis.json。
- **适用条件**：给头像写构建期插件或装配脚本的场合。
- **证据等级**：单一案例（候选）

## 构建后还要按名字断言的对象：先加进 AAO 的排除列表

- **症状**：饰品的构建后断言大面积失败：跟随对象与渲染器「缺失」，另有约 1800 条「改名」误报。
- **机制**：Avatar Optimizer 的自动优化会合并网格、改名形态键、删除它认为没用的对象，构建后按原名、原对象找不到。
- **判据**：断言失败时先看失败对象是否被 AAO 合并或改名；只断言与本饰品有关的键和对象，不把无关的 `AAO_Merged_*` 当错误。
- **当时的修法**（人工作业，供理解机制）：在 AAO 运行前把需要保留原名的对象（身体、饰品的独立链渲染器、跟随对象）加入 Trace And Optimize 的 `debugOptions.exclusions`；断言只查本饰品的键、跟随对象和材质槽。
- **在 Harness 流程里**：在 optimize 的 design.json 用 aao.rationale 说明哪些对象需要保留原名以便核对；设计输入没有排除项字段时写明证据交人，不改 AAO 默认配置。
- **适用条件**：启用 AAO Trace And Optimize、又需要构建后按名验证的工程。
- **证据等级**：单一案例（候选）

## 以画质或性能为由改方案之前先实测：高面数的光滑管面并不更闪

- **症状**：执行方以「几万个三角形会亚像素闪烁」为由，把饰品链改成低模；低模版（14,568 三角）特写出现碎高光和凹口黑坑，不可用。
- **机制**：闪烁与否取决于实际渲染表现，不是面数本身；推测没有经过测量。
- **判据**：同机位、同采样设置对比渲染：光滑管面版并不比低模更闪；中等面数版（17,928 三角）碎高光与黑坑都消除，最终选用约 5.8 万三角的版本（整链预算由用户放宽到 ≤60k）。
- **当时的修法**（人工作业，供理解机制）：提出性能或画质理由时先给实测；预算约束由用户明确（本例用户直接给了整链三角上限）。
- **在 Harness 流程里**：设计输入的 rationale 里只写有实测依据的画质或性能理由；没有测量结果时写「未测」并交人决定。
- **适用条件**：自建饰品的建模与选型。
- **证据等级**：单一案例（候选）
