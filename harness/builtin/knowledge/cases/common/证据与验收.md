# 案例：证据、验收与改动边界

跨阶段的验收与改动边界实例。工程身份已匿名。每例一节，按「症状、机制、判据、修法、适用条件」写。

## 案例：元数据写着新算法，权重数组却与旧版逐项相同

- **症状**：下游的扫掠测量与渲图全部基于一份「新版」权重数据，直到后面的回归才发现结果不对。
- **机制**：生成脚本算出了新权重却没有写回；数据文件的元数据（`algorithm`、`checks` 字段）写着新算法（盒形核），`weights` 数组 494/494 项与旧版逐项相同。验收只看了元数据。
- **判据**：产出是数据文件时，抽一个字段同时与「上一版」和「按新算法重算」比较：等于上一版就是没写回；对不上新算法就是算错了。
- **修法**：重跑并确认写回；验收比较内容，不比较描述内容的元数据。
- **适用条件**：任何由元数据描述内容的产出（权重表、参数表、清单、配方）。

## 案例：执行方自验 382 组全过，独立核查仍查实 5 个缺陷

- **症状**：执行方报告菜单组合自验 382 组全部通过、差异为 0。
- **机制**：自验只验了它自己的假设。独立核查（多路只读核查从 YAML 与源码取证，每条失败再由另一方尝试推翻）查实 5 个缺陷，全在自验的前提之外：①真实构建链改写了 Write Defaults，而自验按 WD=False 模拟；②轮盘中间值与远端量化，自验只测了整档值；③4 个及以上材质槽的渲染器：生成器循环写死 3 槽，自检只覆盖了一件衣服；④Modular Avatar 实际取哪个字段当菜单名。
- **判据**：菜单、动画层、配色这类「组合多、靠推理验」的交付，验收换四个视角核：构建链的真实语义（VRCFury、Modular Avatar、NDMF 会改什么）；边界与中间值（轮盘中间、k/127 量化）；覆盖面（每件、每槽，不抽样）；工具实际读哪个字段（读插件源码）。核查结论写到「路径:行」，让第二个人能复核。
- **修法**：按四个视角补测并修复；自验结果与独立核查结果分开记录，自验不能替代核查。
- **适用条件**：任何带自测的生成器或执行方自验。

## 案例：按目录提交，把并行任务刚写的文件一起带走

- **症状**：一次提交里多出不是本任务改的文件，提交信息与内容张冠李戴；另一次写记录的脚本因缩进错误没执行，后面用 `;` 接着的提交照跑，只提交了别的文件，提交信息却写着「验收完成」。
- **机制**：两个并行任务写同一目录，一方按目录提交，把另一方 30 秒前写入的文件带了进去；另一种触发是「先 `git add` 点名路径，再提交整个暂存区」，别人已暂存的文件被一起提交。编辑命令与提交命令之间没有「成功才继续」的连接。
- **判据**：提交后 `git show --stat HEAD` 只有自己点名的路径；提交前看得到编辑脚本打印出的确认值。
- **修法**：提交只点名文件，不点目录；确需点目录，先 `git status -- <目录>`，不是自己改的不带；用只提交点名路径的语义（`git commit --only -- <文件>`）；编辑与提交之间用 `&&`；搬移文件（`git mv`）后只点名新路径，旧路径的删除已随搬移暂存，点名盘上已不存在的旧路径会让整个提交中止；提交前用 `git status --porcelain -- <旧目录> <新目录>` 看 `R`、`D` 行都已暂存。发现带了别人的文件时，在记录里注明，不要 reset 别人的工作。
- **适用条件**：同一仓库里多个任务并行写入。

## 案例：测试副本与解压件被当成产物提交

- **症状**：仓库里出现 GB 级的工程副本、被提交成 gitlink 的克隆目录、厂商包的解压件。
- **机制**：自测每跑一次就硬链接拷出一份约 3.9 GB 的工程副本且不删；测试用的 `git clone` 放在未被忽略的临时目录里，被提交成 gitlink；厂商包解压到未被忽略的临时目录后被一起提交。
- **判据**：提交前 `git status --short` 里不应出现临时目录、工程副本或解压件。
- **修法**：测试克隆、工程副本、厂商包解压一律放进被忽略的临时目录，并在 `finally` 里删除；提交前单独看一眼临时目录有没有混进来。
- **适用条件**：写自测、需要工程副本或解压素材的任务。

## 案例：预演没在副本里做，真工程被同步脏了

- **症状**：一次「干跑」用相对工程名，把三个真工程里的审查工具目录同步脏了；随后又在真仓库里 `git checkout` 并删了 14 个文件来收拾，而事前没有记录原状态。另一次写给他人执行的步骤里，heredoc 加了引号导致变量不展开，`revert --all` 之前没查工作树是否干净（会丢未提交的场景改动）。
- **机制**：预演与真执行共用同一套路径与仓库；步骤书把 Unity 前后的 shell 写在同一段里，复制执行就跨过了 Unity 那一步；步骤没有先在不依赖 Unity 的部分上干跑。
- **判据**：预演只在副本里做；跑完预演，真仓库的 `git status` 与跑之前一致；凡会动工作树的步骤，第一行写「`git status` 非空就停」。
- **修法**：Unity 前后的 shell 拆成独立代码块；相对路径先 `cd` 到确定目录；写给他人执行的步骤，先干跑其中不依赖 Unity 的部分；真仓库里禁止 `checkout` 与删除，出错就停下报告。
- **适用条件**：写预演脚本或写给他人执行的操作步骤。
