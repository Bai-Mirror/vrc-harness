# 方案：需求落成验收项的案例

## 订单写明的兼容性要求没进验收：交付后才查出面捕破面与脸颈色差

- **症状**：客户下单时写明「面捕要与捏脸、贴图兼容」，还点出了已知风险（一种面捕方案与捏脸不兼容、另一种与脸部贴图不兼容）。首次交付时工程侧从未检查这条要求，复审时才查出面捕闭眼破面与脸颈色差。
- **机制**：需求原话没有变成可执行的验收项，交付检查只覆盖默认状态，面捕参数驱动下的状态从未进入测试。
- **判据**：方案阶段把订单里每条兼容性要求改写成验收项，写清「在什么参数驱动下、读哪些键或看哪张图、什么结果算通过」。例：「面捕参数驱动下，捏脸键与贴图的冲突清单（或 0 条）」。
- **当时的修法**（人工作业，供理解机制）：每条要求在方案里对应一个验收项和负责阶段；交付诊断逐条回填证据，没有证据的要求不能标为满足。
- **在 Harness 流程里**：plan.yaml 的 notes 字段表定为一两句，只点名订单里的兼容性要求与它们不在 Runtime 检查里这件事；逐条验收项（参数驱动状态、读哪些键、何为通过）写不进方案，交人补验收，交付诊断逐条回填。
- **适用条件**：带面捕、捏脸或贴图定制要求的订单（该例为 Kipfel + Fermata 面捕补丁）。
- **证据等级**：单一案例（候选）

## 面捕预设要对上客户的设备：素材里没有设备信息就问

- **症状**：面捕版头像的预设是按某几种头显组合（HD Quest/Pico 等）装的，客户实际用什么设备没人确认过。
- **机制**：不同面捕设备对应不同预设，选错时面捕效果不对；客户素材与订单里常常没有设备信息。
- **判据**：方案阶段查客户素材与订单是否写了设备；没有就列为待用户确认项，不自行假设。
- **当时的修法**（人工作业，供理解机制）：该例用户确认素材里没有设备信息后，决定维持现有预设，并把这个决定写进记录。
- **在 Harness 流程里**：在 plan.yaml 的 notes 里写明面捕设备是否已确认；未确认的列为待用户确认。
- **适用条件**：带面捕的交付（Shinano 素体一例）。
- **证据等级**：单一案例（候选）

## 哪些事要交给用户亲自做：按「拦不拦交付」排出人工卡口清单

- **症状**：全定制单做到一半，有几件事执行方既做不了也不该替用户定：捏脸四组候选选哪组、客户只说「蓝」的眼色落在哪一档、厂商工具需要在编辑器里手点执行、狐耳的缩放系数、只有真机才能验的项目。混在进度里容易被遗漏或被执行方自行拍板。
- **机制**：这些是审美决定、需要图形界面操作的厂商工具，或者证据不足以定量的比例；厂商商品图只有一张 3/4 角度插画时量不出可靠比例，两个子代理都拒绝自己拍一个系数，这是正确的。
- **判据**：清单里每一项写明：拦不拦交付、依据（候选图、实测色值、尺寸，例：狐耳包围盒 0.332 × 0.178 × 0.139 m，相对素体身高 1.179 m 约为宽 28.2%、高 15.1%）、用户具体要做什么；不拦交付的项先按默认值交付（狐耳 k=1）。
- **当时的修法**（人工作业，供理解机制）：把清单单独成文，和交付前清理清单放在一起；用户逐项拍板后记录结果（该例用户看过 1.0 / 0.9 / 0.8 三档对照图后维持 1.0）。平台相关的改动在编辑器里验不出来，列为真机测试的人工项。
- **在 Harness 流程里**：在 plan.yaml 的 notes 里列出需要用户亲自决定或执行的事项，以及是否拦交付。
- **适用条件**：全定制单（捏脸、配色、配饰装位）的交付前阶段。
- **证据等级**：单一案例（候选）
