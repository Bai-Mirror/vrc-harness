# 装配：新买服装套上素体的贴合案例

## 衣服整体悬空：实例把厂商烘在预制件根上的缩放覆盖成了 1

- **症状**：一件新衣（Trinity2088「The Velour」Kaguya 版）套上后整件上移到接近头部高度，两条袖筒平展悬在手臂上方约 0.23 m；看图还以为「右臂没有袖子」。MergeArmature 的全部字段与厂商预制件一致。
- **机制**：
  1. 厂商把适配各素体的缩放烘在预制件根的 Transform 上：Kaguya 版根 `m_LocalScale` 为 0.807521，Rurune 版 0.95，Mizuki 版 1。场景实例把根缩放覆盖成 (1,1,1)，抹掉了厂商值，衣服骨架比素体大 1.2383 倍。
  2. Modular Avatar 合并骨骼时改写 bindpose 以保持网格的世界外观（`MeshRetargeter.RetargetBones`：新 bindpose = 新骨的 worldToLocal × 原骨的 localToWorld × 原 bindpose），不会替你缩放或重定向。骨架静置位姿差多少，衣服就偏多少。
- **判据**：
  - 主干骨吸附：19 根主干骨都「合并到同名骨、角度差 0」，但位置差 dPos 很大（髋 0.174 m、手 0.245 m）就是缩放问题，不是没合上；修后 dPos 最大 0.002 m，衣服髋高与素体髋高之比为 1.000000。
  - 袖子顶点到对应手臂骨的平均距离：0.235 m → 0.062 m（修后约为袖子半径）。
  - 「右袖不见」要用数据排除：主导骨为右臂的顶点 3090 个、右袖三角 5069 个，右袖在，只是和左袖一起被抬走了。
- **当时的修法**（人工作业，供理解机制）：只还原实例根的这一个属性：`PrefabUtility.RevertPropertyOverride(根.transform, "m_LocalScale")`。实例化厂商预制件时不要覆盖根缩放。
- **在 Harness 流程里**：Runtime 实例化厂商预制体时保留根 Transform，执行方改不了根缩放；报主干骨位置差大或衣服悬空时，先查厂商预制件的根缩放与适配版比例，写明出处，停下交人。
- **适用条件**：Kaguya 素体；厂商按素体烘缩放到预制件根上的服装。
- **证据等级**：单一案例（候选）

## 没有对应素体版本的衣服：按髋高比例缩放根，由用户拍板

- **症状**：一件新衣（Dollit「PuNyaNya」）商品页写支持 Kaguya，但下载到的文件里只有 Rurune 版；原样套上后整件上移 13–18 cm，袖套水平悬在手臂上方约 0.16 m。
- **机制**：Rurune 版预制件根缩放为 1，骨架比 Kaguya 大 1.1765 倍；与上一例同理，合骨保持世界外观，不会自动缩放。
- **判据**：用素体髋骨高度与衣服髋骨高度之比算缩放（0.73061 / 0.85952 = 0.850022），并与同一体系其他厂商给出的比例互证（另一厂商 Kaguya/Rurune 版根缩放之比 0.807521 / 0.95 ≈ 0.85）；修后 19 根主干骨 dPos 最大 0.0017 m，袖套到手臂骨距离 0.164 → 0.050 m，左右对称。
- **当时的修法**（人工作业，供理解机制）：首选下载并换用厂商的 Kaguya 版文件；拿不到时，经用户同意把 Rurune 版实例根缩放设为 0.850022。用户当时的疑问是「有同体系适配件为什么还要自己缩放」，要讲清：一件是还原厂商值，一件是按比例推算、非厂商明示。
- **在 Harness 流程里**：借用其他素体版本属于选型决定：在 plan.yaml 的 notes 里写明缩放依据与风险，经用户确认后再装配。
- **适用条件**：Kaguya 与 Rurune 同体系素体之间借用服装；比例只在这两个素体间实测过。
- **证据等级**：单一案例（候选）

## 判断合骨是否成功：截到 Transforming 阶段的克隆上数骨骼槽

- **症状**：想确认新衣的骨骼是否都合到了素体骨上，但跑完整构建后衣服网格已被合并进身体、衣服对象都被销毁，量不到；把优化组件的 `enabled` 关掉也没用。
- **机制**：Avatar Optimizer 的主流程注册在 NDMF 的 Optimizing 阶段，会合并网格、删除骨骼，并且不看组件的 `enabled`。
- **判据**：
  - 反射调用带阶段参数的 `AvatarProcessor.ProcessAvatar(克隆, BuildPhase.Transforming)`，跑到 Transforming 即停，衣服层级保留。
  - 对该件每个蒙皮网格的 `bones[]` 逐槽判断是否落在素体 `Armature` 子树内：三件分别 445、927、3556 个骨槽，未落在素体骨下的都是 0，`nullBone` 为 0。
  - 衣服自带骨中被同名素体骨取代的会被删除（78 个），其余（物理骨链等）留下并挂在素体骨下；判断「有没有同名骨」要用合并前的素体骨名集合，用合并后的集合会自指。
- **当时的修法**（人工作业，供理解机制）：合骨检查一律在阶段截断的克隆上做，并把报告写成文件；单次处理超过 20 秒时不要在远程执行接口里同步等待，改为延迟调用 + 报告文件 + 单飞锁（一次同步长调用曾引发编辑器原生崩溃）。
- **在 Harness 流程里**：执行方不跑构建；读 Runtime 的合骨读回（映射骨数、未落在素体骨下的骨槽数）判断。
- **适用条件**：NDMF + MA + AAO 工程；Kaguya 素体上三件新衣实测。
- **证据等级**：单一案例（候选）

## 袖长左右不一样：看网格权重定性，不看渲图

- **症状**：修正缩放后，一件新衣的右袖比左袖短。两个视觉模型对厂商三视图的结论相反：一个说设计本就不对称，一个说是对称长袖、只是摆拍屈臂。
- **机制**：袖子长度由网格本身决定，可以直接量。
- **判据**：右臂链顶点对 `Right Hand` 的权重为 0，而左侧对 `Left Hand` 有 548 个顶点；静置姿势下左袖口越过手腕 4.7 cm，右袖口离手腕 9.2 cm。网格本身右袖短，是厂商设计，不是装配缺陷。
- **当时的修法**（人工作业，供理解机制）：不修；把数据结论写进记录，视觉模型的结论与数据相反时不采纳。
- **在 Harness 流程里**：诊断里以网格权重数据定性，视觉模型的结论与数据相反时不采纳。
- **适用条件**：任何「左右不对称」「某部件缺失」类的视觉疑问。
- **证据等级**：单一案例（候选）

## 把厂商服装放进自建分组后 Bone Proxy 找不到目标：改 subPath

- **症状**：构建报 MA-1100（Bone Proxy 目标为空），某套服装附带的小刀机关失效。
- **机制**：厂商 Bone Proxy 的 subPath 假设服装根名为厂商原名、并且直接挂在头像根下；装配时把服装放进了自建分组并改了名（`_Outfit/Outfit_<名>`），路径解析不到。
- **判据**：构建日志里的 MA-1100 条目逐个定位到组件；修后 Play 读回道具挂到目标节点下、世界位置不变，构建不再报 MA-1100。另外两个命中来自不进头像的备份预制体，可忽略。
- **当时的修法**（人工作业，供理解机制）：在场景实例上把 subPath 改成实际层级（例 `_Outfit/Outfit_<名>/KnifeGimmick_Shinano/ConstRoot/ConstItem`），所有头像根都改，作为预制体覆盖，不改厂商预制件。
- **在 Harness 流程里**：执行方设不了 Bone Proxy 的目标（装配层由 Runtime 按方案重建）；构建报 MA-1100 时写明组件路径证据，停下交人。
- **适用条件**：把厂商服装重命名或放进分组的装配方式；Shinano 素体上实测。
- **证据等级**：单一案例（候选）
