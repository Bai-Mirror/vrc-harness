# 建工程：打开与运行 Unity 带来的副作用案例

## 首次打开工程：lilToon 启动钩子把 lilToonSetting.json 改成全开

- **症状**：只是打开工程（该组案例为 `-batchmode -force-vulkan` 首次导入），版本控制里就出现 `ProjectSettings/lilToonSetting.json` 的改动：一例中 30 个 `LIL_FEATURE_*` 从 false 变成 true（如 `MainGradationTex`、`Main2ndBlendMask`、`AnisotropyTangentMap`）。
- **机制**：lilToon 的编辑器启动钩子在打开工程时按需开启功能开关，这是设计行为；经核查不影响上传包。
- **判据**：打开前后对比 `lilToonSetting.json`；改动只落在 `LIL_FEATURE_*` 开关上，且没有其他资产变化，就归为这一类。
- **当时的修法**（人工作业，供理解机制）：不要当成工程被损坏去排查；按工程约定，要么在提交前还原，要么把两版分别提交留作对比（有一例就是把 true 版另行提交）。与本次任务相关的改动不要和它混在同一个提交里。
- **在 Harness 流程里**：执行方不开 Unity；诊断时把 lilToonSetting.json 的这类差异归为已知副作用，不当作缺陷。
- **适用条件**：装有 lilToon 的 VRChat 头像工程，首次在新环境打开或重建 `Library/` 时；三个工程都出现过。
- **证据等级**：多工程验证

## Unity 会话后 ProjectSettings 漂移：形态键 clamp 开关与 iOS m_Automatic

- **症状**：在编辑器会话里跑过实测后，`ProjectSettings` 出现两类非本次意图的改动：`legacyClampBlendShapeWeights` 从 0 变成 1；iOS 支持设置的 `m_Automatic` 从 0 变成 1。一个工程先后两次出现 clamp 变化，另一个工程的版本历史里两处都出现过、后来被一并还原，第三个工程每次进 Play 后都要还原 clamp。
- **机制**：VRChat SDK 初始化时其 EnvConfig 会改写 clamp 开关；早先有记录把它归因于「Play 构建」，后来一次只进出 Play 的实测没有改它，更准确的说法是 SDK 初始化时发生（进 Play 往往会触发 SDK 初始化）。开关为 1 时，超过 100 的形态键权重会被截断。`m_Automatic` 的改写来源未查，只知道出现在跑过编辑器会话之后。
- **判据**：形态键相关的实测前后，这个开关是什么值？工程提交的值是 0。若实测中出现过大于 100 的权重，开关值会改变结论；一例全体帧最大权重 75.1，截断不影响结果。交付前用版本历史找出只含这两处改动的提交。
- **当时的修法**（人工作业，供理解机制）：每次会话结束后核对并还原为工程提交的值再提交；实测报告里写明测量时的开关值（一例的验证脚本把开关的前后值写进报告，前后不一致就报错）；交付前把 ProjectSettings 与交付基线逐字节比对。
- **在 Harness 流程里**：执行方不开 Unity；读 Runtime 的形态键实测时核对报告里的 clamp 值，差异写进诊断。
- **适用条件**：装有 VRChat SDK 的工程，在编辑器里触发 SDK 初始化的会话。
- **证据等级**：多工程验证

## 批处理保存场景后 m_IndirectSpecularColor 被重算

- **症状**：批处理脚本改完组件并保存场景后，场景文件除预期改动外，`m_IndirectSpecularColor` 也变了。
- **机制**：Unity 保存场景时会重算环境光相关的缓存值，批处理环境下算出的值与原值不同。
- **判据**：保存后看场景文件差异；除本次预期改动外只剩 `m_IndirectSpecularColor` 一处变化，就是这个副作用。
- **当时的修法**（人工作业，供理解机制）：提交前把该字段手工改回原值，让场景差异只包含本次改动。
- **在 Harness 流程里**：执行方不存场景；产物差异里只有这一项时归为副作用，写明即可。
- **适用条件**：用批处理脚本修改并保存场景的工程；两个工程共出现三次。
- **证据等级**：多工程验证

## 进 Play 前先存盘：Linux 下进 Play 多次段错误崩溃

- **症状**：在 Linux 主机上用 Vulkan 跑 Unity，进 Play 时编辑器多次段错误（SIGSEGV）退出；一次在还原组件后没存盘就进 Play，改动全部丢失。同一会话里第 6 次进 Play 时又崩溃过。
- **机制**：崩溃发生在驱动层，与工程改动无关，但会带走未保存的场景改动。
- **判据**：进 Play 前场景是否已保存、版本控制里是否能看到本次改动。
- **当时的修法**（人工作业，供理解机制）：先保存场景再进 Play；崩溃后重启 Unity，先核对场景改动是否在盘上，再继续。
- **在 Harness 流程里**：执行方不进 Play；Runtime 报编辑器崩溃时写明证据交人。
- **适用条件**：只在 Linux 宿主机上以 Vulkan 运行 Unity 2022.3 时观察到；其他平台未验证，不要推广。
- **证据等级**：单一案例（候选）

## 编辑器模态框会卡住自动化：保存确认、安全模式、参数超限弹框

- **症状**：远程驱动编辑器时，桥接卡住、只能杀进程。三个工程里出现过三种模态框：退出编辑器时的「是否保存场景」（两个工程）；审查代码在 Unity 里编译失败、开工程时弹「Enter Safe Mode?」；进 Play 构建时 VRCFury 弹「参数超限」对话框挡住主线程。
- **机制**：
  1. 进出 Play 会把场景标脏，退出时触发保存确认，而改动其实早已存盘。
  2. 离线 `csc` 编译不按 asmdef 取引用，漏引 `VRCSDKBase.dll` 的程序集离线能过、进 Unity 编译失败，于是弹出安全模式对话框。
  3. 无人值守的自动化无法点这些对话框。
- **判据**：退出前查场景 `isDirty`、改动是否已在盘上（版本控制差异可见）；新脚本在目标工程的 asmdef 口径下编译通过；运行时记录被屏蔽的对话框。
- **当时的修法**（人工作业，供理解机制）：需要的改动先保存；退出前确认没有未保存的场景；审查或探针程序集在 asmdef 里补齐引用；自动化会话里屏蔽单按钮对话框并记日志。卡住时经用户同意再杀进程，删除锁文件后核对改动仍在、还原 ProjectSettings。
- **在 Harness 流程里**：执行方不驱动编辑器；Runtime 卡住时写明证据交人。
- **适用条件**：用 MCP 等桥接远程驱动 Unity 编辑器的会话。
- **证据等级**：多工程验证

## 常驻的旧诊断脚本每次进 Play 都在改参数：先清掉再测

- **症状**：用户自己进 Play 测试时，抱熊的档位被锁在 0.5；每次退出 Play，工程里的两份说明文档被改写。
- **机制**：早期留下的两个诊断脚本带 `[InitializeOnLoad]`，每次进 Play 自动运行，每帧强写两个参数为 0.5，退出时改写文档。
- **判据**：搜索工程 `Assets/` 下带 `[InitializeOnLoad]` 或 Play 回调的编辑器脚本，确认它们是否还在用；Play 中观察参数是否被非菜单来源改写。
- **当时的修法**（人工作业，供理解机制）：删除这些脚本（连同 `.meta`），刷新后编译 0 错误、类型不再出现在程序集里；审查工具运行期间也摘掉这类回调。交付清理时一并检查。
- **在 Harness 流程里**：执行方不删工程脚本；诊断里列出常驻脚本及其影响，交人处理。
- **适用条件**：接手有历史调试痕迹的工程。
- **证据等级**：单一案例（候选）

## 新衣服是洋红色：导入顺序让 FBX 的材质重映射结果过期

- **症状**：导入一件新衣后，一个颜色变体的 26 个材质槽有 25 个为空，渲染成洋红；同包其他变体空槽数各不相同（按变体里材质覆盖条数：0、1、5、6、8、10、14、22、23 条）。
- **机制**：变体预制件只覆盖少数槽，其余槽靠 FBX 导入器的材质重映射表（`.meta` 的 `externalObjects`）补上；表里 25 条 GUID 在工程里全部能找到。问题在于该 FBX 是在「材质包尚未导入」时导入的（先导素体包、后导材质包），它的导入结果里材质全空；之后 Unity 不会因为新 GUID 出现而自动重导已导入的 FBX。
- **判据**：
  - 逐槽取证：空槽是否本该由 FBX 的重映射表提供；重映射表里的 GUID 在工程里是否都存在。
  - 判定性对照：把 FBX 复制一份、只改 `.meta` 的 GUID 让 Unity 重新导入，副本 26 槽 0 空、逐槽与重映射表一致 → 厂商包和 GUID 都没问题，只是原导入结果过期。
- **当时的修法**（人工作业，供理解机制）：`AssetDatabase.ImportAsset(FBX 路径, ForceUpdate | ForceSynchronousImport)` 重导入该 FBX，只重算导入结果，不改任何厂商文件（`.meta` 哈希前后相同）、不在场景实例上加材质覆盖；修后实例 26/26、同包 12 个预制件全部 26/26 非空，重启编辑器后仍有效。导入多包服装时先导材质包、再导本体包，或导完后对 FBX 强制重导入。
- **在 Harness 流程里**：处理 setup-project 工具报告的问题时，若本体包与材质包分开、FBX 材质为空，写明证据：导入顺序问题由冻结工具重导入解决，不在场景实例上加材质覆盖。
- **适用条件**：本体与材质分成两个 unitypackage 的厂商服装（该例为 Trinity2088「The Velour」）。
- **证据等级**：单一案例（候选）

## 复制头像根后清空 blueprintId：反射改字段不会存进场景

- **症状**：从已上传的头像根复制出新根，用反射 `FieldInfo.SetValue` 把 `PipelineManager.blueprintId` 清成空串，保存后场景里仍是原来的 `avtr_…`；新根一旦上传就会覆盖原头像。
- **机制**：反射直接改字段不会登记为预制件实例的属性覆盖，`SaveScene` 按预制件值写回。
- **判据**：保存后直接查盘上场景文件：新根实例的 `blueprintId` 值为空，原根的值不变。另把原根的「逐物体路径 + activeSelf + localPosition」清单在复制前后各导出一次，逐字节比对为 0 差异。
- **当时的修法**（人工作业，供理解机制）：用 `SerializedObject.FindProperty("blueprintId").stringValue = ""` 加 `ApplyModifiedProperties()`；并把新根改名，避免按名字前缀认根的工具把它当成原根的克隆。
- **在 Harness 流程里**：执行方不复制头像根；在 plan.yaml 的 notes 或诊断里写明新根需要清空 blueprintId，由人或 Runtime 执行。
- **适用条件**：同一工程里分出新头像根、两个根分别上传的场合。
- **证据等级**：单一案例（候选）

## 商品目录名带方括号：glob 把它当字符集，扫出 0 个文件

- **症状**：按商品目录查找素材文件时扫出 0 个，一度误报「文件还没下载」。
- **机制**：商品目录名里常有 `[PB]`、`[セール中]` 之类的方括号，Python `glob` 把方括号当成字符集匹配。
- **判据**：路径里有 `[`、`]`、`*`、`?` 时，glob 结果为 0 要先怀疑匹配语法，而不是文件缺失。
- **当时的修法**（人工作业，供理解机制）：用 `glob.escape()` 转义目录名，或改用 `os.walk`/`pathlib` 的精确路径拼接。
- **在 Harness 流程里**：工具报告找到 0 个文件时先怀疑路径匹配，写明证据交人。
- **适用条件**：按厂商商品目录名批量查找素材的脚本。
- **证据等级**：单一案例（候选）

## 渲图工具关掉的渲染器没恢复：下一次存盘把它们写进了场景

- **症状**：一次只改 3 条组件绑定的存盘，场景差异却有 3819 行增、114 行删：735 条 `m_Enabled=0` 的预制件覆盖和 114 处直接改动，全是之前几轮拍照、测距工具在内存里关掉的渲染器。
- **机制**：拍照工具在内存里关渲染器，拍完「恢复」后的核对只比层级清单（路径、activeSelf、位置），不含 `Renderer.enabled`，恢复不全没被发现；随后用 `ClearSceneDirtiness` 清掉脏标记，只是把问题藏起来，内存状态并没还原。下一次任何存盘都会把它写进场景。
- **判据**：
  - 基线清单要包含每个渲染器的 `enabled` 位和粒子的 emission 位（该例 861 个渲染器中 12 个关闭、78 个粒子中 12 个关闭），修后重算清单哈希应与基线一致；
  - 存盘后看 `git diff --numstat`，行数应与本次预期改动相符。
- **当时的修法**（人工作业，供理解机制）：改动前先从磁盘重新打开场景（`OpenScene`），丢掉内存残留，再做最小改动并存盘；多出的无关改动用版本控制还原后重做。拍照、测距类工具的恢复核对补上渲染器开关状态。
- **在 Harness 流程里**：执行方不存场景；产物差异里出现大量 m_Enabled=0 时写明证据交人。
- **适用条件**：在同一编辑器会话里先跑取证工具、再做修改存盘的场合。
- **证据等级**：单一案例（候选）

## 编辑器开着时从外部改场景文件：触发重导，编辑器卡死

- **症状**：为了还原一行派生值，在 Unity 开着时直接改了盘上的 `.unity` 文本；随后远程调用连续超时，编辑器主线程卡死，只能强制结束进程。另一次在编辑器里做全量刷新（`refresh_unity` 全范围）后，脚本编译请求卡住。
- **机制**：外部改动打开中的场景会触发场景资产重导，同时 NDMF 预览代理重建；与排队中的编辑器操作叠在一起时卡死。卡死前的修改已经落盘。
- **判据**：卡死的特征是远程调用连续超时、日志里「命令超时」计数在没有新指令时仍在增长、资产数据库锁文件的时间停住。
- **当时的修法**（人工作业，供理解机制）：不要在编辑器开着时从外部改它打开的场景；需要还原派生值时，在编辑器里改或关闭编辑器后再改。脚本改动只刷新脚本，不做全量刷新。卡死后经确认再结束进程、删除锁文件、重开，并核对盘上场景哈希是否为预期状态。
- **在 Harness 流程里**：执行方不改打开中的场景文件；Runtime 卡死时写明证据交人。
- **适用条件**：用远程接口驱动 Unity 编辑器、同时有外部脚本读写工程文件的场合。
- **证据等级**：单一案例（候选）
