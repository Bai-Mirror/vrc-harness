# 建工程：导入厂商素材包的案例

## 同一商品的两个分包不能都导：它们共用文件夹与材质 GUID

- **症状**：素体商品同时提供普通版与改模支持版（AMS）两个包，内容 88 个图像条目逐字节相同，只差安装包本身与改模支持手册。
- **机制**：同商品的分包共用文件夹与材质 GUID，导入第二个会搬走第一个的文件，并静默丢掉同路径的资产。改模支持版可能依赖额外的工具包，缺依赖时厂商预制体上会出现丢失的脚本，不报错、只是静默不生效。
- **判据**：比较两个包的成员清单与大小，确认只装一个；导入后检查 Hierarchy 里没有 Missing MonoBehaviour，未验证前不标完成。
- **当时的修法**（人工作业，供理解机制）：按订单需要选一个（该例有定制捏脸，选改模支持版），另一个不导。
- **在 Harness 流程里**：setup 阶段只导清单里选中的一个分包；工具报告两个分包都在时写明证据交人。
- **适用条件**：同一商品提供多个分包（普通版、改模支持版、不同素体版）的素材。
- **证据等级**：单一案例（候选）

## 两家厂商带着同一个上游 GUID 放在不同路径：Unity 静默改号，引用断链

- **症状**：导入两个发型商品后，其中一个发型预制体上的宝石挂件材质变成缺失（洋红），而导入前的断引用清单里没有这一条。
- **机制**：两家厂商都打包了同一份第三方公共宝石材质，原样带着上游的同一个 GUID，却各自放在不同路径。Unity 打开工程时把这种非法状态「修复」掉：两份 `.meta` 都被换成全新的 GUID，原本写死引用旧 GUID 的预制体随之断链。自写的解包脚本只检查「同路径、GUID 不同」与「同路径、内容不同」两种碰撞，没有检查「同 GUID、不同路径」。
- **判据**：导入前对所有待导包的全部成员建 GUID → 路径索引，穷举查「同 GUID、不同路径」（该例 24 个包、6170 个唯一 GUID，只此一处）；导入后对比 `.meta` 的修改时间与 GUID，重扫断引用。
- **当时的修法**（人工作业，供理解机制）：给断链的预制体手工重指材质（用户确认后）；解包工具补上第三种碰撞检测。
- **在 Harness 流程里**：工具报告同 GUID 不同路径或引用断链时写明证据交人；执行方不手改材质引用。
- **适用条件**：同时导入多个共用第三方公共素材的厂商商品。
- **证据等级**：单一案例（候选）

## BlendShare 1.0.3 散装进 Assets 后编译失败：UPM 不读 Assets 下的 package.json

- **症状**：导入面捕框架后编译报 72 个错误，全是 `Autodesk.Fbx` 命名空间下的类型找不到；批处理因「Scripts have compiler errors」中止，Missing MonoBehaviour 等后续检查都无法进行。
- **机制**：三层原因：① 厂商源码 `BlendShapeDataSOEditor.cs` 第 235 行在 `#if !ENABLE_FBX_SDK` 分支里缺一个分号（与源包逐字节比对证实是厂商原样）；② BlendShare 依赖 Autodesk FBX SDK；③ 根因：`com.triturbo.blendshare 1.0.3` 的 `package.json` 声明了 `com.autodesk.fbx: 4.2.1`，但它是从 unitypackage 散装解进 `Assets/Packages/` 的，UPM 不读 `Assets/` 下的 `package.json`，依赖没有被解析。
- **判据**：编译错误是否集中在一个散装进 `Assets/` 的包；该包的 `package.json` 声明了哪些依赖、`Packages/manifest.json` 里有没有。
- **当时的修法**（人工作业，供理解机制）：在 `Packages/manifest.json` 里加 `"com.autodesk.fbx": "4.2.1"`；经用户同意补上那个分号，原件备份到 `Assets/` 之外。
- **在 Harness 流程里**：处理编译错误时可以在 Packages/manifest.json 补缺失的依赖（属于 setup 可写范围）；改厂商源码需用户同意，写明证据交人。
- **适用条件**：以 unitypackage 形式分发、却自带 `package.json` 依赖的厂商工具（该例为 Triturbo 面捕框架附带的 BlendShare）。
- **证据等级**：单一案例（候选）

## 导入后的断引用逐条定性：只修自己导错的

- **症状**：导入 24 个素材包后扫出 130 条断引用（之后又多出 1 条）。
- **机制**：断引用来源不同：自己导错或导漏；只在同商品旧版本里存在（多半是厂商新版遗留的旧引用）；厂商根本没随包发（多头像通用材质模板里未购花色的槽位、没一起发的贴花贴图）。
- **判据**：按引用方所属商品分组，对每个商品在已导入包与同家族兄弟包的全部成员里穷举查找（不抽样）；找得到而没导对的才算导入错误。该例 44 条来自一个丝袜商品的多头像材质模板、25 条来自客户自备服装未随包的贴花，都属厂商未发。
- **当时的修法**（人工作业，供理解机制）：只修导入错误；「旧版本里有」的先报告，不要把旧文件塞回来（可能再触发分包共用 GUID 的问题）；厂商未发的记录在案、交付说明说明。
- **在 Harness 流程里**：把工具报告的断引用按「导入错误 / 旧版遗留 / 厂商未发」分类写进报告，只处理导入错误。
- **适用条件**：多素材包导入的全定制单。
- **证据等级**：单一案例（候选）
