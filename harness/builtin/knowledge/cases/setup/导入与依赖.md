# 案例：素材导入与依赖

素材导入阶段出过的问题。每例固定写症状、机制、判据、修法、适用条件；工程身份均已匿名。

## 同厂商两款发型同装后，宝石材质断链、渲染成洋红

- **症状**：同一厂商的两款发型装进同一个工程后，两个发型预制体上的宝石各断 1 处材质引用，渲染成洋红或棋盘格。控制台什么都不报。
- **机制**：宝石材质是该厂商公共目录里的共用素材。一款发型的新版本把它挪进了子目录，却保留了原来的 GUID；另一款发型的旧版本仍在原路径带着同一个 GUID。一个 GUID 对应两个路径是非法状态，Unity 打开工程时静默给两侧都重新发号。逐包的冲突计数只查「同路径不同 GUID」，所以没拦住。
- **判据**：全工程穷举「一 GUID 多路径」，以厂商共享目录为边界，而不是按单个商品配对。
- **当时的修法**（人工作业，供理解机制）：去源 `.unitypackage` 取回厂商原始 GUID，原地改 `.meta`，删掉重复的那一份；不要删了重建。修完重开 Unity，确认 GUID 没被再改、旧路径没被重建、两个预制体的未解析引用都是 0。
- **在 Harness 流程里**：`setup-project` 遇到 GUID 已在别处存在时不再写入，多数情形挡得住；工具仍报一 GUID 多路径时，setup 执行方可以在 `Assets/` 里按原 GUID 改 `.meta`、删掉重复那份，复验交 Runtime 的 Unity 步骤；两份内容不同时写明证据交人。
- **适用条件**：同一厂商的多个商品同装，且厂商在某个商品升版时挪动过公共素材的位置。

## 兽耳配饰包自带 lilToon 兜底副本，GUID 与已装的 lilToon 相同

- **症状**：一个兽耳兽尾配饰包按包内路径会把 `lts.shader`、`ltspass_opaque.shader`、一张噪声贴图落到 `Assets/lilToon/` 下。
- **机制**：这是厂商给没装 lilToon 的用户准备的兜底副本，GUID 与工程里 `Packages/jp.lilxyzw.liltoon` 的同名文件完全相同，形成一 GUID 两路径，波及面是全工程所有 lilToon 材质，不止这件配饰。
- **判据**：导入后跑一次全工程一 GUID 多路径审计；逐个核对该配饰的材质仍指向包里的着色器。
- **当时的修法**（人工作业，供理解机制）：导入后立即删除这几个文件（连 `.meta`）和随之新建的空目录；下次装同一商品要重复这一步。
- **在 Harness 流程里**：lilToon 的 GUID 已在 `Packages/` 下，`setup-project` 不会再把这几份写进 `Assets/`；工具仍报撞号时，在 setup 阶段最后一次调用工具之后删掉它们，复验交 Runtime。
- **适用条件**：配饰或服装包里带着常用着色器的副本；工程已通过包管理器装了同一着色器。

## 面捕框架包被解进 Assets/，安装器只说「未检测到框架」

- **症状**：面捕插件的安装窗口只显示一句「框架未检测到，请导入」，而框架就在盘上、472 个资产一个不少。编译零错误，控制台干净。
- **机制**：框架以带 `package.json` 的 zip 发布，却被解到了 `Assets/Packages/<包名>/`。包管理器不认 `Assets/` 下的目录，安装插件 asmdef 里的 `versionDefines` 永远不成立，插件编译进 `#else` 分支。
- **判据**：看插件编译产物 dll：`#if` 分支独有的类型（基类 `FaceTrackingInstaller`）必须出现，`#else` 分支独有的字段（`addonConfig`）必须不出现；只查前者会被两边都有的 `EditorWindow` 骗到。`.csproj` 会给出过期的假答案。
- **当时的修法**（人工作业，供理解机制）：关掉 Unity，把包连 `.meta` 一起搬进工程根的 `Packages/`，删掉包根目录自己的 `.meta`；搬前后比对「消费方指向包内的 GUID 集合」完全一致；重启后全量重导入（约 3 分钟）。不要手工加 Scripting Define Symbols。
- **当前 Harness 流程**：正常内嵌 UPM 与 VPM 分别按已接受环境、声明、解析锁和实装内容验证，不按目录数要求相等。`setup-project` 仍不直接安装这类任意厂商 zip；记录来源与实际消费需求，供受管环境修订，不自行搬包、手改 `locked` 或加宏。尚无可用换版入口时保留阻断，不声称已安装。
- **适用条件**：功能插件以 VPM 包 zip 发布，依赖它的插件用 `versionDefines` 检测它。

## 散装进 Assets/ 的子包依赖不解析，补了分号还剩约 72 个编译错误

- **症状**：导入面捕框架后编译报厂商源码缺分号；补上分号后仍有约 72 个错误，全是 `FbxManager`、`FbxScene`、`FbxImporter` 找不到。与此同时 `Assembly-CSharp-Editor.dll` 照常更新（有一次 24 个错误时它也是新文件），按它判断会以为编译通过。
- **机制**：三层叠在一起。表层是厂商源码在 `#if !ENABLE_FBX_SDK` 分支里缺一个分号（三个可选版本都有，字节比对确认是厂商原样）；中层是依赖 Autodesk FBX SDK；根因是这个子包的 `package.json` 声明了 `com.autodesk.fbx` 4.2.1，但它被散装进 `Assets/`，UPM 不读 `Assets/` 下的 `package.json`，依赖永远不会解析。另一个工程里同一子包作为正规包装在 `Packages/` 下，UPM 自动拉了 FBX SDK，从未暴露这个问题。
- **判据**：厂商程序集自己的 dll 是否产出，或日志里 `error CS` 的行数；不看 `Assembly-CSharp-Editor.dll`。
- **当时的修法**（人工作业，供理解机制）：把子包作为正规包装进 `Packages/`，让 UPM 解析依赖；改厂商源码需要用户授权。
- **在 Harness 流程里**：同上一例，作为包安装本流程做不到；依赖也不能自己加进 `manifest.json`（每次被基准覆盖）。写明根因交人。
- **适用条件**：厂商把自带 `package.json` 的包散装进 `Assets/` 下的某个目录。

## 插件用硬编码 GUID 找自己的目录，拖文件夹后构建被模态框中断

- **症状**：构建时弹出模态框中断，报错点在插件自己的代码里，控制台不报缺资源，看起来像插件 bug。
- **机制**：插件用硬编码的 `AssetDatabase.GUIDToAssetPath("<guid>")` 定位自己的目录。文件夹被手工拷进工程、`.meta` 没跟着，Unity 给文件夹重新生成了 GUID，定位失败 → `Instantiate(null)`。
- **判据**：插件行为异常却不报缺资源时，查它的目录 GUID 是否与源包一致。
- **修法**：用保 GUID 的解包工具重新导入该插件；不拖文件夹，不用导入对话框。
- **适用条件**：插件按 GUID 定位自身资源。

## 渐变发色材质父级缺失，渲染带一层出厂默认色差

- **症状**：一个发色材质渲染出来带一层不该有的色差，阴影颜色是 lilToon 的出厂默认值，而不是素体调好的值。
- **机制**：它是材质变体，父材质从没随包发出，只序列化了 8 条属性，其余约 700 行设定回落到着色器默认值。同一个包里另一个材质是完整的独立材质，打包方式不一致。
- **判据**：数材质文件行数，完整的 lilToon 材质 700 行以上，几十行的就是断链变体。
- **当时的修法**（人工作业，供理解机制）：就地断开变体链，用 `CopyPropertiesFromMaterial` 从素体同类材质取完整设定，再盖回作者真正改过的几条；不换 GUID。
- **在 Harness 流程里**：修不持久：就地改会在下次 `setup-project` 时计为内容冲突，复制到别处又没有下游引用。写明材质路径、行数与可参照的同类材质，交人。
- **适用条件**：lilToon 材质变体（在 lilToon 2.3.4 上遇到）。

## 只索引 Assets/，误报 3 个 GUID 解析不了

- **症状**：断链扫描报告 3 个 GUID 找不到对应资产。
- **机制**：GUID 索引只扫了 `Assets/`。3 个里只有 1 个是真的撞号断链，另外 2 个是 `com.vrchat.avatars` 与 GoGo Loco 包里的组件脚本 GUID。
- **判据**：索引同时含 `Assets/`、`Packages/`、`Library/PackageCache/`。
- **修法**：扩大索引范围后重扫。
- **适用条件**：任何断链或引用扫描。

## 使用率统计：挂在头像上的插件显示 0，没装的配饰显示 56

- **症状**：素材使用率表跑出来的数看着都合理、一个都不报错，但反查时发现：明明挂在头像上的插件显示 0 次引用；刚导入、还没装到头像上的配饰显示 56 次。
- **机制**：三个判据坑叠加——按目录名猜商品（解出来的目录名与商品名无关）；按扩展名判断文件（`.prefab` 被当成目录漏掉）；可达性从所有场景出发（厂商演示场景把整包标成「用上了」）。
- **判据**：出数前做已知答案反查：确定用了的必须大于 0，确定没用的必须等于 0。
- **修法**：按 `.unitypackage` 原始 GUID 与工程 `.meta` 取交集认商品；目录＝另一个条目的父路径；只从工作场景出发算可达性。先修判据，再出数。
- **适用条件**：一切覆盖率、使用率、完整性类统计。
