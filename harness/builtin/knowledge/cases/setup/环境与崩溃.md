# 案例：编辑器环境、崩溃与内存

编辑器崩溃、进程残留与内存耗尽的实例。工程身份已匿名。每例一节，按「症状、机制、判据、修法、适用条件」写。

## 案例：编辑器无人操作时自己崩溃，窗口矩形正好等于旧屏宽

- **症状**：Unity 在无人操作时自己退出，工程目录留下 `mono_crash.mem.<pid>.1.blob`；`Editor.log` 末尾是 gdb 栈加 `Exiting early due to double fault.`；之后每次重开都崩在同一处，不是偶发。
- **机制**：栈的形状是 `ContainerWindow_CUSTOM_set_Internal_Position_Injected`（C# 侧设窗口位置）→ `ContainerWindow::SetRect` → `SetGtkWindowSizeAndPositionSync` → `PumpGtkMainloop` → `gtk_main_do_event` → `OnConfigure` → `GUIView::ReshapeIfNeeded` → `ThreadedWindow::Reshape` → `GfxDeviceClient::WindowReshape` → `Semaphore::WaitForSignal`，即主线程卡在 `WaitForGtkEvent` 等渲染线程。图形会话是远程桌面（xrdp 的 Xorg，窗口管理器 kwin_x11），远程客户端先后把屏幕改成 2560×1600、3840×2160（`~/.xorgxrdp.<显示号>.log` 里的 `screen resized to …`）；Unity 在偏好里存的主窗口矩形 `RestoredMainWindowSizeX/Y/W/H` 是 0,115,2560×1485，宽度正好等于旧屏宽。启动时把这个矩形同步给窗口管理器，协商不收敛，主线程卡死后 double fault。
- **判据**：`RestoredMainWindowSizeW` 是否恰好等于某个历史屏宽。与另一种崩溃分开认：那一种落在 `libnvidia-glcore`、发生在反复进出 Play 或构建弹进度条时；这一种落在 GTK 窗口重排，与 Play 无关。同期日志若出现 `Missing X server or $DISPLAY … The platform failed to initialize.`，说明 X 侧确有异动。
- **修法**：先看 `git status`（这类崩溃不损坏已保存的资产）；另存崩溃日志后，清掉 `mono_crash*.blob`、`Temp/UnityLockfile` 与编辑器桥的实例状态文件；备份 `~/.local/share/unity3d/prefs` 后把主窗口矩形改成明显不贴边的值（如 120,120,1800×1100），`IsMainWindowMaximized=0`，编辑器桥窗口的坐标（`MCPForUnity.Editor.Windows.*x/y`）也挪离原点；确认没有活着的 Unity 进程后重开。一次见效，日志 `MCP_READY after 5s`。远程桌面改分辨率或刚重连之后，别立刻弹由 C# 设位置的窗口（如登录认证窗口）。
- **适用条件**：Linux 远程桌面图形会话里的交互编辑器（Unity 2022.3.22f1）；批处理模式没有窗口，不适用。

## 案例：编辑器崩溃但进程还活着，被删锁后另起批处理打开同一工程

- **症状**：可用内存跌到约 1 GB 时交互编辑器原生崩溃，但进程还活着（RSS 7.4 GB、CPU 50%），卡在「Launching bug reporter」（复制状态文件时权限不够），编辑器桥连不上。
- **机制**：崩溃栈是 `DebugProxy::CallOverridenDebugHandler` 与 `Scripting::LogException` 无限递归；bug reporter 起不来，进程不退出，锁文件仍由这个活进程持有。执行方当时删了 `Temp/UnityLockfile`，换一个临时 HOME 以 `-batchmode` 打开同一个工程跑完了取证。两个 Unity 同开一个工程会抢写 `Library/`，可能坏库；那次侥幸只顺带改了 `ProjectSettings/lilToonSetting.json`（已还原）。
- **判据**：编辑器桥连不上时，先 `ps -o stat,etime,%cpu,rss -p <pid>` 并看 `Editor.log` 末尾；末尾是崩溃栈或 bug reporter，就判「崩溃未退出」。锁对应的 pid 还在，就不许删锁。
- **修法**：停下报告「崩溃未退出」，不删锁、不另起实例；由有权限的一方结束该进程（自己起的可以直接结束，别人正在用的先问），确认进程消失后再删锁，再重开或改走批处理。
- **适用条件**：任何 Unity 版本；与内存压力强相关，内存紧张时更要先查进程状态。

## 案例：内存耗尽，同一进程组里的编辑器、批处理与执行会话一起被杀

- **症状**：一次内核 OOM 把代理应用所在的整个进程组杀掉：两台交互 Unity、一个批处理导入 Unity、后台 Blender、约 9 个执行会话连同各自的工具子进程全部一起死，代理本身也被重启；峰值为 22.3 GB 内存加 5.6 GB 交换区，本机总内存 30 GB。后果是执行产出写完未提交、编辑器与导入队列中断。
- **机制**：从代理会话里起的所有进程都在同一个进程组里，没有各自的内存上限；Unity 每台 3–8 GB，是主要占用者；并发按「感觉还有空」起，没有看可用内存。
- **判据**：起重进程前看可用内存与同类进程数；被杀后逐个检查被杀任务的产出是否完整（JSON 字段、渲图），再决定补记还是重做。
- **修法**：每个 Unity 进程放进带内存上限的独立单元（交互 14 GB、批处理 10 GB），超限只死它自己；批处理全机串行；可用内存 < 8 GB 不起新的重活；看门狗在可用内存 < 3 GB 时先结束批处理 Unity。事后清理各工程的陈旧 `Temp/UnityLockfile`、编辑器桥状态文件与持有者已死的交接锁。
- **适用条件**：单机上多个编辑器与执行会话并发；阈值在一台 30 GB 内存的主机上标定。

## 案例：全机换页被误判成 Unity 崩溃

- **症状**：代理客户端被重启，一个辅助进程报 `Missing X server or $DISPLAY … The platform failed to initialize. Exiting.`，看起来像 Unity 崩了。
- **机制**：全机在换页：30 GiB 内存用到 22 GiB、可用 1.7 GiB，交换区 13/15 GiB；占用前列是 Unity（RSS 4.4 GB，托管 1.6 GB、保留 2.3 GB）、一台虚拟机 2.5 GB 以及若干客户端进程；用户的 Blender 常驻只有 450 MB，却被换出 1.99 GB。
- **判据**：Unity 自始至终没崩：没有 `mono_crash*.blob`，编辑器桥秒回，日志里只有正常的资源刷新。报「崩溃」之前先找崩溃证据。
- **修法**：开工前看 `free -h`，交换区用掉一半以上先清场再干活；无头 Blender 串行、跑完即退，能在已开着的 Blender 会话里只读测量就不另起；用户的 Blender、Unity 不能由执行方关闭（可能有未保存的改动），把可关的进程列给人决定。
- **适用条件**：单机上编辑器、无头 Blender 与其他大进程并存时。
