# 菜单：表达参数预算的案例

## VRCFury 参数压缩只压菜单里用得到的参数：复制菜单树让它从 256 变成 318

- **症状**：给新头像根装了一个饰品后，构建日志报参数 423/256、最大压缩后仍 318/256，「would have failed to upload」；游戏内的功能菜单（姿势系统、互动、计时等）也整片消失。装饰品前同一个根压缩后正好 256/256。
- **机制**：装配脚本为了「不动原根」深拷贝了新根的整棵菜单树，并把新根的 `menuToAppend` 指向拷贝；场景里其他 MA Menu Installer 仍指向原菜单资产，于是它们装进的是一棵没人用的树，新根菜单控件从 325 个掉到 53 个。VRCFury 的参数压缩只处理菜单里用到、类型符合条件的参数，31 个参数（80 bit）因此从「可压」变成「不可压」。
- **判据**：
  - 读 VRCFury 压缩器的判定（该例用运行时钩子读出候选参数、成本与决策），核对「成本公式 318 = 日志 318」；
  - 构建后菜单控件数与装配前是否一致；
  - 复制菜单资产前先查谁以它为 `installTarget` 或 `menuToAppend`。
- **当时的修法**（人工作业，供理解机制）：不拷贝菜单树；把饰品对菜单的改动（该例 2 处：一个开关改成轮盘、新增一个开关）写回原菜单资产，`menuToAppend` 指回原根菜单。修后菜单控件 326、压缩后 256/256、VRCFury 无报错。余量为 0 时，经用户同意把「材质色」「链型」并进同一个嘴部挂饰轮盘（一个 Float 分 6 档），不再单设开关。
- **在 Harness 流程里**：执行方不复制菜单资产，菜单改动都写进 design.json；Runtime 报参数预算超限时，把压缩结果与控件数写进诊断并交人。
- **适用条件**：用 VRCFury 参数压缩把 300+ bit 压进 256 的头像（Kaguya 素体，多套服装加多种机关）。
- **证据等级**：单一案例（候选）

## 参数超限时的决策：压缩器能压过就不砍功能，但预算检查失败必须当上传阻断

- **症状**：构建时 VRCFury 弹框报 342/256、压缩后 291/256「would have failed to upload」；另一种按导出表的算法得到同步 144 个 = 256 bit，两个口径不一致。弹框是模态的，会挡住编辑器主线程。
- **机制**：参数位数有多种统计口径（只数自建表达参数、构建后含厂商参数、压缩前、压缩后）；真正决定能否上传的是完整 SDK 构建链压缩后的结果。
- **判据**：以完整预处理链（NDMF、MA、VRCFury、AAO）后的压缩结果为准，并与日志原文对账；自动化运行时屏蔽或记录单按钮模态框，避免卡住。
- **当时的修法**（人工作业，供理解机制）：用户决定「不再为参数砍功能，靠 VRCFury 压缩上传」，同时约定上传实测失败再回到砍参数方案。新增功能优先复用已有参数（例：发色从 4 档扩到 5 档仍用同一个 Float、饰品选项并进已有轮盘），NotSynced 参数不计入同步位。验证脚本里任何「预算通过 = false」都算上传阻断。
- **在 Harness 流程里**：预算类检查失败一律当上传阻断写进 diagnosis.json；砍功能还是并档由用户决定，方案优先复用已有参数。
- **适用条件**：参数接近 256 bit 上限的头像。
- **证据等级**：单一案例（候选）
