# 菜单：厂商菜单与部件开关的案例

## FX 层默认权重为 0：参数和状态机都正常，物体就是不动

- **症状**：
  - 一例：厂商子菜单里的 9 个换装开关在 36 个状态里显隐与形态键零变化，客户点了没反应；厂商衬衫 clip 本该写的身体收缩也从未生效。
  - 另一例：自建的贴纸轮盘层参数面板一切正常，物体却不动。
- **机制**：层的默认权重为 0 时，状态机照常求值、参数驱动器照常触发，但曲线写不出去。第一例是厂商 FX 的 `Outfit *` 层 `m_DefaultWeight: 0`，控制器里没有任何 VRC Animator Layer Control 把权重拉起来；第二例是用 `AnimatorController.AddLayer(string)` 建的层，建出来就是 0，而 MA 合并时只把每个被合并控制器的第一层强制成权重 1，其余层的 0 一路带到构建后。
- **判据**：构建后读合并控制器里每个相关层的权重（应为 1），并搜索针对权重为 0 的层的 Layer Control；实机逐个切换开关，显隐与形态键必须变化。在补丁之前跑的回归抓不到这类问题，改动后要重跑。
- **当时的修法**（人工作业，供理解机制）：自建层写 `layers[i].defaultWeight = 1f`，并把整个 `layers` 数组赋值回控制器（`layers` 返回的是副本，只改副本无效）。厂商层的那一例由用户决定删掉死菜单：复制厂商菜单资产、去掉引用死子菜单的那一项，让 MA Menu Item 指向副本，厂商文件不动。
- **在 Harness 流程里**：在 design.json 里不把权重为 0 的厂商层当作有效开关（不列进 vendor_clips）；Runtime 读回开关无效时写明层权重证据，「删掉死菜单还是接通」交用户。
- **适用条件**：Kipfel 厂商 FX v1.1.1（该工程的 FX 已并入面捕补丁的层，另一个 Kipfel 工程里同名厂商眼镜层能正常切换，权重 0 的来源未查）；Shinano 工程的自建生成器。
- **证据等级**：多工程验证

## 同一菜单里开关语义相反：统一成「点亮＝脱掉」

- **症状**：静态审查以为 6 个部位开关「永远不显示」；实际是这 6 个开关「点亮＝脱掉」，而同一菜单里的眼镜开关「点亮＝戴上」，两种语义混在一起。
- **机制**：MA Object Toggle 的规则是：菜单项开启时对象取 `Active` 字段的值，关闭时取构建时的场景初值（也会被其他动画改写）。6 个开关 `Active=0`，所以菜单默认全关＝全穿；眼镜 `Active=1`。
- **判据**：列出菜单里每个 Object Toggle 的 `Active`、`Inverted` 与菜单项默认值，确认同一组开关的「点亮」含义一致。
- **当时的修法**（人工作业，供理解机制）：用户同意后，把眼镜的 Object Toggle 设为 `Inverted`、菜单项默认开，8 个开关统一为「点亮＝脱掉或摘掉」，眼镜默认仍不戴，外观不变。验收：眼镜参数默认 1 且存档；默认态眼镜不显示；参数 0 → 显示，1 → 隐藏。
- **在 Harness 流程里**：在 design.json 里同一分组的 control 统一 default 语义（例如全部「开＝穿着」），不混用。
- **适用条件**：用 MA Object Toggle 自建的部位开关菜单。
- **证据等级**：单一案例（候选）

## 部位开关逐套核对：一个开关管多件、漏管某一套都会出错

- **症状**：
  - 一例：某套服装（FuriMeow「シェルマリン」）的开衫、裙子、鞋都挂在「外套」开关上，点一次「外套」三件一起消失，只剩泳衣和赤脚；「裙子」「鞋子」开关在这一档无效。
  - 另一例：「袜子/鞋子」开关管住了其他几套的鞋袜，却漏了素体基础装的靴和过膝袜，切到基础装时开关无效。
- **机制**：部位开关要横跨所有套装，但装配时是按套装逐件加目标的：要么把整套附件都塞进一个开关，要么新增一套时忘了把它的部件加进已有开关。
- **判据**：逐套服装列「开关 → 目标对象」表：每个开关只控制它名字所指的部位及其组成物，并且每一套里该部位的件都在列表中；逐个单关时只消失对应部位。
- **当时的修法**（人工作业，供理解机制）：
  - 把裙子移到「裙子」开关、鞋移到「鞋子」开关，「外套」只保留外套类。验收：全穿时各件都在且 `High_heel`=50；只点「鞋子」只少鞋且 `High_heel` 回 0。
  - 把基础装的靴、过膝袜追加到「袜子/鞋子」的 Object Toggle（`Active=0`，开关打开时隐藏）；场景里有两个头像根就各改一处（8 → 10 条）。验收：构建后求值，换装轮盘 6 个取值 × 开关两态，非基础装物体 12 格全部不变，基础装的两件只在基础装档且开关关时显示；参数位数不变。
- **在 Harness 流程里**：在 design.json 里每个 control 的 targets 按衣装逐套列全该部位的组成物，不把整套附件塞进一个 control，也不漏掉某一套。
- **适用条件**：多套服装共用一组部位开关的菜单（Kipfel 一例、Rurune 一例）。
- **证据等级**：多工程验证

## 点不到的厂商参数白占同步位：用 EditorOnly 剥离，不删厂商件

- **症状**：服装预制体自带的 `cardigan_OFF`、`skirt_OFF`、`crown_OFF` 三个参数已声明、同步，但菜单里没有控件（其所在的厂商子菜单已被移除），白占 3 bit。
- **机制**：这三个参数来自预制体内三个物体上的 MA Object Toggle 与 MA Menu Item（默认关、自动参数、同步）；只要这些组件还在，构建就会分配参数。
- **判据**：构建后导出的参数表里有没有这三项；它们有没有可达的菜单控件。
- **当时的修法**（人工作业，供理解机制）：在场景里把这三个挂组件的物体设为 `EditorOnly` tag（作为预制体实例覆盖，可逆；构建时被剥离），不删厂商件。验收：构建后参数表里三项消失；该套全穿态开衫、裙子、头冠仍显示，默认态隐藏，外观不变。
- **在 Harness 流程里**：不改厂商预制体的物体 tag，也不为这些参数建控件；参数白占写进诊断，由用户决定。
- **适用条件**：MA 组件随服装预制体自带菜单与参数、但菜单入口被移除的情况。
- **证据等级**：单一案例（候选）

## 厂商参数驱动器写入越界值：先证实后果，无可见后果就不动

- **症状**：厂商面捕控制器里帽子层的默认 `_ON` 状态带一个 ParameterDriver，把 `Cat_Ear` 写成 12，疑似厂商遗留错误。
- **机制**：`Cat Ear` 层只在 `Cat_Ear`=0–6 时切换（Reset、Idle、Pyoko 等），12 不匹配任何转移，耳朵层停在原状态；`Cat_Ear`、`Cat_Tail` 是同步 Int，没有菜单控件。
- **判据**：列出能到达写入状态的控件；枚举目标层对该参数值的全部转移；再在 Play 里读参数与可见结果。
- **当时的修法**（人工作业，供理解机制）：判定无可见后果，不改厂商参数（改动有牵连风险）。这两个参数各白占 8 bit，参数预算不紧时保留。
- **在 Harness 流程里**：不改厂商参数；诊断里写明「无可见后果、不动」及证据。
- **适用条件**：Kipfel 厂商面捕控制器；方法适用于任何「厂商逻辑看起来错了」的情况。
- **证据等级**：单一案例（候选）

## 生成器删目录重建资产：另一个头像根上的引用被置空，构建后菜单与 FX 脱钩

- **症状**：重跑菜单生成器后，Play 渲图里两套不同的服装看起来一模一样，渲染器数从 166 掉到 114；构建后自建 FX 没有合进来，菜单断开。
- **机制**：生成器开头删掉整个生成目录再重建，新资产的 GUID 全变了；场景里启用的面捕根有 13 处引用指向旧资产（MA Merge Animator、描述符的 `expressionsMenu`、11 个 MA Menu Installer 的 `installTarget`/`menuToAppend`），全部被置空。生成器只按名字把新资产接回了停用的原件根。菜单与 FX 脱钩后，AAO 把所有衣服当成静态件合并成一块。
- **判据**：重跑生成器前后，统计场景对生成资产的 GUID 引用数与 `{fileID: 0}` 数，逐资产比对（该例启用根的引用数减半）；Play 渲染器数与各套服装渲图是否仍各不相同。
- **当时的修法**（人工作业，供理解机制）：一次性回填：按相同相对路径、同类型同序号组件、同属性路径，把原件根的引用抄给面捕根。根治：生成器末尾增加「把原件根的生成资产引用镜像到克隆根」一步（只填空值、不覆盖）；此后每次重跑都检查日志里「回填 13 处」与引用计数不变。
- **在 Harness 流程里**：执行方不跑生成器；Runtime 重建后若出现引用丢失（菜单或 FX 未合并、渲染器数骤减），写明证据，停下交人。
- **适用条件**：用脚本生成菜单与动画资产、场景里有多个头像根的工程（Kaguya 素体，自研菜单生成器）。
- **证据等级**：单一案例（候选）

## 改厂商菜单项的显示名：要改 label，只改 Control.name 不生效

- **症状**：想把厂商 MA Menu Item 的显示名改成更易懂的中文（例：「锁定」改为「牵引锁定」），改了 `Control.name` 后菜单里仍显示旧名。
- **机制**：MA 1.18.1 把菜单项转换成 VRChat 菜单时（`PortableMenuControl.CloneToVRCSDK()`）取的是 `label`，`label` 为空才取 GameObject 名；`Control.name` 不参与。
- **判据**：构建后导出的菜单里该项的显示名。
- **当时的修法**（人工作业，供理解机制）：在场景实例上覆写该组件的 `label`（场景差异只多这一处覆写），厂商预制件不动。
- **在 Harness 流程里**：在 design.json 的 control 里用 label 写显示名；改厂商菜单项名称本流程没有对应通道，遇到时写明证据，停下交人。
- **适用条件**：MA 1.18.1 的 Menu Item；其他版本先用构建后导出验证。
- **证据等级**：单一案例（候选）

## 轮盘里的一档是空档：两个档位的 clip 效果完全相同，那个件从来没接线

- **症状**：耳尾轮盘的「猫耳尾」档看起来有效，其实只在穿某一套服装时才出现猫耳；两份阶段报告为此写了各自的根因。
- **机制**：该档的 clip 与「无」档效果完全相同，都只把狐耳四件写成 0；全部菜单资产里没有任何地方提到猫耳、猫尾对象。猫耳能出现只是因为它是那套服装的子物体，轮盘从来没接过线。
- **判据**：逐档比较 clip 的曲线集合，效果相同的档就是空档；搜索菜单与动画资产里是否引用了该档声称控制的对象。
- **当时的修法**（人工作业，供理解机制）：给该档补写猫耳、猫尾显示 = 1，其他档写 0；并把这两件移出服装子树，否则 clip 写 1 也会被服装的显隐压掉。这一发现推翻了早先两份报告的根因。
- **在 Harness 流程里**：在 design.json 里为每个档位列出它实际控制的对象；发现两档写入完全相同时在诊断里写明，按用户意图补齐 targets。
- **适用条件**：服装自带的附件（耳、尾）被单独做成轮盘选项的菜单。
- **证据等级**：单一案例（候选）
