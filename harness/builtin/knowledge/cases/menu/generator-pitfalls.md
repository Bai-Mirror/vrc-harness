# 菜单：用脚本生成动画层与菜单时的案例

## 生成器把厂商 ON clip 的路径全收进开关组：备选件被同时打开，外套两层重叠

- **症状**：某套服装的外套有两个网格：常规版与大胸敞开版。两者同时启用，烘焙比对大胸版 70% 的顶点离常规版 ≤0.5 mm、84% ≤2 mm（两层几乎重合，会 z-fighting 且渲染量翻倍）。
- **机制**：厂商说明书要求二选一，大胸版默认关；厂商的外套 ON clip 只写两者的 `m_Enabled`，不写 `m_IsActive`。自建生成器却把厂商 ON clip 里出现的所有路径都收进外套开关组，生成的整套档与外套开关都对大胸版写了 `m_IsActive=1`。
- **判据**：列出厂商 ON clip 的路径中「预制体默认关闭」的对象，逐个按说明书判断是不是备选件；构建后检查同一部位是否有两个几乎重合的网格同时启用。
- **当时的修法**（人工作业，供理解机制）：删掉生成动画里对备选件的 `m_IsActive` 曲线（保留 `m_Enabled`），生成器加「厂商备选件排除表」。修后常规版随外套开关正常切换，大胸版没人激活、被 AAO 从构建产物里清掉；外套开关时内层收缩键 100↔0 正常。
- **在 Harness 流程里**：在 menu 的 design.json 里，vendor_clips.allow_default_off 只列说明书与单独预览证明属于该功能的对象；备选件不列，也不写进 targets.objects。
- **适用条件**：Kaguya 素体的厂商默认服装；其他工程审查时专门查过同型结构，未再发现。
- **证据等级**：单一案例（候选）

## 通过远程调用跑生成器：超时被重发，控制器从 125 KB 涨到 38 MB

- **症状**：依赖编译器的 Apply 通过远程执行代码的接口调用，接口报超时；随后控制器从 125 KB 涨到 38 MB，每个生成层有 4 份，`AnimatorStateTransition` 多达 28,782 条，一轮约 4 分钟、46 次资产刷新。
- **机制**：
  1. 超时后同一 Apply 被重发执行了 4 次；
  2. Unity 会把层名里的 `.` 改成 `_`，生成器按原名对账找不到旧层，每次都新增；
  3. 条件取反按析取范式展开是指数级的，单层就能生成上万条转移。
- **判据**：对账只认回读的实际层名；计划里打印每层的转移条数，并与写入后回读的条数比对；连续 Apply 三次，层数、转移总数、组件数、写者清单哈希都应逐次相同（控制器字节可因随机 fileID 不同，按对象比较应语义相同）。
- **当时的修法**（人工作业，供理解机制）：层名规范化后记录实际名；转移按「浮点切片 × 布尔子句」求值再合并相邻区间（该例合计 42 条）；资产写入包在 `StartAssetEditing`/`StopAssetEditing` 里并一次保存；长操作改成「请求文件 + 状态文件」的异步菜单，远程执行接口只做短小、幂等的操作。修后每次 Apply 约 0.2–0.35 秒。
- **在 Harness 流程里**：执行方不在编辑器里跑生成器，菜单由 Runtime 按 design.json 生成；Runtime 报控制器异常增大或层重复时写明证据交人。
- **适用条件**：用 MCP 之类的远程执行接口驱动 Unity 编辑器的生成类脚本。
- **证据等级**：单一案例（候选）

## 同一属性只能有一个写者：两个生成器或厂商组件重复写时要删掉一方

- **症状**：
  - 为了「外套开时隐藏领带」，先在菜单生成器里加了一个压制层，结果与声明驱动的依赖层成了同一属性的两个写者，只好撤掉；
  - 厂商的 Blendshape Sync 与自建「胸围」层同时写 4 件衣服的同两个胸型键，当前值相同所以看不出差异；
  - 先跑依赖编译器、再跑菜单生成器时，后者会清掉前者生成的 11 个层与 clip，必须按固定顺序再跑一次。
- **机制**：同一属性有多个写者时，最终值取决于层序和各层当前状态，改动任何一方都可能出现不可预期的覆盖；两个工具写同一控制器时，后跑的会覆盖或清掉先跑的产物。
- **判据**：盘点每个属性（对象显隐、形态键、材质槽）的全部写者：生成层、厂商层、MA 组件；一个属性只允许一个权威写者。迁移前后比较「(状态, 路径, 键) → 值」集合，只允许少掉有意删除的条目。
- **当时的修法**（人工作业，供理解机制）：领带「跟衬衣走、外套开时隐藏」写成一条声明（可见外套 → 领带隐藏），只由依赖编译器生成；厂商 Blendshape Sync 保留、删掉自建层对这 4 件 × 2 键的写入；生成顺序固定为「菜单生成器 → 依赖编译器」，后来把生成器的三张表迁进声明，顺序问题一并消失。
- **在 Harness 流程里**：在 design.json 里每个对象只归一个 control，不和厂商 vendor_clips 重复写同一属性；「外套开时藏领带」这类联动用 disable_when_on 表达。
- **适用条件**：同一控制器由多个工具生成、厂商组件与自建层并存的工程。
- **证据等级**：单一案例（候选）

## 控制台报参数类型与转移条件不符：看合并后的类型和有没有可达写者

- **症状**：控制台警告厂商耳朵控制器的 AnyState 转移使用的参数 `FaceLock` 与条件类型不兼容，担心该转移永不触发或总是触发。
- **机制**：该控制器经 MA Merge Animator 合进 FX 时，MA 1.18.1 把 `FaceLock` 统一成 Float、条件不改（`Less 0.5` 在 Float 上有效）；构建后 `FaceLock` 不在表达参数与菜单里，唯一写它的参数驱动器挂在一个孤立状态上。
- **判据**：看构建后的参数类型；列出能写这个参数的所有写者，并确认它们所在的状态是否可达。没有可达写者就没有可见后果。
- **当时的修法**（人工作业，供理解机制）：判定无可见后果，关闭，不改厂商控制器。
- **在 Harness 流程里**：不改设计输入；诊断里写明合并后的参数类型与写者可达性，无可见后果就记录关闭。
- **适用条件**：MA 1.18.1 合并厂商控制器的工程。
- **证据等级**：单一案例（候选）

## 从现有头像根分支新根：生成资产做副本、清悬空曲线、按名字隔离

- **症状**：在同一工程里从已上传的头像根分出一个只保留原装与三件新衣的新根。直接共用原根的生成资产，会让重跑生成器时改到新根、或新根删衣服后动画里留下大量找不到对象的曲线。
- **机制**：自建工具按名字前缀识别「原根的克隆」并自动回填引用；新根如果沿用前缀，就会被当成克隆改写。删掉衣服后，动画与菜单里指向这些对象的曲线变成悬空。
- **判据**（该例的验收）：
  - 新根改名，不再以原根名开头；两个判定式（克隆识别、依赖编译器的同源根）都把新根排除；
  - 生成目录整份复制为新目录，副本内只把动画与菜单两类主资产的相互引用改指副本（80 处）；新根的 13 处引用全部指向副本、指向原目录为 0；
  - 删掉非原装衣服后，副本里删悬空曲线 176 条（浮点 138、材质槽 38），删后悬空 0、误伤 0；空 clip 保留状态结构；
  - 原根逐物体清单改前改后逐字节相同，原目录版本控制差异为空。
- **当时的修法**（人工作业，供理解机制）：按上述步骤做；把整体失效的控件从新菜单里摘掉。注意删件后残留的控件：一个高跟鞋开关只剩「关掉原装鞋」这一条曲线，开它会让鞋消失而不显示高跟，必须摘掉。副本是快照，之后改声明或重跑原生成器不会同步到新根。
- **在 Harness 流程里**：本流程在独立派生层里生成每个造型，不从旧根复制；遇到分支头像根的需求时写明证据，停下交人。
- **适用条件**：同一工程里维护多个头像根、使用自建生成器的场合。
- **证据等级**：单一案例（候选）

## VRCFury 的 FixWriteDefaults 在构建时把 FX 统一成 WD on：层设计要在两种语义下都成立

- **症状**：独立核查推断「新菜单依赖空 clip 透传，而构建时 WD 被强制为 on，原装件开关会失灵、嘴部挂饰会被写回默认」，据此要求重构。
- **机制**：三个头像根都挂着 VRCFury 的 FixWriteDefaults（Auto）；构建日志里可以看到原文「VRCFury is fixing write defaults (ALL layers) -> ON counts (… FX:698 on|117 off …) mode (Auto)」，即全部 FX 状态被改成 WD on。空 clip 在 WD on 与 off 下行为不同，但「会失灵」只是推理：随后 Play 实测的 4 个例子都与期望一致，原根 16 个档 0 用例也全部一致，推理没有复现。
- **判据**：
  - 先抄构建日志里的 WD 整行，确认实际模式；
  - 层设计按「一个属性只有一个写者层、每个状态显式写满本层拥有的属性」做，再分别按 WD on、WD off 两种语义模拟一遍，两者结果相同才算过（一例 166 个属性、冲突 0）；
  - 共用同一轮盘参数的各层，转移阈值统一用档中点（0.125/0.375/0.625），进出同一个数，没有重叠带；
  - 空 clip 做压制层的 Off 态会出问题：摘掉帽子后，被帽子压住的加装耳尾不恢复。
- **当时的修法**（人工作业，供理解机制）：按上述原则重构；推理出来的缺陷先实测再对用户下结论，不能直接断言「原来已上传的根也坏了」。
- **在 Harness 流程里**：设计输入按「每个 control 显式列全所拥有的对象」来写，不依赖空 clip 透传；诊断里引用构建日志的 WD 行即可。
- **适用条件**：挂有 VRCFury FixWriteDefaults（Auto）的 MA 工程（Kaguya 素体，三个头像根）。
- **证据等级**：单一案例（候选）

## 原装件 activeSelf=1 不等于看得见：要读 activeInHierarchy，并做正对照

- **症状**：实测原来两个已上传头像根的菜单：86 个用例里 18 个「失败」，全是同一类：切到非原装整套时，原装的水手服、袜、鞋、包、嘴部挂饰 `activeSelf=1`（期望 0）。看起来像「换整套时原装衣服漏出来」。
- **机制**：部位开关的 On 态 clip 显式把这些件写成 1，且层序在整套层之上（生成器文件头「On 不写、透传」的注释已过时）；但整套层在非 0 档把原装衣服的父物体 `kaguya_cloth` 关掉了，这些件 `activeInHierarchy=0`，实际不可见。
- **判据**：
  - 同时读 `activeSelf` 与 `activeInHierarchy`，以后者判断可见性；
  - 渲图：隐藏这 5 件与不隐藏逐字节相同（PNG 哈希相同），而档 1/3/5 与档 0 的全身差 6.4–7.4%，说明渲图对服装差异敏感；
  - 正对照：强行打开父物体后重渲，全身差 16086 像素（1.53%），再关掉外层服装差 59785 像素（5.70%）——证明父物体确实在管这些件、并非被合并成空壳或被完全遮挡；
  - 同参数重复渲染有 0.1–0.4% 的噪声底，跨状态比像素要扣掉。
- **当时的修法**（人工作业，供理解机制）：判定不是用户可见缺陷，不改；清理冗余写入属于状态卫生，交用户决定。探针在预处理失败时必须报错退出，不能拿未构建的控制器继续出数。
- **在 Harness 流程里**：读 Runtime 的状态读回时以 activeInHierarchy 判可见性；判为非缺陷时在 diagnosis.json 里写明正对照证据，不改设计。
- **适用条件**：父物体按整套开关、子件由部位开关控制的菜单结构（Kaguya 素体，两个原头像根）。
- **证据等级**：单一案例（候选）

## 两条方向相反的压制层互锁：头顶什么都不剩

- **症状**：客户反馈头部饰品和新加的耳尾「互相压没了」：两者同时开时，头顶什么都不显示。
- **机制**：压制层里同时存在「耳尾 = 新耳尾时压掉帽子与服装兽耳」和「头部饰品开时压掉新耳尾」两条方向相反的规则，两个条件同时成立时互相把对方压没。
- **判据**：冲突表里出现「A 压 B」又有「B 压 A」就是错的，每条规则都要能说出它在优先级链上的位置；验收遍历「服装档 × 冲突开关」的全部组合，每格断言「这个身体位置至少有一件是开的」，死锁格为 0 才算过，并且必须用真实动画数据驱动（该例 4 套 × 头部开/关 = 8 格，死锁 0）。
- **当时的修法**（人工作业，供理解机制）：按客户既定的优先级链（服装头部小件 > 耳朵）只保留单向压制，删掉反向那条。冲突分三类处理：只在切换时关一次的用参数驱动器改对方参数；开着期间一直压的用单独一层写对方的属性；同位置互斥的定优先级链、只压低优先级一侧。
- **在 Harness 流程里**：在 design.json 的 disable_when_on 里只写按用户优先级链的单向让位，不让两个 control 互相让位；Runtime 报死锁格时改 disable_when_on。
- **适用条件**：头部饰品、帽子、兽耳、加装耳尾并存的菜单（Kaguya 素体一例）；另一工程的菜单规范评估也用同一死锁格判据。
- **证据等级**：多工程验证
