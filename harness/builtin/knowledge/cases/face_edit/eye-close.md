# 捏脸：闭眼与眼睑的案例

## 捏脸候选表里的「闭眼穿模 −3.3 mm」是估算：实测后再下结论

- **症状**：待办里挂着一条「闭眼时 −3.3 mm 穿模」，一直没人复核，被当成已知缺陷。
- **机制**：这个数字来自捏脸阶段为比较眼型候选写的「开度当量表」，是估算，不是实测穿模。
- **判据**：默认态停 Animator，把脸部网格的 `eye_close`（AAO 合并后在合并网格上的序号不同，要按原名映射）设为 100；Head 半径 0.3、1024 像素、8 个方位，与睁眼同机位对照裁出眼部：闭眼时上睫毛线落在下睫毛之上，正面与两侧 3/4 都看不到虹膜、眼白露出或上睑穿过下睑；第二个模型盲测 0 条缺陷。描述符的 eyelidType 为 None，眨眼由动画驱动。
- **当时的修法**（人工作业，供理解机制）：判定无可见穿模，关闭；另两套闭眼键（`eye_joy`、面捕的左右闭眼）未单测，暂按同一眼睑网格的结论处理，并在记录里写明。
- **在 Harness 流程里**：本流程尚无捏脸阶段；诊断时把估算表里继承来的「缺陷」标为未实测，不当作已知缺陷。
- **适用条件**：Shinano 素体的捏脸头像；任何从设计阶段估算表里继承来的「缺陷」。
- **证据等级**：单一案例（候选）

## 捏脸候选给用户挑之前：差异只在五官区、相邻组拉开到门槛以上、说明口径与依据

- **症状**：四组捏脸候选要交用户（再转客户）选组，候选之间差异看不出、渲图状态与交付态不同、某组依据不足，都会让选择失真。
- **机制**：候选按眼尾倾斜排成一条链（例：+0.00050、−0.00101、−0.00252、+0.00206，相邻差约 0.0015，刚过门槛），动一组相邻的要跟着动；为了看清眉眼隐藏了素体刘海（眉区显著差异像素从 5,668 增到 22,015），但隐藏刘海反而让眼尾更难判读（同一比较三次都判「看不出」，带刘海时判「支持」），刘海遮住上挑的假设被证伪。
- **判据**（闭式检查，不必人工复核）：图不是纯色；两两像素差足够大；差异只出现在眼眉区域，其余区域精确为 0；46 个键名全部在形态键清单里、左右无错配、无超范围外推；每组施加后回读、清零 526/526、场景不保存。
- **当时的修法**（人工作业，供理解机制）：交付说明写清三件事：哪一组没有参考图依据（客户点名要、图里给不出样本的实验组）；这批图不是交付态（隐藏了刘海、未装发型），需要时再渲带发型的版本；哪一侧的证据弱。用户选定后再走烘焙：Blender 烘焙、分左右眼补偿、全量动画外推扫描、导出、二进制自检、重挂材质并扫空槽。
- **在 Harness 流程里**：本流程尚无捏脸阶段；需要用户选组时写明候选、依据与渲图口径，停下交人。
- **适用条件**：全定制单的捏脸选组（Shinano 素体）。
- **证据等级**：单一案例（候选）

## 捏脸烘焙进基底之前：材质基线、闭眼补偿、包围盒重算都要排进计划

- **症状**：捏脸选组定案后要把形态键值烘进素体基底并换 FBX；这一步牵连面广，漏一步就会出现材质全掉、闭眼过闭、网格被剔除等问题。
- **机制**：换 FBX 会重置材质数组；把「半睁」烘进基底后，闭眼类表情（`eye_close`、眨眼、`vrc.Blink` 等）再叠上去就是过闭；挪过骨架不重算包围盒，整个网格会被视锥剔除（日志正常不等于画得出来）；静态校验拦不住 bind pose 错误。
- **判据**（该例的执行计划）：只调厂商形态键数值，不自行编辑顶点；换 FBX 前把全部渲染器的材质槽导出成基线；烘焙后分左右眼做补偿，补偿要精确重建而不是累加，眼部遮罩不可省；全量扫描表情动画有没有因基底改变而外推越界；FBX 落盘后读二进制自检；覆盖回工程后按基线重挂材质并扫空槽（洋红就是空槽）；外套拆装一次验证合骨；重算包围盒。最大风险点单独出特写：该例眼尾由两个键同向叠加下压约 5.1 mm（−3.28 与 −1.80 mm），下睑不动，要渲眼尾外角特写看上睑是否穿过下睑。
- **当时的修法**（人工作业，供理解机制）：贴图接线与换 FBX 两件事不能并行，按「贴图收工 → 导基线 → 烘焙 → 重挂 → 扫空槽」的顺序做；这一步由主执行方亲自做，不外派。
- **在 Harness 流程里**：本流程尚无捏脸烘焙阶段；该计划只供人工执行参考，遇到时写明风险点，停下交人。
- **适用条件**：Shinano 素体的全定制捏脸；以上是执行计划，逐项执行结果未在本案例材料中核对。
- **证据等级**：单一案例（候选）
